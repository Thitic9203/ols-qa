## สรุปสั้น (Executive Summary)

`check.js` ไล่ไฟล์ในโฟลเดอร์ด้วย `readdirSync(DIR).filter(f => REPORT_FILE_RE.test(f))` ตัวกรองบรรทัดเดียวนี้
ทำสองหน้าที่พร้อมกันคือ **เลือกไฟล์ที่จะตรวจ** และ **ทิ้งไฟล์ที่ชื่อไม่ตรงแบบ** ผลคือไฟล์รายงานที่ตั้งชื่อผิด
ไม่เคยถูกส่งเข้ากฎข้อไหนเลย และตัวตรวจพิมพ์ `structure clean` จบด้วยรหัส 0 ทับไฟล์ที่มันไม่เคยเปิด

พิสูจน์สดเมื่อ 2026-09-06 โดยวางไฟล์ `20260906-post-mortem-report-2-bad-name.md` (เลขไม่เติมศูนย์
ไม่มีแถวในบัญชีหนี้) ลงในโฟลเดอร์ ได้ผล `structure clean — 1 report(s), 1 ledger row(s), 0 open.` `exit=0`
เปลี่ยนชื่อเป็น `my-notes-about-a-mistake.md` ซึ่งไม่มีเค้าของรายงานเลย ก็ยังได้ `exit=0` เหมือนเดิม

แก้ด้วยการย้ายการจำแนกไฟล์เข้าไปในโมดูลกฎเป็น `classifyFolder()` ทุกรายการในโฟลเดอร์ถูกจัดกลุ่ม
ไม่มีอะไรถูกกรองทิ้ง — สิ่งที่ไม่ใช่ 3 ไฟล์ที่รู้จักและไม่ใช่ชื่อรายงานที่ถูกต้อง กลายเป็น finding

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

`filter()` เป็นคำที่ซ่อนการตัดสินใจไว้ ในบริบทของตัวตรวจ การกรองคือ **การประกาศว่าอะไรไม่สำคัญ**
แต่โค้ดบรรทัดนั้นถูกเขียนขึ้นด้วยเจตนาแค่ "เลือกเฉพาะไฟล์รายงาน" โดยไม่ได้ตั้งคำถามว่าของที่ถูกทิ้งคืออะไร
สำหรับตัวตรวจ ของที่อ่านไม่ออกคือสิ่งที่น่าสงสัยที่สุด ไม่ใช่สิ่งที่ควรข้ามเป็นอย่างแรก

### 5 Whys

1. **ทำไมไฟล์ที่ตั้งชื่อผิดถึงไม่ถูกจับ?** — เพราะมันไม่เคยเข้าไปในรายการที่ถูกตรวจ
2. **ทำไมถึงไม่เข้า?** — เพราะรายการมาจาก `filter(f => REPORT_FILE_RE.test(f))` ซึ่งคัดออกตั้งแต่ต้นทาง
3. **ทำไมถึงเขียนแบบนั้นตั้งแต่แรก?** — เพราะคิดถึงงานนี้ว่า "หารายงานมาตรวจ" ไม่ได้คิดว่า "โฟลเดอร์นี้ต้องมีอะไรได้บ้าง"
   คำถามแรกทำให้ของแปลกปลอมเป็นเรื่องไม่เกี่ยว คำถามหลังทำให้ของแปลกปลอมเป็นเรื่องที่ต้องรายงาน
4. **ทำไมเทส 29 ข้อถึงไม่จับ?** — เพราะทุกข้อป้อน `reportNames` เข้าไปตรงๆ **ไม่มีข้อไหนเรียกส่วนที่อ่านโฟลเดอร์จริง**
   เทสตรวจ "กฎ" ครบถ้วน แต่ไม่มีอะไรตรวจ "โค้ดที่เลือกว่ากฎจะได้เห็นไฟล์ไหน" และ CI ก็รันเทสชุดเดียวกัน
   จึงเพิ่มจำนวนเครื่องที่รัน ไม่ได้เพิ่มสิ่งที่ถูกวัด
5. **ทำไมการทดสอบทำให้พังรอบแรกเกือบไม่เห็น?** — **root cause:** M1 กับ M2 จบด้วยรหัส 1 ซึ่ง "ถูก" แต่ถูกด้วยเหตุผลอื่น
   คือแถว DONE ในบัญชีหนี้ชี้ไปยังไฟล์ที่หายไปเพราะการเปลี่ยนชื่อ ถ้าดูแค่รหัสจบก็จะสรุปว่าผ่าน
   **รหัสจบไม่ใช่หลักฐานว่าการตรวจที่ตั้งใจได้ทำงานจริง** สิ่งที่ทำให้จับได้คือช่องข้อความที่ว่างเปล่า

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** ชั้น 9 (เทส) ไม่จับเพราะไม่เคยแตะโค้ดอ่านโฟลเดอร์ · ชั้น 10 (CI) ไม่จับ
เพราะรันเทสชุดเดียวกันบนเครื่องอื่น · ชั้น 8 (pre-commit) เรียก `check.js` ซึ่งตอบ 0 จึงปล่อยผ่าน
ทั้งสามชั้นพึ่งข้อสมมติเดียวกันหมด — นี่คือเหตุผลว่าทำไมชั้นที่ "อิสระจากกัน" ต้องอิสระจริงในระดับสิ่งที่มันวัด
ไม่ใช่แค่ในระดับที่มันรันคนละที่

## 5. แนวทางการแก้ไข (Fix)

- ย้ายการจำแนกไฟล์เข้าโมดูลกฎเป็น `classifyFolder(entryNames)` คืน `{reports, strays}` — `tools/postmortem-guard/postmortem_rules.js`

- ประกาศ `NON_REPORT_FILES` ไว้ที่เดียว การจะยอมรับไฟล์ประเภทใหม่ต้องเติมชื่อลงลิสต์นั้นอย่างตั้งใจ

**ยืนยันแล้วด้วย:** วางไฟล์ `20260906-post-mortem-report-2-bad-name.md` → `exit=1` พร้อมข้อความ
`unrecognised entry in docs/post-mortem/` · เปลี่ยนเป็น `my-notes-about-a-mistake.md` → `exit=1` เช่นกัน ·
เทสของโมดูลผ่านทั้งหมด · หลังลบไฟล์ทดสอบออก ตัวตรวจกลับมา `exit=0`

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- การทดสอบแบบทำให้พังกับไฟล์จริงเป็นสิ่งที่ทำให้เจอ — ถ้ารันแค่เทสชุดเดิมซ้ำ จะไม่มีวันเจอ
- ตารางผลทดสอบมีช่อง "ข้อความที่ได้" แยกจากช่อง "รหัสจบ" ความว่างเปล่าจึงมองเห็นได้
- จดหนี้ลงบัญชีก่อนลงมือแก้ตามลำดับที่กฎเขียนไว้ ทำให้ถ้าเซสชันขาดตอนก็ยังไม่หาย

### สิ่งที่ต้องปรับปรุง
- เทสที่ป้อนข้อมูลสมมติเข้าฟังก์ชันโดยตรงครบทุกกฎ ยังทิ้งช่องว่างตรง "โค้ดที่หาอินพุตมาให้" ได้เต็มๆ
  ต้องมีอย่างน้อยหนึ่งเทสที่แตะของจริงเสมอ
- หลายชั้นที่พึ่งข้อสมมติเดียวกัน นับเป็นชั้นเดียว ไม่ใช่หลายชั้น
- คำว่า `clean` ในข้อความของเครื่องมือ ต้องบอกด้วยว่า **สะอาดในขอบเขตไหน** ไม่ใช่คำเปล่าๆ
