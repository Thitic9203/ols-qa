## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไมคลิปเต็มตกเกณฑ์ 48.3% เฟรมค้าง ทั้งที่ rehearsal ผ่าน?** — เพราะคลิปเต็มมีสเต็ปที่ทำให้เบราว์เซอร์ทำงานหนักกว่า rehearsal มาก: `goto` แบบเปลี่ยนหน้าเต็ม 3 ครั้ง (`/admin/community/pending`, `/admin/community/all-media` ซ้ำ, และการโหลด SPA ใหม่ทุกครั้งที่ `goto`) ซึ่งแต่ละครั้งคือการ parse/hydrate JS ใหม่ทั้งหน้า หนักกว่าการ scroll/click ธรรมดาที่ rehearsal ทดสอบมาก — วัดได้จาก manifest: `maxGapMs: 2232` (ช่วงค้างเดี่ยวสูงสุด 2.2 วินาที) เทียบกับ rehearsal ที่ไม่มีค่านี้บันทึกไว้เพราะไม่เคยรันสเต็ปที่หนักขนาดนั้น
2. **ทำไม rehearsal ถึงทดสอบแค่ 2 จาก 10 สเต็ป?** — เพราะตอนแทรกโค้ด `REHEARSAL` ผมวางเงื่อนไข early-return ไว้ที่ "จุดก่อนคลิกโหวต" โดยตีความว่า "ก่อนคลิกโหวต" = "จุดที่ปลอดภัยที่สุดที่จะหยุด" แต่ไม่ได้แยกว่าสเต็ปที่เหลือหลังจากนั้น (เปิดไดอะล็อกตรวจสอบ, คลิกเหตุผล, คลิกยืนยัน) กับสเต็ป**หลังโหวต**ที่ยังต้องมีต่อ (goto ซ้ำ 2 ครั้ง, hover tooltip) ก็เป็นส่วนหนึ่งของภาระงานที่ต้องพิสูจน์ก่อนเชื่อว่าคลิปทั้งเส้นจะผ่าน
3. **ทำไมผมถึงเชื่อว่า rehearsal บางส่วนเพียงพอ?** — เพราะกรอบคิดตอนนั้นคือ "rehearsal มีไว้พิสูจน์ pipeline การอัด (proxy, selector, การเชื่อมต่อ qa_recorder) ทำงานได้" ไม่ใช่ "พิสูจน์ว่าคลิปความยาวเต็มจะผ่านเกณฑ์คุณภาพ" — สับสนระหว่างสองเป้าหมายที่ต่างกัน: (ก) พิสูจน์ความถูกต้องของโค้ด/selector กับ (ข) พิสูจน์ว่าเงื่อนไขเครื่อง ณ ขณะนั้นเพียงพอสำหรับความยาว/ความซับซ้อนของคลิปทั้งเส้น — (ก) พิสูจน์ได้จาก 2 สเต็ปแรก แต่ (ข) พิสูจน์ไม่ได้
4. **ทำไมไม่ทันสังเกตว่าคลิปเต็มมีภาระงานต่างจาก 2 สเต็ปแรกมาก?** — เพราะตอนตัดสินใจ ผมโฟกัสที่ "load average เครื่องลดลงแล้ว (51→32)" เป็นสัญญาณหลักในการตัดสินใจ โดยไม่ได้ทบทวนว่าคลิปเต็มยังมีตัวแปรที่สองที่ rehearsal ไม่ได้ทดสอบเลย (จำนวนและชนิดของ `goto`) — วัดแค่ตัวแปรเดียว (โหลดเครื่อง) แล้วสรุปว่าตัวแปรทั้งหมด (โหลดเครื่อง × ความหนักของสเต็ป) ปลอดภัยไปด้วย
5. **root cause จริง:** ไม่มีกฎบังคับว่า "rehearsal ต้องครอบคลุมทุกสเต็ปจนถึงจุดก่อนกระทำการที่ย้อนกลับไม่ได้" — กฎที่มีอยู่ (`README-training-run.md`, `WRITE_SCOPE_REQUEST.md`) พูดถึงเรื่องขอบเขตการเขียนข้อมูล (ทำอะไรได้/ไม่ได้) แต่ไม่มีข้อไหนพูดถึงมาตรฐานของ "การซ้อมก่อนกระทำจริง" ว่าต้องครอบคลุมแค่ไหนจึงจะนับว่าเพียงพอที่จะเชื่อได้ — ผมจึงใช้วิจารณญาณเองและตัดสินใจผิด (rehearsal บางส่วน + สัญญาณโหลดเครื่องลดลง = พอเชื่อได้)

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- `qa_recorder.js`'s internal gate (`minUniqueFps`) จับไม่ได้เพราะเป็นคนละมิติ (ค่าเฉลี่ย fps) จาก `verify_video.py` (สัดส่วนเฟรมซ้ำ) — คลิปเต็มผ่านเกณฑ์แรก (`"gate": {"passed": true}` ในตัว manifest เอง) แต่ตกเกณฑ์ที่สอง
- `verify_video.py` จับได้ถูกต้องตามที่ออกแบบไว้ (เป็นด่านสุดท้ายก่อนส่งมอบ) — แต่ทำงาน**หลัง**การโหวตเกิดขึ้นแล้ว เพราะลำดับใน `qa_recorder.stop()` คือ encode → verify → throw ซึ่งเกิดหลังจากที่โค้ดเรียกไป (ตามลำดับ, ไม่มีทางตรวจ "ล่วงหน้า" ก่อนกระทำการจริงได้ด้วยตัวมันเอง) — ชั้นที่ต้องกันเรื่องนี้จริงๆ คือ**ก่อน**กดยืนยัน ไม่ใช่หลัง ซึ่งไม่มีอยู่

- ต้องเลือกสื่อ pending ใหม่ของ `tc9020` มาใช้กับเคส Content_TC_005 แทน `นิทานคุณธรรม` (เหลือ 5 ชิ้นจาก `WRITE_SCOPE_REQUEST.md`: `นิทาน 2`, `พื้นฐาน Data Analytics สำหรับมือใหม่`, `ติวสอบเข้า ม.1 โรงเรียนสาธิต`, `5 เทคนิคจำศัพท์ภาษาอังกฤษให้ติดแน่น`) — ยังไม่ได้เลือก/ดำเนินการ (Action Item #2)

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- gate คุณภาพวิดีโอทำงานตามที่ออกแบบไว้จริง ไม่ได้ถูกปิด/ลดเกณฑ์เพื่อให้ผ่าน — throw error และปฏิเสธคลิปตามที่ควร
- assertion ฝั่งฟังก์ชัน (card/dialog/tooltip) ที่ฝังในสคริปต์ยืนยันผลลัพธ์จริงของระบบได้ครบ แม้คลิปจะใช้ไม่ได้ — ข้อมูลที่ได้จากการรันไม่ได้สูญเปล่าทั้งหมด
- เพิ่มแถว `PENDING.md` ทันทีในเทิร์นที่รู้ตัว ไม่ปล่อยผ่าน

### สิ่งที่ต้องปรับปรุง
- "rehearsal ผ่าน" ต้องนิยามให้ชัดเจนตั้งแต่ตอนเขียนโค้ดว่าครอบคลุมอะไรบ้าง ไม่ใช่ตัดสินใจเฉพาะหน้าว่า "น่าจะพอ"
- ไม่ควรใช้สัญญาณเดียว (load average) เป็นเกณฑ์ตัดสินใจกระทำการที่ย้อนกลับไม่ได้ ทั้งที่มีตัวแปรอื่น (ความหนักของสเต็ปที่ยังไม่เคยทดสอบ) ที่ยังไม่ได้วัด
