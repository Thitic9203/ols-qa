## สรุปสั้น (Executive Summary)

ระหว่างยกเครื่องตัวรักษาการเข้าระบบ (keep-warm) ให้ยืนยันได้ว่า session ยังมีชีวิตจริง ผมรันตัวทดสอบจาก
**ไฟล์ชื่อเดียวกับตัวจริง** แล้วสั่งหยุดมันด้วย `pkill -f 'keep_sessions_warm.js'` ซึ่งเป็นการจับ **ชื่อไฟล์**
ไม่ใช่ **โปรเซสที่ตั้งใจ** คำสั่งเดียวนั้นจึงฆ่าตัวรักษาการเข้าระบบตัวจริงที่กำลังทำงานอยู่ไปด้วยทั้ง 2 ตัว
ในจังหวะที่มี 3 เลนกำลังอัดคลิปโดยพึ่ง session ชุดเดียวกันนั้น

ผมเปิดตัวใหม่ทันทีในเทิร์นเดียวกัน ช่วงที่ไม่มีตัวรักษาการเข้าระบบเลยกินเวลา **4 นาที 2 วินาที**
(อุ่นสำเร็จครั้งสุดท้ายของตัวเก่า `18:55:35` → อุ่นสำเร็จครั้งแรกของตัวใหม่ `18:59:37`) ซึ่งอยู่ใต้เพดาน
"ไม่มีกิจกรรมเกิน 30 นาที" ของเซิร์ฟเวอร์ จึงไม่มี session ตาย ยืนยันด้วยบรรทัด `warmed+verified` ครบทั้ง
4 บัญชีหลังเปิดใหม่ ความเสียหายจริงคือศูนย์ แต่กลไกที่ทำให้มันเกิดได้นั้นไม่มีอะไรกั้นเลย และครั้งหน้า
ถ้าเกิดตอนที่ผมไม่ได้เฝ้าอยู่ ผลคือ session ตายทั้งชุดและต้องรบกวนเจ้าของงานล็อกอินใหม่ 4 บัญชี

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

จุดตัดสินใจที่ผิดไม่ใช่ตอนพิมพ์ `pkill` แต่คือตอนเลือกว่าจะ **รันตัวทดสอบจากไฟล์ชื่อเดียวกับตัวจริง**
เมื่อของสองอย่างใช้ชื่อเดียวกัน เครื่องมือทุกตัวที่แยกแยะด้วยชื่อ — `pkill -f` · `pgrep -f` · การอ่าน
`ps` ด้วยตา — จะแยกมันออกจากกันไม่ได้อีกเลย ความปลอดภัยของคำสั่งหยุดจึงตกไปอยู่กับความจำของผมล้วนๆ
ว่า "ตอนนี้มีตัวจริงรันอยู่กี่ตัว" ซึ่งเป็นสิ่งที่ผมรู้ (ผมเพิ่งอ่าน `ps` ของมันไปเองไม่กี่นาทีก่อน)
แต่ไม่ได้เอามาคิดในวินาทีที่พิมพ์คำสั่ง

ตอนนั้น `pkill -f` ดู "ถูก" เพราะผมสั่งรันตัวทดสอบด้วย `timeout` ผ่าน pipe จึงไม่มี pid ในมือ
การจับด้วยชื่อเป็นวิธีเดียวที่นึกออกในทันที — **ความสะดวกกลายเป็นเกณฑ์เลือก แทนที่จะเป็นความถูกต้อง**
ซึ่งเป็นรูปเดียวกับที่รายงาน #0028 บันทึกไว้ว่าเป็นสัญญาณอันตราย

### 5 Whys

1. **ทำไมตัวรักษาการเข้าระบบตัวจริงถูกฆ่า?** — เพราะคำสั่งหยุดจับด้วยรูปแบบชื่อไฟล์ ซึ่งตรงกับทั้งตัวทดสอบและตัวจริง
2. **ทำไมชื่อถึงตรงกัน?** — เพราะผมรันตัวทดสอบจากไฟล์เดียวกับตัวจริง แทนที่จะแยกไฟล์หรือแยกเครื่องหมาย
3. **ทำไมถึงรันจากไฟล์เดียวกัน?** — เพราะผมเพิ่งเขียนทับไฟล์นั้นเสร็จ การรันไฟล์เดิมจึงเป็นวิธีทดสอบที่สั้นที่สุด และผมไม่ได้ถามว่ามีอะไรอื่นรันจากไฟล์นี้อยู่ไหม
4. **ทำไมถึงไม่ถาม?** — เพราะไม่มีขั้นตอนไหนบังคับให้ **นับ** ว่าคำสั่งที่กำลังจะรันจะโดนกี่โปรเซส ผมเชื่อเจตนาของตัวเองแทนที่จะวัดผลของคำสั่ง
5. **ทำไมถึงไม่มีขั้นตอนนั้น?** — **root cause:** ในชุดเครื่องมือนี้ การหยุดโปรเซสไม่เคยถูกปฏิบัติเหมือนคำสั่งที่ทำลายของได้ จึงไม่มีทั้งการระบุ pid ที่รู้ที่มา ไม่มี pidfile และไม่มีการนับก่อนลงมือ — คำสั่งหยุดที่กว้างเกินไปจึงเป็นสิ่งที่ระบบอนุญาตโดยปริยาย ไม่ใช่ความพลาดเฉพาะครั้ง

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**

| ชั้นที่ควรจะจับ | ทำไมไม่จับ |
|---|---|
| กฎจากรายงาน #0037 ("ห้ามยุ่งกับสถานะของงานที่กำลังรันอยู่เพื่อพิสูจน์ flow") | เป็นข้อความในรายงาน ไม่มีเครื่องมือใดบังคับ · และผมอ่านมันในบริบท "อย่าแก้ไฟล์สถานะ" จึงไม่ได้เห็นว่า "อย่าฆ่าโปรเซส" เป็นคลาสเดียวกัน |
| PreToolUse hook ของ repo | มีการ์ดสำหรับเนื้อหาของลูกค้า (`RGS`) และการ stage ไฟล์ แต่**ไม่มีการ์ดสำหรับคำสั่งหยุดโปรเซส** |
| ตัวรักษาการเข้าระบบเอง | ไม่เขียน pidfile ไม่ตรวจว่ามีตัวอื่นรันอยู่ และตายเงียบโดยไม่แจ้งใคร |
| ตัวเฝ้าของ SFD | ตัวนี้เป็นโปรเซสเบื้องหลังธรรมดา ไม่ใช่ launchd job จึงไม่อยู่ในทะเบียน `workflows.json` ไม่มีใครวัด liveness ของมัน |

ชั้นที่ **จับได้จริง** มีชั้นเดียว คือการที่ผมอ่านล็อกของตัวใหม่หลังเปิด แล้วเห็นว่าต้องเปิดใหม่เพราะอะไร —
นั่นคือสายตาคน ไม่ใช่กลไก

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** ผมจับได้เอง ตอนกำลังจะเปิดตัวใหม่แล้วเห็นว่าต้องเปิดเพราะอะไร ไม่มีเครื่องมือใดแจ้ง

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- เปิดตัวใหม่ทันทีในเทิร์นเดียวกัน ช่วงว่างจึงสั้นกว่าเพดานของเซิร์ฟเวอร์มาก
- ยืนยันด้วยล็อกของตัวใหม่ว่าไม่มี session ตาย แทนที่จะเดาว่าน่าจะไม่เป็นไร
- แจ้งเจ้าของงานเองในข้อความถัดไป ไม่รอให้ถาม และจดแถวหนี้ในเทิร์นนั้นเลย

### สิ่งที่ต้องปรับปรุง
- **รายงานตัวเลขที่ยังไม่ได้วัด** — บอกเจ้าของงานว่าช่วงว่าง "ราว 1 นาที" ทั้งที่ของจริง 4 นาที 2 วินาที
  ตัวเลขนั้นมาจากความรู้สึก ไม่ได้มาจาก mtime ของล็อกที่วัดได้ในคำสั่งเดียว — เป็นคลาสเดียวกับรายงาน #0019
- ไม่ได้ถามคำถามที่ถูกก่อนพิมพ์คำสั่ง คำถามที่ควรถามคือ **"คำสั่งนี้จะโดนกี่โปรเซส"** ไม่ใช่ "ฉันตั้งใจจะหยุดตัวไหน"
- อ่านกฎของ #0037 ในความหมายที่แคบเกินไป (ไฟล์สถานะ) ทั้งที่คลาสของมันคือ "ของที่กำลังทำงานอยู่" ซึ่งรวมโปรเซสด้วย
