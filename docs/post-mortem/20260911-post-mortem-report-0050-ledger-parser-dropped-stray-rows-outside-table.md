## สรุปสั้น (Executive Summary)

`parseLedger()` (Node) และ `ledger_open_count.sh` (awk fallback) อ่านเฉพาะบรรทัดที่อยู่ **ระหว่างหัวตารางกับบรรทัดแรกที่ไม่ขึ้นต้นด้วย `|`** เท่านั้น — แถว `| PM-... |` ที่วางไว้ก่อนหัวตาราง หรือหลังตารางจบ (เช่นใต้หัวข้อ "## วิธีเขียนแถวใหม่" ท้ายไฟล์) จึงไม่เคยถูกทั้งสองฝั่งมองเห็นเลย ตั้งแต่วันที่เขียนโค้ดทั้งคู่ครั้งแรก ทำซ้ำยืนยันแล้วด้วยการเติมแถว OPEN ไว้หลังตาราง: `check.js` พิมพ์ `structure clean — 49 report(s), 50 ledger row(s), 1 open` (นับได้แค่แถวเดิม ไม่เห็นแถวที่เติม) `ledger_open_count.sh` คืนเลข `1` ขณะที่ `grep -c "| OPEN |"` นับได้ `2` และรันจริงผ่าน `scripts/hooks/pre-commit` ในโฟลเดอร์ทดลองพบว่า**คอมมิตผ่าน (exit 0) ทั้งที่มีหนี้ OPEN ค้างอยู่จริง** ทั้ง 2 ตำแหน่ง (ก่อนหัวตาราง/หลังตารางจบ) และทั้งมี-ไม่มี `node` แก้แล้วด้วยการให้ทั้งสองไฟล์สแกนทั้งไฟล์หาสิ่งที่ "ดูเหมือนแถว" แล้วรายงานทุกอันที่อยู่นอกขอบเขตของตาราง แทนที่จะปล่อยให้ตำแหน่งที่ loop เดินถึงเป็นตัวกำหนด

## 1. ปัญหา (Problem Statement)

- `tools/postmortem-guard/postmortem_rules.js` ฟังก์ชัน `parseLedger()` (ก่อนแก้): วนอ่านตั้งแต่ `headerIdx + 1` แล้ว `break` ทันทีที่เจอบรรทัดแรกที่ไม่ขึ้นต้นด้วย `|` — ไม่เคยอ่านอะไรก่อนบรรทัดหัวตารางเลยด้วย (แค่สแกนหา "หัวตารางคือบรรทัดไหน" ไม่ได้ตรวจว่าบรรทัดก่อนหน้านั้นมีแถวหลงอยู่หรือไม่)
- `tools/postmortem-guard/ledger_open_count.sh` (ก่อนแก้): บรรทัด `!/^[[:space:]]*\|/ { if (hdr) done = 1; next }` ร่วมกับ `{ if (done) next ... }` ในบล็อกหลัก — ทำให้บรรทัดที่ขึ้นต้นด้วย `|` ใดๆ หลัง `done=1` ถูก `next` ทิ้งทันทีโดยไม่มีการตรวจสอบใดๆ และบรรทัดที่ขึ้นต้นด้วย `|` ก่อนพบหัวตารางก็ตกเข้า branch `if (!hdr) { ... }` ซึ่งถ้าไม่ใช่หัวตารางจริง ก็แค่ `next` เงียบๆ เช่นกัน
- ทำซ้ำยืนยันสด (2026-09-11, ในสำเนาทดลอง ไม่แตะไฟล์จริง): เติมแถว `| PM-2099-01-01-01 | 2099-01-01 | stray row appended after the table | test | OPEN | — |` ต่อท้าย `docs/post-mortem/PENDING.md`
  - `node tools/postmortem-guard/check.js` (ก่อนแก้) → `structure clean — 49 report(s), 50 ledger row(s), 1 open.` (exit 0)
  - `bash tools/postmortem-guard/ledger_open_count.sh docs/post-mortem/PENDING.md` (ก่อนแก้) → `1` (exit 0)
  - `grep -c "| OPEN |" docs/post-mortem/PENDING.md` → `2`
  - รัน `scripts/hooks/pre-commit` จริงในโฟลเดอร์ git ทดลอง (staging เฉพาะไฟล์ที่ไม่เกี่ยวกับ ledger) → **exit 0 ทั้งที่มีแถว OPEN ค้างอยู่จริง** ทั้งกรณีแถวอยู่ก่อนหัวตารางและหลังตารางจบ ทั้งมีและไม่มี `node` ใน PATH
- แถวที่วางอยู่ **ในตาราง** (control case) ยังคงถูกจับได้ถูกต้องตลอด — pre-commit exit 1 ทุกครั้ง แสดงว่ารูอยู่ที่ "ขอบเขตของตาราง" เท่านั้น ไม่ใช่ตรรกะการนับหลัก

**สิ่งที่ควรจะเป็น:** ตัวป้องกันชั้น 7-8 ต้องรายงานหนี้ทุกแถวที่มีอยู่จริงในไฟล์ ไม่ว่าจะวางผิดตำแหน่งแค่ไหน — ตรงตามที่ `tools/postmortem-guard/README.md` ("What the gate refuses") และคอมเมนต์ของ `check.js`/`postmortem_rules.js` เองเขียนหลักการไว้ตั้งแต่รายงาน #0002 ว่า "nothing is filtered away … a check that silently ignores what it cannot parse reports success for the wrong reason" — หลักการนี้ถูกใช้กับ "ไฟล์ไหนคือรายงาน" (`classifyFolder`) แต่ไม่เคยถูกขยายไปถึง "บรรทัดไหนอยู่ในตารางบัญชีหนี้"

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไมแถวที่อยู่นอกตารางถึงไม่ถูกนับ?** — เพราะ `parseLedger()`'s row-loop เริ่มอ่านที่ `headerIdx + 1` และ `break` ทันทีที่เจอบรรทัดแรกที่ไม่ขึ้นต้นด้วย `\|` หลังจากนั้น ไม่มีโค้ดจุดไหนกลับไปดูอะไรนอกช่วงนี้อีกเลย เช่นเดียวกัน `ledger_open_count.sh` ตั้ง `done=1` แล้ว `next` ทุกบรรทัดที่ขึ้นต้นด้วย `\|` ถัดจากนั้นไปโดยไม่ตรวจสอบ
2. **ทำไม loop ถูกออกแบบให้หยุดแบบนั้น?** — เพราะตอนเขียนครั้งแรก (2026-09-05/06) โจทย์ที่คิดไว้คือ "หาตารางให้เจอโดยไม่พึ่งเลขบรรทัด" (แก้ปัญหาที่บทเรียน PM-010 พูดถึง คือ paragraph ที่เพิ่มก่อนตารางต้องไม่ทำให้ parse เพี้ยน) — โค้ดแก้ปัญหานั้นได้จริงสำหรับ "จุดเริ่มของตาราง" แต่ไม่เคยถูกถามคำถามเดียวกันสำหรับ "จุดจบของตาราง"
3. **ทำไมไม่มีใครถามคำถามเดียวกันสำหรับจุดจบของตาราง?** — เพราะฉากทดสอบทุกฉากที่เขียนไว้ตอนนั้น (และของทุกรายงานที่ตามมา) มีแถวข้อมูลอยู่ "ติดกับ" หัวตารางเสมอ ไม่มีเคสไหนที่ทดสอบว่า "มีอะไรอยู่หลังตารางจบ" เพราะไฟล์จริง ณ ตอนนั้นก็ไม่เคยมีอะไรอยู่ตรงนั้นจริงๆ — ข้อสมมติที่ไม่เคยถูกเขียนไว้ตรงๆ กลายเป็นจุดบอด
4. **ทำไมรายงาน #0002 (ซึ่งเขียนกฎ "อย่า filter สิ่งที่ parser ไม่รู้จักทิ้งเงียบๆ" ไว้ในไฟล์เดียวกันนี้) ไม่จับเรื่องนี้ไปด้วย?** — เพราะ #0002 แก้ที่ `classifyFolder()` ซึ่งตัดสินว่า **ไฟล์** ไหนในโฟลเดอร์คือรายงาน กับ **บรรทัด** ไหนในไฟล์ PENDING.md คือแถวบัญชีหนี้ เป็นคนละฟังก์ชัน คนละข้อมูล แก้จุดหนึ่งแล้วไม่ได้ไล่หาคลาสเดียวกันในจุดอื่นของไฟล์เดียวกัน — ตรงกับบทเรียนของรายงาน #0012 เองว่า "ปิดจุดเดียวไม่ใช่การปิดคลาส"
5. **root cause จริง — โมดูลที่ตัดสินว่า "อะไรคือข้อมูลในตาราง" ไม่เคยแยกความหมายระหว่าง "ไม่มีข้อมูลตรงนี้จริงๆ" กับ "ข้อมูลอยู่นอกขอบเขตที่โปรแกรมมองหา"** ทั้งสองกรณีถูกยุบเป็นคำตอบเดียวกันคือ "ไม่นับ" ตั้งแต่ตอนออกแบบ loop ครั้งแรก — เป็นรูปแบบเดียวกับบทเรียนของรายงาน #0003 ("ค่าที่อ่านไม่ได้ห้ามเดินเข้าการเปรียบเทียบเชิงตัวเลข") แต่เกิดที่ระดับ **เส้นแบ่งของตาราง** แทนที่จะเป็นค่าตัวเลขตัวเดียว

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**

| ชั้น (ก่อนแก้) | ทำไมไม่จับ |
|---|---|
| 1-6 (reminder ทุกจุด) | ทุกจุดเรียก `check.js --debt` ซึ่งพึ่ง `parseLedger()` ตัวเดียวกัน — พังพร้อมกันเพราะใช้ตรรกะเดียวกัน |
| 7 (`check.js` เอง) | พึ่ง `parseLedger()` ตัวเดียวกันโดยตรง ไม่มีชั้นตรวจสอบซ้ำ |
| 8 (`pre-commit`) | เรียก `check.js --gate` ก่อน ถ้าได้ 0 หรือ 1 ก็เชื่อทันทีไม่ cross-check กับ shell counter — และ shell counter (`ledger_open_count.sh`, ใช้เป็น fallback เมื่อไม่มี node) ก็มีรูแบบเดียวกันอยู่แล้วตั้งแต่วันที่เขียน ทั้งที่ README ของตัวเครื่องมือเองเขียนไว้ว่า "two layers sharing a runtime fail together, and the whole point of ten layers is that they do not" — หลักการนี้ถูกต้อง แต่ใช้ไม่ได้ผลเพราะทั้งสอง runtime มีข้อบกพร่อง**เดียวกัน**ตั้งแต่ต้น ไม่ใช่ข้อบกพร่องที่ต่างกันแล้วมาซ้อนทับ |

ไม่มีชั้นไหนในทั้ง 8 ชั้นครอบเรื่องนี้ได้เลย เพราะทุกชั้นสุดท้ายพึ่ง (โดยตรงหรือโดยอ้อม) ตรรกะการหาขอบเขตตารางแบบเดียวกัน

## 5. แนวทางการแก้ไข (Fix)

- `tools/postmortem-guard/postmortem_rules.js` — เขียน `parseLedger()` ใหม่: เพิ่ม `firstCellIsPmId()` ที่ตรวจทุกบรรทัดในไฟล์ (ไม่ใช่แค่ช่วงตาราง) ว่าขึ้นต้นด้วย `\|` และ cell แรกขึ้นต้นด้วย `PM-` หรือไม่ แล้ว sweep ทุกบรรทัดนอกช่วง `[headerIdx+1, tableEnd)` — บรรทัดที่ตรงเงื่อนไขกลายเป็น `problems` entry แทนที่จะหายไปเงียบๆ ครอบทั้งกรณี "ไม่พบหัวตารางเลย" และ "หัวตารางมีจำนวนคอลัมน์ผิด" ที่โค้ดเดิม `return` ออกก่อนถึงจุดนี้ด้วย
- `tools/postmortem-guard/ledger_open_count.sh` — เพิ่มเช็คเดียวกัน 2 จุด: ใน `if (!hdr) { ... }` (ก่อนพบหัวตาราง) และใน `if (done) { ... }` (หลังตารางจบ) — เจอ `\| PM-...` นอกขอบเขต → `REFUSE:...` พร้อมเลขบรรทัดและ id ที่เจอ, `exit 2`
- **ยืนยันแล้วด้วย:**
  - `node tools/postmortem-guard/postmortem_rules.test.js` → 32/32 ผ่าน (รวม 4 เคสใหม่)
  - `node tools/postmortem-guard/hook_gate.test.js` → 21/21 ผ่าน (รวม 3 เคสใหม่)
  - `node tools/postmortem-guard/pre_commit.test.js` → 10/10 ผ่าน (ไม่กระทบ)
  - `bash scripts/run-test-suites.sh` → `[ols-qa] ✅ เขียวครบ 31 ชุด`
  - จำลอง repro เดิมหลังแก้: `check.js` exit `1`, `--gate` exit `2`, shell counter `REFUSE:line 86 ... "PM-2099-01-01-01"` exit `2`
  - รัน `scripts/hooks/pre-commit` จริงในโฟลเดอร์ git ทดลอง 4 เคส: stray-after → exit 1 (เดิม 0), stray-before → exit 1 (เดิม 0), control (ในตาราง) → exit 1 (เหมือนเดิม, ไม่กระทบ) — ทั้งมีและไม่มี `node`

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- Reproduce ก่อนแก้เสมอ ด้วยสำเนาทดลองแยกจาก repo จริง (ไม่แตะไฟล์จริงระหว่างสืบสวน) แล้วยืนยันซ้ำด้วยการรัน `scripts/hooks/pre-commit` จริงในโฟลเดอร์ git ทดลอง — ไม่ใช่แค่เชื่อ unit test เพียงอย่างเดียว จับได้ว่า "control case" (แถวอยู่ในตารางจริง) ยังทำงานถูกอยู่ ไม่ over-fix จนกระทบเคสที่ไม่เกี่ยวข้อง

### สิ่งที่ต้องปรับปรุง
- หลักการ "identity, not position" (บทเรียนของ PM-010) ถูกนำไปใช้แค่กับ "จุดเริ่มของตาราง" ตอนเขียนครั้งแรก ไม่เคยถูกขยายไปถึง "ขอบเขตทุกด้าน" ของสิ่งที่ parse — ครั้งหน้าเมื่อใช้หลักการนี้กับฟังก์ชันไหน ต้องถามว่า "ขอบเขตทุกด้านหรือยัง" ไม่ใช่แค่ด้านที่เพิ่งมีปัญหา
