## สรุปสั้น (Executive Summary)

ตอนจะให้เจ้าของงานล็อกอินเก็บการเข้าระบบของ pre-prod ผมเปิดหน้าเข้าสู่ระบบ **ของอีกสภาพแวดล้อมหนึ่ง** ให้เจ้าของงานกรอก
เพราะหยิบที่อยู่หน้าเข้าสู่ระบบมาจากค่าที่จำไว้ ทั้งที่ค่านั้นไม่ได้ระบุว่าเป็นของสภาพแวดล้อมไหน
พอแก้รอบแรกแล้ว ยังพลาดซ้ำเรื่องที่สอง คือใช้ **รายชื่อบัญชีของ production** มาล็อกอินกับ pre-prod
ซึ่งเป็นคนละชุดบัญชีกันโดยสิ้นเชิง เจ้าของงานต้องทักรวม 3 ครั้งกว่าจะได้หน้าจอและบัญชีที่ถูกต้อง
สาเหตุจริงไม่ใช่แค่ "ไม่ได้ตรวจ" แต่คือ **ทั้งสองค่าเป็นค่าที่ไม่มีชื่อสภาพแวดล้อมกำกับอยู่ในตัวมันเอง**
แฟ้มค่าคงที่มีรายการหน้าเข้าสู่ระบบเพียงรายการเดียวโดยไม่ระบุ environment และไม่มีรายการของ pre-prod อยู่เลย
ส่วนเครื่องมือเก็บการเข้าระบบมีค่าปริยายของรายชื่อบัญชีชี้ไปที่ไฟล์ของ production
แก้ด้วยการแยกไฟล์รายชื่อบัญชีของ pre-prod ออกมาต่างหาก และทำให้เครื่องมือ 3 ตัวรับรายชื่อจากภายนอกได้

## 1. ปัญหา (Problem Statement)

**ความผิดพลาดที่ 1 — เปิดหน้าเข้าสู่ระบบของอีกสภาพแวดล้อม**

- ที่อยู่หน้าเข้าสู่ระบบที่ใช้ มาจากค่าที่จำไว้ ไม่ได้เปิดของจริงยืนยันในรอบนั้น
- ในแฟ้มค่าคงที่นอก repo มีรายการชื่อ `<SSO_PORTAL_HOST>` อยู่ **รายการเดียว** และ **ไม่มีคำว่า environment กำกับในชื่อรายการเลย**
- ค้นทั้งแฟ้มด้วยคำที่เป็นชื่อของ pre-prod แล้ว **ไม่พบรายการหน้าเข้าสู่ระบบของ pre-prod อยู่เลยแม้แต่รายการเดียว**
  (พบเพียง 4 บรรทัดที่มีคำนั้น และทั้ง 4 เป็นรหัสไฟล์ชีทกับชื่อแท็บ ไม่ใช่ที่อยู่หน้าเข้าสู่ระบบ)
- สภาพแวดล้อมฝึกอบรมกลับมีรายการหน้าเข้าสู่ระบบของตัวเองเขียนไว้ชัดเจนแยกอีกบรรทัดหนึ่ง
  → แฟ้มจึงสอนโดยปริยายว่า "หน้าเข้าสู่ระบบมีอันเดียว ยกเว้นของฝึกอบรม" ซึ่งไม่จริง

**ความผิดพลาดที่ 2 — ใช้รายชื่อบัญชีของ production กับ pre-prod**

- เครื่องมือกำหนดค่าปริยายของรายชื่อบัญชีไว้ที่ไฟล์ของ production
  `const ROSTER = process.env.ROSTER || path.join(HERE, 'accounts.json');` (`capture/session_verify.js:40`)
- ไฟล์นั้นสร้างจากชีท Go-Live แท็บที่เป็นบัญชีของ production มี **15 บัญชี** และถูกรีเฟรชในวันเดียวกันเมื่อ 13:39 น.
- บัญชีของ pre-prod เป็นคนละชุด อยู่คนละแหล่ง (ชีทติดตามงานของ QA แท็บ `Account_Test`) มี **13 บัญชี**
  ไฟล์นี้ยังไม่มีอยู่จนกระทั่งถูกสร้างขึ้นเป็นส่วนหนึ่งของการแก้ เมื่อ 18:10 น.
- ผลคือชื่อบัญชีที่กรอกให้เจ้าของงาน เป็นบัญชีที่ไม่มีอยู่บนสภาพแวดล้อมที่กำลังจะใช้

**สิ่งที่ควรจะเป็น:** ค่าที่ระบุ **ปลายทาง** และค่าที่ระบุ **ตัวตน** ต้องถูกยืนยันกับของจริงในรอบนั้นก่อนใช้เสมอ
และทั้งสองค่าต้องมีชื่อสภาพแวดล้อมกำกับอยู่ในตัวมันเอง เพราะกฎของ repo กำหนดว่าการเลือกสภาพแวดล้อมเป็นสิทธิ์ของเจ้าของงาน
เครื่องมือจึงห้ามเดาปลายทางให้เงียบๆ (กฎเดียวกับที่ออกมาจากรายงาน #0009)

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

ความผิดพลาดทั้งสองครั้งเป็นเรื่องเดียวกันในรูปแบบที่ต่างกัน คือ **ใช้ค่าที่ "จำได้" แทนค่าที่ "ตรวจแล้ว"**
และทั้งสองค่ามีคุณสมบัติร่วมกันอย่างหนึ่งที่ทำให้พลาดง่ายเป็นพิเศษ คือ **ตัวค่าเองไม่ได้บอกว่ามันเป็นของสภาพแวดล้อมไหน**

ที่อยู่หน้าเข้าสู่ระบบที่จำไว้ อ่านแล้วดูเหมือนเป็น "หน้าเข้าสู่ระบบของระบบนี้" ไม่ได้อ่านว่า "หน้าเข้าสู่ระบบของ production"
รายชื่อบัญชีที่ชื่อไฟล์ว่า `accounts.json` ก็อ่านเหมือนเป็น "รายชื่อบัญชี" เฉยๆ ไม่ได้อ่านว่า "รายชื่อบัญชีของ production"
เมื่อชื่อของค่าไม่มีสภาพแวดล้อมกำกับ การหยิบผิดจึงไม่มีอะไรสะดุดตาเลยแม้แต่นิดเดียว

จุดที่ทำให้เรื่องแย่ลงอีกชั้นคือ **ทั้งสองค่าเป็นค่าที่ผิดแล้วยัง "ทำงานได้"** ในความหมายที่ว่าหน้าเว็บเปิดขึ้นจริง
และช่องกรอกอีเมลรับข้อความได้จริง ระบบไม่ได้ปฏิเสธอะไรตั้งแต่ต้น ความผิดพลาดจึงไปโผล่ที่สายตาของเจ้าของงาน
แทนที่จะโผล่ที่ข้อความแจ้งข้อผิดพลาดของเครื่องมือ — ตรงกับบทเรียนของรายงาน #0005 ที่ว่าค่าที่ไม่ว่างแต่ผิด อันตรายกว่าค่าว่าง

### 5 Whys

1. **ทำไมเจ้าของงานได้หน้าจอผิด?** — เพราะที่อยู่หน้าเข้าสู่ระบบที่ใช้ เป็นของอีกสภาพแวดล้อม
2. **ทำไมถึงใช้ที่อยู่ของอีกสภาพแวดล้อม?** — เพราะหยิบมาจากค่าที่จำไว้ ไม่ได้เปิดแฟ้มค่าคงที่ยืนยันในรอบนั้น
3. **ทำไมการเปิดแฟ้มยืนยันถึงไม่ช่วย?** — เพราะแฟ้มมีรายการหน้าเข้าสู่ระบบของสภาพแวดล้อมนี้อยู่รายการเดียวโดยไม่ระบุ environment และ **ไม่มีรายการของ pre-prod อยู่เลย** ต่อให้เปิดอ่านก็ได้ค่าเดียวกันนั้น
4. **ทำไมความผิดพลาดที่สองจึงตามมาทันทีหลังแก้ครั้งแรก?** — เพราะค่าที่สอง (รายชื่อบัญชี) มีปัญหาชนิดเดียวกันเป๊ะ คือค่าปริยายชี้ไปที่ของ production และชื่อไฟล์ไม่ได้บอกว่าเป็นของ production
5. **ทำไมค่าที่ผูกกับสภาพแวดล้อมถึงถูกเก็บโดยไม่มีสภาพแวดล้อมกำกับ?** — **เพราะตอนที่เขียนค่าเหล่านั้นลงไป มีสภาพแวดล้อมที่ใช้งานอยู่เพียงชุดเดียว ชื่อที่ไม่ระบุจึงเพียงพอในตอนนั้น และไม่มีอะไรบังคับให้ต้องเติมเมื่อสภาพแวดล้อมที่สองเข้ามา** — นี่คือ root cause จริง ปิดได้ด้วยการทำให้ค่าประเภทนี้ต้องมีชื่อสภาพแวดล้อมเสมอ และให้เครื่องมือปฏิเสธเมื่อผู้เรียกไม่ระบุ

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- **กฎเรื่องยืนยัน environment ก่อนทดสอบ** — ครอบเฉพาะคำถามว่า "จะเทส env ไหน" ซึ่งรอบนี้ตอบถูกแล้วว่า pre-prod ตั้งแต่ต้น กฎไม่ได้ครอบไปถึงค่าที่ใช้ **ระหว่างทาง** ว่าตรงกับ env ที่ตอบไว้หรือไม่
- **บทเรียนจากรายงาน #0009** — ปิดช่องเรื่องค่าปริยายของ **ปลายทางที่จะยิงคำขอ** ไปแล้วจริง แต่ค่าปริยายของ **รายชื่อบัญชี** เป็นตัวแปรคนละตัวในไฟล์เดียวกัน และไม่ได้ถูกไล่ปิดไปพร้อมกัน ตรงกับบทเรียนของ #0012 ที่ว่าปิดจุดเดียวไม่ใช่การปิดทั้งคลาส
- **เครื่องมือเก็บการเข้าระบบ** — ออกแบบมาให้กรอกอีเมลให้แล้วรอคนพิมพ์รหัส มันจึงไม่มีทางรู้ว่าอีเมลที่ตัวเองกรอกนั้นมีอยู่บนปลายทางหรือไม่
- **ตัวยืนยันหลังเก็บ** — มีอยู่จริงและทำงานถูก แต่มันตรวจ **หลัง** ล็อกอินสำเร็จ จึงช่วยอะไรไม่ได้ในขั้นที่ยังล็อกอินไม่ผ่าน

  (ไฟล์ `capture/accounts_preprod.json` off-repo · สร้างเมื่อ 8/Sep 18:10)
- **ทำให้เครื่องมือ 3 ตัวรับรายชื่อบัญชีจากภายนอกได้** ผ่านตัวแปร `ROSTER` — ตัวเก็บการเข้าระบบ ตัวยืนยัน และด่านตรวจบทบาทก่อนอัด
  พร้อมสำรองไฟล์เดิมไว้ทุกตัว (`*.bak-roster` · `*.bak-preprodroster`)

  (`capture/session_verify.js:37-39`)

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** เจ้าของงานเห็นหน้าจอด้วยตาเองแล้วทัก ทั้ง 3 ครั้ง — ไม่มีกลไกใดในระบบจับได้เลย
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** รู้เร็ว เพราะเจ้าของงานอยู่หน้าจอในจังหวะนั้นพอดี แต่ถ้าเป็นงานที่ไม่มีคนดูอยู่ ความผิดพลาดชนิดนี้จะไปโผล่ตอนที่ล็อกอินไม่ผ่านโดยไม่รู้สาเหตุ
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** ด่านก่อนอัดตาม P3 จะจับได้เองว่า session ที่ถืออยู่เป็นบัญชีอะไรจริงๆ
  ส่วนความผิดพลาดชนิด "เปิดหน้าเข้าสู่ระบบผิดสภาพแวดล้อม" จะจับได้เร็วก็ต่อเมื่อทำ P2 เสร็จ เพราะปัจจุบันไม่มีค่าที่ถูกต้องให้เทียบเลย

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- เมื่อรู้ตัว แก้ที่โครงสร้างของค่าเลย คือแยกไฟล์และเปิดช่องให้ส่งจากภายนอก แทนที่จะจำว่า "คราวหน้าอย่าลืม"
- สำรองไฟล์เครื่องมือเดิมไว้ครบทุกตัวก่อนแก้ ทำให้ย้อนได้ถ้าการแก้พลาด
- เขียนคำเตือนไว้ตรงบรรทัดที่คนจะหยิบผิดจริงๆ ไม่ใช่เขียนไว้ในเอกสารที่แยกจากโค้ด

### สิ่งที่ต้องปรับปรุง
- พลาดเรื่องเดียวกัน 2 ครั้งซ้อนในเรื่องเดียวกัน แปลว่าหลังแก้ครั้งแรกไม่ได้ถามว่า "ค่าอื่นที่เป็นชนิดเดียวกันมีอีกไหม" ซึ่งเป็นคำถามที่ #0012 บังคับไว้แล้ว
- ที่อยู่หน้าเข้าสู่ระบบของ pre-prod **ยังไม่ได้ถูกบันทึกจนถึงตอนเขียนรายงานนี้** — ช่องโหว่ที่ทำให้พลาดครั้งแรกจึงยังเปิดอยู่ และถูกยกเป็น P2 ที่ยังค้าง ไม่ใช่เขียนให้ดูเหมือนปิดครบแล้ว
