## สรุปสั้น (Executive Summary)

แก้บั๊ก "อ่านรายการเนื้อหาแค่หน้าแรก" ใน `contentList()` ของ `media-list-view.spec.ts` โดยต่อ
`&page=N` ท้าย URL ทุกกรณี ไม่ได้ตรวจว่ามีผู้เรียก 3 จุดที่ใส่ `page=1` มาในพาธอยู่แล้ว
ผลคือได้ `page=1&page=1` ซึ่ง API ตอบ 400 `{"page":["Expected number, received nan"]}`
ทำให้ **8 เคสที่ผ่านอยู่ก่อนหน้ากลายเป็นไม่ผ่าน** — MLV-027 · 028 · 029 · 030 · 105 · 106 · 107 · 110

จับได้เองจากการรันเต็มชุดหลังแก้ ไม่มีอะไรหลุดออกไปนอกทีม แก้จบและยืนยันเขียวในรอบถัดมา

## 1. ปัญหา (Problem Statement)

การแก้ที่ตั้งใจให้ตัวอ่านรายการไล่ครบทุกหน้า เขียนไว้ว่า

```ts
const sep = rel.includes('?') ? '&' : '?';
const res = await contentListPage(ctx, `${rel}${sep}page=${page}`);
```

ซึ่งถูกต้องกับผู้เรียกที่ส่ง `api/me/courses?limit=50` แต่พังกับผู้เรียกที่ส่ง
`api/me/courses/learning?limit=50&progress=in-progress&page=1` เพราะได้ `page=1&page=1`
API อ่านพารามิเตอร์ซ้ำแล้วตีความเป็น `NaN`

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไม 8 เคสจึงพัง** — เพราะ URL มี `page` ซ้ำสองตัว
2. **ทำไมจึงซ้ำ** — เพราะโค้ดที่เขียนใหม่ต่อ `page=` ท้าย `rel` โดยไม่ดูว่ามีอยู่แล้วหรือไม่
3. **ทำไมจึงไม่ดู** — เพราะตอนออกแบบมองผู้เรียกแค่ 2 จุดที่ตั้งใจแก้ (`authoredCourses`,
   `authoredLearningPaths`) ไม่ได้ไล่ผู้เรียกทั้งหมดของฟังก์ชันที่กำลังเปลี่ยนสัญญา
4. **ทำไม typecheck และ lint จึงไม่จับ** — เพราะเป็นการต่อสตริง ชนิดข้อมูลถูกต้องทุกประการ
   ความผิดอยู่ที่ค่าที่ได้ ไม่ใช่ที่ชนิด
5. **ทำไมจึงไม่มีด่านก่อนหน้ารันเต็มชุด** — เพราะหลังแก้ ตรวจแค่ typecheck กับ lint แล้วรันเต็มชุดเลย
   ไม่ได้รันเฉพาะไฟล์ที่แตะก่อนเพื่อดูผลเร็ว

**สาเหตุที่แท้จริง:** เปลี่ยนพฤติกรรมของฟังก์ชันที่ใช้ร่วมกัน โดยตรวจเฉพาะผู้เรียกที่เป็นต้นเหตุ
ไม่ได้ไล่ผู้เรียกทั้งหมด — คือคลาสเดียวกับบทเรียน #0003 แต่กลับด้าน: รอบนั้นปิดคลาสไม่ครบ
รอบนี้ปิดคลาสแล้วแต่ไม่ได้ดูว่าใครใช้ของที่เปลี่ยนบ้าง

## 4. ผลกระทบ (Impact)

- 8 เคสที่เคยผ่าน แสดงผลเป็นไม่ผ่านอยู่ประมาณ 15 นาที ภายในเซสชันเดียว
- ไม่มีรายงานฉบับใดถูกส่งออกด้วยตัวเลขชุดนั้น ไม่มีข้อมูลบนระบบเสียหาย เพราะทุกเคสเป็นการอ่านอย่างเดียว
- ต้นทุนจริงคือรันเต็มชุดเพิ่ม 1 รอบ ประมาณ 3.5 นาที

## 5. แนวทางการแก้ไข (Fix)

ให้ตัวไล่หน้าเคารพ `page=` ที่ผู้เรียกระบุมาเอง แทนที่จะไล่ทับ

```ts
// ผู้เรียกที่ปักหมุด page= มาแล้ว ต้องการหน้านั้น ไม่ใช่ให้ไล่ทุกหน้า
if (/[?&]page=/.test(rel)) return (await contentListPage(ctx, rel)).rows;
```

ยืนยันด้วยการรันเต็มชุด 133 เคสซ้ำ — 8 เคสกลับมาผ่านครบ และไม่มีเคสอื่นเปลี่ยนสถานะ

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

1. **เปลี่ยนสัญญาของฟังก์ชันที่ใช้ร่วมกัน ต้องไล่ผู้เรียกทุกจุดก่อน แล้วรายงานจำนวนที่นับได้**
   — `grep -rn "<ชื่อฟังก์ชัน>"` ก่อนแก้ ไม่ใช่หลังแก้ · เขียนไว้ใน `/smoke-test` Stage 5
   ว่าให้รายงานทั้งจำนวนที่สแกนและจำนวนที่เปลี่ยน
2. **บันทึกกับดักนี้ไว้ตรงๆ ในสกิล** — ต่อ `page=` ทับของเดิมได้ `page=1&page=1` แล้ว API ตอบ 400
   `Expected number, received nan`
3. **หลังแก้ ต้องรันเต็มชุด ไม่ใช่เฉพาะเคสที่ตั้งใจซ่อม** — เขียนเป็นข้อบังคับใน `/smoke-test`
   Stage 5 ข้อ 3 พร้อมเหตุผลว่าการซ่อม 11 เคสแล้วทำพัง 8 เคสคือขาดทุน

## 7. การตรวจจับปัญหา (Detection)

จับได้จากการรันเต็มชุดหลังแก้ ซึ่งเป็นขั้นที่ตั้งใจทำอยู่แล้ว ไม่ใช่ความบังเอิญ
ด่านที่ยังขาดคือด่านก่อนหน้านั้น คือการไล่ผู้เรียกก่อนลงมือ

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- รันเต็มชุดหลังแก้ ทำให้เห็น regression ทันทีในเซสชันเดียวกัน
- รายงานเจ้าของงานตรงๆ ว่าเป็นความผิดของตัวเอง ไม่กลบว่าเป็นความไม่เสถียรของระบบ

### สิ่งที่ต้องปรับปรุง
- typecheck และ lint เขียวไม่ได้แปลว่าปลอดภัย เมื่อความผิดอยู่ที่ค่าไม่ใช่ชนิด
- "ปิดคลาส" ต้องรวมการไล่ผู้เรียกของสิ่งที่กำลังเปลี่ยนด้วย ไม่ใช่แค่ไล่จุดที่มีอาการเดียวกัน
