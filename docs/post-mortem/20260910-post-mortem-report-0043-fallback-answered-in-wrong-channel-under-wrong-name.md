## สรุปสั้น (Executive Summary)

เจ้าของงานรีพลายถาม **OLS QA Testing Bot** ในช่อง deployment แต่คำตอบไปโผล่ใน **เธรด QA** ในชื่อ
**"Spidey Bot"** ต้นเหตุคือทางสำรองใน `listener/index.js` — เมื่อ `msg.reply()` ล้ม มันเรียก
`postWebhookResilient()` ซึ่งต่อ `?thread_id=<เธรด QA>` **ตายตัว** และพูดผ่าน webhook ที่ Discord
ตั้งชื่อไว้ว่า "Spidey Bot" ทางสำรองนี้จึง **เปลี่ยนทั้งห้องและเปลี่ยนทั้งตัวตนของผู้พูด** ทุกครั้งที่ทางหลักล้ม
ไม่ว่าจะล้มด้วยเหตุใด

ที่ทำให้ทางหลักล้มรอบนี้คือ discord.js ตั้ง `failIfNotExists` เป็น `true` เป็นค่าปริยาย และผู้ถามลบข้อความ
ของตัวเองภายใน 47 วินาทีที่ listener ใช้ก่อนจะตอบ Discord จึงปฏิเสธทั้งคำขอด้วยรหัส 50035

ระหว่างสืบพบข้อบกพร่องซ้อนอีก 3 ข้อ ซึ่งข้อแรกทำให้ฟีเจอร์นี้ **ไม่เคยทำงานได้เลย** ตั้งแต่ติดตั้ง:
`spawn('claude')` เป็น ENOENT ทุกครั้งเพราะ launchd ให้ PATH ที่ไม่มีไบนารีนั้น · ตัวแปรผลตรวจสิทธิ์ถูก
handler ตัวที่สองเขียนทับ ทำให้เหตุผลที่รายงานผิดตั้งแต่ข้อความที่ 2 เป็นต้นไป · และตัวโพสต์ webhook
ไม่เคยอ่านรหัสสถานะ HTTP จึงพิมพ์ว่าสำเร็จได้แม้ Discord ปฏิเสธ

แก้ครบทุกข้อและขึ้นใช้งานจริงแล้ว การตัดสินปลายทางย้ายไปอยู่โมดูลบริสุทธิ์ที่มีเทสต์ตรึง 18 ข้อ

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 3.1 ทางสำรองเลือกปลายทางเอง

โค้ดที่เป็นเหตุ (`listener/index.js` ก่อนแก้):

```js
const say = async (content) => {
  try { await msg.reply({ content, allowedMentions: { parse: [] } }); return; }
  catch (e) {
    console.error(`... mention reply failed (code ${e.code}) — webhook fallback`);
    await postWebhookResilient(content);      // ← เปลี่ยนทั้งห้องและทั้งชื่อ
  }
};
```

และ `postWebhookResilient` ต่อปลายทางตายตัวเสมอ:

```js
args.push(`${wh}?thread_id=${QA_THREAD_ID}`, ...)
```

จุดตัดสินใจที่ผิดคือ **เอา "ทางหลักล้ม" มาเป็นเงื่อนไขของการใช้ webhook** ทั้งที่ข้อเท็จจริงข้อนั้น
ไม่ได้บอกอะไรเลยว่าคำตอบควรไปอยู่ที่ไหน เงื่อนไขที่ถูกต้องคือ **ปลายทางเป็นเธรดที่ webhook ผูกอยู่หรือไม่**

ตอนเขียนมันดูถูก เพราะตอนนั้นบอทพูดอยู่ในเธรด QA ที่เดียว ปลายทางของ webhook จึงบังเอิญตรงกับ
ปลายทางที่ต้องการเสมอ **ความถูกต้องมาจากความบังเอิญ ไม่ได้มาจากเงื่อนไข** พอวันที่ 2026-09-09
ขยายขอบเขตให้ตอบในช่อง deployment ได้ ความบังเอิญนั้นก็หมดลงทันที และทางสำรองกลายเป็น
"ผิดเสมอเมื่ออยู่นอกเธรด QA" โดยไม่มีใครแตะโค้ดของมันเลย

### 3.2 ทำไมทางหลักถึงล้มด้วย 50035

discord.js 14.26.5 ตั้ง `failIfNotExists: true` เป็นค่าปริยาย
(`node_modules/discord.js/src/util/Options.js:120`) และ `index.js` ไม่ได้ override ไว้ แปลว่าถ้าข้อความ
ต้นทางที่จะรีพลายถูกลบไปแล้ว Discord จะ **ปฏิเสธทั้งคำขอ** แทนที่จะโพสต์เป็นข้อความธรรมดา

หลักฐานประกอบ: ข้อความเนื้อหาเดียวกันเป๊ะส่งสำเร็จในช่องเดียวกันอีก 11 วินาทีถัดมา จึงตัดเรื่องเนื้อหา
ยาวเกินหรือว่างเปล่าออกได้ · ตัวแปรเดียวที่ต่างคือข้อความที่ถูกอ้างถึง · และข้อความบอทที่รอดอยู่ตอนนี้
ก็ไม่มีฟิลด์ `referenced_message` แล้ว = ต้นทางถูกลบเช่นกัน

**ข้อจำกัดที่ต้องบอกตรงๆ:** sub-error ของ Discord ไม่เคยถูกบันทึก เพราะ `catch` เก็บแค่ `e.code`
ข้อสรุปนี้จึงยืนบนหลักฐานแวดล้อมที่ครบทุกทาง แต่ยกข้อความ `MESSAGE_REFERENCE_UNKNOWN_MESSAGE`
มาอ้างตรงๆ ไม่ได้ การที่ยกไม่ได้ก็คือข้อบกพร่องอีกข้อ และถูกแก้ในรอบนี้แล้ว

### 3.3 ทำไมบอทถึงตอบคำถามจริงไม่ได้เลย

launchd รันบริการนี้ด้วย PATH ปริยาย `/usr/bin:/bin:/usr/sbin:/sbin` (อ่านจาก `launchctl print`)
ส่วนไบนารี `claude` อยู่ใต้ prefix ของ nvm ซึ่งไม่อยู่ใน PATH นั้น `spawn('claude', …)` จึงเป็น ENOENT
**ทุกครั้งนับตั้งแต่วันติดตั้ง** ฟีเจอร์นี้จึงไม่เคยตอบคำถามได้แม้แต่ครั้งเดียว ทุกคำถามได้ประโยคสำรอง

วัดเพิ่มระหว่างแก้: บนเครื่องนี้ `claude` มีอยู่ใต้ node v20.20.2 (ตัวที่ plist ตรึงไว้) และ **ไม่มี**
ใต้ v24.16.0 ที่เชลล์ใช้อยู่ — การพึ่ง PATH ที่สืบทอดมาคือการพึ่งสถานะที่โปรเซสนี้ไม่ได้ควบคุม

### 3.4 เหตุผลที่รายงานออกมาไม่ใช่เหตุผลจริง

ใน `authPreflight` ตอน spawn ล้ม Node จะยิงทั้ง event `error` และ `close` ตัว `resolve()` ตัวที่สอง
ไม่มีผล แต่ **การเขียนทับตัวแปร `preflight` ยังเกิด** ผลคือ handler `close` ทับผลของ `error`
ล็อกจึงบอกเหตุผลคนละเรื่องกันสำหรับความล้มเหลวเดียว (บรรทัด 53150 บอก `spawn claude ENOENT`
ส่วน 53156 บอก `auth status returned nothing readable`)

### 3.5 ตัวโพสต์ webhook พิมพ์ว่าสำเร็จโดยไม่ได้วัด

`postWebhookResilient` เรียก curl โดยไม่มี `--fail` และไม่อ่านรหัสสถานะ HTTP curl จบด้วยรหัส 0
บน HTTP 400 พอๆ กับบน 201 บรรทัด `resilient webhook POST ok` จึงพิมพ์ได้แม้ Discord ปฏิเสธ
นี่คือคลาสเดียวกับรายงาน #0006 และ #0011 เป๊ะๆ

### 5 Whys

1. **ทำไมคำตอบไปโผล่ผิดห้องและผิดชื่อ?** — เพราะทางสำรองยิงผ่าน webhook ที่ผูกกับเธรด QA
   ตายตัวและมีชื่อแสดงผลเป็นบอทอีกตัว
2. **ทำไมทางสำรองถึงถูกเรียก?** — เพราะ `msg.reply()` ถูก Discord ปฏิเสธด้วย 50035
   จากการที่ข้อความต้นทางถูกลบไปก่อน และ discord.js ตั้งให้กรณีนี้ล้มทั้งคำขอเป็นค่าปริยาย
3. **ทำไมการล้มของทางหลักถึงกลายเป็นการย้ายห้อง?** — เพราะเงื่อนไขของการใช้ webhook คือ
   "ทางหลักล้ม" ซึ่งเป็นข้อเท็จจริงที่ไม่เกี่ยวกับปลายทางเลยแม้แต่น้อย
4. **ทำไมถึงเขียนเงื่อนไขแบบนั้นไว้ตั้งแต่แรก?** — เพราะตอนเขียน บอทพูดอยู่ที่เดียว ปลายทางของ
   webhook จึงตรงกับปลายทางที่ต้องการโดยบังเอิญ ความถูกต้องมาจากสภาพแวดล้อม ไม่ได้มาจากเงื่อนไข
5. **ทำไมความบังเอิญนั้นถึงพังโดยไม่มีใครรู้?** — **เพราะการขยายขอบเขตว่าบอทพูดที่ไหนได้บ้าง
   ไม่มีอะไรผูกไว้กับตัวตัดสินว่าคำตอบไปที่ไหน คนละที่ คนละไฟล์ และไม่มีเทสต์ตัวใดยึดสองเรื่องนี้เข้าด้วยกัน**
   ← root cause จริง แก้แล้วปิดทั้งคลาส เพราะทุกทางที่บอทพูดถูกบังคับให้ผ่านตัวตัดสินตัวเดียว

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**

| ชั้น | ทำไมไม่จับ |
|---|---|
| เทสต์ `test_mention_trigger.js` | ครอบว่า **จะตอบหรือไม่ตอบ** (`route()`) เท่านั้น ไม่มีข้อไหนพูดถึงว่าคำตอบไปที่ไหน — มีข้อที่ยืนยันว่า "reply ในช่อง deployment ต้องตอบ" อยู่แล้วด้วยซ้ำ แต่หยุดตรงคำว่า "ตอบ" |
| เทสต์ `test_answer_runner.js` | ครอบ budget · kill switch · link policy · ภาษา แต่ไม่เคยแตะการเรียกไบนารีหรือปลายทาง |
| ล็อกและ SFD | ล็อกพิมพ์ `webhook fallback` ตรงๆ แต่ไม่มีใครอ่าน และไม่มี alert ผูกไว้ ส่วน `resilient webhook POST ok` ยิ่งทำให้ดูเหมือนทุกอย่างปกติ |
| การทดสอบตอนติดตั้งฟีเจอร์ | ถ้าเคยลองถามบอทจริงสัก 1 ครั้งหลังติดตั้ง จะเจอ ENOENT ทันที — ไม่มีหลักฐานว่าเคยลอง |

## 5. แนวทางการแก้ไข (Fix)

ทั้งหมดอยู่ในชุดเครื่องมือนอก repo (`~/ols-qa-testing-bot/`)

- **`listener/reply_target.js` (ไฟล์ใหม่)** — ตัวตัดสินปลายทางที่เดียว เป็นฟังก์ชันบริสุทธิ์
  `planFallback()` คืนได้ 3 อย่าง: `channel` (ห้องเดิม บอทเดิม) · `webhook` (เฉพาะเมื่อปลายทาง
  **คือ** เธรดที่ webhook ผูกอยู่) · `refuse` (บันทึกเสียงดังแล้วไม่โพสต์) — สถานะที่ 3 มีไว้ตามบทเรียน
  #0005 ว่าการ์ดต้องมีทางเลือกที่แปลว่า "ทำไม่ได้" และทางนั้นต้องไม่ตกไปฝั่งอนุญาต
- **`listener/index.js`** — `say()` ของทั้งเส้นทางรีพลายและเส้นทาง `/bot-testing` เรียก `fallbackSend()`
  ซึ่งเดินผ่านตัวตัดสินตัวเดียวกัน แทนที่จะยิง webhook ตรงๆ (ปิดคลาสเดียวกันในไฟล์ข้างเคียงในรอบเดียวกัน
  ตามบทเรียน #0003)
- **`listener/index.js`** — `msg.reply()` ส่ง `failIfNotExists: false` ข้อความต้นทางหายไปแล้วก็ยังตอบ
  ในห้องเดิมได้ และบันทึก `e.rawError` ไม่ใช่แค่ `e.code`
- **`listener/answer_runner.js`** — `resolveClaudeBin()` หาไบนารีด้วยเส้นทางสัมบูรณ์ ไล่จากตัวแปร
  สภาพแวดล้อม → ไดเรกทอรีเดียวกับ node ที่กำลังรันอยู่ → ทุกเวอร์ชันที่ nvm ติดตั้งไว้ → ตำแหน่งมาตรฐาน
  อื่น · หาไม่เจอ = ปฏิเสธพร้อม **บอกว่าค้นที่ไหนไปบ้าง**
- **`listener/answer_runner.js`** — `authPreflight` settle ครั้งเดียว handler ตัวที่สองเขียนทับไม่ได้อีก
- **`listener/index.js`** — `postWebhookResilient` อ่าน `%{http_code}` ไม่ใช่ 2xx = รายงานว่าถูกปฏิเสธ
  และคืนค่าเท็จ

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** เจ้าของงานเห็นเองบนหน้าจอ Discord ไม่มีกลไกใดในระบบจับได้เลย
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** ประมาณ 5 นาทีสำหรับอาการที่มองเห็น · แต่ข้อบกพร่องที่ทำให้บอท
  ตอบคำถามไม่ได้เลย อยู่มาตั้งแต่วันติดตั้ง **โดยไม่มีใครรู้จนถึงรอบสืบนี้**
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** ชุดเทสต์ที่ตรึงปลายทางจะทำให้การถอยกลับไปเป็นพฤติกรรมเดิม
  แดงทันทีตอนรันเทสต์ · และเทสต์ที่ยืนยันว่าไบนารีหาเจอจริงบนเครื่องนี้ ทำให้ความล้มเหลวชนิด
  "ฟีเจอร์ไม่เคยทำงานเลย" ถูกจับได้โดยไม่ต้องรอให้มีคนถามบอท

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ล็อกมีข้อมูลพอให้ประกอบไทม์ไลน์ได้ครบระดับมิลลิวินาที รวมถึงตัวเลข `age=` ที่ทำให้คำนวณย้อน
  หาเวลาที่ข้อความถูกส่งได้ และตรวจสอบกลับกับ snowflake ได้ตรงพอดี
- ตัวป้องกันการโพสต์ซ้ำและ budget ทำงานปกติ ความเสียหายจึงจำกัดอยู่ที่ข้อความเดียว
- ตอนรันเทสต์ Python แล้วตกทั้ง 41 ชุด ได้หยุดตรวจก่อนว่าทำไม แทนที่จะรายงานว่าพัง 41 จุด —
  ของจริงคือ shim บังคับให้เรียกผ่านตัวรันอีกตัว รันถูกวิธีแล้วเหลือตกจริง 5 ชุดซึ่งไม่เกี่ยวกับรอบนี้เลย

### สิ่งที่ต้องปรับปรุง
- ฟีเจอร์ใหม่ถูกปล่อยขึ้นใช้งานโดยไม่มีหลักฐานว่าเคยถูกใช้จริงสักครั้ง — ถ้าถามบอท 1 คำถาม
  หลังติดตั้ง จะเจอทั้ง ENOENT และเส้นทางสำรองในนาทีเดียว
- เทสต์ของฟีเจอร์ครอบ "ตัดสินใจถูกไหม" ครบถ้วน แต่ไม่ครอบ "ผลลัพธ์ไปถึงที่ที่ควรไปไหม" เลย
  ซึ่งเป็นครึ่งที่ผู้ใช้มองเห็น
- คำว่า `ok` ในล็อกถูกเขียนไว้ก่อนที่ใครจะวัดว่ามันสำเร็จจริง เป็นคลาสที่ repo นี้เขียนรายงานไปแล้ว
  2 ฉบับ (#0006 · #0011) และยังโผล่ในเครื่องมือตัวใหม่
