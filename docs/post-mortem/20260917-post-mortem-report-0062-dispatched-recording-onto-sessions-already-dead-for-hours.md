## 1. ปัญหา (Problem Statement)

- ก่อน dispatch เลนอัดจริง ผมรัน `ps -p 33648` (PID จากไฟล์ `.keepwarm_dev.pid`) แล้วได้ผลว่าไม่มีโปรเซสนั้นอยู่ — ตัวรักษา session ของ dev ตายแล้วจริง
- แทนที่จะหยุด ผมไปตรวจ cookie `expires` ในไฟล์ `state_*.json` ของทั้ง 5 บัญชีโดยตรง (มาตรฐานที่ถูกต้อง
  ตาม post-mortem #0025) ได้ผลว่าเหลือเวลา ~12.2 ชั่วโมง แล้วใช้ผลนี้เป็นหลักในการตัดสินใจ dispatch เลนต่อ
- Dispatch เลน R1-R4 ไปอัด 30 เคส — ทุกเลนรายงาน BLOCKED ครบ 100% (R1: 7/7, R2: 4/4, R3: 9/9, R4: 10/10)
  ด้วยอาการเดียวกัน: `GET /api/auth/get-session` ตอบ HTTP 200 แต่ body ว่างเปล่า (0 ไบต์)
- R4 ถอดรหัส JWT `access_token` เจอว่า `exp` หมดอายุไปแล้วราว 11 ชั่วโมงก่อนที่จะตรวจ ตรงกับเวลาที่
  `keepwarm_dev.log` (`~/ols-qa-testing-bot/out/vdo-4lane-2026-09-16-pm/keepwarm_dev.log`) หยุดเขียน
  บรรทัดสุดท้ายที่ 16/Sep 17:48:31 +07 (85 บรรทัด ไม่มี error ก่อนหยุด)

**สิ่งที่ควรจะเป็น:** พบว่าตัวรักษา session ตายก่อนเริ่มงานที่ต้องพึ่ง session = สัญญาณให้หยุดและตรวจ
session จริงแบบ live กับเซิร์ฟเวอร์ก่อนเสมอ ไม่ใช่หาค่าอื่นมาแทนที่ให้ผลลัพธ์ที่ดูดีกว่า — ตรงกับกฎที่
post-mortem #0026 เขียนไว้แล้ว: "ชั้นป้องกันที่ปิดได้เงียบๆ โดยงานหลักยังเริ่มได้ตามปกติ ไม่ใช่ชั้นป้องกัน
— ต้องผูกให้งานหลักปฏิเสธที่จะเริ่มเมื่อมันไม่ทำงาน"

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

จุดตัดสินใจที่ผิดคือตอนเจอ `.keepwarm_dev.pid` ตาย: ผมมีสัญญาณที่ถูกต้องอยู่ในมือแล้วว่าไม่มีอะไรต่ออายุ
session มาสักระยะ แต่แทนที่จะปฏิบัติกับมันเป็นเหตุผลให้หยุดและตรวจ session จริงแบบ live ผมไปเลือกตรวจ
ค่าอื่น (`expires` ในไฟล์) ที่ดูสบายใจกว่าแทน

### 5 Whys

1. **ทำไมเลนทั้ง 4 อัดไม่ได้เลยสักเคส?** — เพราะ session ของทั้ง 5 บัญชีที่ dispatch ไปใช้ตายจริงฝั่ง
   เซิร์ฟเวอร์อยู่ก่อนแล้ว
2. **ทำไม session ตายโดยไม่มีใครรู้ก่อน dispatch?** — เพราะเช็คแค่ `expires` ในไฟล์คุกกี้ ซึ่งเป็นค่าที่
   ฝั่ง client เก็บไว้เฉยๆ ไม่ได้สะท้อนว่าเซิร์ฟเวอร์ยังรับรอง session นั้นอยู่จริงหรือไม่
3. **ทำไมเลือกเช็คค่านั้นทั้งที่รู้ว่าตัวรักษา session ตายไปแล้ว?** — เพราะ `expires` เป็นค่าที่ตรวจง่าย
   และตอบเร็ว (ตรงกับ mandate เดิมของ post-mortem #0025 ที่บอกให้เช็คค่าจากไฟล์โดยตรง) แต่ #0025 พูดถึง
   การไม่เชื่อ "บรรทัดสรุปของเครื่องมือ" ไม่ได้พูดถึงกรณีที่ค่าที่อ่านจากไฟล์เองก็ไม่สะท้อนความจริงของ
   เซิร์ฟเวอร์ — เอากฎมาใช้ผิดบริบท
4. **ทำไมไม่ตีความ `.pid` ตายเป็นสัญญาณเตือนที่หนักแรงกว่า `expires` ที่ยังไม่หมด?** — เพราะไม่มีลำดับ
   ความสำคัญที่ชัดเจนระหว่างสองสัญญาณนี้ในหัว ตอนนั้น — ปฏิบัติกับมันเหมือนเป็นข้อมูล 2 ชิ้นที่เท่ากัน
   ทั้งที่จริงแล้ว `.pid` ตายคือสัญญาณจาก "สิ่งที่ควรจะทำให้ session สดอยู่ ไม่ได้ทำงาน" ซึ่งหนักกว่า
   ค่า `expires` ที่เป็นแค่ตัวเลขคงที่ไม่เกี่ยวกับกิจกรรมจริง
5. **ทำไมไม่มีกลไกบังคับให้ต้องตรวจ session จริงแบบ live ก่อน dispatch เสมอ?** — root cause จริง:
   ไม่มีเครื่องมือ/ด่านใดที่บังคับให้ตรวจ `get-session` จริงกับเซิร์ฟเวอร์ก่อนเริ่มงานที่ต้องพึ่ง session
   — มีแต่ขั้นตอนที่ "ทำได้" (เช่น อ่าน `expires`) ไม่ใช่ขั้นตอนที่ "บังคับก่อนเริ่ม"

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- Post-mortem #0026 เขียนกฎไว้แล้วว่า keepalive ที่ตายเงียบต้องผูกให้งานหลักปฏิเสธการเริ่ม — แต่ไม่เคยมี
  เครื่องมือ (`refilm_preflight.js` หรือเทียบเท่า) ที่บังคับใช้กฎนั้นจริงในเส้นทางที่ผมใช้ dispatch รอบนี้
  — กฎมีอยู่ในเอกสาร แต่ไม่เคยถูกทำให้เป็นเครื่องมือที่บล็อกจริง
- post-mortem #0025 ("อ่านไฟล์ state โดยตรง ไม่เชื่อบรรทัดสรุปของเครื่องมือ") ถูกใช้ถูกกรณีแต่ผิดคำถาม —
  มันตอบคำถาม "ไฟล์นี้บอกว่าอย่างไร" ได้ถูกต้อง แต่ไม่เคยตอบคำถามที่แท้จริงคือ "เซิร์ฟเวอร์คิดอย่างไร"

## 5. แนวทางการแก้ไข (Fix)

- ยืนยัน root cause ด้วยตัวเองตรงอีก 2 บัญชี (boripot, nettie) นอกเหนือจากที่ 4 เลนรายงานมา
- อ่าน `keepwarm_dev.log` เทียบกับเวลาปัจจุบันเพื่อยืนยันช่วงเวลาที่ session ตายจริง (ไม่ใช่แค่บอกว่า "ตาย" ลอยๆ)
- แจ้งเจ้าของงานทันทีพร้อมสิ่งเดียวที่ต้องมาจากคน: ล็อกอินใหม่ 5 บัญชีจริง (agent พิมพ์รหัสผ่านแทนไม่ได้)

**ยืนยันแล้วด้วย:** `lanes/R1_result.json` ถึง `R4_result.json` (30/30 BLOCKED พร้อมหลักฐาน) ·
คำสั่ง `node -e "..."` ตรวจ `get-session` ตรงกับ boripot และ nettie (0-byte body ทั้งคู่) ·
`stat` เทียบ `keepwarm_dev.log` mtime กับเวลาปัจจุบัน

| P1 | สร้าง `recording_preflight.js` — ตรวจสดทั้งตัวรักษา session (ผ่าน PID จริง ไม่ใช่ไฟล์ `.pid` มีอยู่) และ session จริงของทุกบัญชี (`get-session` สด ไม่ใช่ `expires`) ก่อน dispatch เลนอัดทุกครั้ง ปฏิเสธ (exit 1) ถ้าอันใดอันหนึ่งตาย | เครื่องมือ | ทำแล้ว — ทดสอบยืนยันว่าปฏิเสธถูกต้องกับข้อมูลจริงที่ตายอยู่ (2 กรณีแยกกัน: keepalive ตาย, และ session ตายทั้งที่ keepalive จำลองว่าสด) |

**กฎที่เพิ่มจากเหตุนี้:** เจอสัญญาณว่า "สิ่งที่ทำหน้าที่รักษาความสดของ session ไม่ทำงาน" (keepalive ตาย)
ห้ามใช้ค่าคงที่อื่น (เช่น `expires` ในไฟล์คุกกี้) มาหักล้างสัญญาณนั้น — ต้องตรวจ session จริงแบบ live กับ

subagent จริงในรอบถัดไป — ไม่ใช่ปิดเรื่องนี้ว่าจบแล้ว

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** ทั้ง 4 เลนจับได้เองอิสระกัน (แต่ละเลนพยายามอัดจริงแล้วเจออาการเดียวกัน) ผมยืนยันซ้ำเองตรงอีก 2 บัญชี
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** ราว 15-20 นาทีต่อเลน (เวลาที่แต่ละเลนใช้ก่อนสรุปว่า BLOCKED ทั้งคิว) — เสียเวลาไปกับการพยายามซ้ำหลายวิธีต่อเลนก่อนสรุป
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** `recording_preflight.js` (P1) จะจับได้ภายในไม่กี่วินาที ก่อน dispatch เลนแม้แต่ตัวเดียว แทนที่จะปล่อยให้ 4 เลนไปเจอเองพร้อมกัน

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ทั้ง 4 เลนไม่เดา ไม่ฝืนหาทางอ้อม (ไม่พยายามล็อกอินเอง ไม่เรียก `/auth/link/ndlp` เอง) — ปฏิบัติตามกฎ "agent พิมพ์รหัสผ่านไม่ได้" อย่างเคร่งครัดทุกเลน
- R3 ทดสอบผ่าน `session_refresh.js` เองแล้วยอมรับการปฏิเสธของมัน (environment-safety gate) แทนที่จะพยายามข้าม
- R4 ถอดรหัส JWT `exp` เพื่อพิสูจน์เวลาที่แน่นอน ไม่ใช่แค่บอกว่า "session หมดอายุ" ลอยๆ
- ตรวจยืนยันเองซ้ำ (ไม่เชื่อผล subagent อัตโนมัติ) ก่อนสรุปรายงานนี้

### สิ่งที่ต้องปรับปรุง
- ควรหยุดทันทีตอนเจอ `.pid` ตาย แล้วตรวจ session จริงแบบ live ก่อนเลย ไม่ใช่ไปเช็คค่าอื่นที่ดูสบายใจกว่าแทน
- ต้องมีเครื่องมือบังคับ (ไม่ใช่แค่ความจำ) ที่ปฏิเสธการ dispatch เมื่อพบสัญญาณแบบนี้ — สร้างแล้วรอบนี้ (P1) แต่ยังไม่ได้ผูกเป็นด่านบังคับจริง (P2)
