## สรุปสั้น (Executive Summary)

คลิป R130 (สคริปต์ของผม) และ R121 (เลน S) อัดด้วย Playwright `recordVideo` ซึ่ง memory `feedback_recording-skill-latest-version-only`
ห้ามไว้ชัดเจน ได้ไฟล์ไม่มี `capture.json` และ R130 เหลือ 1440×810 แต่ผมใส่ `PASSED` พร้อมลิงก์ในชีทไปแล้วทั้ง 2 แถว เพราะด่านเผยแพร่
ของผม (`publish_pass.py`) ตรวจแค่ภาพในคลิป ไม่ตรวจว่าคลิปมาจากตัวอัดของสกิล เจ้าของงานเป็นคนถามเรื่องคุณภาพจึงพบ
ระหว่างอัดใหม่ ผมยังส่งคำสั่งที่ให้เจ้าของงาน "แทนข้อความด้วยรหัสผ่าน" 2 ครั้ง ซึ่งถูกรันโดยไม่ได้แทน ทำให้เสียรอบเพิ่ม

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. ทำไมคลิปผิดมาตรฐานได้ PASSED? — ด่านเผยแพร่ตรวจแถว/ชื่อเคส/สถานะ แต่ไม่ตรวจที่มาของคลิป
2. ทำไมใช้ `recordVideo`? — ตอนแก้ปัญหาหน้าต่างล็อกอิน (#0074) ผมเขียนสคริปต์ใหม่เอง ไม่ได้เปิด memory เรื่องตัวอัดก่อน · เลน S ใช้เพราะ `record.js` มีหน้าเดียวแต่เคส 121 ต้องปิด-เปิดแท็บ
3. ทำไมไม่มีใครจับ? — memory เป็นข้อความ ไม่มีเครื่องมือบังคับที่จุดเผยแพร่
4. ทำไมคำสั่งรหัสผ่านถูกรันแบบไม่แทนค่า? — ผมให้คำสั่งที่ต้องแก้ข้อความในบรรทัดก่อนรัน ซึ่งผิดง่ายและยังทำให้รหัสผ่านไปอยู่ในประวัติคำสั่ง
5. ทำไมเลือกแบบนั้น? — ไม่ได้คิดถึงวิธีที่ไม่ต้องแก้คำสั่ง (`read -rs`) ตั้งแต่แรก

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** memory และหัวข้อใน SKILL ไม่ได้ผูกกับขั้นตอนเขียนชีท · `verify-video.py` ถูกเรียกเฉพาะเมื่อมีคนเรียก

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

- ด่านเผยแพร่ต้องปฏิเสธคลิปที่ไม่มี `<stem>.capture.json` ข้างไฟล์ และต้องรัน `verify-video.py` ผ่านก่อนเขียนชีท
- คำสั่งที่ต้องใช้รหัสผ่านให้ใช้ `read -rs` ถามตอนรันเสมอ ห้ามให้ผู้ใช้แก้ข้อความในบรรทัดคำสั่ง
- เคสที่ต้องให้คนพิมพ์รหัสผ่านระหว่างอัดด้วยสกิล ให้ใช้ `SR_PASS` ผ่าน Terminal ตั้งแต่แรก ไม่เปิดหน้าต่าง (หน้าเว็บต้องกว้าง 1920 เกินจอ 1470)
