## สรุปสั้น (Executive Summary)

เวลา 22:5x เจ้าของงานอนุมัติ Save A บน pre-prod (ยกเกณฑ์อนุมัติชั่วคราว ไม่ตัดสินสื่อใด) แล้วเธรดหลักส่งคำสั่งให้เลน B2 "ทำทันทีก่อนงานอื่น" โดยไม่ได้ตรวจว่าเลน F2 ยังโหวตไม่อนุมัติบน fixture ที่ผลขึ้นกับเกณฑ์อยู่
เจ้าของงานเตือน "อย่าทำงานชนกัน" เธรดหลักจึงส่งกฎลำดับตามไป แต่ข้อความถึงเลนในรอบ tool ถัดไป — B2 บันทึกเกณฑ์ 3/5/3/1 → 4/6/4/2 ไปแล้วเมื่อ 15:55:09Z ขณะที่ F2 ยังมีงานโหวตไม่อนุมัติที่ผลขึ้นกับเกณฑ์ค้างอยู่ (โหวต HIGH บน fixture อีกชุดที่วางแผนไว้)
แก้แล้ว: หยุดการกระทำย้อนไม่ได้ทั้งหมดบน pre-prod · คืนค่าเกณฑ์หลังล็อกหมด (23:55:09) · แถวที่โหวตหลัง 15:55:09Z ตัดเป็น EVIDENCE_PENDING · แถว G3 ไม่ตัดเป็น BLOCKED

- **สิ่งที่เกิดจริง:** B2 บันทึกเกณฑ์อนุมัติ 15:55:09Z (PUT 200 · อ่านกลับได้ 4/6/4/2 · lockedUntil 16:55:09Z) ขณะที่ F2 ยังไม่จบงานโหวต (ไม่มี `F2_ONEWAY_DONE`) · **ตรวจภายหลัง:** โหวตจริงของ F2 ครั้งสุดท้าย 15:54:08Z ไม่มีโหวตหลัง 15:55:09Z → ผลของ F2 ไม่ถูกกระทบ · โหวต HIGH ที่วางแผนไว้ไม่ได้ทำ · บรรทัด `F2 USING` 15:55:01Z ใน `ACCOUNT_LOCKS.log` ถูกเขียนย้อนหลังหลังโหวตเสร็จ ใช้เป็นหลักฐานลำดับเวลาไม่ได้
- **ขอบเขต:** pre-prod เท่านั้น · เกณฑ์รายงานไม่ถูกแก้ (ยัง 5/3/1) · คิวรออนุมัติลดจาก 249 เป็น 248 (fixture ของรอบ 1 รายการออกจากคิว — กำลังตรวจว่าเกิดจากโหวตของ F2 ก่อนหรือหลังการบันทึก)

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไมเกณฑ์กลางถูกเปลี่ยนกลางการทดสอบของอีกเลน?** — B2 ทำตามคำสั่งเธรดหลักที่ให้บันทึกทันที
2. **ทำไมเธรดหลักสั่งทันที?** — ส่งต่อมติเจ้าของงานโดยไม่ได้อ่านสถานะเลนอื่นใน env เดียวกัน (marker + จองบัญชี) ก่อนสั่ง
3. **ทำไมกฎลำดับที่ส่งตามไปไม่ทัน?** — ข้อความถึง subagent ในรอบ tool ถัดไปของมัน เลนที่กำลังทำขั้นตอนหนึ่งอยู่จึงทำต่อก่อนอ่านข้อความ — คำสั่งที่ส่งตามไปไม่ใช่การหยุดที่เชื่อได้
4. **ทำไมไม่มีอะไรกันที่ตัวเลน?** — บรีฟรอบ 3 ไม่มีกฎ barrier ของค่ากลาง (มีแต่ในแผน) และยังไม่มีไฟล์จองที่เลนต้องอ่านก่อนแก้ค่ากลาง
5. **ทำไมบรีฟขาดกฎนี้?** — บรีฟรอบ 3 เขียนจากหัวข้อ Handoff (H1–H5) ไม่ได้คัดกฎ barrier ของ Phase 3 มาด้วย

**สาเหตุราก:** เธรดหลักสั่งงานที่แก้ค่ากลางโดยไม่ตรวจสถานะเลนอื่นของ env เดียวกันก่อน และกฎ barrier ไม่ได้อยู่ในบรีฟที่เลนอ่าน จึงไม่มีด่านใดหยุดได้ทั้งฝั่งเธรดหลักและฝั่งเลน

## 4. ผลกระทบ (Impact)

- เกณฑ์อนุมัติทั้ง env ของ pre-prod เป็น 4/6/4/2 ระหว่าง 22:55:09–23:55:09 (คืนค่าได้หลังล็อกหมด — เกินเส้นตายเที่ยงคืนของเจ้าของงาน แต่อยู่ในมติที่อนุมัติให้คืนหลังเที่ยงคืน)
- ตรวจแล้ว: ไม่มีโหวตของ F2 หลัง 15:55:09Z → ไม่มีแถวใดถูกวัดกับเกณฑ์ผิด · ความเสียหายคือความเสี่ยง + งานโหวตที่เหลือต้องเลื่อนออกไป
- สื่อของผู้ใช้อื่นในคิวไม่ถูกตัดสินจากการบันทึก (ตรวจก่อนบันทึก: คะแนนสูงสุดในคิว อนุมัติ 2 · ไม่อนุมัติ 0 ทุกระดับ)

## 5. แนวทางการแก้ไข (Fix)

- หยุดการกระทำย้อนไม่ได้ทั้งหมดของ B2 และ F2 บน pre-prod (ข้อความ 22:5x · B2 ยืนยัน "no one-way action")
- คืนเกณฑ์เป็น 3/5/3/1 หลัง 23:55:09 (pre-ledger + PUT + อ่านกลับ + `PREPROD_THRESHOLD_RESTORED`)
- แถว G3 7 แถว: EVIDENCE_PENDING พร้อมเหตุผล ไม่ใช่ BLOCKED
- ให้ F2 รายงานเวลากดยืนยันจริงของทุกโหวตหลัง 15:40Z เพื่อแยกแถวที่ถูกกระทบ

**ยืนยันแล้วด้วย:** `ACCOUNT_LOCKS.log` (F2 USING 15:55:01Z) · `LB2/progress.log` + `LB2/ledger.jsonl` (save 15:55:09Z, อ่านกลับ 4/6/4/2, lockedUntil 16:55:09Z)

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- เลน B2 ตรวจก่อนบันทึกว่าไม่มีสื่อใดถูกตัดสิน และเขียน baseline + pre-ledger ครบ ทำให้คืนค่าได้แน่นอน
- มีไฟล์จองบัญชีที่บันทึกเวลา จึงพิสูจน์ลำดับเหตุการณ์ได้ถึงระดับวินาที

### สิ่งที่ต้องปรับปรุง
- ข้อความที่ส่งตามไปหา subagent ไม่ใช่การหยุดที่เชื่อได้ — ต้องจัดลำดับก่อนสั่ง ไม่ใช่สั่งแล้วแก้ทีหลัง
