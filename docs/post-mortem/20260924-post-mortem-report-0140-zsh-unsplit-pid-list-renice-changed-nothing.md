## สรุปสั้น (Executive Summary)

เจ้าของงานอนุมัติให้ลดลำดับ CPU ของ GitHub runner (renice +10) แทนการหยุดงาน เธรดหลักเก็บ pid ด้วย `P=$(… | tr '\n' ' ')` แล้วสั่ง `renice -n 10 -p $P` ใน zsh ซึ่งไม่แยกคำของตัวแปร renice จึงได้สตริงเดียว `"1287 1340 1369 "` และตอบ `pid argument … is invalid` ไม่มีโปรเซสใดถูกเปลี่ยน คอลัมน์ NI ในคำสั่งเดียวกันยังเป็น 0 ทุกตัว จึงจับได้ทันที แก้เป็น array `P=($(…))` + `"${P[@]}"` ได้ nice=10 ครบ 23 ตัว เป็นคลาสเดียวกับ #0118/#0124 ซึ่ง `zsh-split-guard` ยังไม่มีกฎสำหรับ "ตัวแปรที่มีหลายคำถูกใช้เป็นอาร์กิวเมนต์" และยังไม่ผูก hook รอบนี้เพิ่มกฎข้อ 4 พร้อมเทสต์ (19/19)

## 1. ปัญหา (Problem Statement)

- **สิ่งที่ควรเกิด:** runner ทุกตัวได้ nice=10 ทันทีหลังได้รับอนุมัติ เพื่อให้งานอัดคลิปได้ CPU ก่อน
- **สิ่งที่เกิดจริง:** 2 คำสั่งแรก (08:26:56 และ 08:27:08 +07) ไม่เปลี่ยนโปรเซสใดเลย · output จริงของคำสั่งที่ 2: `renice: pid argument 1287 1340 1369  is invalid.` และ NI = 0 ทั้ง 3 ตัว
- **ขอบเขต:** เฉพาะคำสั่ง renice ของเธรดหลัก ไม่มีการเขียนข้อมูลใดๆ ไม่มีโปรเซสใดถูกหยุด

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไม renice ไม่เปลี่ยนโปรเซสใด?** — เพราะได้อาร์กิวเมนต์เดียว `"1287 1340 1369 "` ซึ่งไม่ใช่ pid ที่ถูกต้อง
2. **ทำไมได้อาร์กิวเมนต์เดียว?** — เพราะ Bash tool บนเครื่องนี้รัน zsh และ zsh ไม่แยกคำของ `$P` ที่ไม่ใส่เครื่องหมายคำพูด (bash แยก)
3. **ทำไมเขียนแบบ bash อีก ทั้งที่มี #0118 และ #0124 แล้ว?** — เพราะมาตรการของทั้งสองฉบับเป็นกฎในตัว guard ที่ไม่ได้ผูก hook (ตรวจ: `grep -c zsh-split .claude/settings.json` = 0) คำสั่งจึงไม่ถูกตรวจก่อนรัน
4. **ถ้าผูก hook แล้วจะจับได้ไหม?** — ไม่ได้ · ก่อนแก้ `decideCommand()` คืน `{"block":false}` ทั้งคำสั่ง `P=$(pgrep …); renice -p $P` และคำสั่งของ #0124 `F="a b"; prettier --write $F` เพราะกฎมีแค่ `set -- $X` และ `for … in` (ข้อ 1–3)
5. **ทำไมกฎไม่ครอบรูปนี้?** — (root cause) #0124 ระบุรูป "ตัวแปรหลายคำถูกใช้เป็นอาร์กิวเมนต์" แล้ว แต่มาตรการที่เสนอคือผูก hook เท่านั้น ไม่ได้เพิ่มกฎให้ตรงรูปของเหตุการณ์ของตัวเอง ชั้นเครื่องจึงไม่ครอบคลาสนี้แม้จะผูกแล้วก็ตาม

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- `zsh-split-guard` (#0118) — ไม่ผูก hook และไม่มีกฎสำหรับรูปนี้ (วัดด้วย `decideCommand` ก่อนแก้: false ทั้ง 2 คำสั่ง)
- #0124 — มาตรการ "ผูก hook" ยังไม่ได้ทำ และถ้าทำก็ไม่ครอบ (ข้อ 4)
- ชั้นที่จับได้จริงคือนิสัยพิมพ์ NI ก่อน/หลังในคำสั่งเดียวกัน ซึ่งไม่ใช่ชั้นเครื่อง

## 4. ผลกระทบ (Impact)

- **ผู้ใช้/ระบบ:** ไม่มี · ไม่มีโปรเซสใดถูกเปลี่ยนหรือหยุดจากคำสั่งที่ผิด
- **เวลา:** 21 วินาที (08:26:56 → 08:27:17) ก่อนได้ผลที่ถูกต้อง
- **ความเสี่ยงหากไม่จับ:** งานอัดคลิปจะแย่ง CPU กับ runner ต่อ โดยเข้าใจว่าได้ลดลำดับแล้ว

## 5. แนวทางการแก้ไข (Fix)

- คำสั่งที่ถูก: `P=($(…))` แล้ววน `for p in "${P[@]}"; do renice -n 10 -p $p; done` · ตรวจ NI หลังรัน = 10 ครบ 23 ตัว
- รายชื่อ pid เก็บไว้ใน scratchpad ของ session เพื่อคืนค่า `renice 0` หลังอัดเสร็จ (ตามเงื่อนไขที่เจ้าของงานอนุมัติ)

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

ชั้นใหม่ (แข็งกว่า #0124 ที่เป็นข้อเสนอผูก hook อย่างเดียว):

1. **กฎข้อ 4 ใน `tools/zsh-split-guard/split_rules.js`** — ปฏิเสธเมื่อ (ก) ตัวแปรถูกกำหนดเป็นข้อความในเครื่องหมายคำพูดที่มีช่องว่าง หรือเป็น `$(…)` ที่คำสั่งข้างในพิมพ์รายการ (pgrep/ps/ls/find/grep/awk/cut/…) และ (ข) ถูกใช้แบบไม่ใส่เครื่องหมายคำพูดเป็นอาร์กิวเมนต์ · ยกเว้น `echo $V`, `"$V"`, `${=V}`, array `V=(…)`
2. **เทสต์คู่กฎ** — ต้องพบ 2 ข้อ (คำสั่งของเหตุการณ์นี้ และของ #0124) · ต้องไม่พบ 2 ข้อ (รูปที่ถูก และตัวแปรคำเดียว / `$(date)`) · รวม 19/19
3. **ผูก hook** — ยังต้องได้รับอนุมัติจากเจ้าของงาน (CLAUDE.md §10 แก้ hooks/config ต้องถาม) · บันทึกเป็น Action Item

- จับได้จาก stderr ของ renice และคอลัมน์ NI ที่พิมพ์ในคำสั่งเดียวกัน 3 วินาทีหลังรัน
