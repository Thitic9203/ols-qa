## สรุปสั้น (Executive Summary)

`run.sh` เขียนบรรทัด `FAIL | …` ลง results.log ด้วย `result()` ก่อนเรียก `fail_notify` ทุก branch ส่วนชั้น L4 ใน `fail_notify` ระงับการแจ้งเตือนถ้า results.log "โตขึ้น" ระหว่างรอบ (ถือว่า session เขียนผลแล้ว) บรรทัด FAIL ของบอทเองจึงทำให้ L4 ระงับการแจ้งเตือนจริงทุกครั้ง แก้แล้วโดยให้ `result()` เลื่อน baseline ของตัวเอง

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. ทำไมไม่มีใครได้รับแจ้ง — L4 ระงับ
2. ทำไม L4 ระงับ — `verdict_written_since` เห็น results.log โตกว่า baseline
3. ทำไมโต — `result "FAIL | …"` ของบอทเองถูกเขียนก่อน `fail_notify`
4. ทำไมไม่มีใครเห็น — เทสต์ L4 ใช้บรรทัดที่เขียนเองด้วย printf ไม่ได้เรียก `result()` ตัวจริง จึงไม่เคยทดสอบลำดับ "result แล้ว fail_notify"
5. ทำไม log "SUPPRESSED" ไม่ทำให้สะดุด — ข้อความบอกว่าเป็น false alarm จึงอ่านเหมือนระบบทำงานถูก

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** heartbeat ของ SFD ดูผลของงานตามตาราง ไม่ได้ดูว่า fail_notify ถูกระงับ · ledger false alarm (L9) บันทึกการระงับแต่ไม่มีใครตรวจว่าระงับถูกหรือไม่

## 4. ผลกระทบ (Impact)

ความล้มเหลว 6 รอบไม่ถูกแจ้ง เจ้าของงานไม่รู้ว่าต้อง re-run · ไม่มีการเขียน Jira/ข้อมูลผิด เพราะทุกรอบไม่มีผลตัดสิน

## 5. แนวทางการแก้ไข (Fix)

`result()` เพิ่ม `BEFORE_RUN` ทีละ 1 เมื่อบอทเขียนบรรทัดเอง บรรทัดที่ session เขียนยังระงับได้ตามเดิม

**ยืนยันแล้วด้วย:** `tests/test_false_alarm_defense.sh` เคส L4b (ต้องเจอ: บรรทัด FAIL ของบอทอย่างเดียวต้องแจ้ง — แดงก่อนแก้ · ต้องไม่เจอ: บรรทัด `AUTOTEST BLOCKED` ของ session ต้องระงับ) → `PASSED: false-alarm defense intact` · `tests/test_classify_quota.sh` PASSED all 6 · commit `14794e8`

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

- เทสต์ L4b เรียก `result()` ตัวจริงที่ดึงจาก `run.sh` ไม่ใช่สำเนา
