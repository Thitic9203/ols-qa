## สรุปสั้น (Executive Summary)

- push commit แก้ sync (#0063) ครั้งแรกถูก pre-push บล็อกด้วยข้อความ "ไม่ได้รับรายการ ref ทาง stdin เลย"
- ผมบอกเจ้าของงานทันทีว่า "เมื่อ push ไม่ใช่ fast-forward git ไม่ส่งรายการ ref ให้ pre-push" ในรูปข้อเท็จจริง แล้วค่อยไปทดลองหลังจากนั้น
- ผลทดลอง: กรณี commit ปลายทางยังไม่อยู่ในเครื่อง (`fetch first`) hook ได้ stdin 103 ไบต์ — ประโยคผิด · กรณี commit ปลายทางอยู่ในเครื่องแล้ว (`non-fast-forward`) hook ได้ 0 ไบต์ — ประโยคถูก · เหตุจริงคือกรณีที่สอง
- แก้คำพูดในแชทพร้อมหลักฐานทั้งสองกรณีแล้ว

## 1. ปัญหา (Problem Statement)

- ข้อความที่ส่งถึงเจ้าของงานระบุกลไกของ git แบบไม่มีเงื่อนไข ขณะที่ยังไม่มีการทดลองใดรองรับ
- ของจริงขึ้นกับว่า commit ปลายทางอยู่ในเครื่องหรือไม่ ประโยคนั้นจึงผิดครึ่งหนึ่ง

**สิ่งที่ควรจะเป็น:** กฎข้อแรกสุดของ `CLAUDE.md` — ถ้ายังไม่ได้ตรวจ ให้พูดว่ายังไม่ได้ตรวจ หรือเขียนเป็นสมมติฐานพร้อมวิธีตรวจ ห้ามพูดเหมือนตรวจแล้ว

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

- กลไกที่พูดออกไป "เข้ากับอาการ" (stdin ว่าง + origin เดินหน้า) จึงถูกเขียนเป็นคำอธิบายก่อนที่จะมีหลักฐาน
- ในข้อความเดียวกันผมเขียนว่าจะไปพิสูจน์ แปลว่ารู้อยู่แล้วว่ายังไม่ได้ตรวจ แต่เลือกใช้รูปประโยคแบบข้อเท็จจริง

### 5 Whys

1. **ทำไมพูดกลไกที่ยังไม่ได้วัด?** — ต้องการอธิบายให้เจ้าของงานรู้ทันทีว่าทำไม push ล้ม
2. **ทำไมไม่รอผลทดลองก่อน?** — กฎรายงานความคืบหน้ากดดันให้ส่งข้อความก่อนลงมือ และคำอธิบายที่เข้ากับอาการดูเหมือนพอ
3. **ทำไมไม่เขียนเป็นสมมติฐาน?** — ไม่มีรูปแบบบังคับสำหรับข้อความที่อธิบายสาเหตุระหว่างทาง จึงใช้รูปประโยคเดียวกับข้อเท็จจริงที่ตรวจแล้ว
4. **ทำไมชั้นป้องกันไม่จับ?** — hook ที่มีตรวจคำ hedge (น่าจะ/อาจจะ) แต่ประโยคที่มั่นใจเกินจริงไม่มีคำเหล่านั้น จึงไม่มีอะไรให้จับ
5. **ทำไมรูปแบบนี้เกิดซ้ำ?** — #0004 และ #0019 ก็เป็นข้ออ้างที่ "ฟังเข้ากับอาการ" แล้วถูกพูดก่อนวัดเหมือนกัน การแก้ครั้งก่อนเน้นที่ตัวเลขและคำสั่งให้ผู้อ่านทำ ไม่ได้ครอบคำอธิบายกลไก

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** investigation-guard รายงานคำ hedge แต่ไม่รายงานประโยคที่อ้างกลไกโดยไม่มีหลักฐาน ซึ่งเครื่องแยกไม่ออกจากข้อความที่ตรวจแล้ว — ชั้นนี้จึงยังเป็นวินัยของผู้เขียน

## 4. ผลกระทบ (Impact)

- ไม่มีการลงมือใดตามประโยคนั้น การ rebase และ push ถูกเลือกจากหลักฐาน reflog และ `merge-base` ที่วัดแล้ว
- เจ้าของงานได้รับคำอธิบายที่ถูกเฉพาะบางกรณีอยู่ช่วงสั้นๆ ก่อนถูกแก้พร้อมหลักฐาน

## 5. แนวทางการแก้ไข (Fix)

- แก้คำพูดในแชทพร้อมผลทดลองทั้งสองกรณี และหลักฐาน reflog ว่าเหตุจริงเป็นกรณีไหน

**ยืนยันแล้วด้วย:** repo จำลอง — clone ที่ยังไม่มี commit ปลายทาง: `! [rejected] HEAD -> main (fetch first)` + hook stdin 103 ไบต์ · clone เดียวกันหลัง `git fetch`: `! [rejected] HEAD -> main (non-fast-forward)` + hook stdin 0 ไบต์ · repo จริง: `fe338f8 refs/remotes/origin/main@{09:39:43}: fetch …` ก่อน push ที่ล้มตอน 10:11:02

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

- ข้อความความคืบหน้าที่ต้องอธิบายสาเหตุก่อนวัด เขียนขึ้นต้นว่า "สมมติฐาน:" และบอกวิธีตรวจในประโยคเดียวกัน
- ข้อความของ `scripts/hooks/pre-push` ที่อ้างว่า "git จะป้อนรายการ ref มาให้เสมอ" ไม่จริงในกรณี non-fast-forward — เสนอให้ hook บอกเหตุนี้เองเมื่อ stdin ว่าง เพื่อไม่ให้คนต้องเดากลไกอีก (รอเจ้าของงานตัดสิน)

**กฎที่เพิ่มจากเหตุนี้:** คำอธิบายสาเหตุหรือกลไกที่ยังไม่ได้วัด ต้องเขียนเป็น "สมมติฐาน: … (จะตรวจด้วย …)" ห้ามใช้รูปประโยคแบบข้อเท็จจริง แม้จะตั้งใจไปตรวจต่อในเทิร์นเดียวกัน — สรุปไว้ใน `CLAUDE.md` หัวข้อ Post-mortems (Report #0064)

## 7. การตรวจจับปัญหา (Detection)

- จับได้เองจากผลทดลองกรณีแรก (103 ไบต์) ที่ขัดกับประโยคที่พูดไป แล้วทดลองกรณีที่สองให้ครบก่อนแก้คำพูด

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี

- ไม่ได้ลงมือจากประโยคนั้น แต่เลือกทางแก้จากหลักฐานที่วัดแล้ว
- เมื่อผลทดลองแรกขัดกับคำพูด ไม่ได้ยึดคำพูดเดิม แต่ทดลองกรณีที่เหลือให้ครบก่อนสรุป

### สิ่งที่ต้องปรับปรุง

- คำอธิบายที่ "เข้ากับอาการ" ยังถูกเขียนเป็นข้อเท็จจริงได้ง่าย ต้องใช้รูปแบบสมมติฐานเสมอจนกว่าจะวัด
