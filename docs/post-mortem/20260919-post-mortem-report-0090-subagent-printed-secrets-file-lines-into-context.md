**ระบบ:** OLS QA workspace — การสั่งงาน subagent ที่ต้องอ่านค่าคอนฟิกจากไฟล์ secrets นอก repo
**สภาพแวดล้อมที่ได้รับผลกระทบ:** context ของ subagent และ transcript ของเซสชันบนเครื่องเจ้าของงาน (ไม่เกี่ยวกับ env ใดของ OLS)
**วันที่เกิดเหตุ:** 2026-09-19
**วันที่ค้นพบ:** 2026-09-19
**วันที่จัดทำรายงาน:** 2026-09-19
**ผู้จัดทำ:** Claude (ในเซสชันของเจ้าของงาน)
**ระดับความรุนแรง:** Medium — ค่าลับจริง (รหัสผ่านบัญชีทดสอบ · token Figma · id ชีท/Drive/Discord) เข้า context ของโมเดลและ transcript บนเครื่อง แต่ไม่ถูกเขียนลงไฟล์งาน ไม่เข้า git ไม่ถูกส่งไปช่องทางที่คนอื่นเห็น
**ประเภท:** อื่นๆ — ข้อมูลลับเข้า context เพราะคำสั่งกรองแบบ fail-open และ brief ไม่มีข้อห้าม

## สรุปสั้น (Executive Summary)

subagent ที่ถูกส่งไปแก้ `capture/session_refresh.js` (นอก repo) ต้องหา auth host ของ pre-prod และเริ่มค้นจากไฟล์ `~/.ols-qa-secrets/ols-secrets.md`
มันรัน `grep -n … | sed …` โดยตั้งใจให้ `sed` ตัดค่าออกเหลือแต่ชื่อ key แต่ pattern ของ `sed` ไม่ได้เผื่อเลขบรรทัดที่ `grep -n` เติมไว้หน้าบรรทัด
เมื่อ pattern ไม่ตรง `sed` ก็ปล่อยบรรทัดเดิมผ่านทั้งบรรทัด ค่าลับหลายรายการจึงเข้า context ของ agent
ต้นเหตุเชิงระบบคือไม่มีชั้นใดกำหนดว่า "ค่าในไฟล์ secrets ห้ามเข้า context" · brief จากเธรดหลักก็ไม่ได้ห้าม และไม่มีเครื่องมือกลางที่อ่านได้แค่ชื่อ key
agent รายงานความผิดพลาดนี้เองในไฟล์ผล · ยังไม่มีการหมุน token ใดๆ เพราะเป็นการตัดสินใจของเจ้าของงาน

## 1. ปัญหา (Problem Statement)

- ไฟล์ผลของ agent (`~/ols-qa-testing-bot/out/lanes-2026-09-19/RF_fix_RESULT.md` §5) บันทึกว่า `grep -n … | sed` บนไฟล์ secrets พิมพ์ **บรรทัดลับทั้งบรรทัด** (ไม่ใช่แค่ชื่อ key) เข้า context เพราะ pattern ของ sed ไม่ตรงกับ prefix จาก `-n`
- บรรทัดที่หลุด (ตามบันทึกของ agent): รหัสผ่านบัญชีทดสอบ · token Figma · id ชีท/Drive/Discord
- บันทึกขั้นตอน `RF_fix.jsonl` ขั้น `src1_secrets` (2026-09-19 10:54:43Z) ระบุ "grep accidentally echoed full secret lines into agent context (local only)"
- brief ของเธรดหลักสั่งให้หา auth host ของ pre-prod โดยไล่แหล่งตามลำดับ (ไฟล์ secrets เป็นแหล่งแรก) แต่ไม่มีข้อความห้ามพิมพ์ค่าจากไฟล์นั้น
- รายงานฉบับนี้ไม่ได้เปิดไฟล์ secrets และไม่ได้พิมพ์ค่าลับใดๆ ข้อเท็จจริงข้างต้นมาจากไฟล์ผลของ agent ซึ่งอ่านผ่านตัวกรองที่ปิดสตริงยาว/อีเมลก่อนแสดง

**สิ่งที่ควรจะเป็น:** การหาค่าจากไฟล์ secrets ต้องเห็นแค่ **ชื่อ key หรือจำนวนที่ตรง** (เช่น `grep -c '^KEY_NAME'`) และค่าที่จำเป็นต้องใช้ให้ส่งเข้าโปรแกรมโดยตรง ไม่ผ่านหน้าจอ — `CLAUDE.md` §5 วางหลักว่าค่าจริงอยู่ใน `~/.ols-qa-secrets/` เท่านั้น และ §0 กำหนดว่าเครื่องมือที่เขียนเองต้องผ่านตัวอย่างที่รู้คำตอบก่อนเชื่อ

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

agent ตั้งใจจะเห็นแค่ชื่อ key จึงเขียนคำสั่งสองท่อน: `grep -n` หาบรรทัด แล้ว `sed` แทนส่วนค่าให้หายไป
แต่ `sed s/…/…/` เป็นการ **แปลง** ไม่ใช่การ **คัดเลือก** — บรรทัดที่ pattern ไม่ตรงจะถูกพิมพ์ออกมาตามเดิม
เมื่อ `grep -n` เติม `<เลขบรรทัด>:` หน้าบรรทัด pattern ที่ยึดต้นบรรทัดก็ไม่ตรงเลยสักบรรทัด ตัวกรองจึงไม่กรองอะไร
คำสั่งนี้ไม่เคยถูกลองกับตัวอย่างปลอมก่อนใช้กับไฟล์จริง จุดที่ผิดพลาดจึงเห็นหลังจากค่าเข้า context ไปแล้ว

### 5 Whys

1. **ทำไมค่าลับถึงเข้า context ของ agent?** — เพราะคำสั่ง `grep -n … | sed …` ปล่อยบรรทัดเดิมผ่านทั้งบรรทัด เมื่อ pattern ของ sed ไม่ตรงกับ prefix เลขบรรทัดที่ `-n` เติมไว้
2. **ทำไมตัวกรองที่ไม่ตรงถึงปล่อยค่าลับออกมา?** — เพราะมันเป็นตัวกรองแบบ fail-open (sed พิมพ์ทุกบรรทัดที่ไม่ตรงตามเดิม) และไม่ได้ลองกับตัวอย่างที่รู้คำตอบก่อนรันกับไฟล์จริง ตามที่ `CLAUDE.md` §0 กำหนดไว้กับเครื่องมือที่เขียนเอง
3. **ทำไม agent ถึงต้องเขียนตัวกรองเองกับไฟล์ secrets?** — เพราะไม่มีเครื่องมือกลางที่ตอบว่า "มี key นี้ไหม / มี key อะไรบ้าง" โดยไม่แสดงค่า ทุก agent ต้องประดิษฐ์คำสั่งเองทุกครั้ง
4. **ทำไม brief ถึงไม่กันไว้?** — เพราะเธรดหลักเขียน brief ให้ "หา auth host ของ pre-prod" และระบุไฟล์ secrets เป็นแหล่งแรก แต่ไม่มีข้อบังคับว่าห้ามพิมพ์ค่า และ `agent-dispatch-guard` ตรวจแค่ข้อ persist-before-print ไม่มีกฎเรื่องไฟล์ secrets
5. **ทำไมไม่มีชั้นใดครอบเลย?** — เพราะกฎเรื่อง secrets ทั้งหมดใน repo (`CLAUDE.md` §5 · `scripts/check-no-secrets.sh` · git-staging-guard) ออกแบบมากัน **การ commit/เผยแพร่** เท่านั้น ไม่มีชั้นใดถือว่า "ค่าในไฟล์ secrets ห้ามเข้า context ของโมเดล" ความปลอดภัยจึงขึ้นกับว่าคำสั่งเฉพาะกิจของแต่ละ agent เขียนถูกหรือไม่ **(root cause)**

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- `scripts/check-no-secrets.sh` และ git-staging-guard ทำงานตอน stage/commit เท่านั้น ค่าไม่ได้ถูก commit จึงไม่มีอะไรให้จับ
- `agent-dispatch-guard` ตรวจ brief แต่ไม่มีกฎเรื่องการอ่านไฟล์ secrets (ค้น `grep -rlE 'ols-secrets|secret' tools/agent-dispatch-guard/` ไม่พบไฟล์ใด)
- `.claude/settings.json` ไม่มี hook ใดอ้าง `ols-secrets` (`grep -c 'ols-secrets' .claude/settings.json` = 0) — ไม่มีชั้นใดดัก Bash/Read ที่แตะไฟล์นี้
- hook ที่อ่านไฟล์นี้ (`inject-context.sh` · `customer-content-guard.sh`) ใช้แค่เช็คว่ามีไฟล์/หา host ไม่ได้ทำหน้าที่กัน

## 5. แนวทางการแก้ไข (Fix)

- รายงานฉบับนี้และแถว `PENDING.md` ทำตามลำดับ `CLAUDE.md` §1 — บันทึกเหตุ ต้นเหตุ และมาตรการ
- **ไม่ได้หมุน token หรือรหัสผ่านใด** และไม่ได้ลบ transcript — ทั้งสองเรื่องเป็นการตัดสินใจของเจ้าของงาน (Action 3–4)
- ไม่ได้ติดตั้ง hook หรือแก้ `.claude/settings.json` — `CLAUDE.md` §10 กำหนดว่าแก้ hooks/config ต้องถามก่อน มาตรการ P3 จึงเป็นข้อเสนอ

**ยืนยันแล้วด้วย:** `node tools/postmortem-guard/check.js` และ `bash scripts/run-test-suites.sh` ผ่านก่อน commit (ผลอยู่ใน commit ของรายงานนี้) · รายงานนี้ไม่มีค่าลับ host id หรือชื่อบัญชี (ข้อความอ้างถึงไฟล์ผลของ agent อ่านผ่านตัวกรองที่ปิดสตริงยาวและอีเมล)

- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** hook จาก P3 จะปฏิเสธคำสั่งก่อนรัน แทนที่จะรู้หลังค่าเข้า context ไปแล้ว

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- agent บันทึกความผิดพลาดของตัวเองทันทีทั้งใน log และไฟล์ผล ไม่ซ่อน
- agent ไม่คัดลอกค่าที่เห็นไปใส่ไฟล์ผลหรือโค้ด ค่าจึงไม่ลงดิสก์ในไฟล์งานและไม่เข้า git

### สิ่งที่ต้องปรับปรุง
- เธรดหลักส่ง agent ไปหาค่าจากไฟล์ secrets โดยไม่บอกวิธีอ่านที่ปลอดภัย
- ตัวกรองที่มีหน้าที่ซ่อนข้อมูลต้องลองกับตัวอย่างปลอมก่อน และต้องเป็นแบบ fail-closed
