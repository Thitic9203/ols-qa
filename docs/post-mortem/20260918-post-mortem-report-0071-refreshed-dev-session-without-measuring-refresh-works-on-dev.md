**ระดับความรุนแรง:** Medium — ข้อมูลไม่เสียหาย แต่ทำ session ที่ใช้งานได้ตายไป 1 บัญชี และเจ้าของงานต้องล็อกอินให้ใหม่ ช่วงที่รอบงานมีเป้าหมายต้องเสร็จก่อนเที่ยง

## สรุปสั้น (Executive Summary)

เซสชันนี้มี 2 เหตุ เหตุแรก ตอนเปิดหน้าต่างให้เจ้าของงานล็อกอินบัญชี dev ใหม่ ผมเปิดหน้า sign-in ของพอร์ทัลตรงๆ
ไม่ได้ใส่ `SIGNIN_URL` ชี้หน้าแอป OLS เจ้าของงานต้องทักว่า "เปิดที่ OLS เท่านั้น" ซึ่งเป็นเรื่องเดียวกับรายงาน #0065
เหตุที่สอง เจ้าของงานอนุมัติให้ต่ออายุ session dev 9 บัญชีที่คุกกี้จะหมดราว 10.20 น. ผมทดสอบกับ 1 บัญชีที่ยังใช้ได้
โดยไม่เคยวัดว่าการต่ออายุใช้ได้บน dev ผลคือเซิร์ฟเวอร์ไม่คืนคุกกี้ และ session นั้นตายทันที
หยุดไม่แตะอีก 8 บัญชี จดหนี้ไว้ในเทิร์นนั้น แล้วเจ้าของงานล็อกอินบัญชีที่เสียให้ใหม่ ตอนนี้ใช้ได้ครบ

## 1. ปัญหา (Problem Statement)

- **เหตุที่ 1:** รอบแรกเรียก `session_capture.js` ด้วย `PORTAL` กับ `OLS` เท่านั้น ไม่มี `SIGNIN_URL`
  เครื่องมือจึงเปิดหน้าปริยายคือ `PORTAL + '/sign-in/embed'` (`capture/session_capture.js:92`) ·
  log รอบนั้นแสดงว่าหน้าต่างค้างอยู่ที่ `…/sign-in/embed` ของพอร์ทัล
- **เหตุที่ 2:** บัญชีที่ทดสอบผ่าน `session_verify.js` เป็น `ok` ในการตรวจรอบ 07:52 ·
  หลังสั่ง `session_refresh.js <บัญชีนั้น>` เวลา 07:53 เครื่องมือตอบ `session rejected by server — needs human login` ·
  ตรวจซ้ำด้วย `session_verify.js` ได้ `NO SESSION (dead or rejected)` · ไฟล์ state ไม่ถูกเขียนทับ (`cmp` ยืนยันว่าไม่เปลี่ยน)
- เครื่องมือผ่านด่าน `recognisedHere()` แล้วยิง `POST {AUTH_API}/auth/refresh-token` จริง (`capture/session_refresh.js:235-247`)
  โดย `AUTH_API` มาจากคีย์ `AUTH_API_HOST` ที่ dev ใช้ร่วมกับ pre-prod (`capture/env_hosts.js:48-49`)

**สิ่งที่ควรจะเป็น:**
- หน้าต่างล็อกอินต้องเปิดที่หน้าแอป OLS ของ env นั้น ตามหัวไฟล์ `capture/session_capture.js:87-92` และรายงาน #0065
- endpoint ที่เปลี่ยนสถานะถาวรต้องวัดก่อนว่าใช้ได้กับ env นั้น ก่อนยิงกับ session ที่ใช้งานได้ ตามรายงาน #0038

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

ทั้ง 2 เหตุมีจุดตัดสินใจเดียวกัน คือใช้เครื่องมือ session กับ dev โดยเชื่อค่าปริยายหรือข้อเท็จจริงที่วัดมาจาก env อื่น
แทนที่จะวัดบน env ที่กำลังทำงานอยู่ · ข้อเท็จจริง "ต่ออายุได้จริง" ใน `CLAUDE.md` วัดมาจาก production
เมื่อ 2026-09-04 ไม่เคยวัดบน dev แต่ถูกอ่านเป็นข้อเท็จจริงของทุก env

### 5 Whys

1. **ทำไม session ตาย?** — เพราะยิง refresh แล้วเซิร์ฟเวอร์ไม่คืนคุกกี้ใหม่
2. **ทำไมยิงทั้งที่ไม่รู้ว่าได้ผลบน dev?** — เพราะอ่าน "ต่ออายุได้จริง" ใน `CLAUDE.md` เป็นข้อเท็จจริงของทุก env
3. **ทำไมถึงอ่านแบบนั้น?** — เพราะประโยคในกฎไม่ได้ระบุว่าวัดบน env ไหน · ต้องไปเปิดดูบรรทัดยืนยันถึงจะเห็นว่าเป็น production
4. **ทำไมไม่มีอะไรกันไว้?** — เพราะ `session_refresh.js` มีด่านเดียวคือ `recognisedHere()` ซึ่งตอบว่า session นี้เป็นของ env นี้ไหม
   ไม่ได้ตอบว่า endpoint refresh ของ env นี้ใช้ได้ไหม
5. **ทำไมสองคำถามนี้ถึงถูกรวมเป็นข้อเดียว?** — เพราะ "เป็นของ env นี้" ถูกเข้าใจว่าเท่ากับ "ต่ออายุได้ที่ env นี้"
  **root cause:** ความสามารถของเครื่องมือที่เปลี่ยนสถานะถาวร ไม่มีการบันทึกว่าวัดแล้วบน env ไหน เครื่องมือจึงยอมยิงบน env
  ที่ไม่เคยพิสูจน์

เหตุที่ 1 ใช้รูปเดียวกัน: `session_capture.js` มีค่าปริยายเปิดหน้าพอร์ทัล และไม่ปฏิเสธเมื่อไม่ได้ใส่ `SIGNIN_URL`

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- กฎ #0038 บังคับให้เตรียมที่เก็บผลก่อนยิง ซึ่งเครื่องมือทำครบ แต่กฎไม่ได้ถามว่า env นั้นเคยวัดแล้วหรือยัง
- `recognisedHere()` จากรายงาน #0046 ผ่านถูกต้อง เพราะ session เป็นของ dev จริง
- กฎ #0065 เป็นร้อยแก้วกับ memory ไม่ได้บังคับในตัวเครื่องมือ รอบนี้ memory ไม่ถูกเปิดก่อนเรียกเครื่องมือ

## 5. แนวทางการแก้ไข (Fix)

- หยุดการต่ออายุทั้งหมดทันทีหลังพบ ไม่แตะอีก 8 บัญชี
- เปิดหน้าต่างล็อกอินที่หน้าแอป OLS ด้วย `SIGNIN_URL` แล้วเจ้าของงานล็อกอินบัญชีที่เสียใหม่
- วัดแบบอ่านอย่างเดียวแล้ว: หน้าเว็บ dev ไม่เรียก refresh จากฝั่งเบราว์เซอร์เลย · โค้ด OLS เรียก refresh ใน sign-out เท่านั้น
  (`apps/api/src/modules/auth/application/use-cases/sign-out.use-case.ts:49`) · โฮสต์ auth ของ dev เป็นค่า deploy ไม่อยู่ในโค้ด
  → **ยังตรวจไม่ได้ว่า dev ต่ออายุได้หรือไม่ และที่อยู่ที่ถูกต้องคืออะไร** จึงเลือกทางล็อกอินใหม่ด้วยมือแทน
- บันทึกกฎหน้าล็อกอินไว้บรรทัดแรกของหมวดกฎแกนใน memory (`feedback_login-window-open-at-ols-app`)

**ยืนยันแล้วด้วย:** `session_verify.js` ของบัญชีที่เสีย กลับมาเป็น `ok` หลังล็อกอินใหม่ · log การเก็บ session จบด้วย `all captured.`

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ทดสอบทีละบัญชี ความเสียหายจึงจำกัดที่ 1 บัญชีจาก 9
- ถามเลนอัดของอีกเซสชันก่อนว่าใช้บัญชีไหนอยู่ จึงไม่ทำให้เลนที่กำลังอัดหลุด
- หยุดทันทีเมื่อผลไม่ตรงคาด และจดหนี้ในเทิร์นนั้น

### สิ่งที่ต้องปรับปรุง
- บัญชีแรกที่ใช้ทดสอบควรเป็นบัญชีที่เสียได้ แต่การทดสอบนี้ไม่ควรเกิดตั้งแต่แรก เพราะไม่มีหลักฐานว่า dev ต่ออายุได้
- ต้องเปิด memory เรื่องหน้าล็อกอินก่อนเรียกเครื่องมือเก็บ session ทุกครั้ง
