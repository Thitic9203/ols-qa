## สรุปสั้น (Executive Summary)

ระหว่างเตรียมข้อมูลทดสอบของ Content_TC_007 ผมเปิดตัวเก็บ session บน dev ให้เจ้าของงานล็อกอิน 6 บัญชี
เจ้าของงานขอเปลี่ยนบัญชี ผมจึงสั่ง `kill` โปรเซสนั้น คำสั่งถัดมานับโปรเซสได้ 1 แต่ผมไม่ได้ตรวจซ้ำ และรายงานว่า "ชุดเดิมผมหยุดแล้ว"
โปรเซสเดิมยังทำงานต่อและเปิดหน้าต่างล็อกอิน dev ของบัญชีถัดไปเรื่อยๆ ขณะที่ผมเปิดตัวเก็บชุดใหม่ซ้อนอีก 4 รอบ
เจ้าของงานเห็นหน้าต่างหลายชุดสลับกัน ล็อกอินได้บ้างไม่ได้บ้าง จนสรุปว่า "งงไม่ได้อีกละ" และคิดว่า URL ผิด
เหตุเดียวกันเกิดอีกครั้งกับโปรเซสรอบ pre-prod (pid ของรอบบัญชี A) ที่ค้างอยู่ระหว่างเปิดรอบถัดไป

## 1. ปัญหา (Problem Statement)

**สิ่งที่เกิดขึ้น:** รายงานว่าหยุดโปรเซสแล้วโดยไม่มีหลักฐาน และเปิดโปรเซสใหม่ซ้อนกับของเดิมที่ยังมีชีวิต
**สิ่งที่ควรจะเป็น:** หลังสั่งหยุด ต้องยืนยันด้วย `kill -0 <pid>` ของ pid ที่รู้ที่มาว่าหายจริง (CLAUDE.md §0 สถานะโปรเซส) ก่อนรายงานหรือเปิดโปรเซสใหม่

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. ทำไมหน้าต่างล็อกอิน dev เด้งซ้ำ — โปรเซสรอบแรกยังไม่ตาย และเดินไปบัญชีถัดไปเมื่อหมดเวลาของบัญชีก่อน
2. ทำไมผมไม่รู้ว่ามันไม่ตาย — ผมอ่านเลข 1 จาก `pgrep -f` ว่าเป็น "เงาของคำสั่งตัวเอง" โดยไม่ได้พิสูจน์
3. ทำไมไม่พิสูจน์ — ไม่มีขั้นบังคับให้ยืนยันด้วย pid ก่อนรายงาน การตรวจขึ้นกับการตัดสินใจเฉพาะหน้า
4. ทำไมโปรเซสซ้อนกันได้ — `session_capture.js` ไม่มีการกันไม่ให้รันซ้อน (ไม่มี lock) จึงเปิดหน้าต่างพร้อมกันหลายชุดได้
5. ทำไมเรื่องนี้หลุดทั้งที่มี #0030 — มาตรการของ #0030 เป็นกฎการอ่านผลคำสั่ง ไม่ใช่ชั้นเครื่องที่ตัวเครื่องมือปฏิเสธเอง

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** CLAUDE.md §0 ห้ามอ่านสถานะโปรเซสจากผลว่างของ grep แต่เหตุนี้ผลไม่ว่าง (นับได้ 1) แล้วถูกตีความทิ้ง ไม่มี hook หรือเครื่องมือใดตรวจ

## 4. ผลกระทบ (Impact)

- เจ้าของงานล็อกอินหลายรอบโดยไม่รู้ว่าหน้าต่างไหนเป็นของรอบใด บางรอบล็อกอินสำเร็จในหน้าต่างของโปรเซสที่ผมคิดว่าหยุดแล้ว
- เจ้าของงานคิดว่า URL ผิด และย้ายจาก dev ไป pre-prod
- ไม่มีข้อมูลบนระบบใดถูกเขียน · session ที่บันทึกได้มีเพียง บัญชีแอดมินโรงเรียน 1 บัญชี บน dev

## 5. แนวทางการแก้ไข (Fix)

- หยุดโปรเซสค้างทั้ง 2 ตัวด้วย pid ที่รู้ที่มา แล้วยืนยันด้วย `kill -0` ว่าหายทั้งตัวแม่และหน้าต่าง Chrome ลูก
- เปิดหน้าต่างล็อกอินใหม่เพียงชุดเดียว เจ้าของงานล็อกอินครบ 6 บัญชีบน pre-prod

**ยืนยันแล้วด้วย:** `kill -0 68585` → gone · `kill -0 68629` → gone · `pgrep -fl "node session_capture"` เหลือ 1 ตัวคือรอบที่ใช้งาน · ตรวจ session ทั้ง 6 บน pre-prod ด้วย `GET /api/auth/get-session` ได้ ALIVE 6 จาก 6

## 7. การตรวจจับปัญหา (Detection)

- เจ้าของงานเป็นผู้จับได้จากอาการ (หน้าต่างผิด env) ไม่ใช่เครื่องมือ
- ผมยืนยันเหตุจาก `ps -o ppid` ของหน้าต่าง Chrome ที่ค้าง ซึ่งชี้กลับไปที่โปรเซสรอบแรก

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี

### สิ่งที่ต้องปรับปรุง
