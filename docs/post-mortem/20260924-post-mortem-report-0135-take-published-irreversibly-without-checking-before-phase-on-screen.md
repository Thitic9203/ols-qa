## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

ด่านก่อนการเขียนที่มีอยู่ตอบคำถามว่า "กำลังจะเขียนสิ่งที่ถูกต้องหรือไม่" (ชื่อ · สถานะ · RGS · ledger) แต่ไม่มีด่านไหนตอบว่า "หลักฐานที่การเขียนนี้จะถูกใช้ ใช้ได้จริงหรือไม่ ณ ตอนนี้" การตรวจคลิปทั้งหมดเกิดตอนหยุดอัด ซึ่งอยู่หลังการเขียนเสมอในการออกแบบแบบคลิปต่อเนื่อง

### 5 Whys

1. **ทำไมเผยแพร่ (ย้อนไม่ได้) ไปทั้งที่หลักฐานช่วง "ก่อน" ใช้ไม่ได้?** — เพราะสคริปต์เดินจากบรรทัดบันทึก `before_lp_section` เข้าสู่การเผยแพร่ทันที (`f001_take.js:134–139`) ไม่มีอะไรคั่นที่ตรวจจอที่กำลังอัด
2. **ทำไมสคริปต์ถือว่าช่วง "ก่อน" อัดเสร็จแล้ว?** — เพราะ `before_lp_section` บันทึกแค่ช่วงเวลาและชื่อจาก API และค่า `scrollY` ที่ `glideTo()` คืนมาถูกทิ้งทุกจุด หน้าที่เลื่อนไม่ได้จึงดูเหมือนเสร็จเหมือนหน้าปกติ
3. **ทำไมไม่มีการตรวจหน้าต่างทับหน้า?** — เพราะทั้งสคริปต์และ lib ไม่มีการตรวจ modal/dialog เลย (grep = 0) และ preflight ตรวจแค่ session กับ `REC.lock` · การออกแบบไม่ได้คิดว่าหน้าจอของบัญชีจะถูกเปลี่ยนจากภายนอกระหว่างอัด (ต้นเหตุฝั่ง dispatch อยู่ใน #0134)
4. **ทำไมด่านก่อนเขียนถึงดูแค่เป้าหมายของการเขียน?** — เพราะกฎการเขียนที่ย้อนไม่ได้ที่มีอยู่ (ledger intent · ยืนยันชื่อเป้าบนจอ CLAUDE.md §10 · ห้าม RGS) ล้วนเป็นเรื่องเขียนให้ถูกสิ่ง ส่วนการตรวจหลักฐาน (`verify_video` · ดูเฟรม) รันตอน `rec.stop()` ซึ่งอยู่หลังการเขียน
5. **ทำไมไม่มีด่านหลักฐานก่อนการเขียน?** — เพราะหลัก "วัดร่วมเวลาก่อนกระทำการย้อนไม่ได้" (CLAUDE.md §0 จาก #0105) เป็นข้อความ และด่านในโค้ดที่ตามมาจาก #0120 คือ load gate ที่รับเกณฑ์ตัวเลขใดก็ได้ (รอบนี้ 999) — root cause: ไม่มีด่านในโค้ดที่ผูกการเขียนที่ย้อนไม่ได้กับการพิสูจน์บนจอที่กำลังอัด ณ วินาทีก่อนเขียน ทุก take ที่เขียนย้อนไม่ได้กลางคลิปจึงใช้สิทธิ์ไปกับคลิปที่เสียได้

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- `pre_write_check` (`f001_take.js:141–149`): ทำงานถูกต้อง แต่ตรวจหน้าของเจ้าของเส้นทาง ไม่ใช่หน้าที่อัด
- load gate (`t69_lib.js:130–131`): บังคับให้มีค่า LOADMAX แต่รับค่าใดก็ได้ · take นี้ใช้ 999 ผ่านที่ load 42.30 ขณะที่มติ 17.4x ให้เคสย้อนไม่ได้ใช้ 8 · ยังไม่ได้ตรวจว่าค่า 999 มาจากบรีฟของเธรดหลักหรือเลนตั้งเอง (บรีฟต้นฉบับไม่อยู่ในไฟล์ที่ตรวจ)
- `verify_video` ใน `qa_recorder`: รันหลังหยุดอัด ซึ่งอยู่หลังการเผยแพร่
- `REC.lock`: กันการอัดซ้อน ไม่ได้ดูเนื้อหาบนจอ

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ด่าน `pre_write_check` ตรวจเป้าหมายการเขียนครบ (ชื่อบนจอ · สถานะ · RGS) การเผยแพร่จึงตรงสิ่งที่อนุมัติ

### สิ่งที่ต้องปรับปรุง
- ขั้นที่บันทึกว่า "อัดเสร็จ" ต้องวัดจากจอที่อัด ไม่ใช่จากเวลาและข้อมูล API
