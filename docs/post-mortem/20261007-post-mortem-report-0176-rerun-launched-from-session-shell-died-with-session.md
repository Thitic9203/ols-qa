## สรุปสั้น (Executive Summary)

เธรดหลักสั่งรอให้ OLS-778 จบแล้วรัน `run.sh OLS-829` ผ่านคำสั่ง background ของเครื่องมือ Bash ในเซสชัน (มี `nohup` และ `&`) — รอบเริ่มจริงตอน 14:39:52 แต่เมื่อเซสชันจบ process ทั้งกลุ่มถูกปิดไปด้วย bot.log ไม่มีบรรทัด END ไม่มี process ไม่มี `.run.lock` และ results.log ไม่มีผล
แก้โดยรันคิวใหม่ผ่านสคริปต์ที่แยก session ด้วย `os.setsid()` + `start_new_session` และเพิ่มขั้นเช็คสถานะจริง (pgrep + seq.log + bot.log) ก่อนรายงานทุกครั้ง
สถานะ: รอบที่สั่งใหม่ (15:15) รันจบจริงและมีบรรทัดผล

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไมรอบ OLS-829 หาย?** — เพราะ process ถูกปิดเมื่อเซสชันของ Claude จบ
2. **ทำไมถูกปิดทั้งที่ใช้ `nohup` และ `&`?** — เพราะยังอยู่ใน process group/session เดียวกับเครื่องมือ Bash ของเซสชัน การปิดเซสชันจึงปิดทั้งกลุ่ม `nohup` กันได้แค่ SIGHUP
3. **ทำไมใช้วิธีนี้?** — เพราะเธรดหลักเลือก Bash background เพื่อ "รอแล้วรัน" โดยไม่ได้ตรวจว่างานต้องอยู่รอดหลังเซสชันจบ ทั้งที่ listener เองใช้ `spawn({detached: true})` อยู่แล้ว
4. **ทำไมไม่มีใครรู้ทันที?** — เพราะ run.sh ไม่มีโอกาสเขียน END และเธรดหลักรายงานจากการสั่ง ไม่ใช่จากการเห็นผล
5. **ทำไมรายงานจากการสั่ง?** — เพราะไม่มีขั้นบังคับว่าก่อนพูดว่า "ตั้งไว้แล้ว/รันอยู่" ต้องแนบหลักฐานว่า process อยู่นอกเซสชัน — root cause

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** guard ของ repo ดูการ kill (process-kill-guard) แต่ไม่มีชั้นที่ดูการ "ปล่อยงานยาว" ว่าแยก session หรือไม่
