## สรุปสั้น (Executive Summary)

เจ้าของงานสั่งไว้ตั้งแต่ 22.02 ว่า "ไม่ blocked หาทางเทสมาให้ได้" และย้ำอีก 2 ครั้ง แต่เลน OLS-807 และ OLS-810 ถูกสร้างด้วย brief ที่มีกฎ "หยุดก่อนคลิกที่เขียนข้อมูล → NEEDS_APPROVAL" คำสั่งใหม่จึงไปถึงเลนเป็นข้อความส่งต่อจาก agent กลางงาน ซึ่งเลนปฏิเสธเพราะไม่ใช่คำพูดของเจ้าของงานในแชทของมันเอง
เธรดหลักเห็นการปฏิเสธแล้วเลือกส่งต่อซ้ำ แทนการยุติเลนแล้ว dispatch agent ใหม่ที่มีคำอนุมัติอยู่ใน prompt ตั้งแต่ต้น พอส่งต่อไม่สำเร็จจึงหันไปถามเจ้าของงานให้พิมพ์ "คัดลอกได้" ทั้งที่มติอยู่ใน `ROUND_DECISIONS.md` แล้ว
ยิ่งไปกว่านั้น ปุ่ม "คัดลอก" ของ OLS-807 ไม่ได้เขียนข้อมูลเลย (โค้ดแค่ดึงรายละเอียดเหรียญแล้วเปิดฟอร์มสร้างที่กรอกค่าไว้ ไม่มีอะไรบันทึกจนกด "เผยแพร่") แต่ไม่มีใครเปิดโค้ดก่อนจัดประเภทว่าเป็นขั้นตอนเขียนข้อมูล
หลังเจ้าของงานยืนยันตรงแล้ว ก็ยังส่งต่อแบบเดิมอีกรอบ และเลน 807 ปฏิเสธอีกครั้ง
ฉบับนี้เสนอชั้นใหม่ 3 ชั้น (ข้อเสนอเท่านั้น ยังไม่ลงมือทำ): brief ต้องมีบล็อกอำนาจเขียนจาก `ROUND_DECISIONS.md` ตั้งแต่ต้น · agent-dispatch-guard ปฏิเสธ brief ที่มีขั้นเขียนแต่ไม่มีบล็อกอำนาจ · ห้ามถามเรื่องที่มีมติแล้ว และต้องจัดประเภท "เขียน" จากโค้ดหรือ network ก่อน

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

มีจุดตัดสินใจผิด 3 จุดซ้อนกัน:
(ก) **ออกแบบ brief ผิดตั้งแต่ต้น** — brief ของเลนใส่กฎ "หยุดก่อนเขียน → NEEDS_APPROVAL" เป็นค่าเริ่มต้น ทั้งที่รอบนี้เจ้าของงานเคยอนุญาตเขียนแบบคืนค่าได้ในรอบก่อนๆ พอเจ้าของงานเปลี่ยนนโยบายกลางรอบ อำนาจจึงต้องเดินทางเป็น relay กลางงาน ซึ่งเป็นช่องทางที่ subagent ถูกออกแบบให้ไม่เชื่อ (ข้อความจาก agent ไม่ใช่ความยินยอมของ user)
(ข) **เลือกช่องทางแก้ผิด** — เมื่อเห็นการปฏิเสธครั้งแรก (23.06) เธรดหลักวินิจฉัยถูกว่าเลนไม่เชื่อ relay แต่กลับเลือก "relay ให้ละเอียดขึ้น" ซึ่งเป็นช่องทางเดิมที่เพิ่งล้ม แทนที่จะยุติเลนแล้ว dispatch agent ใหม่ที่มีบล็อกอำนาจใน prompt แรก (prompt แรกของ agent มาจากเธรดหลักที่ถืออำนาจของ user ในเซสชันนั้น) พอ relay ล้มอีก ทางที่เหลือในสายตาเธรดหลักคือ "ให้เจ้าของงานพิมพ์ยืนยัน" จึงถาม
(ค) **จัดประเภท "เขียน" โดยไม่วัด** — ทั้งเลนและเธรดหลักถือว่าปุ่ม "คัดลอก" เป็นการเขียน (brief 22.03 สั่ง "run คัดลอก for real — record the copy it creates and disable/delete that copy") โดยไม่มีใครเปิด `client.tsx` ซึ่งแสดงว่าคลิกนี้แค่ GET แล้วเปิดฟอร์ม ถ้าวัดก่อน เลนจะรันคลิกนี้ได้ภายใต้กฎเดิมโดยไม่ต้องขออนุมัติเลย

### 5 Whys

1. **ทำไมเธรดหลักถามเจ้าของงานให้พิมพ์ "คัดลอกได้" ทั้งที่มีมติ "ไม่ blocked" แล้ว?** — เพราะเลน 807 ปฏิเสธคำอนุมัติที่ส่งต่อไป 1 ครั้ง (23.06) และเธรดหลักมองว่าทางเดียวที่เหลือคือได้คำพูดสดจากเจ้าของงาน
2. **ทำไมเลนปฏิเสธคำอนุมัติ?** — เพราะอำนาจไปถึงเลนเป็นข้อความ SendMessage กลางงาน ซึ่งขัดกับ brief เดิมที่เลนได้รับตอนเริ่ม (บรรทัด 34 "stop before that click") และกฎความปลอดภัยของ subagent ถือว่าข้อความจาก agent อื่นไม่ใช่ความยินยอมของ user
3. **ทำไมอำนาจต้องไปเป็น relay กลางงาน แทนที่จะอยู่ใน prompt แรก?** — เพราะ brief ถูกเขียนด้วยค่าเริ่มต้น "ไม่เขียน/ขออนุมัติ" และเมื่อนโยบายเปลี่ยน เธรดหลักเลือก "แก้ไฟล์ brief + ส่งข้อความให้อ่านใหม่" แทนการ dispatch agent ใหม่ · หลังถูกปฏิเสธครั้งแรกก็ยังเลือก relay ซ้ำ (23.07 และ 23.49) ไม่มีจุดไหนที่บังคับให้เปลี่ยนช่องทาง
4. **ทำไมไม่มีใครสังเกตว่า "คัดลอก" ไม่ต้องขออนุมัติตั้งแต่แรก?** — เพราะการจัดประเภทขั้นตอนว่า "เขียนข้อมูล" มาจากชื่อปุ่มและข้อความในเคส ไม่ได้มาจากโค้ดหรือ network · brief ไม่มีขั้น "ยืนยันว่าเขียนจริง" ก่อนขึ้น NEEDS_APPROVAL
5. **ทำไมสิ่งทั้งหมดนี้หลุดได้ แม้เพิ่งเขียน #0161 ในวันเดียวกัน?** — root cause: **ไม่มีชั้นใดบังคับว่าอำนาจเขียนของรอบต้องอยู่ใน prompt ตอน dispatch และไม่มีชั้นใดตรวจคำถามถึงเจ้าของงานเทียบกับ `ROUND_DECISIONS.md`** · มาตรการของ #0161 (ask-guard `verdict-question` + Stop hook) ยังเป็นข้อเสนอ และถึงทำแล้วก็ครอบเฉพาะคำถามที่มีคำ verdict — คำถาม "พิมพ์ 'คัดลอกได้'" ไม่มีคำ verdict จึงหลุดอยู่ดี · agent-dispatch-guard ตรวจแค่สัญญาการเขียนผลลงดิสก์ (`hasPersistenceContract`) ไม่ตรวจอำนาจเขียน

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

มาตรการของ #0150 เป็นชั้น memory และของ #0161 เป็น ask-guard ที่ครอบเฉพาะคำถาม verdict (ยังเป็นข้อเสนอ) — ทั้งสองไม่ครอบคลาสนี้ ฉบับนี้จึงเสนอชั้นที่ต่างออกไป: บังคับที่ **ตอน dispatch** (ต้นทางของอำนาจ) และที่ **ตอนจัดประเภทขั้นเขียน** ไม่ใช่แค่ตอนถาม ทุกข้อเป็น **ข้อเสนอ ยังไม่ลงมือทำ**

| # | มาตรการ | ชนิด | สถานะ |
|---|---------|------|-------|
| P1 | **agent-dispatch-guard กฎใหม่ `write-authority-block`:** ถ้า brief/prompt ของ Agent มีขั้นเขียนข้อมูล (คำเช่น `save` `create` `suspend` `delete` `toggle` `คัดลอก` `บันทึก` `ระงับ` `ลบ` `write_ledger` `NEEDS_APPROVAL`) ต้องมีบล็อก `## WRITE AUTHORITY` ที่มี (1) คำพูดเจ้าของงานคำต่อคำ (2) เวลา (3) บรรทัดที่ตรงกันใน `ROUND_DECISIONS.md` ของรอบ (guard เปิดไฟล์แล้วหาข้อความนั้นจริง) (4) รายการเป้าหมาย + วิธีคืนค่า — ไม่ครบ = deny · ข้อความที่ไม่พบใน `ROUND_DECISIONS.md` = deny (จะจับเคส `LANE_BRIEF.md:58` ที่อ้างบรรทัดที่ไม่มีอยู่ได้ด้วย) | เครื่องมือ (PreToolUse บน Agent) + test คู่ใน `dispatch_rules.test.js` | ข้อเสนอ — รออนุมัติ |
| P2 | **agent-dispatch-guard ปฏิเสธ SendMessage ที่พาอำนาจเขียน:** ถ้า SendMessage ถึง agent เดิมมีคำ `approve/confirmed/อนุมัติ/ยืนยัน` + ขั้นเขียน → deny พร้อมข้อความ "อำนาจเขียนต้องอยู่ใน prompt แรก — ยุติเลนนี้แล้ว dispatch ใหม่พร้อมบล็อก WRITE AUTHORITY" (ปิดทาง relay ที่ล้ม 2 รอบในเหตุนี้) | เครื่องมือ (PreToolUse บน SendMessage) | ข้อเสนอ — รออนุมัติ |

**กฎที่เพิ่มจากเหตุนี้:** ยังไม่มีกฎใหม่ใน `CLAUDE.md` — ข้อความกฎที่ต้องใช้มีอยู่แล้ว (§0 ห้ามเดา · §3 ถามเจ้าของงาน · §12 resume subagent ต้องมีข้อความสด) สิ่งที่ขาดคือด่านบังคับ P1–P4 ซึ่งต้องได้รับอนุมัติก่อนทำ (แก้ `tools/**` + hooks ตาม `CLAUDE.md` §10)

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** เจ้าของงานเห็นคำถาม "พิมพ์ 'คัดลอกได้'" แล้วทักเอง · เรื่องปุ่มคัดลอกไม่เขียนข้อมูล ผู้ประสานงานตรวจโค้ดภายหลัง
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** จากการปฏิเสธครั้งแรก 23.06.24 ถึงเจ้าของงานทัก 23.45.48 = 39 นาที 24 วินาที · จากคำสั่ง "ไม่ blocked" 22.02.50 ถึงเจ้าของงานทัก = 1 ชั่วโมง 42 นาที 58 วินาที
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** P1 บล็อกตั้งแต่ dispatch (ก่อนเลนเริ่ม) · P2 บล็อก relay ครั้งแรก (22.03) · P3 บล็อกคำถามก่อนถึงเจ้าของงาน — ทั้งหมดรันเองโดยไม่ต้องมีคนคอยดู

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- เลนไม่เขียนข้อมูลบน Dev โดยไม่มีอำนาจที่เชื่อถือได้ — ไม่มีข้อมูลเสีย
- เธรดหลักรับผิดทันที (23.46) และเปิดแถว PENDING ในเทิร์นเดียวกัน
- มติ 23.4x ถูกบันทึกลง `ROUND_DECISIONS.md` ทันที

### สิ่งที่ต้องปรับปรุง
- เมื่อช่องทางหนึ่งล้ม (relay) ห้ามลองช่องทางเดิมซ้ำ ให้เปลี่ยนเป็น dispatch ใหม่ทันที
- brief ของรอบต้องสะท้อนมติ ณ เวลาที่ dispatch และอำนาจที่คาดว่าจะต้องใช้ ไม่ใช่ใส่ค่า "หยุดขออนุมัติ" ไว้ก่อนแล้วค่อยแก้กลางทาง
- ก่อนเรียกขั้นใดว่า "เขียน" ต้องเปิดโค้ดหรือ network ก่อน — ปุ่มชื่อ "คัดลอก" ไม่ใช่หลักฐานว่ามีการบันทึก
- ข้ออ้างใน brief ว่า "บันทึกใน ROUND_DECISIONS แล้ว" ต้องตรวจกับไฟล์จริงก่อนส่ง
