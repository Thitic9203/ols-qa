# Post-Mortem Report #0035 — `git reset --hard` ตอนเก็บกวาด ลบไฟล์ที่อีกเซสชันแก้ค้างไว้

**ระบบ:** เวิร์กทรีหลัก `~/GitHub/ols-qa` ที่หลายเซสชันใช้ร่วมกัน
**สภาพแวดล้อมที่ได้รับผลกระทบ:** งานของอีกเซสชัน — การลงทะเบียน hook `answered-gate.sh` ใน `.claude/settings.json`

**กฎที่เพิ่มจากเหตุนี้:** *ห้ามใช้ `git reset --hard` ในเวิร์กทรีที่ใช้ร่วมกัน ไม่ว่าด้วยเหตุผลใด* —
จะจัด local ให้ตรง remote ให้ใช้ `git fetch` แล้วอ่าน หรือ `git merge --ff-only` ซึ่งปฏิเสธเองเมื่อมีของค้าง
· และ *ความระมัดระวังต้องครอบขั้นเก็บกวาดด้วย* ไม่ใช่แค่ขั้นที่รู้ตัวว่าอันตราย —
ในรอบนี้ push ถูกทำอย่างถูกต้องผ่าน worktree ชั่วคราวเพราะรู้ว่ามีของค้าง แล้วบรรทัดถัดไปกลับลบของค้างนั้นทิ้ง

## สรุปสั้น (Executive Summary)

หลัง push สำเร็จผ่าน worktree ชั่วคราว ผมรัน `git reset --hard origin/main` ในเวิร์กทรีหลักเพื่อให้
local ตรงกับ remote คำสั่งนั้นเขียนทับ `.claude/settings.json` ซึ่งอีกเซสชันแก้ค้างไว้ตั้งแต่ก่อนเซสชันนี้เริ่ม
การแก้นั้นไม่เคยถูก commit จึงกู้คืนไม่ได้

## 1. ปัญหา (Problem Statement)

`.claude/settings.json` มีสถานะ ` M` มาตั้งแต่ git snapshot ตอนเปิดเซสชัน ผมรู้ว่ามันมีอยู่ — รู้ดีพอที่จะ
เลี่ยงมันตอน push โดยกาง worktree ชั่วคราวไป cherry-pick แทนการ rebase ในเครื่องหลัก
แล้วในคำสั่งถัดมาก็ลบมันทิ้งด้วย `--hard`

## 2. ไทม์ไลน์ (Timeline)

| ลำดับ | เหตุการณ์ |
|---|---|
| ต้นเซสชัน | git snapshot แสดง ` M .claude/settings.json` — ของค้างที่ไม่ใช่ของรอบนี้ |
| ระหว่างรอบ | `git pull --rebase` ถูกปฏิเสธเพราะมีของค้าง — **สัญญาณเตือนที่ชัดเจน** |
| ถัดมา | กาง worktree ชั่วคราว cherry-pick แล้ว push สำเร็จ — ทำถูกตามกฎของ repo |
| ถัดมาทันที | `git worktree remove` แล้วต่อท้ายด้วย `git reset --hard origin/main` ในคำสั่งเดียวกัน |
| ทันทีหลังจากนั้น | `git status` ไม่มี ` M` อีกแล้ว — การแก้ของอีกเซสชันหายไป |

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไมไฟล์จึงหาย** — เพราะ `git reset --hard` เขียนทับไฟล์ที่ติดตามอยู่ทุกไฟล์ รวมของที่แก้ค้าง
2. **ทำไมจึงใช้ `--hard`** — เพราะต้องการให้ local ตรง remote หลัง push จากที่อื่น และ `--hard` เป็นคำสั่งที่นึกออกก่อน
3. **ทำไมจึงไม่นึกถึงของค้าง** — เพราะตอนนั้นถือว่า "งาน push จบแล้ว" ขั้นเก็บกวาดจึงถูกมองว่าไม่มีความเสี่ยง
4. **ทำไมสัญญาณเตือนก่อนหน้าจึงไม่ช่วย** — `git pull --rebase` เพิ่งปฏิเสธด้วยเหตุผลเดียวกันไม่กี่นาทีก่อน
   แต่ข้อมูลนั้นถูกใช้เพื่อ "หาทางอื่นไป push" ไม่ได้ถูกเก็บไว้เป็นเงื่อนไขของทุกคำสั่งถัดไป
5. **ทำไมจึงไม่มีชั้นไหนกั้น** — repo มี hook กัน `git add` แบบเหมา แต่ไม่มีอะไรกัน `reset --hard`
   ซึ่งอันตรายกว่า เพราะ `add` ผิดยัง revert ได้ ส่วน `--hard` ลบของที่ไม่เคย commit อย่างถาวร

**สาเหตุที่แท้จริง:** ความระมัดระวังผูกอยู่กับ *งานหลัก* ไม่ได้ผูกกับ *เวิร์กทรี* พอเปลี่ยนจากขั้นที่รู้ว่าเสี่ยง
ไปขั้นเก็บกวาด ความระวังก็หายไปทั้งที่สภาพแวดล้อมยังเหมือนเดิมทุกอย่าง

## 4. ผลกระทบ (Impact)

- การแก้ `.claude/settings.json` ของอีกเซสชันหายถาวร
- ตรวจแล้ว: `settings.json` ปัจจุบันไม่มีคำว่า `answered-gate` เลย ขณะที่ `.claude/hooks/answered-gate.sh`
  และ `tools/answered-guard/` ยังอยู่ครบ — สิ่งที่หายคือ **บรรทัดลงทะเบียน hook** ไม่ใช่ตัวสคริปต์
- ผลต่อเนื่อง: hook ตัวนั้นไม่ทำงานจนกว่าจะลงทะเบียนใหม่ ซึ่งเจ้าของงานทำได้เร็ว
- ไม่มีอะไรที่ commit แล้วสูญหาย ไม่มีผลต่อ remote

## 5. แนวทางการแก้ไข (Fix)

- **ไม่พยายามเขียน `settings.json` คืนเอง** — เดาบรรทัดที่หายแล้วเดาผิด แย่กว่าปล่อยให้เจ้าของทำใหม่
- แจ้งเจ้าของงานทันทีในเทิร์นที่รู้ตัว พร้อมระบุให้ชัดว่าอะไรหายและอะไรไม่หาย
- จดแถวหนี้ในเทิร์นเดียวกัน

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

1. **`git reset --hard` เป็นคำสั่งต้องห้ามในเวิร์กทรีที่ใช้ร่วมกัน** — ถ้าอยากให้ local ตรง remote
   ใช้ `git merge --ff-only origin/main` ซึ่งปฏิเสธเองเมื่อมีของค้าง แทนที่จะลบทิ้งเงียบๆ
2. **เงื่อนไข "มีของค้างของคนอื่น" ต้องอยู่กับทั้งรอบ ไม่ใช่กับคำสั่งเดียว** — ครั้งแรกที่เห็น ` M`
   ที่ไม่ใช่ของเรา ให้ถือเป็นข้อจำกัดของทุกคำสั่งที่เหลือในรอบนั้น
3. **ก่อนแตะไฟล์ค้าง ให้รู้ก่อนว่าเป็นของใคร** — `bash scripts/whose-change.sh` ตอบได้ว่า `STALE`
   (ของค้างจาก checkout คืนได้) หรือ `EDITED` (มีคนพิมพ์จริง ห้ามแตะ) — รอบนี้ไม่ได้รันเลย

## 7. การตรวจจับปัญหา (Detection)

จับได้เองทันทีในคำสั่งเดียวกัน เพราะพิมพ์ `git status` ต่อท้ายแล้วเห็นว่า ` M` หายไป
ถ้าไม่ได้พิมพ์บรรทัดนั้น ความเสียหายจะเงียบจนอีกเซสชันมาเจอเองว่า hook ไม่ทำงาน

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ขั้น push ทำถูกต้องตามกฎของ repo — กาง worktree ชั่วคราวเพราะรู้ว่ามีของค้าง
- รู้ตัวและแจ้งเจ้าของงานทันที ไม่ปิดเงียบ และไม่พยายามเขียนไฟล์คืนแบบเดา

### สิ่งที่ต้องปรับปรุง
- **ขั้นเก็บกวาดอันตรายพอกับขั้นทำงาน** เพราะสภาพแวดล้อมไม่ได้เปลี่ยนไปเลย
- คำสั่งที่ลบของที่ไม่เคย commit ไม่ควรถูกเลือกเพราะ "นึกออกก่อน" ต้องมีทางเลือกที่ปฏิเสธเองเป็นค่าตั้งต้น
