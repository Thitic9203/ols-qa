## สรุปสั้น (Executive Summary)

การ์ดเรียก `python3` สองครั้ง — ครั้งแรกเพื่อดึงคำสั่งออกจาก payload ครั้งที่สองเพื่อปรับข้อความ (NFKC + ตัดอักขระล่องหน)
ก่อนค้นหาคำว่า `RGS` ผลของครั้งที่สองถูกตรวจแค่ว่า "ว่างหรือไม่" แล้ว **ค่าว่างถูกแปลว่าไม่พบ marker จึงอนุญาต**

วัดจริงเมื่อ 2026-09-06 ด้วยคำสั่งเขียนที่ระบุ marker และเล็งไปที่ปลายทาง OLS: การ์ด **ปล่อยผ่าน (รหัสจบ 0) ทั้ง 3 รูปแบบ
ความล้มเหลวของ `python3`** คือเรียกไม่ได้เลย · ตัวขวางพิมพ์ข้อความทาง stdout · ตัวขวางพิมพ์ทาง stderr
โดยเครื่องนี้ **เคยมีตัวขวาง `python3` แบบนั้นจริง** และเคยทำการ์ดอีกตัวพังมาแล้ว (บันทึกไว้ 2026-08-09)

แก้โดยตรวจ **รหัสจบ** ของ `python3` ทุกจุด · เมื่อตัวปรับข้อความล้มเหลวให้ใช้การค้นแบบ shell ล้วนที่ตั้งใจให้กว้างเกินไว้ก่อน ·
และถ้ายังหา marker ไม่เจอทั้งที่ตรวจไม่ได้ **ห้ามออกตรงนั้น** ให้เดินต่อไปถึงจุดตัดสิน ซึ่งจะปฏิเสธคำสั่งเขียนที่เล็งไปยัง
ปลายทาง OLS อยู่แล้ว หลังแก้ ทั้ง 3 รูปแบบบล็อกครบ และคำสั่งทำงานปกติไม่ถูกบล็อกเพิ่ม

## 1. ปัญหา (Problem Statement)

- คำสั่งเขียนที่ระบุ marker ของลูกค้าและเล็งไปที่ปลายทาง OLS **ผ่านการ์ดไปได้** เมื่อ `python3` ล้มเหลว
- เกิดกับความล้มเหลวทั้ง 3 แบบที่ทดสอบ ไม่ใช่แบบเดียว
- แบบที่อันตรายที่สุดคือตัวขวางที่ **พิมพ์ข้อความออก stdout** เพราะทางสำรองที่มีอยู่ (`[ -z "$CMD" ] && CMD="$INPUT"`)
  ทำงานเฉพาะตอนค่าว่าง พอได้ค่าที่ **ไม่ว่างแต่ผิด** ทางสำรองจึงไม่ทำงาน แล้วการ์ดไปค้นหา marker ในข้อความแจ้งข้อผิดพลาดแทน
- คอมเมนต์ในไฟล์เขียนไว้เองว่า *"over-matching here can only cause a false BLOCK, never a false ALLOW"*
  ซึ่งจริงเฉพาะกับตัวแปรตัวแรก และไม่มีใครเคยตรวจสอบข้อความนั้น

**สิ่งที่ควรจะเป็น:** การ์ดที่ตรวจไม่สำเร็จต้องปฏิเสธ ไม่ใช่อนุญาต — ทิศทางที่ผิดพลาดได้คือบล็อกเกิน
ซึ่งเสียแค่การยืนยันหนึ่งครั้ง ส่วนอีกทิศทางคือข้อมูลของลูกค้าที่เรากู้คืนให้เขาไม่ได้

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

การ์ดมีสถานะได้แค่ "พบ" กับ "ไม่พบ" ไม่มีสถานะ "ตรวจไม่ได้" เมื่อเครื่องมือที่ใช้ตรวจล้มเหลว ผลลัพธ์จึงตกลงไป
รวมกับ "ไม่พบ" โดยอัตโนมัติ ซึ่งเป็นฝั่งที่อนุญาต — โครงสร้างแบบนี้ทำให้ **ทุกความล้มเหลวกลายเป็นการอนุญาต**

### 5 Whys

1. **ทำไมคำสั่งเขียนของลูกค้าผ่านการ์ดไปได้?** — เพราะการ์ดสรุปว่าไม่พบ marker
2. **ทำไมถึงสรุปแบบนั้น?** — เพราะตัวแปร marker ว่าง และบรรทัดถัดมาคือ `[ -z "$MARKER" ] && exit 0`
3. **ทำไมตัวแปรถึงว่าง?** — เพราะ `python3` ที่ใช้ปรับข้อความล้มเหลว และผลของมันถูกอ่านแค่ค่า ไม่ได้อ่านรหัสจบ
4. **ทำไมทางสำรองที่มีอยู่ถึงไม่ช่วย?** — เพราะทางสำรองผูกกับเงื่อนไข "ค่าว่าง" อย่างเดียว ตัวขวางที่พิมพ์ข้อความ
   ออก stdout จึงให้ค่าที่ไม่ว่างแต่ผิด ซึ่งเดินผ่านทางสำรองไปได้ — **ค่าผิดที่ไม่ว่าง อันตรายกว่าค่าว่าง**
5. **ทำไมถึงไม่มีใครเห็นตั้งแต่แรก?** — **root cause:** คอมเมนต์ในไฟล์ประกาศไว้เองว่าพลาดได้แค่ทางบล็อกเกิน
   แล้วประโยคนั้นถูกอ่านเป็นข้อสรุปแทนที่จะเป็นข้ออ้างที่ต้องพิสูจน์ · เป็นบทเรียนเดียวกับรายงาน #0001 คือ
   **คอมเมนต์ที่เราเขียนเองไม่ใช่หลักฐาน** และคราวนี้มันปกป้องสิ่งที่แพงที่สุดในระบบ

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** เทสของการ์ด (`customer_hook.test.js`) ครอบเคสได้ดีทุกข้อ **แต่ทุกข้อรันบนเครื่องที่
`python3` ทำงานปกติ** ไม่มีข้อไหนถามว่า "ถ้าเครื่องมือที่การ์ดพึ่งพาพังล่ะ" · ชั้น 12 (ตัวกันใน shell profile)
คุ้มครองคำสั่งที่คนพิมพ์เอง ไม่ได้คุ้มครองคำสั่งที่เอเจนต์เรียกผ่านเครื่องมือ ซึ่งเป็นเส้นทางที่การ์ดตัวนี้รับผิดชอบ

## 5. แนวทางการแก้ไข (Fix)

- ตรวจ **รหัสจบ** ของ `python3` ทั้งสองจุด (`CMD_RC` และ `MARKER_RC`) ไม่ใช่ดูแค่ว่าได้ข้อความมาหรือไม่
- ทางสำรองของ `CMD` ทำงานเมื่อ **รหัสจบไม่เป็นศูนย์ หรือ ค่าว่าง** ไม่ใช่แค่ค่าว่าง
- เมื่อตัวปรับข้อความล้มเหลว ใช้การค้นแบบ shell ล้วนที่ตั้งใจให้กว้างเกิน — ยอมให้มีอักขระคั่นระหว่างตัวอักษรได้ และเทียบรูปแบบตัวเต็มความกว้างตรงๆ
- **ถ้าตรวจไม่ได้และหา marker ไม่เจอ ห้ามออกตรงนั้น** ให้เดินต่อไปถึงจุดตัดสิน แล้วปฏิเสธคำสั่งเขียนที่เล็งไปยังปลายทาง OLS พร้อมข้อความบอกว่าปฏิเสธเพราะยืนยันไม่ได้
- ไม่มีการเรียก API ไม่มีการแตะข้อมูลใดๆ ตลอดการแก้และการทดสอบ ตามคำสั่งเจ้าของงาน

**ยืนยันแล้วด้วย:** ทั้ง 3 รูปแบบความล้มเหลวตอนนี้ **บล็อกครบ (รหัสจบ 2)** · คำสั่งทั่วไปยังผ่านปกติทั้งตอน `python3` ดีและพัง ·
คำสั่งเขียนของเราเองที่ไม่มี marker ยังผ่านตอน `python3` ปกติ และถูกกันไว้ก่อนตอน `python3` พัง ซึ่งเป็นพฤติกรรมที่ตั้งใจ ·
เทสในไฟล์เดิมเพิ่ม 4 ข้อ ผ่านทั้งหมด

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ไล่ปิด "ทั้งคลาส" ตามบทเรียนของ #0003 จริง ไม่ใช่แค่ปิดไฟล์ที่เกิดเหตุ — และนั่นคือสิ่งเดียวที่ทำให้เจอ
- ทดสอบด้วยการจำลองความล้มเหลวจริงในไฟล์แยก ไม่ได้สรุปจากการอ่านโค้ด
- ตอนการ์ดบล็อกคำสั่งทดสอบของตัวเอง เลือกเปลี่ยนวิธีทดสอบ ไม่ใช่ปลดการ์ด

### สิ่งที่ต้องปรับปรุง

**หลักฐานตอนยังพัง:**

```
1 python3 ปกติ              exit=2
2 python3 เรียกไม่ได้        exit=0   <-- ปล่อยผ่าน
3 ตัวขวางพิมพ์ stdout        exit=0   <-- ปล่อยผ่าน
4 ตัวขวางพิมพ์ stderr        exit=0   <-- ปล่อยผ่าน
```

**หลักฐานหลังแก้:**

```
1 python3 ปกติ              exit=2
2 python3 เรียกไม่ได้        exit=2
3 ตัวขวางพิมพ์ stdout        exit=2
4 ตัวขวางพิมพ์ stderr        exit=2

คำสั่งธรรมดา ตอน python3 พัง   exit=0   (ไม่บล็อกงานปกติเพิ่ม)
เขียนของเราเอง ตอน python3 พัง exit=2   (กันไว้ก่อนโดยตั้งใจ)
```
