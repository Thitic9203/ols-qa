## สรุปสั้น (Executive Summary)

เจ้าของงานสั่ง "เด้งหน้าต่างล็อกอิน dev" Claude คัดลอกคำสั่งรอบก่อนแล้วส่งรายชื่อ 15 บัญชีจากไฟล์ roster ในเครื่อง โดยไม่อ่านแท็บบัญชีทดสอบในชีทสดก่อน ทั้งที่มี memory และรายงาน #0088 กำหนดไว้แล้ว ชีทจริงมีบัญชี dev 10 บัญชี เจ้าของงานจึงพิมพ์รหัสให้บัญชีที่ไม่อยู่ในชีท และเมื่อตัวเก็บ session ล้มกลางรอบด้วย error ที่ไม่ถูกจับ ทั้งรอบหยุดโดยไม่สรุปว่าบัญชีไหนบันทึกแล้ว เจ้าของงานพิมพ์ซ้ำให้หน้าต่างที่ไม่ได้บันทึกแล้ว ในงานเดียวกัน Claude วางและสร้างขั้น 3–7 ของ RTT auto-test โดยไม่เคยเรียก Claude ด้วย token ของบอทจริง จึงเพิ่งรู้ตอนขั้น 7 ว่า token ถูกเพิกถอนตั้งแต่ 2026-09-21 มาตรการ P1 ของ #0088 (ให้เครื่องมือปฏิเสธเอง) เคยเป็นแค่ข้อเสนอ ครั้งนี้สร้างเป็นด่านในตัวเครื่องมือแล้ว

## 1. ปัญหา (Problem Statement)

- ส่ง 15 tag จาก `capture/accounts_dev.json` เข้า `session_capture.js` รวม 5 บัญชีที่ไม่อยู่ในชีทบัญชี (แถว 1:43 มี Env `Dev / Pre-prod` 10 แถว อ่านสดหลังเจ้าของงานทัก)
- รอบแรกบันทึก 4 บัญชี แล้วล้มที่บัญชีที่ 5 ด้วย `browserContext.newPage: Target page, context or browser has been closed` (`capture/session_capture.js:153`) ซึ่งเป็น unhandled rejection ทำให้ทั้งโปรเซสจบโดยไม่มีบรรทัดสรุป
- เจ้าของงานพิมพ์ "ใส่ครบแล้ว" ทั้งที่หน้าต่างหลังจากนั้นไม่ได้ถูกบันทึก ต้องเปิดใหม่และพิมพ์ซ้ำ
- รอบที่สองยังส่งบัญชีนอกชีท (หน้าต่างแรกของรอบ) จนเจ้าของงานสั่ง "หยุด" และ "อ่านแค่แอคในชีท"
- `claude -p` ด้วย `~/ols-qa-bot/.oauth_token` ตอบ `401 OAuth access token has been revoked` — บอทล็อกอินรายวันบันทึกอาการนี้ตั้งแต่ 2026-09-21 10:35 แต่ Claude สร้างขั้น 3–7 ทั้งหมดโดยไม่เคยลองเรียกจริง จึงรู้เมื่อ shadow ได้ `runner-error` ครบ 8 ใบ

**สิ่งที่ควรจะเป็น:** รายชื่อบัญชีมาจากชีทบัญชีของรอบเท่านั้น อ่านสดก่อนเด้งทุกครั้ง (CLAUDE.md §9 "ข้อมูลบัญชีอ้างจากชีทบัญชีของรอบเท่านั้น" · memory บัญชีทดสอบอ่านสดตาม Env · #0088) · บัญชีที่ล้มต้องไม่พาทั้งรอบล้ม และต้องสรุปว่าบันทึกแล้วกี่บัญชี · ทรัพยากรที่งานพึ่ง (token) ต้องวัดว่ามีชีวิตก่อนวางงานบนมัน (CLAUDE.md §0)

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไมเด้งบัญชีนอกชีท?** — เพราะรายชื่อมาจาก roster ในเครื่อง ไม่ได้มาจากชีท
2. **ทำไมใช้ roster?** — เพราะ Claude คัดลอกคำสั่งที่ใช้ได้เมื่อวาน (ซึ่งรับ tag เป็นอาร์กิวเมนต์) และถือว่า "ทุก tag ใน roster dev" = "บัญชี dev"
3. **ทำไมคำสั่งเดิมไม่บังคับให้อ่านชีท?** — เพราะ `session_capture.js` รับ tag ใดก็ได้ที่อยู่ใน roster ไม่มีด่านเทียบกับชีท
4. **ทำไมไม่มีด่านนั้น ทั้งที่ #0088 พลาดแบบเดียวกัน?** — มาตรการ P1 ของ #0088 (เครื่องมือปฏิเสธเอง) ค้างสถานะ "เสนอ" ไม่เคยสร้าง เหลือแค่ P2 ที่เป็นกฎ ซึ่งพึ่งความจำ
5. **ทำไมกฎที่พึ่งความจำถึงไม่พอ?** — root cause: การเลือกบัญชีเป็นการตัดสินใจที่ทำให้คนต้องพิมพ์รหัส (ย้อนไม่ได้ เสียเวลาคน) แต่ไม่มีชั้นเครื่องที่ผูกรายชื่อกับแหล่งจริง ณ ขณะเด้ง

ฝั่ง token: ทำไมไม่รู้ว่า token ตาย → เพราะตอน "ตรวจค่าใช้จ่าย" ตรวจแค่ชนิดของ auth (subscription) จากโค้ด ไม่ได้เรียกจริง → เพราะขั้น 3–6 ทดสอบด้วยตัวจำลองทั้งหมด ไม่มีขั้นไหนบังคับการเรียกจริงครั้งแรกก่อนเดินต่อ

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- memory "อ่านชีทสด" — โหลดอยู่ในบริบท แต่ไม่ใช่ด่านที่บล็อกคำสั่ง
- ask-guard / agent-dispatch-guard — ไม่ครอบคำสั่ง Bash ที่เด้งหน้าต่าง
- `session_capture.js` — ตรวจหน้าล็อกอินว่ามีจริง แต่ไม่ตรวจว่าบัญชีควรถูกเด้งไหม · และไม่มี try/catch ต่อบัญชี
- SFD — แจ้ง DM ว่าบอทล็อกอินล้มหลายวัน แต่ heartbeat มองว่า job สำเร็จ (exit 0) จึงไม่ยกระดับ (แก้แล้วที่ commit `6f5c11f` ของ repo บอท)

## 5. แนวทางการแก้ไข (Fix)

- อ่านชีทสดแถว 1:43 แล้วเด้งเฉพาะบัญชีในชีทที่ยังไม่มี session — `session_verify --touch` ok ครบ 10 บัญชีในชีท
- shadow ตรวจ token ด้วยการเรียกจริงก่อนเริ่มรอบ · token ตาย = หยุดทั้งรอบ + DM ครั้งเดียว · classify เก็บข้อความ error (repo บอท commit `5493355`)
- heartbeat ไม่นับ job ที่ trap รายงานว่าล้มเป็นความสำเร็จ (repo บอท commit `6f5c11f`, 7 tests)

**ยืนยันแล้วด้วย:** `session_verify.js --touch` → 10 บัญชีในชีท ok · `test_rtt_shadow_preflight.py` 5/5 · `test_sfd_trap_exit0.py` 7/7 · heartbeat รอบถัดไปไม่ขยับ `last_ok` ของ login-check

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** เจ้าของงานเห็นบัญชีนอกชีทในหน้าต่าง แล้วสั่งหยุด · token จับได้จาก `runner-error` ครบทุกใบใน shadow
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** บัญชีนอกชีท — รอบสองของการเด้ง · token — 15 วันหลังตาย และหลังสร้างขั้น 3–7 เสร็จ
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** P2 ปฏิเสธก่อนเปิดหน้าต่างแรก · shadow preflight หยุดก่อนใบแรก · heartbeat ยกระดับเมื่อ job ล้มเกินเพดาน

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- หยุดโปรเซสของตัวเองด้วย pid ที่รู้ที่มาทันทีที่เจ้าของงานสั่ง
- หลังอ่านชีท เด้งเฉพาะบัญชีที่ขาดและตรวจ `session_verify` ครบก่อนรายงาน

### สิ่งที่ต้องปรับปรุง
- คัดลอกคำสั่งที่ "เคยใช้ได้" ไม่ใช่การตรวจว่าเป้าหมายครั้งนี้ถูก — ต้องผ่านเครื่องมือที่อ่านแหล่งจริง
- มาตรการเครื่องที่ค้าง "เสนอ" ในรายงานเก่า เท่ากับยังไม่มีการป้องกัน
- เจอปัญหากลางงานให้แยก agent สืบ ไม่ไล่เองในเธรดหลักจนเจ้าของงานรอ
