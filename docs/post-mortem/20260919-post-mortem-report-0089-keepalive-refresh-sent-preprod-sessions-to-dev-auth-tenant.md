## สรุปสั้น (Executive Summary)

เจ้าของงานล็อกอินบัญชี pre-prod ด้วยมือ 3 บัญชีเมื่อ 17:40–17:41 น. แล้วเมื่อ 17:45 น. ผม (เธรดหลัก) เริ่มงานวน keepalive ที่เรียก `session_refresh.js` กับ pre-prod
โดยไม่ได้ตรวจว่าสคริปต์จะส่งคำขอ refresh ไปที่ auth host ไหน
ของจริงสคริปต์เลือก env `dev` ให้ทุกงานที่ไม่ใช่ prod และตารางค่าคงที่ผูก pre-prod ไว้กับ auth key ตัวเดียวกับ dev ซึ่งชี้ไปที่ tenant dev
ขณะที่ pre-prod ล็อกอินผ่านอีก tenant หนึ่ง (พอร์ทัลของ pre-prod tenant)
tenant dev ไม่รู้จักโทเคนจึงล้างคุกกี้ access ทิ้ง แล้ว proxy ตัดการเข้าระบบของ OLS ก็ปิด session ฝั่งเซิร์ฟเวอร์ตาม ผลคือ session ตาย 2 จาก 3 บัญชี
หยุด keepalive แล้ว ส่วนการแก้ที่ต้นเหตุ (pre-prod มี auth key ของตัวเอง · หา env จาก host ของ OLS · ด่านตรวจ tenant ก่อนส่ง · เทสต์) เจ้าของงานอนุมัติแล้ว **อยู่ระหว่างทำโดย agent อีกตัว ยังไม่เสร็จและยังไม่ได้ตรวจ**

## 1. ปัญหา (Problem Statement)

- `capture/session_refresh.js:132-137` ฟังก์ชัน `resolveAuthApi()` เรียก `resolveEnv(prod ? 'prod' : 'dev', …)` คืองานที่ไม่ใช่ prod จะได้ auth host ของ `dev` เสมอ ไม่มีทางได้ของ pre-prod
- `capture/env_hosts.js:39-50` ตาราง `ENV_KEYS` ให้ `dev` `pre-prod` และ `preprod` ใช้ auth key ชื่อเดียวกัน (`AUTH_API_HOST`) คอมเมนต์เหนือตารางบอกว่าตรวจแล้วเมื่อ 2026-09-03 ว่าสอง env ใช้ร่วมกัน
- แต่ pre-prod ล็อกอินผ่านคนละ tenant กับ dev (วัดไว้เมื่อ 2026-09-17 ตามบันทึกเรื่องหน้าล็อกอินของแต่ละ env) ค่าในตารางและคอมเมนต์จึงล้าสมัย
- คุกกี้ของ pre-prod ผูกกับโดเมนแม่ร่วมกัน จึงถูกส่งไปหา auth host ของ tenant dev ด้วย tenant นั้นไม่รู้จักโทเคนและตอบกลับด้วยการล้างคุกกี้ หลังคำขอนั้น `access_token` หายจาก context ของเบราว์เซอร์ ทั้งที่ไฟล์ state ยังมีอายุเหลือ 23.9 ชั่วโมง (`DBG_refresh_RESULT.md` ข้อ 2.2)
- ใน `ols-monorepo` ไฟล์ `apps/web/src/lib/proxy/with-session-revoke.proxy.ts` เมื่อคำขอมีคุกกี้ session ของ OLS แต่ไม่มี `access_token` proxy จะเรียก `endCurrentSession()` ซึ่งปิด session ฝั่งเซิร์ฟเวอร์ (`DBG_refresh_RESULT.md` ข้อ 2.3) สคริปต์รอ 2 วินาทีโดยหน้า OLS ยังเปิดอยู่ คำขอใดที่เกิดในช่วงนั้นจึงทำให้ session ถูกปิด — คำขอไหนที่ยิงจริง **ยังไม่ได้วัด** ถือเป็นสมมติฐาน
- probe ครั้งเดียวเมื่อ 17:48:41–17:48:42 น. (`GET /api/auth/get-session` ของ pre-prod) เธรดหลักตรวจซ้ำแล้ว: บัญชี A ยังอยู่ (body 299 ไบต์ มี `user`) · บัญชี B และบัญชี C ตาย (body 0 ไบต์)
- ทั้ง 3 session ยังมีชีวิตตอนเริ่ม refresh เพราะสคริปต์จะไปถึงขั้นส่งคำขอได้ก็ต่อเมื่อผ่านด่าน `recognisedHere()` ซึ่งต้องได้ `user` จาก get-session ก่อน ถ้าตายอยู่แล้วจะพิมพ์ข้อความ "ข้ามไป" แทน (`DBG_refresh_RESULT.md` ข้อ 1)

**สิ่งที่ควรจะเป็น:** ก่อนเริ่มงานที่ส่งโทเคนไปหาเซิร์ฟเวอร์ ต้องรู้ว่าปลายทางที่เครื่องมือจะใช้เป็นของ tenant ที่ออกโทเคนนั้นจริง — กฎจากรายงาน #0027 ("ค่าที่ระบุปลายทางต้องมีชื่อ env อยู่ในตัว และต้องเปิดของจริงยืนยันในรอบนั้นก่อนใช้เสมอ") และกฎจาก #0071 (ห้ามยิง refresh บน env ที่ยังไม่เคยวัดว่าทำได้) ครอบเรื่องนี้อยู่แล้ว

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

เครื่องมือเลือก auth host จาก **ค่าปริยาย** (`'dev'` สำหรับทุกงานที่ไม่ใช่ prod) ไม่ได้หาจาก **เป้าหมายที่กำลังทำงานด้วย** (host ของ OLS ที่ session นั้นสังกัด)
และตาราง env ก็ผูก pre-prod ไว้กับ key เดียวกับ dev ตามข้อเท็จจริงที่ถูกต้องเมื่อ 2026-09-03 แต่ไม่จริงแล้วตั้งแต่ pre-prod ย้ายไปใช้ tenant ของตัวเอง
ด่านเดียวที่มีก่อนส่งคำขอคือ `recognisedHere()` ซึ่งมาจากการแก้ของ #0046 มันพิสูจน์แค่ว่า **OLS** ยังรู้จัก session ไม่ได้พิสูจน์ว่า **auth host ที่จะส่งไป** เป็นผู้ออกโทเคน
ความถูกต้องของปลายทางจึงขึ้นกับว่าคนเรียกจำได้หรือไม่ว่า env ไหนใช้ tenant ไหน — และรอบนี้ผมไม่ได้ตรวจ

### 5 Whys

1. **ทำไม session pre-prod ตาย 2 จาก 3 บัญชี?** — เพราะคำขอ refresh ไปที่ auth ของ tenant dev ซึ่งล้างคุกกี้ access ในเบราว์เซอร์ทิ้ง แล้ว proxy ของ OLS เห็นคุกกี้ session ที่ไม่มี `access_token` จึงปิด session ฝั่งเซิร์ฟเวอร์
2. **ทำไมคำขอไปที่ tenant dev?** — เพราะ `resolveAuthApi()` เลือก env `dev` ให้ทุกงานที่ไม่ใช่ prod และ `ENV_KEYS` ให้ pre-prod ใช้ auth key ตัวเดียวกับ dev
3. **ทำไมตารางยังผูก pre-prod ไว้กับ key ของ dev?** — เพราะตารางเขียนตอนที่สอง env ใช้ tenant เดียวกันจริง (ตรวจแล้ว 2026-09-03) เมื่อ pre-prod ย้าย tenant (วัดได้ 2026-09-17) ข้อเท็จจริงใหม่ถูกบันทึกไว้ในความจำ แต่ไม่มีอะไรผูกให้ตารางในเครื่องมือต้องเปลี่ยนตาม
4. **ทำไมผมเริ่ม keepalive โดยไม่เห็นว่าปลายทางผิด?** — เพราะถือว่าเครื่องมือที่ผ่านการแก้จาก #0046 แล้ว "เลือกปลายทางถูกเอง" ไม่ได้อ่านว่า `resolveAuthApi()` คืนค่าอะไรสำหรับ pre-prod และเครื่องมือไม่มีโหมดที่พิมพ์ปลายทางที่จะใช้จริงก่อนส่ง
5. **ทำไมเครื่องมือยอมส่งโทเคนไปหาปลายทางที่ไม่ได้ออกโทเคนนั้น?** — **เพราะปลายทางของคำขอที่มีผลถาวรมาจากค่าปริยาย ไม่ได้หาจากตัวเป้าหมาย และไม่มีด่านใดเทียบว่าปลายทางเป็นผู้ออกโทเคนของ session ก่อนส่ง** กฎของ #0027 ปิดคลาสนี้ไว้ด้วยข้อความในเอกสารเท่านั้น ไม่ได้ปิดในโค้ด — นี่คือ root cause ปิดทั้งคลาสได้ด้วยการให้เครื่องมือหา env จาก host เป้าหมาย ไม่มี key = โยน error และปฏิเสธก่อนส่งเมื่อ tenant ไม่ตรง

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- **กฎจาก #0027** (ค่าที่ระบุปลายทางต้องมีชื่อ env และต้องเปิดของจริงยืนยันในรอบนั้น) — เป็นกฎเอกสาร ไม่มีเครื่องมือบังคับ และ Action Item 4 ของ #0027 ("ไล่หาค่าปริยายอื่นที่ผูกกับ env แต่ไม่ระบุ ในชุดเครื่องมือเดียวกัน") ยังเป็น Open บรรทัด `'dev'` ใน `resolveAuthApi()` คือค่าแบบนั้นพอดี
- **ด่าน `recognisedHere()` จาก #0046** — ตรวจ session กับ OLS ของ env เป้าหมายถูกต้อง แต่คำถามที่ด่านนั้นตอบคือ "OLS รู้จัก session นี้ไหม" ไม่ใช่ "auth host นี้ออกโทเคนนี้ไหม" ข้อสมมติว่า "หนึ่งคู่ env ของ OLS มี tenant เดียว" จึงเป็นชั้นเดียวที่ถือทั้งหมดไว้ และพังเมื่อ pre-prod ย้าย tenant
- **กฎจาก #0071** (ห้าม refresh บน env ที่ยังไม่เคยวัดว่าทำได้) — ผมไม่ได้วัดว่า refresh ใช้ได้กับ pre-prod tenant ก่อนเริ่มงานวน กฎนี้ก็เป็นกฎเอกสารเช่นกัน
- **ข้อความผลของสคริปต์** — พิมพ์ `session rejected by server` ทุกครั้งที่ไม่มี `access_token` หลังคำขอ ทำให้อ่านเหมือน session ตายอยู่ก่อน ทั้งที่คำขอของเราเป็นตัวทำให้ตาย

## 5. แนวทางการแก้ไข (Fix)

- **หยุดงานวน keepalive แล้ว** ด้วย pid ที่รู้ที่มา ตรวจตอน 18:00:44 น.: `pgrep -fl session_refresh` ไม่พบโปรเซส (รหัสจบ 1)
- **ยืนยันสถานะ session จากของจริง** ด้วย probe get-session ครั้งเดียว (ผลในภาคผนวก) เธรดหลักตรวจซ้ำแล้ว บัญชี A ใช้ได้ · บัญชี B และ C ต้องล็อกอินใหม่
- **การแก้ที่ต้นเหตุ — เจ้าของงานอนุมัติแล้ว อยู่ระหว่างทำโดย agent อีกตัว ยังไม่เสร็จ และยังไม่ได้ตรวจ:**
  - pre-prod มี auth key ของตัวเองใน `env_hosts.js` และถ้าไม่มี key ให้โยน error ไม่ถอยไปใช้ของ dev
  - `session_refresh.js` หา env จาก host ของ OLS เป้าหมาย host ที่ไม่ตรงกับ env ใดเลย = ปฏิเสธด้วย exit 2
  - ด่านตรวจ tenant ก่อนส่ง: auth host ที่จะส่งต้องเป็นผู้ออกโทเคนของ session นั้น ไม่ตรง = ไม่ส่ง
  - เทสต์ครอบทุกข้อด้านบน

**ยืนยันแล้วด้วย:** เฉพาะการหยุดโปรเซส (`pgrep` ด้านบน) และผล probe · ตอน 18:00:44 น. โค้ดทั้งสองจุดยังเป็นแบบเดิม (`session_refresh.js:135` ยังเป็น `resolveEnv(prod ? 'prod' : 'dev', …)` · `env_hosts.js` pre-prod ยังใช้ `AUTH_API_HOST`) การแก้จึง **ยังไม่ปิด**

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** สคริปต์พิมพ์ `session rejected by server` ตอน 17:45 น. จึงแยก agent สืบด้วย systematic-debugging แล้วเธรดหลักตรวจผล probe ซ้ำ — ไม่มีกลไกใดหยุดคำขอก่อนส่ง
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** จากเริ่มงานวน 17:45 น. ถึง probe ยืนยัน 17:48:42 น. แต่ความเสียหายเกิดตั้งแต่คำขอแรกแล้ว การรู้เร็วจึงไม่ได้ช่วยลดความเสียหาย
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** P2 และ P3 จะปฏิเสธ **ก่อน** ส่งคำขอ คือจับได้ตั้งแต่ก่อนเกิดความเสียหาย ไม่ต้องรอให้ session ตาย

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- แยก agent สืบด้วย systematic-debugging ทันที และได้ต้นเหตุพร้อม `path:line` เมื่อ 17:49:04 น. (ขั้นสุดท้ายใน `DBG_refresh.jsonl`) โดยไม่ยิง refresh ซ้ำและไม่ probe auth host ของ pre-prod ที่ไม่ได้รับอนุญาต
- ใช้ probe ครั้งเดียวแยกบัญชีที่ยังใช้ได้ออกจากบัญชีที่ตาย เจ้าของงานจึงล็อกอินใหม่แค่ 2 บัญชี ไม่ใช่ทั้ง 3
- หยุดงานวนด้วย pid ที่รู้ที่มา ไม่ใช้ `pkill -f`

### สิ่งที่ต้องปรับปรุง
- ก่อนเริ่มงานวนที่ยิงคำขอที่มีผลถาวร ต้องอ่านว่าเครื่องมือจะไปปลายทางไหนสำหรับ env นี้ ไม่ใช่เชื่อว่าการแก้รอบก่อน (#0046) ครอบแล้ว
- Action Item 4 ของ #0027 (ไล่ค่าปริยายที่ผูก env ทั้งชุดเครื่องมือ) ค้างมาตั้งแต่ 2026-09-08 และบรรทัดที่ทำให้พลาดรอบนี้อยู่ในขอบเขตของข้อนั้นพอดี — ของที่ค้างใน Action Item ต้องถูกยกขึ้นมาก่อนใช้เครื่องมือตัวนั้นกับ env ใหม่
- ข้อเท็จจริงที่วัดได้ใหม่ (pre-prod แยก tenant, 2026-09-17) ถูกบันทึกไว้แค่ในความจำ ไม่ได้ไล่แก้ตารางในเครื่องมือตาม
