## สรุปสั้น (Executive Summary)

ประกาศ deploy dev รอบ v2026.10.20.1 มีเครื่องหมาย `\` ต่อท้ายลิงก์ tag (markdown ขึ้นบรรทัดใหม่)
ตัวดึงลิงก์ `build_url` เก็บ `\` ไว้ ข้อความ "Starting smoke test" จึงไม่ตรงรูปแบบที่ notify-guard L2 รับ และถูกปฏิเสธ
ตัวเฝ้าได้บันทึกว่า deploy นี้ "จัดการแล้ว" ไปก่อนโพสต์ ทุก tick หลังจากนั้นพิมพ์ว่าไม่มี deploy ใหม่ รอบจึงไม่รันเลย
แก้แล้ว: ตัดเครื่องหมาย markdown ท้ายลิงก์ · บันทึกว่าจัดการแล้วหลังโพสต์สำเร็จเท่านั้น · รอบนี้รันและส่งผลแล้ว (87 เคสผ่าน, อนุมัติก่อนส่ง)
ระหว่างไล่ปิดรอบยังพบอีก 3 ช่องในเส้นทางเดียวกัน (path รายงานตายตัว · checkout หลักอยู่ผิด branch · ไม่มีขั้นตัด pass-only อัตโนมัติ) แก้ครบใน PR เดียวกัน

## 1. ปัญหา (Problem Statement)

- **คาดหวัง:** ประกาศ deploy dev ที่เสร็จแล้ว → ภายใน 2 นาทีตัวเฝ้าโพสต์ "Starting smoke test" แล้วรันรอบ
- **ที่เกิดจริง:** tick 15:43:13 จับ deploy ได้ แต่ notify-guard L2 ปฏิเสธข้อความ (ลิงก์ลงท้าย `\`) จบด้วย exit 1 · tick ถัดๆ ไปพิมพ์ `no new dev deploy to act on` ไม่มีรอบเกิดขึ้น

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไมรอบ smoke ไม่รัน?** — เพราะ tick ที่จับ deploy ได้จบด้วย exception ก่อนเริ่มรอบ และ tick หลังจากนั้นข้าม deploy นี้
2. **ทำไม tick นั้นจบด้วย exception?** — เพราะข้อความ start มีลิงก์ลงท้าย `\` ซึ่ง `START_RE` ไม่รับ — `build_url` ตัดแค่ `> ) . ,`
3. **ทำไม tick หลังจากนั้นข้าม?** — เพราะ `claim()` อยู่ก่อน `send_start` deploy ถูกเขียนลง state ว่าจัดการแล้วทั้งที่ยังไม่มีอะไรโพสต์
4. **ทำไมลำดับนี้ไม่ถูกจับ?** — ความเห็นในโค้ดคิดกรณี "preflight ล้มเหลว" (VPN/host) ไว้แล้ว จึงย้าย claim ไปหลัง preflight แต่ไม่ได้มองว่าการโพสต์เองก็ล้มเหลวได้ และไม่มีเทสต์ของ `main()` ที่ป้อนความล้มเหลวหลัง claim
5. **ทำไมไม่มีเทสต์นั้น?** — root cause: ตัวเฝ้าไม่มีกฎ "deploy จะถูกนับว่าจัดการแล้วเมื่อขั้นที่ต้องเห็นภายนอก (โพสต์ start) สำเร็จเท่านั้น" เป็นกฎที่มีเทสต์ตรึง — ขั้นใดที่ fail หลัง claim จะทำให้ deploy หายเงียบทั้งคลาส ไม่ใช่แค่ `\`

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- notify-guard L2 ทำงานถูก (ปฏิเสธรูปแบบผิด) แต่ไม่มีชั้นไหนดูแลว่าหลังปฏิเสธแล้ว deploy ยังอยู่ในคิว
- SFD harness ส่ง DM แจ้ง exit 1 แล้ว แต่ข้อความบอกแค่ traceback ไม่ได้บอกว่า "deploy นี้จะไม่ถูกรันอีก"
- `test_deploy_trigger.py` มีเคสลิงก์ แต่ใช้ลิงก์ที่สะอาดเท่านั้น ไม่มีข้อความ deploy จริงที่มี markdown ต่อท้าย

## 4. ผลกระทบ (Impact)

- รอบ smoke ของ v2026.10.20.1 เริ่มช้ากว่าที่ควร 26 นาที (15:23 → 15:49) และเริ่มได้เพราะเจ้าของงานถาม
- ระหว่างนั้นห้อง QA release ไม่มีข้อความใดบอกว่ารอบไม่ได้เริ่ม
- ไม่มีข้อมูลเสียหาย ไม่มีข้อความผิดถูกโพสต์

## 5. แนวทางการแก้ไข (Fix)

ทั้งหมดอยู่ใน PR #8 ของ repo บอท (merge แล้ว `c03279c`) สเปก `docs/sdd/smoke-watch-start-tag/` R1–R6

- R1 `build_url` ตัดเครื่องหมาย markdown ท้ายลิงก์ (`\ * _ \` |`) — เทสต์ใช้บรรทัดจริงของวันนี้ + ตรวจ `START_RE`
- R2/R3 โพสต์ start ก่อน แล้วค่อย `claim()` — เทสต์: start ถูกปฏิเสธ ⇒ deploy ยังอยู่ในคิว (fail ก่อนแก้) · สำเร็จ ⇒ จัดการแล้ว
- R4 `passed_report` อ่านรายงานจาก checkout ที่รอบรันจริง
- R5 รอบอัตโนมัติรันจาก worktree ใหม่ของ origin/main เสมอ (checkout หลักวันนี้อยู่บน feature branch)
- R6 `passed_report` ตัดผล pass-only เองจากรอบที่จบแล้ว (เดิมรอบ 16/Oct ตัดด้วยมือ)

**ยืนยันแล้วด้วย:** เทสต์ 6 ชุดเขียว (46 · 81/0 · 1 · 6 · 9 · 2) · post start จริง 15:49:27 ลิงก์สะอาด · ตัด pass-only กับรอบ 16/Oct ได้ 95 = 95 และ control 107 ต่างกัน · เส้นทางอัตโนมัติจากผลดิบวันนี้ได้ 87 เคสเดียวกับที่ส่ง · ส่งผลจริงหลังอนุมัติ read-back ผ่าน

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

**กฎที่เพิ่มจากเหตุนี้:** งานอัตโนมัติที่ทำเครื่องหมายว่า "จัดการแล้ว" ต้องทำหลังขั้นที่มองเห็นจากภายนอกสำเร็จเท่านั้น ขั้นใดล้มเหลวหลังทำเครื่องหมาย = งานหายเงียบ (สเปกบอท R2 + `test_smoke_watch_claim.py`) · ตัวรันและตัวอ่านผลของรอบเดียวกันต้องอ่าน path จากไฟล์บันทึกเดียวกัน ห้ามต่างคนต่างเดา (R4/R5)

- กฎในสเปก R2: deploy นับว่าจัดการแล้วเมื่อโพสต์ start สำเร็จเท่านั้น — มีเทสต์ตรึง (`test_smoke_watch_claim.py`) ถ้าใครย้าย claim กลับ เทสต์แดง
- เทสต์ลิงก์ใช้ข้อความ deploy จริงที่มี markdown ต่อท้าย ไม่ใช่ลิงก์สะอาด
- ปิดคลาส "checkout ผิด" ทั้งสองฝั่ง: ตัวรันและตัวอ่านรายงานใช้ไฟล์ `e2e_dir` เดียวกัน (R4+R5) ไม่ใช่ path ที่แต่ละไฟล์เดาเอง

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี

- ตอน VPN หลุด ตัวเฝ้าหยุดก่อนโพสต์และคงคิวไว้ ตามที่ออกแบบ

### สิ่งที่ต้องปรับปรุง
