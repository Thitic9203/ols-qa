## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

ตัวอัดเก็บเฟรมพร้อมเวลาจริงของแต่ละเฟรม แล้วตอนประกอบไฟล์คำนวณความยาวของเฟรมที่ `i`
จากช่องว่างถึงเฟรมที่ `i+1` วิธีนี้ถูกต้องสำหรับทุกเฟรมยกเว้นเฟรมสุดท้าย เพราะไม่มีเฟรมถัดไป
เฟรมสุดท้ายจึงได้ค่าปริยาย `1/fps` เสมอ จังหวะค้างที่ประกาศตอนปิดการอัด (`closedAtStop`)
คือเวลาที่ผ่านไปหลังเฟรมสุดท้าย ซึ่งแปลว่ามันจะถูกตัดออกทั้งหมดทุกครั้ง ไม่ใช่บางครั้ง

### 5 Whys

1. **ทำไมผลลัพธ์อยู่ในคลิปแค่ 0.2 วินาที?** — เพราะไฟล์จบก่อนจังหวะค้างท้ายที่ตั้งใจให้เห็น
2. **ทำไมไฟล์จบก่อน?** — เพราะเฟรมสุดท้ายถูกให้ความยาว `1/fps` แทนความยาวของจังหวะค้าง
3. **ทำไมถึงให้ `1/fps`?** — เพราะสูตรคำนวณความยาวอิงช่องว่างถึงเฟรมถัดไป และเฟรมสุดท้ายไม่มีเฟรมถัดไป จึงตกลงค่าปริยาย
4. **ทำไมไม่มีใครจับได้ตอนอัด?** — เพราะ manifest ประกาศช่วงค้างนั้นไว้ และด่านตรวจไฟล์ใช้ manifest เป็นความจริง ไม่ได้ตรวจย้อนว่าไฟล์ครอบคลุมช่วงที่ประกาศ
5. **ทำไมด่านถึงเชื่อ manifest?** — **root cause: ของสองชิ้นที่ต้องพูดตรงกัน (manifest กับไฟล์) ไม่มีชั้นไหนผูกให้ตรงกัน** — ปิดได้ด้วยการทำให้ไฟล์เป็นไปตามที่ประกาศ และมีเทสต์ที่ล้มถ้าไม่เป็น

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- ด่าน 7 ชั้นของ mp4 ตรวจความละเอียด · โคเดก · ความนิ่ง · overlay — ไม่มีชั้นไหนเทียบความยาวไฟล์กับ `holdSpans`
- ชั้น 1b ใช้ `holdSpans` เป็นข้อมูลนำเข้า (ยกเว้นช่วงค้างออกจากการวัดกระตุก) จึงยิ่งกลบปัญหา: ช่วงที่ไม่มีอยู่จริงก็แค่ยกเว้นเฟรมที่ไม่มี
- การตรวจ "เฟรมสุดท้ายไม่ใช่หน้าว่าง" ผ่าน เพราะเฟรมสุดท้ายเป็นหน้าจอที่ถูกต้อง เพียงแต่อยู่สั้นเกินกว่าจะอ่าน

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ไม่พลิก verdict จากผลด่านอัตโนมัติ จึงเปิดคลิปดูแล้วเจอก่อนที่มันจะกลายเป็นหลักฐานของเคสที่ผ่าน
- หาเหตุที่ต้นทางแทนการแนบภาพนิ่งเสริม ทำให้คลิปอื่นที่จะอัดต่อจากนี้ไม่เจอปัญหาเดิม

### สิ่งที่ต้องปรับปรุง
- manifest ที่เครื่องมือเราเขียนเอง ไม่ใช่หลักฐานว่าไฟล์เป็นแบบนั้น — ต้องวัดไฟล์ก่อนส่งมอบทุกครั้ง
- ด่านตรวจที่รับค่าจาก manifest มาใช้ ต้องตรวจความสอดคล้องของค่านั้นกับไฟล์ก่อน ไม่ใช่ใช้เลย
