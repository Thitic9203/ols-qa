## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

ตัวเลือกการ์ดเดิมตามที่เลนบันทึกไว้ใน `MISTAKE_confirmed` คือ `div.filter(hasText).filter(has button).last()` บนรายการรออนุมัติที่ไม่ได้กรอง
(รายการนั้นมี 288 รายการตามบรรทัด `probe_result`) `div` ชั้นนอกที่ครอบหลายการ์ดก็เข้าเงื่อนไข "มีข้อความชื่อนี้และมีปุ่ม" เช่นกัน
และ `.last()` เลือกจากลำดับใน DOM ไม่ได้เลือกจากความใกล้กับชื่อ ปุ่มที่ได้จึงเป็นของการ์ดอื่น
ข้อความของตัวเลือกเดิมนี้เป็นคำบรรยายของเลน เธรดหลักไม่ได้เห็นโค้ดเดิมเพราะไฟล์ถูกแก้ทับแล้ว สิ่งที่เธรดหลักยืนยันเองคือผลลัพธ์ (M3 `REJECTED`) และโค้ดหลังแก้

### 5 Whys

1. ทำไมโหวตผิดสื่อ — สคริปต์คลิกปุ่ม "ตรวจสอบ" ของการ์ดอื่น แล้วเดินต่อจนกดยืนยัน
2. ทำไมเดินต่อได้ — ไม่มีขั้นใดเทียบชื่อในหน้าต่างรีวิวกับชื่อสื่อที่ตั้งใจ
3. ทำไมซ้อม 3 รอบไม่จับ — รอบซ้อมตรวจเฉพาะเฟรมเรตและการเดินขั้นตอนครบ และหยุดก่อนกดยืนยัน จึงไม่มีคำตอบจากเซิร์ฟเวอร์ให้เทียบ และไม่มีการตรวจชื่อเช่นกัน
4. ทำไมสคริปต์ไม่มีด่านนี้ตั้งแต่ต้น — คำสั่งงานที่เธรดหลักจ่ายให้เลน RC3 ไม่ได้กำหนดว่าก่อนคลิกที่เขียนข้อมูลต้องยืนยันตัวตนของเป้าหมาย กำหนดแค่ให้ซ้อมก่อนอัดจริง
5. ทำไมคำสั่งงานไม่กำหนด — เธรดหลักถือว่า "ซ้อมแบบไม่เขียนผ่าน" เท่ากับ "อัดจริงปลอดภัย" ทั้งที่การซ้อมวัดคุณภาพคลิป ไม่ได้วัดว่าเป้าหมายถูกตัว

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** รายงาน #0039 ให้กฎว่าคำสั่งที่ทำลายของได้ต้องระบุเป้าหมายด้วยตัวตนที่รู้ที่มา ห้ามจับด้วยรูปแบบ
และต้องถามว่า "คำสั่งนี้จะโดนกี่ตัว" กฎนั้นเขียนผูกกับคำสั่งหยุดโปรเซส จึงไม่มีใครนำมาใช้กับตัวเลือก element บนหน้าเว็บ
ซึ่งเป็นการจับด้วยรูปแบบแบบเดียวกัน และด่านก่อนอัดกับหลังอัดตรวจคลิป ไม่ได้ตรวจว่าการเขียนข้อมูลลงถูกรายการ

- สื่อทดสอบ M3 บน dev เปลี่ยนเป็น "ไม่อนุมัติ" 1 รายการ ย้อนกลับไม่ได้ เป็นข้อมูลที่เราสร้างเอง ไม่ใช่ของผู้อื่น และไม่มีคำว่า RGS

- ไม่มีคลิปผิดถูกส่งมอบ ไม่มีการเขียนชีท Jira หรือ Discord จากเหตุนี้

## 5. แนวทางการแก้ไข (Fix)

- เลนเปลี่ยนตัวเลือกการ์ดเป็นฟังก์ชัน `cardButton()` ซึ่งไล่จากข้อความชื่อขึ้นไปหา ancestor ที่ใกล้ที่สุดที่มีปุ่มตรงเงื่อนไข **เพียง 1 ปุ่ม** และปฏิเสธถ้า ancestor นั้นมีชื่อของสื่อทดสอบรายการอื่นปนอยู่ (`rec3_reject.js:31-38`)
- เพิ่มด่านตรวจชื่อ 2 จุด คือหน้าต่างสถานะ (`rec3_reject.js:62`) และหน้าต่างรีวิวก่อนกดยืนยัน (`rec3_reject.js:97`) ไม่ตรง = `throw` ก่อนคลิก
- สคริปต์อนุมัติของ Content_TC_004 ใช้ด่านเดียวกัน และการอัดจริงของเคสนั้นโหวตถูกสื่อ M1

**ยืนยันแล้วด้วย:** เธรดหลักอ่านสถานะสด M1 `PUBLISHED/APPROVED` · M2 `REJECTED` ตรงกับที่ตั้งใจทั้งคู่ · คลิป Content_TC_005 รอบที่ 2 ผ่าน `verify_video.py` รหัสจบ 0
และเฟรมสุดท้ายที่เธรดหลักเปิดดูแสดงชื่อสื่อ M2 กับสถานะ "ไม่อนุมัติ"

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- เลนเขียนผลลงดิสก์ก่อนเรียกเครื่องมือตัวถัดไป หลักฐานทั้งหมดจึงอยู่ครบแม้เลนจะถูกตัดตอนท้าย
- เลนหยุดอัดทันที ไม่อัดซ้ำทับ และไม่สร้างข้อมูลทดสอบใหม่เองเกินขอบเขต
- คลิปของรอบที่ผิดถูกเปลี่ยนชื่อและแยกออก ไม่ปนกับคลิปที่ส่งตรวจ

### สิ่งที่ต้องปรับปรุง
- คำสั่งงานควรกำหนดด่านยืนยันเป้าหมายตั้งแต่ใบแรกที่มีการเขียนข้อมูล ไม่ใช่หลังเสียข้อมูลทดสอบไปแล้ว
- กฎที่ได้จากรายงานก่อนควรถูกอ่านเป็นคลาส (การเลือกเป้าหมายด้วยรูปแบบ) ไม่ใช่อ่านเฉพาะเครื่องมือที่เกิดเหตุ
