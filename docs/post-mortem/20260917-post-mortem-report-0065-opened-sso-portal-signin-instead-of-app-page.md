**ระบบ:** ตัวเก็บ session ของชุดเครื่องมือ QA (`capture/session_capture.js`)
**สภาพแวดล้อมที่ได้รับผลกระทบ:** รอบเก็บ session ของ env `dev` — ไม่มีการเขียนข้อมูลลงระบบ OLS
**วันที่เกิดเหตุ:** 2026-09-17

**ระดับความรุนแรง:** Medium — เจ้าของงานต้องสั่งซ้ำ 3 ครั้ง และเสียเวลารอบเก็บ session ไปหนึ่งรอบ ไม่มีข้อมูลเสียหาย

## สรุปสั้น (Executive Summary)

รอบเก็บ session ก่อนงานอัดหลักฐานวิดีโอ ผมเปิดหน้าต่างให้เจ้าของงานกรอกรหัสผ่านที่ **หน้า sign-in ของพอร์ทัล SSO**
(ค่าปริยายของเครื่องมือ) แทนที่จะเปิด **หน้าแอปของ env ที่เจ้าของงานสั่ง** ทั้งที่ตัวเครื่องมือเองเขียนเงื่อนไขข้อนี้ไว้ในหัวไฟล์
ตั้งแต่ 2026-09-12 แล้วว่า env ที่ล็อกอินผ่าน drawer ต้องตั้ง `SIGNIN_URL` เป็นหน้าแอป (`capture/session_capture.js:87-92`)
ผลคือเจ้าของงานต้องสั่งซ้ำ 3 ครั้ง และคำสั่ง `/systematic-debugging` ที่เจ้าของงานยิงมาระหว่างนั้นถูกตอบว่า
`No response requested.` โดยไม่มีการสืบอะไรเลย แก้ด้วยการตั้ง `SIGNIN_URL` เป็นหน้าแอปของ env นั้นแล้วเปิดใหม่
ไม่มีรหัสผ่านหลุด ไม่มีข้อมูลเสียหาย แต่เสียเวลาไปหนึ่งรอบเต็ม

## 1. ปัญหา (Problem Statement)

- เจ้าของงานสั่งเก็บ session ของ env หนึ่ง ผมรันตัวเก็บ session โดยไม่ตั้ง `SIGNIN_URL` → เครื่องมือใช้ค่าปริยาย
  `PORTAL + '/sign-in/embed'` (`capture/session_capture.js:92`) ซึ่งเป็นหน้าฟอร์มเปล่าของพอร์ทัล ไม่ใช่หน้าแอปของ env ที่สั่ง
- หัวไฟล์ของเครื่องมือตัวเดียวกันเขียนเงื่อนไขไว้ชัดแล้วว่า host ที่ล็อกอินผ่าน drawer บนหน้าแรกของตัวเอง
  "needs the app URL instead, so the operator ends up ON the app after signing in" (`capture/session_capture.js:87-92`)
- เจ้าของงานต้องทักซ้ำ **3 ครั้ง** กว่าจะได้หน้าที่ถูก และคำสั่ง `/systematic-debugging` ระหว่างนั้นถูกตอบว่า
  `No response requested.` โดยไม่ได้ลงมือสืบ

**สิ่งที่ควรจะเป็น:** ก่อนเปิดหน้าต่างให้มนุษย์กรอกรหัสผ่าน ต้องเปิดซอร์สของเครื่องมือรอบนั้นอ่านว่าค่าปริยายชี้ไปไหน
และเทียบกับ env ที่เจ้าของงานสั่ง — กฎ repo ข้อแรกสุด (ห้ามพูด/ทำสิ่งที่ยังไม่ตรวจ) และบทเรียน #0009
(เครื่องมือที่เลือกปลายทางห้ามมีค่าปริยาย)

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไมหน้าที่เปิดให้กรอกรหัสผ่านถึงผิด?** — เพราะรันเครื่องมือโดยไม่ตั้ง `SIGNIN_URL` จึงได้ค่าปริยายของพอร์ทัล
2. **ทำไมถึงไม่ตั้ง?** — เพราะไม่ได้เปิดซอร์สอ่านก่อนรัน คิดว่า "เครื่องมือนี้เคยใช้แล้วได้" จากความจำ
3. **ทำไมความจำถึงใช้ไม่ได้?** — เพราะเงื่อนไขนี้เพิ่งถูกเขียนลงไฟล์เมื่อ 2026-09-12 พร้อมกับตอนที่มี env ที่สอง
   ที่ล็อกอินคนละแบบ ความจำที่ถืออยู่เป็นภาพก่อนหน้านั้น
4. **ทำไมไม่มีอะไรบังคับให้ระบุ?** — เพราะ `SIGNIN_URL` เป็น optional และมีค่าปริยาย จึงไม่มีจุดไหนที่ทำให้
   "ลืมเลือก" ต่างจาก "ตั้งใจเลือก"
5. **root cause:** เครื่องมือที่ต้องเลือก **ปลายทางต่อ env** ยังมีค่าปริยาย — ซึ่งเป็นคลาสเดียวกับ #0009 ที่ปิดไปแล้ว
   ฝั่ง host แต่ไม่ได้ปิดฝั่ง "หน้าล็อกอินต่อ env"

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** #0031 เพิ่มการตรวจว่าหน้าที่เปิดตอบ HTTP < 400 จริง (`session_capture.js:163`)
— หน้าพอร์ทัลตอบ 200 ปกติ จึงผ่านด่านนั้น เพราะด่านนั้นวัดว่า "หน้ามีชีวิต" ไม่ได้วัดว่า "เป็นหน้าของ env ที่สั่ง"

## 5. แนวทางการแก้ไข (Fix)

- ตั้ง `SIGNIN_URL` เป็นหน้าแอปของ env ที่เจ้าของงานสั่ง แล้วเปิดหน้าต่างใหม่ — เจ้าของงานล็อกอินสำเร็จ
- บันทึกตาราง env → host → หน้าล็อกอิน ลง memory `reference_ols-env-hosts-and-login-portals`

**ยืนยันแล้วด้วย:** เจ้าของงานล็อกอินผ่านหน้าที่เปิดใหม่ได้จริง และ session ที่ได้ถูกตรวจสดกับเซิร์ฟเวอร์ด้วย
`capture/recording_preflight.js` ในรอบเดียวกัน (7 บัญชีใช้ได้จริง · 6 ตาย)

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

| # | มาตรการ | ชนิด | สถานะ |
|---|---------|------|-------|
| P1 | memory `reference_ols-env-hosts-and-login-portals` — ตาราง env → host → หน้าล็อกอิน อ่านก่อนเปิดหน้าล็อกอินทุกครั้ง | กฎ/memory | ทำแล้ว |
| P2 | `SIGNIN_URL` ต้องเลิกมีค่าปริยาย — ให้ผู้เรียกระบุเสมอ และล้มดังๆ เมื่อไม่ระบุ (คลาสเดียวกับ #0009) | เครื่องมือ | **ค้าง** — แก้เครื่องมือกลางที่เจ้าของงานใช้ ต้องขออนุมัติก่อน |
| P3 | ด่านตรวจว่าหน้าที่จะเปิดอยู่บนโฮสต์ของ env ที่สั่งจริง (ไม่ใช่แค่ตอบ 200) | เครื่องมือ + เทส | **ค้าง** |

**กฎที่เพิ่มจากเหตุนี้:** *ก่อนเปิดหน้าใดให้มนุษย์กรอกรหัสผ่าน ต้องเปิดซอร์สของเครื่องมือรอบนั้นอ่านว่าค่าปริยายชี้ไปไหน
แล้วเทียบกับ env ที่เจ้าของงานสั่ง — ค่าปริยายของเครื่องมือไม่ใช่คำตอบของคำถามว่า "env ไหน"*
· และ *คำสั่ง `/systematic-debugging` ของเจ้าของงานเป็นคำสั่ง ไม่ใช่ข้อมูลประกอบ — ห้ามตอบว่าไม่ต้องตอบ*

- **ใครจับได้ / จับได้ยังไง:** เจ้าของงานเห็นหน้าที่เปิดขึ้นมาเองแล้วทัก

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ไม่มีการพยายามให้ agent กรอกรหัสผ่านเอง — กฎห้ามข้อนั้นถูกรักษาไว้ตลอด

### สิ่งที่ต้องปรับปรุง
- เงื่อนไขที่เขียนไว้ในหัวไฟล์ของเครื่องมือ ถูกอ่านหลังพลาด ไม่ใช่ก่อนรัน
- คำสั่งของเจ้าของงานถูกตอบว่า "ไม่ต้องตอบ" — ห้ามเกิดอีก
