## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### เหตุที่ 1 — ข้อมูลชุดเดียวมี 2 รูป และผมใช้รูปของอีกปลายทางหนึ่ง

ข้อมูลเลนถูกใช้ 2 ทางในหน้าเดียวกัน

| ทาง | ตัวอ่าน | รูปที่ต้องการ |
|---|---|---|
| ข้อมูลตั้งต้นที่ฝังในหน้า | `arr(SEED.lanes)` | **อาเรย์** |
| ฐานข้อมูลสด | `arr(d.items)` | ออบเจ็กต์ที่มีคีย์ `items` |

ไฟล์บนดิสก์เก็บรูปที่สอง เพราะมันมีไว้ส่งเข้าฐานข้อมูล ผมหยิบไปวางในช่องของทางแรก ความต่างคือ
**การแกะกล่องหนึ่งชั้น** ซึ่งตัวอ่านฐานข้อมูลทำให้เองที่ `arr(d.items)` แต่ทางข้อมูลตั้งต้นไม่มีใครทำให้

### เหตุที่ 2 — `arr()` ออกแบบมาให้ทนทาน จึงกลืนความผิดพลาดนี้เงียบสนิท

`arr(x)` คืน `[]` เมื่อ `x` ไม่ใช่อาเรย์ ซึ่งเป็นพฤติกรรมที่ถูกต้องสำหรับกรณี "ยังไม่มีข้อมูล" และเป็นสิ่งที่
ทำให้หน้าเว็บไม่พังเมื่อข้อมูลขาด แต่กับกรณีนี้มันแปลง **ข้อมูลผิดรูป** ให้กลายเป็น **ไม่มีข้อมูล**
ซึ่งบนจอหน้าตาเหมือนกันทุกประการ — ช่องว่างเปล่าที่ไม่มีข้อความแจ้งอะไรเลย

นี่คือคลาสเดียวกับที่ repo บันทึกไว้หลายครั้งแล้วในบริบทอื่น คือ **"อ่านไม่ได้" กับ "ไม่มี" ถูกยุบเป็น
คำตอบเดียวกัน** (#0003 · #0005) รอบนี้เกิดในหน้าเว็บแทนที่จะเกิดในเชลล์

### เหตุที่ 3 — ยืนยันที่ไฟล์กับที่คำสั่ง แทนที่จะยืนยันที่สิ่งที่ผู้อ่านเห็น

สิ่งที่ผมตรวจก่อนเผยแพร่คือ ไฟล์ถูกเขียนแล้ว ขนาดเปลี่ยนจริง และคำสั่งเผยแพร่ตอบว่าสำเร็จ ทั้งหมดเป็น
สถานะของ**ช่องทางลำเลียง** ไม่ใช่สถานะของ**หน้าเว็บ** และตัวเลขไบต์ที่พิมพ์ออกมาก็ยิ่งทำให้รู้สึกว่า
ได้วัดอะไรไปแล้ว ทั้งที่วัดความยาวสตริง ซึ่งไม่มีความสัมพันธ์ใดกับความถูกต้องของรูปข้อมูล

### 5 Whys

1. **ทำไมช่องเลนถึงว่าง** — เพราะ `SEED.lanes` เป็นออบเจ็กต์ และ `arr()` คืนอาเรย์ว่างเมื่อได้ออบเจ็กต์
2. **ทำไม `SEED.lanes` ถึงเป็นออบเจ็กต์** — เพราะเอาเนื้อไฟล์ `lanes.json` ไปวางทั้งก้อน
3. **ทำไมถึงวางทั้งก้อน** — เพราะถือว่ารูปของเอกสารในฐานข้อมูลกับรูปของข้อมูลตั้งต้นเป็นรูปเดียวกัน
4. **ทำไมถึงถืออย่างนั้นโดยไม่ตรวจ** — เพราะไม่ได้เปิดตัวอ่านของหน้าเว็บมาเทียบ ทั้งที่ตัวอ่านทั้งสองอยู่ในไฟล์เดียวกัน ห่างกันประมาณ 60 บรรทัด และเป็นไฟล์ที่ผมกำลังแก้อยู่ในเทิร์นนั้น
5. **ทำไมถึงเผยแพร่ก่อนตรวจ** — เพราะสคริปต์จบโดยไม่มี error และพิมพ์ตัวเลขไบต์ออกมา **ตัวเลขที่ไม่ได้วัดสิ่งที่สนใจ ถูกอ่านเป็นการยืนยัน** (คลาสเดียวกับรายงาน #0019 ในวันเดียวกัน)

## 5. แนวทางการแก้ไข (Fix)

แก้ที่จุดประกอบข้อมูล ให้แกะกล่องชั้นเดียวกับที่ตัวอ่านฐานข้อมูลทำ

```python

```

แล้วยืนยัน **จากไฟล์ที่เขียนแล้ว** ไม่ใช่จากตัวแปรในหน่วยความจำ และหลังเผยแพร่อ่านหน้าที่เผยแพร่จริง

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

รายงาน #0018 จบด้วยคำเตือนว่าให้ดูสิ่งที่เจ้าของงานเห็น และคำเตือนนั้นล้มเหลวภายในวันเดียวกัน
มาตรการรอบนี้จึงต้องเป็นสิ่งที่ **ทำงานเองตอนเขียน** ไม่ใช่สิ่งที่ต้องจำตอนเผยแพร่

**P1 — ต้องมีตัวตรวจรูปข้อมูลตั้งต้น ที่รันก่อนเผยแพร่ทุกครั้ง และปฏิเสธเมื่อรูปไม่ตรง**

ตัวตรวจอ่านข้อมูลตั้งต้นออกจากหน้าเว็บที่เขียนเสร็จแล้ว แล้วยืนยันชนิดของทุกช่องที่หน้าเว็บอ่าน
(`lanes` · `blockers` · `corrections` · `events` ต้องเป็นอาเรย์ · `meta` ต้องเป็นออบเจ็กต์ที่มีช่องเวลา)
และ **ปฏิเสธเมื่ออาเรย์ใดยาวศูนย์** เพราะบอร์ดของรอบนี้ไม่มีช่องไหนที่ควรว่าง — ศูนย์คือสัญญาณของ
รูปข้อมูลผิด ไม่ใช่สถานะที่ถูกต้อง ตัวตรวจนี้ต้องจบด้วยรหัสไม่เป็นศูนย์เมื่อไม่ผ่าน เพื่อให้ขั้นตอนเผยแพร่
สะดุดเอง ไม่ใช่รอให้คนสังเกต

**P2 — รูปข้อมูลต้องถูกแปลงที่เดียว ไม่ใช่แปลงซ้ำที่ผู้เรียกแต่ละราย**

ต้นเหตุจริงคือมีข้อมูลชุดเดียวที่ถูกแทนด้วย 2 รูป และการแปลงระหว่างกันถูกฝากไว้กับความจำของคนเขียน
ทางที่ถูกคือให้มีฟังก์ชันเดียวที่ประกอบข้อมูลตั้งต้นจากไฟล์ทั้ง 3 ไฟล์ แล้วทั้งขาเผยแพร่และขาเขียน
ฐานข้อมูลเรียกฟังก์ชันเดียวกัน — เป็นกฎเดียวกับที่ repo เขียนไว้แล้วในบริบทอื่นว่า **การตัดสินต้องอยู่ที่
โมดูลเดียว** (#0003)

**P3 — ตัวเลขที่พิมพ์ตอนเสร็จ ต้องเป็นตัวเลขของสิ่งที่สนใจ**

`seed ในหน้าเว็บ 34510 ไบต์` ไม่ได้บอกอะไรเกี่ยวกับความถูกต้อง บรรทัดที่ควรพิมพ์คือจำนวนเลน
จำนวนรายการในแต่ละช่อง และเวลาที่อัปเดต ซึ่งเป็นตัวเลขที่ผิดแล้วมองเห็นทันที (ปัจจุบันเปลี่ยนแล้ว
บรรทัดยืนยันพิมพ์ว่า `lanes list 5 | events N | corrections N | เวลา`)

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี

- จับได้เองก่อนเจ้าของงานเห็น และแก้ทันทีในเทิร์นเดียวกับที่เจอ
- หลังแก้ ยืนยันจากไฟล์ที่เขียนแล้วและจากหน้าที่เผยแพร่จริง ไม่ใช่จากตัวแปรในหน่วยความจำ
- ยอมรับกับเจ้าของงานตรงๆ ในข้อความว่าเขียนผิดจริง ไม่ได้แก้เงียบ

### สิ่งที่ต้องปรับปรุง

- **โค้ดที่ออกแบบมาให้ทนทาน จะกลืนความผิดพลาดของคนป้อนข้อมูลเสมอ** `arr()` ทำหน้าที่ของมันถูกต้อง แต่ทำให้ "ผิดรูป" กับ "ไม่มี" แยกไม่ออกบนจอ — ตรงนี้ต้องมีตัวตรวจอยู่เหนือขึ้นไป ไม่ใช่ไปแก้ `arr()`
- **ข้อมูลชุดเดียวที่มี 2 รูป คือกับดักที่รอวันสะดุด** ตราบใดที่การแปลงยังอยู่ในหัวคน
- **จับได้เพราะบังเอิญ ไม่นับว่ามีการตรวจจับ** ต้องเขียนชั้นที่จับได้ทุกครั้งแม้ไม่มีใครไปเปิดดู

## 10. Technical Appendix

**ตัวอ่าน 2 ตัวในไฟล์เดียวกัน ที่ต้องการคนละรูป**

```js
// ขาข้อมูลตั้งต้น — ต้องการอาเรย์
var state = { meta: SEED.meta || {}, lanes: arr(SEED.lanes), … };

// ขาฐานข้อมูลสด — แกะ items ให้เอง
else if (doc.id === "lanes") state.lanes = arr(d.items);

// ตัวกลืนความผิดพลาด
function arr(x) { return Array.isArray(x) ? x : []; }
```

**สิ่งที่ตรวจก่อนเผยแพร่ กับสิ่งที่ควรตรวจ**

```
ที่ตรวจ  : ไฟล์ถูกเขียน · ขนาดเปลี่ยน · คำสั่งเผยแพร่ตอบสำเร็จ · seed 34510 ไบต์
ที่ควรตรวจ: อ่าน seed กลับจากไฟล์ที่เขียนแล้ว → lanes เป็น list และยาวไม่เป็นศูนย์
```

**กฎที่เพิ่มจากเหตุนี้:** *ก่อนเผยแพร่หน้าที่ฝังข้อมูลไว้ในตัวเอง ต้องอ่านข้อมูลนั้นกลับออกมาจากไฟล์ที่เขียนแล้ว
แล้วยืนยันชนิดของทุกช่องที่หน้าเว็บอ่าน และปฏิเสธเมื่ออาเรย์ใดยาวศูนย์* เพราะโค้ดหน้าเว็บที่ออกแบบมา
ให้ทนข้อมูลขาด จะแปลง **ผิดรูป** เป็น **ไม่มี** ซึ่งบนจอหน้าตาเหมือนกันทุกประการ · *ข้อมูลชุดเดียวที่มี
มากกว่า 1 รูป ต้องมีจุดแปลงจุดเดียวที่ทุกผู้เรียกใช้ร่วมกัน* ห้ามฝากการแปลงไว้กับความจำของผู้เรียกแต่ละราย ·
และ *ตัวเลขที่พิมพ์ตอนงานเสร็จ ต้องเป็นตัวเลขของสิ่งที่สนใจ* — จำนวนไบต์ของสตริงอ่านเหมือนการยืนยัน
ทั้งที่ไม่มีความสัมพันธ์ใดกับความถูกต้อง (คลาสเดียวกับ #0019 ในวันเดียวกัน)
