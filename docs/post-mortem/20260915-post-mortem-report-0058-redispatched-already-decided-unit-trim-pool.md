## สรุปสั้น (Executive Summary)

ตอนคัดกรองคิวตัดฉาก 28 เคส Unit track ใช้เกณฑ์เดียวคือ mtime ของไฟล์ผลตัดสิน (`< 14/Sep 17:00` = ยังไม่เคยแตะ)
โดยไม่ได้เช็คว่ามีบันทึกการตัดสินใจจากรอบ 14/Sep 14:00 อยู่แล้วหรือไม่ ทำให้ dispatch เลน "Unit batch B" (14 เคส)
ไปทำงานที่ถูกตัดสินไปแล้วจริง — เอกสารแผนงานเขียนห้ามไว้ชัดว่า "ห้ามส่งเลนใหม่ไปทำซ้ำ pool นี้" agent ที่ถูก
dispatch พบเรื่องนี้เอง ตรวจสอบซ้ำแล้วยืนยันว่าตัวเลขตรงกับของเดิมทุกเคส ไม่มีการเขียนทับ ไม่มีข้อมูลเสียหาย
แก้โดยไม่มีอะไรต้องแก้เพิ่ม (agent หยุดเองไม่เขียนทับ) — สิ่งที่ปิดคือแนวทางคัดกรองคิวรอบหน้า

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไม dispatch ไปทำงานซ้ำ?** — เพราะเกณฑ์คัดกรอง "ยังไม่เคยถูกแก้" อิง mtime ของไฟล์ผลตัดสินอย่างเดียว
2. **ทำไม mtime ถึงบอกผิด?** — เพราะเคสเหล่านี้ถูกตัดสินไปแล้วตั้งแต่ 14:00 (ก่อน cutoff 17:00 ที่ตั้งไว้เพื่อจับ
   เฉพาะเคสที่ยังไม่ผ่านตัวจำแนกรุ่นล่าสุด) — cutoff เดียวใช้ตอบ 2 คำถามที่ต่างกัน: "ผ่านตัวจำแนกล่าสุดหรือยัง"
   กับ "มีคนตัดสินใจเรื่องนี้จบแล้วหรือยัง" ซึ่งเป็นคนละคำถามที่บังเอิญมีคำตอบตรงกันสำหรับ System แต่ไม่ตรงกันสำหรับ
   เซ็ตย่อยของ Unit
3. **ทำไมไม่เช็คคำถามที่สอง?** — เพราะตอนคัดกรองไม่ได้เปิดเอกสารแผนงานอ่านทั้งหมดก่อน (เอกสารมีประโยคห้ามชัดเจน
   อยู่แล้ว "ห้ามส่งเลนใหม่ไปทำซ้ำ pool นี้") — ใช้แค่การนับไฟล์ในเครื่อง ไม่ได้ตรวจ context ที่มีอยู่แล้ว
4. **ทำไมไม่เปิดเอกสารก่อน?** — เพราะกำลังทำงานภายใต้ deadline ("แยก agent ทำให้มากที่สุด ต้องเสร็จเที่ยงนี่")
   เลือกทางที่นับไฟล์เร็วกว่าการอ่านเอกสาร 1000+ บรรทัดทั้งฉบับ
5. **Root cause:** เกณฑ์คัดกรองงานที่ "ยังไม่เคยแก้" ต้องมาจากแหล่งข้อมูลที่ตอบคำถามนั้นตรงๆ (บันทึกการตัดสินใจ/
   เอกสารแผนงาน) ไม่ใช่ proxy อย่าง mtime ของไฟล์ — mtime บอกได้แค่ "ไฟล์ถูกแก้เมื่อไหร่" ไม่ได้บอกว่า "เรื่องนี้ถูก
   ตัดสินจบหรือยัง" สองอย่างนี้ใกล้เคียงกันมากพอที่จะดูเหมือนใช้แทนกันได้ แต่ไม่ใช่สิ่งเดียวกัน

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** ไม่มีชั้นไหนครอบ — นี่คือขั้นตอนคัดกรองก่อน dispatch ซึ่งทำในเธรดหลัก
ไม่มี gate อัตโนมัติตรวจสอบ

**ยืนยันแล้วด้วย:** agent รายงาน verify สด 5/14 + cross-check log เดิม 9/14 ตรงกันทั้งหมด

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- คำสั่งที่ dispatch ไปบังคับให้ agent "verify rather than assume" อยู่แล้ว — เป็นเหตุผลที่จับได้ก่อนเขียนทับ

### สิ่งที่ต้องปรับปรุง
