## สรุปสั้น (Executive Summary)

ตัวรักษา session ของรอบ prod เปิดบริบทเบราว์เซอร์จากไฟล์ session โหลดหน้า `/content` ก่อน แล้วค่อยถาม `GET /api/auth/get-session`
ผ่านบริบทเดียวกันนั้น คำตอบจึงสะท้อน **คุกกี้ในหน่วยความจำหลังการโหลดหน้า** ไม่ใช่ไฟล์ที่ตัวรันเทสต์จะเปิดใช้ และตัวรักษาไม่เคยเซฟไฟล์กลับ
ผลคือบัญชีผู้ดูแลระบบถูกบันทึก `warmed+verified` ทั้งก่อนและหลังนาทีที่ตัวรันเทสต์อ่านไฟล์เดียวกันแล้วได้ "session ตาย" จน 4 เคสติด BLOCKED
· กลไกที่ทำให้คุกกี้ในหน่วยความจำต่างจากไฟล์ (เช่นแอปออก session ใหม่ให้เองระหว่างโหลดหน้า) **ยังไม่ได้ยืนยันจากไฟล์** · ยังไม่ได้แก้ตัวรักษา

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไม 4 เคสติด BLOCKED ทั้งที่ตัวรักษาบอกว่า session ใช้ได้?** — เพราะตัวรักษากับตัวรันเทสต์วัดคนละสิ่ง
2. **ทำไมวัดคนละสิ่ง?** — ตัวรักษาถาม `get-session` หลังโหลดหน้าในบริบทเดียวกัน (`:74`→`:78`) ส่วนตัวรันเทสต์ถามจากไฟล์ตรง
3. **ทำไมตัวรักษาถามหลังโหลดหน้า?** — การโหลดหน้ามีไว้ "อุ่น" (ต่ออายุ idle) แล้วเอาบริบทเดิมไปพิสูจน์ต่อเพราะสะดวก ไม่ได้แยกขั้นพิสูจน์ออกเป็นบริบทสะอาดจากไฟล์
4. **ทำไมไม่มีใครเห็นว่าสองอย่างนี้ต่างกัน?** — รุ่นก่อนหน้าของไฟล์ (หัวไฟล์ `:8-11`) เคยพลาดเพราะนับ "โหลดหน้าได้" เป็นผ่าน การแก้รอบนั้นเพิ่ม `get-session` แต่ไม่ได้ถามว่า `get-session` ถูกเรียก **ด้วยคุกกี้ชุดไหน**
5. **ทำไมคำถามนั้นไม่ถูกถาม?** — ด่านถูกออกแบบจากคำถาม "เซิร์ฟเวอร์ยังรู้จักบัญชีนี้ไหม" แทนที่จะเป็น "ไฟล์ที่งานถัดไปจะเปิด ใช้ได้ไหม" — ตัวชี้วัดไม่ได้ผูกกับอินพุตของผู้ใช้ปลายทาง

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** กฎจาก #0062 และ #0072 สั่งให้ตรวจสดก่อนส่งงาน แต่ไม่ได้บอกว่าตรวจ **จากอินพุตไหน** · ด่านมีสถานะที่ 3 (`unknown`) ตามกฎ #0005 ครบ แต่ทั้ง 3 สถานะวัดจากบริบทที่ผ่านการนำทางแล้ว · ไม่มีเทสต์ของตัวรักษาที่เทียบผลของมันกับการอ่านไฟล์ตรง
