## 1. ปัญหา (Problem Statement)

- 3 เคส (`Profile_TC_005` · `Profile_TC_007` · `LiveStream_TC_017`) — โน้ตของเคสเองยังระบุว่าป้ายบทบาทบนหัวเว็บอ่านได้ว่า
  "ผู้สร้างสื่อ" ทั้งที่นิยามเคสใน `jobs_all.json` เป็นบทบาทผู้เรียนล้วน ไม่มีขั้นตอนสลับโหมด แต่ `verdict` ถูกตั้งเป็น `ผ่าน`
  และ `codes` ถูกล้างเป็น `[]` โดยการแก้ที่บันทึกไว้ในโน้ตพูดถึงแค่การตัดช่วงจอนอกระบบที่ไม่เกี่ยวกับบทบาทเลย
- 5 เคส (`LiveStream_TC_016` · `LiveStream_TC_005/009/014` · `Feed_TC_012`) — `codes` ยังมี `ROLE_MISMATCH` ค้างอยู่จริง
  (ไม่ได้ถูกล้างเหมือนกลุ่มแรก) แต่ `verdict` ก็ยังถูกตั้งเป็น `ผ่าน` อยู่ดี — `LiveStream_TC_016` มีหลักฐานที่ชัดที่สุด:
  เอกสารมติเจ้าของงานเอง (`FINAL_URL_CLASSIFICATION.md` บรรทัด 24-33) ระบุตรงๆ ว่าเคสนี้อยู่ในกลุ่ม "ยังติดเรื่องอื่น...บทบาทผิด"
  ไม่ได้อยู่ในกลุ่ม 3 เคสที่ผ่านทันทีจากมติเรื่องลูกโป่งเบราว์เซอร์
- log ของ `laneB` (`laneB_heartbeat.log` · `laneB_rerun.log` · `laneB_batch.log`) ยืนยันว่ามันสแกน/ตัดได้เฉพาะโค้ดกลุ่มเฟรม
  (`RAWAPI`/`CONSOLE`/`CAPTION`/`VERDICT_IN_CLIP`/`WEB_ADDRESS`) เท่านั้น — **ไม่มีบรรทัดไหนในทุก log ของ laneB พิมพ์คำว่า
  `ROLE_MISMATCH` เลยสักครั้ง** เพราะมันไม่ใช่สิ่งที่ laneB ถูกออกแบบมาตรวจ

**สิ่งที่ควรจะเป็น:** ไฟล์ `classify.py` ในชุดเครื่องมือเดียวกันเขียนนิยามไว้เองแล้วว่า `ROLE_MISMATCH` เป็นโค้ดกลุ่ม `HARD`
("ตัดแล้วไม่หาย เพราะสิ่งที่ขาดคือของที่ไม่เคยถูกอัด") ต่างจากกลุ่ม `FRAME` ที่ตัดจอแก้ได้จริง — เคสที่ `codes` ยังมีโค้ดกลุ่ม
`HARD` ค้างอยู่ ไม่ควรมีทางถูกตั้ง `verdict` เป็น `ผ่าน` ได้เลยจนกว่าจะมีการยืนยันแยกต่างหากว่าโค้ดนั้นหมดไปแล้วจริง

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไม 9 เคสถูกตั้งเป็นผ่านทั้งที่บทบาทยังผิด?** — เพราะการตั้ง `verdict` อ้างอิงผลของเครื่องมือตัดจอ/ยืนยันตัวเดียว (`rc=0`)
   โดยไม่ได้เช็คว่าช่อง `codes` เดิมมีโค้ดอะไรค้างอยู่บ้างก่อน
2. **ทำไมไม่เช็ค `codes` ก่อนตั้ง `verdict`?** — เพราะกระบวนการตัดจอกับกระบวนการตัดสิน `verdict` แยกกันคนละขั้น
   และไม่มีขั้นตอนบังคับให้เทียบ `codes` เดิมกับสิ่งที่เครื่องมือตัดจอเพิ่งแก้ไปจริงๆ ว่าตรงกันหรือไม่
3. **ทำไมเครื่องมือตัดจอถึงไม่ตรวจบทบาทด้วยเลย?** — เพราะ `cliptool.py`/`laneB` ถูกออกแบบมาแก้ปัญหา "มีจอที่ไม่ใช่ระบบ
   ปนอยู่ในคลิป" (โค้ดกลุ่ม `FRAME`) เท่านั้น การตรวจว่าบัญชีที่อัดเป็นบทบาทถูกไหมเป็นปัญหาคนละชั้น ต้องดูป้ายบทบาทบนจอ
   ซึ่งเป็นงานที่เครื่องมือกลุ่มนี้ไม่เคยถูกสร้างมาให้ทำ
4. **ทำไมไม่มีใครสังเกตว่าโค้ดกลุ่ม `HARD` (`ROLE_MISMATCH`/`ER_INCOMPLETE`/`DUPLICATE_FILE`) ค้างอยู่แต่ `verdict` เปลี่ยน
   เป็นผ่าน?** — เพราะไม่มีการตรวจสอบ **ความสอดคล้องภายในของ record เดียวกัน** (`verdict` ต้องไม่ขัดกับ `codes`)
   ก่อนจะยืนยันว่าเคสนั้นปิดงานแล้ว — แต่ละคนที่แก้ (ทั้งสองรอบ) เชื่อผลของด่านที่ตัวเองเพิ่งรันแทนที่จะเปิด record เดิมทั้งก้อน
5. **ทำไมชั้นป้องกันที่มีอยู่ (`classify.py` ที่แยกกลุ่ม `HARD`/`UNSURE`/`FRAME` ไว้ชัดเจนแล้ว) ไม่ช่วยจับตรงนี้?** —
   root cause: **`classify.py` มีแค่นิยาม ไม่มีการบังคับใช้ (enforcement)** — ไม่มีโค้ดส่วนไหนเรียก `classify.py` ตอนเขียน
   `verdict` ลง `short.json` เพื่อปฏิเสธการตั้ง `ผ่าน` เมื่อ `codes` ยังมีโค้ดกลุ่ม `HARD` อยู่ นิยามที่ถูกต้องถูกเขียนไว้
   แต่ไม่เคยถูกต่อสายเข้ากับจุดที่ตัดสินใจจริง

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** `w5_scope_75.py` เป็นเครื่องมือคนละตัวที่ใช้นิยาม "โค้ด `ROLE_MISMATCH` = ต้องอัดใหม่"
เหมือนกัน แต่มันเป็นเครื่องมือ **รายงาน** (อ่านอย่างเดียว คำนวณตัวเลขสรุป) ไม่ใช่เครื่องมือ **เขียน** — มันจะจับความขัดแย้งนี้ได้
ถ้าถูกรันหลังการแก้ทุกครั้ง แต่ตอนตรวจพบว่ามันรันไม่ได้อยู่แล้วเพราะข้อมูลมีโค้ด 2 ตัวที่ไม่รู้จัก (`ER_MISMATCH_NEEDS_PO`,
`INTERNAL_NAME_ON_SCREEN`) ซึ่งเป็นปัญหาที่มีอยู่ก่อนหน้าและไม่ได้ถูกแก้ในรายงานฉบับนี้ (ดูหัวข้อป้องกัน P3)

## 5. แนวทางการแก้ไข (Fix)

- ดึงกลับเป็น `ไม่ผ่าน` + `codes: ["ROLE_MISMATCH"]` ครบ 8 เคส พร้อมโน้ตอ้างหลักฐานเฉพาะของแต่ละกลุ่ม
  (3 เคสแรกอ้างโน้ตเดิมของตัวเอง · `LiveStream_TC_016` อ้าง `FINAL_URL_CLASSIFICATION.md` · อีก 4 เคสอ้าง log ของ laneB)
- ตรวจแยก `Course_TC_009` ซึ่งโค้ดเดิมเป็นกลุ่ม `UNSURE` (`ER_UNCLEAR`) ไม่ใช่ `HARD` — เปิด OCR จริงจากคลิปหลังตัด
  (`lane2_scan/OLS_Integration_Course_TC_009.json`) พบเฟรมสุดท้าย (t=42.0 จาก 42.96 วินาที) อ่านได้ชัดว่า
  "สถานะ: ยกเลิกการเผยแพร่" ตรงผลคาดหวังเป๊ะ ไม่มีแผงคอนโซลหลงเหลือในทุกเฟรมที่สแกน ชื่อคอร์สเป็นชื่อจริงไม่ใช่รหัสทดสอบ

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ก่อนพิมพ์ตัวเลขผ่าน/ไม่ผ่านลงเอกสารที่เจ้าของงานจะอ่าน ได้ไล่เทียบ `codes` ของทุกเคสที่สถานะเป็น `ผ่าน` กับ baseline
  ก่อนคอมมิตครั้งก่อน (ไม่ใช่เชื่อ `short.json` ปัจจุบันเฉยๆ) — จึงจับได้ก่อนตัวเลขผิดหลุดออกไปที่อื่น
- เมื่อเจอ 3 เคสแรก ไม่ได้หยุดแค่นั้น แต่ขยายการตรวจเป็นทั้งชุด (ทุกเคส `ผ่าน` เทียบ baseline) จึงเจออีก 5 เคส
  จากกลไกคนละตัว (`laneB`) ที่ไม่เคยถูกสงสัยมาก่อน

### สิ่งที่ต้องปรับปรุง
- P1/P2 ควรถูกต่อสายเป็นโค้ดจริงตั้งแต่รอบก่อนหน้าที่เขียน `cliptool.py`/`laneB` — ถ้าทำไว้แต่แรก ปัญหานี้จะไม่มีวันเกิด
  ไม่ต้องรอให้มีใครมาตรวจซ้ำทีหลัง
- รอบแรกที่พบ 3 เคส ควรตั้งคำถามทันทีว่า "เครื่องมือกลุ่มเดียวกันมีอันไหนอีกที่ทำแบบเดียวกัน" แทนที่จะพอใจกับ 3 เคสแรก
  ก่อนขยายสแกนทั้งชุด
