## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

จุดตัดสินใจที่ผิดคือตอนที่เธรดหลักเขียนคำอธิบายของ NDLP_TC_005 ลงมติ 23.4x ข้อ (b) ในขั้นนั้น ER ไม่ได้มาจากการอ่านชีทสด
ก่อนการอ่านสด 07:46 มีไฟล์ JSON ใต้ `out/` ที่มีข้อความ ER นี้เพียง 2 ไฟล์จาก 5694 ไฟล์ และทั้งคู่ลงวันที่ 13/Sep
เธรดหลักบันทึกไว้ในแถว PENDING ว่าหยิบมาจากแคชชีท eyeball ส่วนคำสั่งที่ใช้ตอนนั้นไม่มี log จึงตรวจไม่ได้

ในแคช รหัสเคสอยู่แค่ในชื่อไฟล์คลิปซึ่งเป็นช่องสุดท้ายของแถว การค้นด้วยรหัสเคสแล้วอ่านข้อความต่อจากจุดที่เจอจึงตกไปที่แถวถัดไปเสมอ
ในไฟล์นี้ข้อความที่ต่อจาก `OLS_System_NDLP_TC_005.mp4` คือ `["12", "เชื่อมต่อ NDLP", "ตรวจสอบเลือกสื่อแล้วกดนำเข้าสื่อ ...` ซึ่งเป็นแถวของ TC_006
และรหัสนี้เจอ 2 ชีท โดย System อยู่ก่อน Integration ในไฟล์ ผลคือได้ ER ที่ผิดทั้งแถวและผิดชีทในครั้งเดียว

ตอนนั้นมันดูถูก เพราะข้อความที่ได้เป็นเคสเชื่อมต่อ NDLP ที่อ่านแล้วเข้ากับรหัส "NDLP_TC_005" และค่าในแคชก็ตรงกับชีทจริงทุกช่อง (12/12 แถว NDLP)
ไม่มีช่องไหนดูเก่าหรือเพี้ยนให้สะดุด ความผิดอยู่ที่ว่าช่องไหนเป็นของแถวไหน ซึ่งตาเห็นไม่ได้จากข้อความ ER เพียงอย่างเดียว

### 5 Whys

1. **ทำไมมติ 23.4x (b) และบรีฟเลนใช้ ER ของ System NDLP_TC_006 เป็นของ Integration NDLP_TC_005?** — เพราะข้อความ ER มาจากสำเนาชีท 13/Sep (แคช eyeball ตามที่เธรดหลักบันทึก) ไม่ได้มาจากการอ่านชีทสดของแถว NDLP_TC_005
2. **ทำไมการหยิบจากแคชได้แถวผิด?** — เพราะในแคชรหัสเคสอยู่แค่ในชื่อไฟล์คลิปที่ช่องสุดท้ายของแถว การค้นรหัสแล้วอ่านข้อความต่อไปจึงได้แถวถัดไป บวกกับรหัสเดียวกันมีทั้งในชีท System และ Integration และ System มาก่อน โดยไม่ได้ล็อกชีทและแท็บ
3. **ทำไมไม่ล็อกชีท + แท็บ + รหัสเคสแล้วอ่านสด?** — เพราะไม่มีขั้นใดบังคับว่า ER ในมติหรือบรีฟต้องมาจากการอ่านสดของแถวที่ระบุตัวตนครบ ข้อความ ER ถูกเขียนเป็นข้อความอิสระ ไม่มีช่องบอกแหล่ง แถว และเวลาอ่าน
4. **ทำไมเลนและผู้ตรวจรอบแรกไม่จับ?** — เพราะบรีฟส่ง ER มาเป็นข้อเท็จจริง เลนทำงานตามนั้น เลน laneT69 สังเกตได้ว่า ER1/ER2 อาจไม่ตรงโค้ด แต่ไม่ได้ถูกสั่งให้เทียบกับแถวสด จึงรายงานเป็นข้อสังเกตเรื่องโค้ด ไม่ใช่เรื่องแหล่งของ ER มีเพียง subagent ชุด B ที่มีตาราง source บังคับให้อ่านชีทสดจึงจับได้
5. **ทำไมไม่มีชั้นเครื่องที่ปิดคลาสนี้?** — (root cause) ข้อมูลสเปกที่ไหลเข้ามติและบรีฟไม่ผูกกับตัวตนของแถวสด (ชีท + แท็บ + รหัสเคส + เวลาอ่าน) และไม่มีตัวตรวจที่ขอบการจ่ายงานที่เทียบ ER ในบรีฟกับแถวสด ณ เวลาจ่ายงาน ทั้งคลาสจึงผ่านได้ทุกครั้ง ไม่ว่าจะเป็น ER จากแคช จากสำเนา จากแถวข้างเคียง หรือจากชีทผิด

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- CLAUDE.md §0 (สำเนา/บันทึกต้องตรวจซ้ำรอบนี้) และ §7 (char-exact ทั้ง 2 ฝั่ง) — เป็นกฎตัวหนังสือ ไม่มีตัวบังคับตอนเขียนมติหรือบรีฟ
- #0088 — มาตรการคือกฎให้อ่านชีตบัญชีสดก่อนเลือกบัญชี และเสนอตรวจ env ใน `session_capture.js` ครอบเฉพาะชีตบัญชี ไม่ครอบชีท TC และ ER
- #0079 — แก้ตัวอ่านเลขข้อ (`split_items`) ที่อ่านภายในเซลล์ ไม่เกี่ยวกับการระบุว่าเซลล์เป็นของแถวไหน
- `agent-dispatch-guard` — กฎที่มีคือ persist · proxy preload · screenshot · unbounded scan ค้น `expected|sheet|ชีท` ใน `dispatch_rules.js` ได้ 0 ครั้ง จึงไม่มีการตรวจ ER ในบรีฟ
- ด่าน ledger-intent-before-write — ทำงานถูก (ไม่มีการเขียน) แต่เป็นด่านของการเขียน ไม่ใช่ด่านของความถูกต้องของสเปก

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ด่าน ledger-intent-before-write และการ dry run ก่อน take ทำให้ทั้ง 2 รอบหยุดที่ BLOCKED ก่อนเขียนอะไร
- เลน laneT69 บันทึกว่า ER1/ER2 อาจไม่ตรงโค้ด โดยเขียนชัดว่า "not a bug claim" ไม่เปิดบั๊กจากสเปกที่ยังไม่ยืนยัน
- subagent ชุด B อ่านชีทสดแล้ววางข้อค้นพบไว้บนสุดของไฟล์ ("Read first") และแยก 3A/3B ไม่ผสมกัน

### สิ่งที่ต้องปรับปรุง
- รหัสเคสในชีทนี้อยู่แค่ในชื่อไฟล์คลิปช่องสุดท้าย การค้นรหัสในข้อความดิบไม่ใช่การระบุแถว ต้องจับคู่จากช่องของแถวเดียวกันและล็อกชีท + แท็บ
- ค่าที่ "ตรงกับชีทจริง" ในแคชไม่ได้พิสูจน์ว่าหยิบถูกแถว ต้องอ่านสดตามตัวตนของแถว
- คำอธิบายเคสในมติที่อนุญาตการเขียน ต้องมาจากแถวสด ไม่ใช่การสรุปของเธรดหลัก
