## สรุปสั้น (Executive Summary)

ระหว่างเตรียมงานอัดคลิปต่อ ผมสั่ง `ps aux` ต่อท่อเข้า `grep keep_sessions_warm` เพื่อดูว่าตัวรักษาการเข้าระบบเดินอยู่ไหม
ได้ผลว่าง จึงบอกเจ้าของงานว่า *"ตอนนี้ไม่ได้รันอยู่"* แล้วเปิดตัวใหม่ขึ้นมา
ของจริงคือมันรันอยู่แล้วตั้งแต่ 8/Sep เวลา 22:19:39 น. คือเปิดไว้ตั้งแต่หลังเจ้าของงานล็อกอินให้
พิสูจน์ได้ในภายหลังด้วย `ps -o pid,lstart,command -p <pid>` ซึ่งเห็นทั้ง 2 โปรเซสพร้อมเวลาเริ่มชัดเจน
สาเหตุคือผมตีความผลว่างของคำสั่งหนึ่งว่าเป็นคำตอบว่า "ไม่มี" ทั้งที่ในสภาพแวดล้อมนี้มันแปลว่า "คำสั่งนั้นมองไม่เห็นรายการโปรเซส"
ซึ่งเป็นคนละความหมายกันโดยสิ้นเชิง ผลคือมีตัวรักษารันซ้อนกัน 2 ตัว (อ่านอย่างเดียว ไม่เป็นอันตราย) และเจ้าของงานได้รับข้อมูลที่ไม่จริง
แก้ด้วยการแจ้งเจ้าของงานทันทีที่รู้ตัว และไม่ฆ่าโปรเซสของอีกเซสชันทิ้ง

## 1. ปัญหา (Problem Statement)

- คำสั่งที่ใช้ตรวจ คือ `ps aux` ต่อท่อเข้า `grep -E 'keep_sessions_warm|node .*capture'` แล้วต่อ `grep -v grep`
  ผลที่ได้คือ **ไม่มีบรรทัดใดเลย**
- ผมสรุปจากผลว่างนั้นว่าไม่มีโปรเซส แล้วพิมพ์บอกเจ้าของงานว่า
  *"เปิดตัวรักษา session ก่อน (ตอนนี้ไม่ได้รันอยู่ และเป็นบทเรียนข้อ 11)"* แล้วเปิดตัวใหม่
- ต่อมาเมื่อรันด่านก่อนอัดที่เพิ่งสร้าง ซึ่งใช้ `pgrep -f keep_sessions_warm.js` มันรายงานว่าพบ **2 โปรเซส**
- ตรวจซ้ำด้วยคำสั่งที่ระบุหมายเลขโปรเซสตรงๆ ได้ผลชัดเจน

```
  PID STARTED                      COMMAND
 2094 Tue Sep  8 22:19:39 2026     node out/review-vdo-integration/keep_sessions_warm.js
27483 Tue Sep  8 23:50:08 2026     node out/review-vdo-integration/keep_sessions_warm.js
```

  โปรเซส 2094 คือตัวที่มีอยู่แล้ว เริ่มเมื่อ 22:19:39 น. · โปรเซส 27483 คือตัวที่ผมเปิดเพิ่มเมื่อ 23:50:08 น.
  ข้อความว่า "ไม่ได้รันอยู่" จึงเป็นเท็จตั้งแต่วินาทีที่พิมพ์

**สิ่งที่ควรจะเป็น:** ก่อนสรุปว่า "ไม่มี" จากผลว่าง ต้องพิสูจน์ก่อนว่าเครื่องมือที่ใช้ถาม **มองเห็นสิ่งที่กำลังถามหาได้จริง**
ตามกฎข้อแรกสุดของ repo ที่ว่ามีได้ 3 สถานะเท่านั้น คือตรวจแล้ว · ยังไม่ตรวจ · ตรวจไม่ได้
กรณีนี้สถานะจริงคือ **ตรวจไม่ได้** แต่ถูกรายงานออกไปเป็น **ตรวจแล้วและไม่มี**

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

กลไกที่ทำให้พลาดคือ **การใช้คำสั่งที่ตอบได้แค่ 2 อย่าง กับคำถามที่มีคำตอบได้ 3 อย่าง**

`grep` บนผลของ `ps aux` ตอบได้แค่ "เจอ" กับ "ไม่เจอ" มันไม่มีวิธีตอบว่า "ฉันไม่ได้รับรายการโปรเซสมาให้ค้นเลย"
เมื่อคำสั่งชั้นแรกมองไม่เห็นสิ่งที่ควรเห็น ผลลัพธ์ที่ออกมาจากปลายท่อจึงหน้าตาเหมือนกับกรณีที่ไม่มีโปรเซสจริงทุกประการ
นี่คือรูปเดียวกับที่รายงาน #0003 อธิบายไว้ว่า ค่าที่อ่านไม่ได้ห้ามเดินเข้าการเปรียบเทียบ เพราะ "อ่านไม่ได้" กับ "ไม่มี"
จะกลายเป็นคำตอบเดียวกันตั้งแต่ระดับชนิดข้อมูล และรูปเดียวกับ #0005 ที่ว่าการ์ดต้องมีสถานะที่ 3 คือ "ตรวจไม่ได้"

สิ่งที่ทำให้ผลว่างนั้นดูน่าเชื่อเป็นพิเศษคือ **มันเข้ากับเรื่องที่ผมกำลังเขียนอยู่พอดี**
ในนาทีนั้นผมกำลังเขียนรายงาน #0026 ซึ่งมีใจความว่า "ตัวรักษาถูกปิดไประหว่างอัด"
ผลว่างจึงอ่านเหมือนหลักฐานยืนยันเรื่องที่กำลังเล่าอยู่ แทนที่จะอ่านเหมือนสิ่งที่ต้องตรวจซ้ำ
ทั้งที่กติกาข้อ 4 ที่ตกผลึกไว้เองในเอกสารแผนงานเขียนว่า *ผลลัพธ์ที่เข้ากับเรื่องที่เชื่ออยู่แล้วพอดี คือเหตุให้ตรวจซ้ำ ไม่ใช่เหตุให้ผ่าน*

### 5 Whys

1. **ทำไมถึงบอกเจ้าของงานว่าตัวรักษาไม่ได้รันอยู่?** — เพราะคำสั่งที่ใช้ตรวจคืนผลว่าง
2. **ทำไมผลว่างถึงถูกอ่านว่า "ไม่มีโปรเซส"?** — เพราะ `grep` ที่ไม่เจออะไร กับ `grep` ที่ไม่ได้รับข้อมูลมาให้ค้น ให้ผลลัพธ์หน้าตาเหมือนกันเป๊ะ
3. **ทำไมถึงไม่รู้ว่าคำสั่งนั้นมองไม่เห็นรายการโปรเซส?** — เพราะไม่เคยทดสอบว่าคำสั่งนั้นเห็นอะไรได้บ้างในสภาพแวดล้อมนี้ ใช้เพราะเป็นคำสั่งที่คุ้นเคยจากที่อื่น
4. **ทำไมถึงไม่ตรวจซ้ำก่อนพูด?** — เพราะผลว่างเข้ากับเรื่องที่กำลังเขียนอยู่พอดี จึงไม่รู้สึกว่าต้องตรวจอะไรเพิ่ม
5. **ทำไมข้อความที่ยังไม่ผ่านการตรวจถึงออกไปถึงเจ้าของงานได้?** — **เพราะประโยคนั้นถูกเขียนปนอยู่ในรายงานความคืบหน้าปกติ ซึ่งเป็นบริบทที่ทุกประโยครอบข้างเป็นเรื่องที่ตรวจแล้ว มันจึงได้รับความน่าเชื่อถือจากเพื่อนบ้านโดยที่ตัวเองไม่เคยถูกตรวจ** — นี่คือ root cause จริง และเป็นข้อเดียวกับที่รายงาน #0004 สรุปไว้แล้วว่าห้ามวางข้อความที่ยังไม่ได้วัดไว้ย่อหน้าเดียวกับข้อความที่ตรวจแล้ว

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- **กฎข้อแรกสุดของ repo** ครอบเรื่องนี้ตรงตัว แต่เป็นข้อความในเอกสาร ไม่มีกลไกบังคับ ณ จุดที่พิมพ์
- **บทเรียนจาก #0004** เขียนไว้แล้วว่าข้อความประเภทนี้ยืมความน่าเชื่อถือจากเพื่อนบ้าน — แต่รอบนั้นตัวอย่างเป็นข้อความ "ข้อจำกัด" ท้ายรายงาน จึงไม่ถูกนึกถึงเมื่อประโยคที่มีปัญหาอยู่กลางย่อหน้าความคืบหน้า
- **ด่านก่อนอัดที่ผมเพิ่งเขียนเอง** ใช้ `pgrep` ซึ่งมองเห็นโปรเซสได้จริง และมีสถานะที่ 3 คือ "ตรวจไม่ได้" อยู่แล้ว — **มันคือสิ่งที่จับความผิดพลาดนี้ได้ในที่สุด** แต่มันถูกเขียนขึ้น *หลัง* ข้อความที่ผิดถูกส่งไปแล้ว

## 5. แนวทางการแก้ไข (Fix)

- **แจ้งเจ้าของงานทันทีที่รู้ตัว** ว่าข้อความก่อนหน้าผิด พร้อมของจริงและเวลาเริ่มของโปรเซสทั้งสอง — ไม่แก้เงียบ
- **ไม่ฆ่าโปรเซสของอีกเซสชัน** ถึงจะเป็นตัวซ้ำ เพราะเป็นของที่เซสชันอื่นเปิดไว้ และการฆ่าของที่คนอื่นเปิดโดยอ้างเหตุผลเรื่องภาระเครื่อง
  เป็นคลาสเดียวกับที่รายงาน #0023 และ #0026 บันทึกไว้แล้วว่าห้ามทำ · ทั้งคู่เป็นโปรเซสอ่านอย่างเดียว การรันซ้อนจึงไม่เป็นอันตราย
- **จดแถวหนี้ทันทีในเทิร์นที่รู้ตัว** ก่อนเขียนรายงานฉบับนี้

**ยืนยันแล้วด้วย:** คำสั่งที่ระบุหมายเลขโปรเซสตรงๆ ซึ่งเห็นทั้งสองตัวพร้อมเวลาเริ่ม และผลของด่านก่อนอัดที่รายงานว่าพบ 2 โปรเซส

```
[PASS] keep-warm loop running — keep-warm running (pid 2094, 27483)
```

· ถามสถานะโปรเซสด้วยคำสั่งที่มีรหัสจบแยกความหมายได้ อย่า `ps` ต่อท่อ `grep` ซึ่งยุบ "มองไม่เห็น" กับ "ไม่มี" เข้าเป็นผลลัพธ์เดียวกัน

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** เครื่องมือที่ผมเพิ่งเขียนเองจับได้ คือด่านก่อนอัดที่ใช้ `pgrep` แล้วพิมพ์หมายเลขโปรเซสออกมา
  ตัวเลข 2 ตัวในบรรทัดนั้นคือสิ่งที่ขัดกับสิ่งที่ผมเพิ่งพูดไป
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** ประมาณ 20 นาทีหลังพิมพ์ข้อความที่ผิด
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** ถ้าถามด้วย `pgrep` ตั้งแต่แรก จะได้คำตอบที่ถูกทันทีในคำสั่งเดียว
  และการที่ด่านพิมพ์ **หมายเลขโปรเซสจริง** ไม่ใช่แค่คำว่าผ่าน คือสิ่งที่ทำให้ความขัดแย้งมองเห็นได้ — ตรงกับบทเรียนของ #0006 ที่ว่าเครื่องหมายถูกเปล่าๆ ปิดบังของที่ผิดได้

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- เครื่องมือที่เขียนขึ้นเพื่อป้องกันความผิดพลาดของเมื่อวาน จับความผิดพลาดของวันนี้ได้ภายในไม่กี่นาทีหลังเขียนเสร็จ
- แจ้งเจ้าของงานทันทีที่รู้ตัว ไม่แก้เงียบ และไม่ลดทอนว่าเป็นเรื่องเล็ก
- ไม่ฆ่าโปรเซสของอีกเซสชันเพื่อ "ทำให้เรียบร้อย" ซึ่งเป็นสิ่งที่รายงานก่อนหน้าห้ามไว้แล้ว

### สิ่งที่ต้องปรับปรุง
- ความผิดพลาดนี้เกิดขึ้น **ในระหว่างที่กำลังเขียนรายงานเรื่องการไม่ตรวจสอบ** ซึ่งแสดงว่าการรู้กฎกับการใช้กฎเป็นคนละเรื่องกันจริงๆ
- ผลว่างเข้ากับเรื่องที่กำลังเล่าอยู่พอดี และผมใช้มันเป็นหลักฐานทันทีแทนที่จะสงสัยมัน ซึ่งเป็นกติกาข้อ 4 ที่เขียนไว้เองในเอกสารแผนงานไม่กี่ชั่วโมงก่อนหน้า
- คำสั่งที่คุ้นเคยจากสภาพแวดล้อมอื่น ถูกใช้โดยไม่ทดสอบว่ามันเห็นอะไรในสภาพแวดล้อมนี้
