## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

ตัวเขียนตรวจเพียงว่า "ค่าที่เขียนลงไปอ่านกลับมาตรง" ซึ่งเป็นการตรวจของปลายทางที่เขียน ไม่ใช่การตรวจว่าแถวทั้งแถวยังสอดคล้องกัน ·
ผลคาดหวังเปลี่ยนเรื่องที่เคสตรวจ (จากการเรียก API เป็นหน้าจอ · จากปุ่มปิดใช้งานเป็นไม่แสดงปุ่ม) แต่ขั้นตอนและชื่อเคสยังเป็นของเดิม

### 5 Whys

1. ทำไมเคสขัดกันเอง — เพราะเราแก้ผลคาดหวังแต่ไม่ได้แก้ชื่อเคสและขั้นตอนที่อ้างวิธีตรวจเดิม
2. ทำไมไม่ได้แก้ — เพราะงานถูกนิยามเป็น "แก้ผลคาดหวังที่ล้าสมัย" และตัวเขียนรับเฉพาะคอลัมน์ผลคาดหวัง
3. ทำไมตัวเขียนไม่รู้ว่าขัด — เพราะด่านของมันคือ read-back ซึ่งวัดแค่ว่าเซลล์ที่เขียนมีค่าที่ตั้งใจ ไม่ได้อ่านช่องอื่นในแถว
4. ทำไม `readback_ok: true` ถูกอ่านเป็น "เขียนเสร็จเรียบร้อย" — เพราะไม่มีใครถามว่าด่านนี้วัดอะไรและไม่ได้วัดอะไร (คลาสเดียวกับ #0080 ที่ตัวตรวจวัดน้อยกว่าที่อ้าง)
5. ทำไมบันทึกสถานะไม่บอกว่าเราทำให้ขัด — เพราะความขัดถูกจดตอนเห็นอาการ โดยไม่ย้อนดูว่าแถวนั้นเพิ่งถูกเราเขียน

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- กฎเหล็ก "ข้อความขัดกันเอง = ถามก่อนแก้" ใช้กับเคสที่ขัดอยู่ก่อน แต่ไม่มีขั้นตอนใดตรวจว่า **การเขียนของเราเอง** สร้างความขัดใหม่
- read-back ของตัวเขียนครอบเฉพาะเซลล์เป้าหมาย
- เลน CatchAI จับได้ แต่เป็นชั้นท้ายรอบ หลังเขียนชีทส่งมอบไปแล้ว

## 4. ผลกระทบ (Impact)

- ชีทส่งมอบไฟล์ `(ALL)` มี 2 แถวที่ขัดกันเอง: TC003 แถว 32 (Integration) ติดผล "ผ่าน" อยู่ · TC005 แถว 6 (Unit)

- ไม่มีข้อมูลสูญหาย ค่าเดิมยังอยู่ใน snapshot ก่อนเขียน

## 5. แนวทางการแก้ไข (Fix)

- **ยังไม่ได้แก้ชีท** — รอเจ้าของงานเลือกระหว่าง ปรับชื่อเคสและขั้นตอนให้ตรงกับผลคาดหวังใหม่ หรือคืนผลคาดหวังเดิมจาก snapshot · ทั้ง 2 แถว
- ผล "ผ่าน" ของ TC003 แถว 32 ต้องถูกตรวจเทียบกับข้อความที่ไม่ขัดแล้วก่อน จึงจะยืนเป็นผ่านได้ (กฎเหล็กเดียวกัน)
- เอกสารประกอบเคส `Profile_TC_009` ต้องแก้ให้ตรงกับ E32 จริง (4 ข้อ) หรือกลับกัน ตามที่เจ้าของงานเลือก

**ยืนยันแล้วด้วย:** บรรทัด log `written … TC003 … E32 … readback_ok:true` ของตัวเขียน · ค่า C32/D32/E32/F32 ที่เธรดหลักอ่านสด · snapshot หลังเขียนของ `Search_TC_003` (TC005 แถว 6)

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

1. **ตัวเขียนผลคาดหวังต้องเทียบช่องอื่นในแถวเดียวกัน (ชื่อเคส · ขั้นตอน) กับข้อความใหม่ และปฏิเสธเมื่อขั้นตอนยังอ้างหน้าจอหรือวิธีตรวจที่ข้อความใหม่ตัดออก** — ข้อเสนอ ยังไม่ได้สร้าง
2. **บันทึกสถานะที่จดเคสขัดกัน ต้องระบุว่าใครทำให้ขัด** — อ่านประวัติการเขียนของแถวนั้นก่อนจด
3. ผล read-back ต้องรายงานพร้อมขอบเขตที่วัด ("เซลล์เป้าหมาย 1 ช่อง") ไม่ใช่เครื่องหมายผ่านเปล่าๆ

**กฎที่เพิ่มจากเหตุนี้:** ไม่มีกฎใหม่ในเครื่องมือรอบนี้ เพราะมาตรการข้อ 1 ยังเป็นข้อเสนอรออนุมัติ · หลักที่ใช้ทันที: *การแก้ข้อความช่องหนึ่งของเคส ต้องอ่านทั้งแถวก่อนเขียน และความขัดที่เกิดจากการเขียนของเรา ต้องถามเจ้าของงานก่อน ห้ามจดเป็นความขัดที่มีอยู่เดิม*
