## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

กติกา "intent ก่อนทุกการเขียน" ถูกผูกกับคำสั่งเขียนที่สคริปต์เรียกเอง (`T.ledger(...)` ก่อน `put(...)` และ `onceGuard()`) แต่การเขียนครั้งนี้ไม่ได้มาจากคำสั่งของสคริปต์ มันมาจากโค้ดของแอปเองที่ทำงานเมื่อเปิดหน้า สคริปต์มองการเปิดหน้าเป็นการอ่าน จึงไม่มีอะไรกั้น

### 5 Whys

1. **ทำไมมีการเขียนลงระบบโดยไม่มีบรรทัด intent?** — เพราะเมื่อ `prep2` เปิดหน้าเรียนของคอร์สที่ 2 ตัวอ่าน ebook ของแอปส่งความคืบหน้า 100% เองทันที (23:51:44.167Z) ก่อนที่สคริปต์จะถึงบรรทัดเขียน intent ของ BI3M
2. **ทำไมสคริปต์เปิดหน้าเรียนโดยไม่คิดว่าเป็นการเขียน?** — เพราะสคริปต์ถือว่าการเปิดหน้าเป็นการอ่าน และใส่ intent เฉพาะหน้าคำสั่ง `PUT` ที่ตัวเองเรียก (โค้ดปัจจุบันที่ `b001i_run.js:187` มีคอมเมนต์ยอมรับว่าการเปิดหน้านี้ทำให้ ebook เขียนเอง)
3. **ทำไมกติกาถึงครอบแค่คำสั่งของสคริปต์?** — เพราะมาตรการจาก #0123 คือเติมการเรียก `ledger()` ก่อน "ทุกจุดเขียนในสคริปต์" ซึ่งนับเฉพาะจุดที่คนเขียนสคริปต์มองเห็น ไม่มีรายการหน้าที่แอปเขียนเองเมื่อเปิด (ตัวอ่าน ebook · เครื่องเล่นวิดีโอ)
4. **ทำไมไม่มีกลไกกั้นการเขียนที่ไม่ได้สั่ง?** — เพราะการบล็อก request ที่ไม่ใช่ GET มีแค่ในโหมดอ่านอย่างเดียว (`vidprobe` ที่ `b001i_run.js:88–89` และ keepalive ที่ `b001i_keepalive.js:23`) โหมดที่มีการเขียน (`prep2`) เปิดให้ทุก request ผ่าน ไม่ใช่เฉพาะรายการที่มี intent แล้ว
5. **ทำไมด่านการเขียนถึงออกแบบให้เปิดทั้ง context?** — เพราะด่านอยู่ที่ระดับคำสั่งของสคริปต์ (สิ่งที่สคริปต์ตั้งใจทำ) ไม่ได้อยู่ที่ระดับ network (สิ่งที่ออกจากเบราว์เซอร์จริง) — root cause: ไม่มีด่าน default-deny ที่ปล่อย request เขียนเฉพาะเมื่อมีบรรทัด intent ของรายการนั้นแล้ว การเขียนที่แอปทำเองจึงหลุดได้ทุกเคส ไม่ใช่แค่ ebook

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- `ledger()` + `onceGuard()` ในสคริปต์ (มาตรการจาก #0123): ครอบเฉพาะคำสั่งที่สคริปต์เรียก การเขียนนี้ไม่ผ่านคำสั่งนั้น
- ด่าน GUARD "new badge current 3, expected 2": จับได้จริง แต่หลังการเขียน 2 วินาที (23:51:46.156Z)
- การบล็อก non-GET: มีแค่ในโหมดอ่านอย่างเดียว ไม่มีในโหมดเขียน
- `write_guard.js`: ยังไม่ได้ตรวจในรายงานนี้ว่าครอบ request ที่แอปส่งเองในหน้าที่ Playwright เปิดหรือไม่ (เลนรันด้วย `HANDS_OFF_EXCEPTION` ตาม `b001i_progress.jsonl` บรรทัด 18)

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

มาตรการจาก #0123 (เติม `ledger()` ก่อนทุกจุดเขียนของสคริปต์) ไม่พอ เพราะเหตุนี้ไม่ผ่านจุดเขียนของสคริปต์ ชั้นใหม่ต้องอยู่ที่ network

| # | มาตรการ | ชนิด | สถานะ |
|---|---------|------|-------|
| P1 | `prep2` ไม่เปิดหน้าเรียนอีก (`b001i_run.js:187–188`) | แก้สคริปต์ของเคส | ทำแล้ว (เฉพาะสคริปต์นี้) |
| P2 | เขียน intent ก่อนการเดินหน้าเรียนใน take (`BI4N`, `b001i_run.js:250`) | แก้สคริปต์ของเคส | ทำแล้ว (เฉพาะสคริปต์นี้) |
| P3 | ด่าน default-deny ใน `newCtx` ของ lib เลน: ทุก context บล็อก request ที่ไม่ใช่ GET/HEAD/OPTIONS เป็นค่าเริ่มต้น ปล่อยเฉพาะ method+path ที่สคริปต์ประกาศผ่าน `allowWrite(writeId)` ซึ่งตรวจว่ามี intent ของ writeId นั้นใน ledger แล้ว 1 บรรทัด · request ที่ถูกบล็อกบันทึกลง log | เครื่องมือ (lib ของเลน / `capture/`) | ยังไม่ได้ทำ |
| P4 | เทสต์คู่กับ P3 ที่รู้คำตอบ: หน้าที่แอปเขียนเองเมื่อเปิด ต้องถูกบล็อก 1 · request ที่มี intent ต้องผ่าน 1 | เทส | ยังไม่ได้ทำ |

**กฎที่เพิ่มจากเหตุนี้:** ไม่มีกฎข้อความใหม่ — กฎ "intent ก่อนทุกการเขียน" มีอยู่แล้ว ชั้นที่ขาดคือด่านในโค้ดระดับ network (P3/P4 ยังไม่ได้ทำ ต้องให้เจ้าของงานตัดสินก่อน เพราะแก้ lib ที่หลายเลนใช้ร่วมกัน)
