## สรุปสั้น (Executive Summary)

เวลา 08:26 เธรดหลักถามเจ้าของงานผ่าน popup ว่าจะลดลำดับ CPU ของ runner (renice +10) แทนการหยุดงาน และระบุว่า "คืนค่าด้วย renice 0 หลังอัดเสร็จ" เจ้าของงานอนุมัติ พออัดเสร็จเวลา 08:37 คำสั่ง `renice -n 0` คืนรหัส 0 แต่ค่า NI ยังเป็น 10 เพราะบน macOS `-n` คือการบวกเพิ่ม ส่วน `renice 0 -p` ขึ้น `setpriority: Permission denied` เพราะผู้ใช้ปกติลดค่า nice ไม่ได้ ตอนนี้โปรเซสหลักของ runner 2 ชุด (runsvc · caffeinate · Runner.Listener รวม 6 ตัว) ยังค้างที่ nice 10 และงาน CI ถัดไปจะสืบค่านี้ไปด้วย คืนค่าได้ด้วย sudo ของเจ้าของงาน หรือรีสตาร์ต service ตอนที่ไม่มีงานรัน

## 1. ปัญหา (Problem Statement)

- **สิ่งที่ควรเกิด:** หลังอัดเสร็จ runner กลับมาที่ nice 0 ตามเงื่อนไขที่เจ้าของงานอนุมัติ
- **สิ่งที่เกิดจริง:** 6 โปรเซสที่ยังมีชีวิตค้างที่ nice 10 · อีก 17 จาก 23 ตัวเป็นโปรเซสของงานที่จบไปแล้ว
- **ขอบเขต:** runner ของอีกโปรเจกต์บนเครื่องเจ้าของงาน ไม่มีการหยุดหรือลบงานใด

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไม runner ยังค้างที่ nice 10?** — เพราะคำสั่งคืนค่าทั้ง 2 แบบไม่เปลี่ยนค่า
2. **ทำไมคำสั่งคืนค่าไม่ได้ผล?** — `renice -n 0` บน macOS เป็นการบวกเพิ่ม 0 · `renice 0` ต้องลดค่า nice ซึ่ง macOS อนุญาตเฉพาะ root
3. **ทำไมไม่รู้ตั้งแต่ก่อนขออนุมัติ?** — เพราะเขียนทางย้อนกลับในคำถามจากความเข้าใจทั่วไปของ Linux/bash และไม่ได้รันทางย้อนกลับกับเป้าทดสอบก่อนถาม
4. **ทำไมไม่มีขั้นใดบังคับให้ทดสอบทางย้อนกลับ?** — กฎเดิม (CLAUDE.md §10 "ขออนุมัติเขียน/ลบต้องอ่านสถานะสดทุกรายการ") ครอบการอ่านสถานะปัจจุบัน แต่ไม่ครอบคำอ้างว่า "ย้อนกลับได้"
5. **ทำไมคลาสนี้ผ่านได้?** — (root cause) คำมั่นเรื่องการย้อนกลับถูกใช้เป็นเหตุผลให้อนุมัติ แต่ถือเป็นข้อความอิสระที่ไม่ต้องมีหลักฐาน เจ้าของงานจึงตัดสินใจบนข้อสมมติที่ไม่ได้ตรวจ

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- CLAUDE.md §0 (ห้ามพูดสิ่งที่ยังไม่ตรวจ) เป็นกฎตัวหนังสือ ไม่มีตัวตรวจตอนเขียนคำถาม
- `ask-guard` ตรวจว่าค้นบันทึกก่อนถามข้อมูลอ้างอิงหรือยัง ไม่ได้ตรวจเนื้อหาคำมั่นในตัวเลือก
- คำสั่งคืนค่า `renice -n 0` คืนรหัส 0 · ถ้าไม่พิมพ์ NI หลังรันจะรายงานผิดว่าคืนแล้ว (จับได้เพราะพิมพ์ NI ตาม #0140)

## 4. ผลกระทบ (Impact)

- **runner:** 2 ชุดได้ CPU ทีหลังโปรเซสอื่นจนกว่าจะคืนค่า · งาน CI ที่เริ่มหลังจากนี้สืบ nice 10
- **การตัดสินใจ:** เจ้าของงานอนุมัติบนเงื่อนไข "คืนค่าได้" ที่ไม่จริงสำหรับสิทธิ์ของ agent
- **ข้อมูล:** ไม่มีการเขียนหรือหยุดงานใด

## 5. แนวทางการแก้ไข (Fix)

- เจ้าของงานรันคำสั่งเดียว (ต้องใส่รหัสเครื่องเอง): `sudo renice 0 -p <pid ทั้ง 6>` แล้วตรวจ NI = 0
- หรือรีสตาร์ต service ของ runner ตอนที่ไม่มีงานรัน (โปรเซสใหม่เริ่มที่ nice 0) — ห้ามทำตอนมีงาน เพราะจะหยุดงานที่รันอยู่

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

1. **กฎ (บันทึกใน CLAUDE-ARCHIVE):** ตัวเลือกใน popup ที่อ้างว่า "ย้อนกลับได้ด้วย X" ต้องแนบผลของการรัน X กับเป้าทดสอบชนิดเดียวกันด้วยสิทธิ์ของ agent ในเทิร์นนั้น ถ้าย้อนกลับต้องใช้สิทธิ์ของเจ้าของงาน (sudo) ต้องเขียนไว้ในตัวเลือก
2. **ข้อเท็จจริงของเครื่องนี้ที่วัดแล้ว:** บน macOS ผู้ใช้ปกติเพิ่ม nice ได้อย่างเดียว · `renice -n N` เป็นการบวกเพิ่ม (โปรเซสจาก Bash tool เริ่มที่ nice 5 จึงได้ 15)
3. **ชั้นเครื่อง (เสนอ ยังไม่ได้ทำ):** เพิ่มกฎใน `zsh-split-guard` หรือ guard ใหม่ ให้ปฏิเสธ `renice -n <บวก>` เมื่อ euid ไม่ใช่ 0 พร้อมข้อความว่าจะคืนค่าเองไม่ได้ — ต้องได้รับอนุมัติก่อนผูก hook

## 7. การตรวจจับปัญหา (Detection)

- จับได้จากการพิมพ์ NI หลังคำสั่งคืนค่า (นิสัยจาก #0140) ไม่ใช่จากรหัสจบ ซึ่งเป็น 0

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- เก็บรายชื่อ pid ไว้ตั้งแต่ตอนเปลี่ยน ทำให้รู้ขอบเขตที่ต้องคืนค่าได้ครบ
- ตรวจผลด้วยค่า NI จริง ไม่เชื่อรหัสจบ

### สิ่งที่ต้องปรับปรุง
- ทางย้อนกลับเป็นส่วนหนึ่งของคำขออนุมัติ ต้องทดสอบก่อนเสนอเหมือนตัวคำสั่งหลัก
