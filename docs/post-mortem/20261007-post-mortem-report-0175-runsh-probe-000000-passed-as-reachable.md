## สรุปสั้น (Executive Summary)

`ndlp_reachable()` และบรรทัดเช็ค `<DEV_HOST>` ใช้ `"$(curl ... -w '%{http_code}' ... || echo 000)" != "000"`
เมื่อ curl timeout มันพิมพ์ `000` ผ่าน `-w` แล้วจบด้วยรหัส 28 — `|| echo 000` จึงต่ออีกชุดเป็น `000000` ซึ่งไม่เท่ากับ `"000"` สคริปต์จึงบันทึกว่า "NDLP reachable already — not touching any VPN service" และ "dev-ols reachable (HTTP 000000)" ทั้งที่ VPN ทั้งสองตัว Disconnected
แก้ให้ตัดสินจากรหัสจบของ curl (แบบเดียวกับการเช็คกลางรอบที่ทำงานถูกอยู่แล้ว) + เทสที่มีเคสต้องเข้าไม่ได้และเคสต้องเข้าได้
สถานะ: แก้แล้ว เทสเขียว มีผลตั้งแต่การรันครั้งถัดไป

- **อาการที่เห็น:** รอบ OLS-829 (15:16) และ OLS-778 (15:19) ผ่าน gate ก่อนเริ่ม แล้ว session รายงาน `SKIPPED — <DEV_HOST> unreachable (curl timeout)`

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไม run.sh เริ่ม session ทั้งที่เข้า `<DEV_HOST>` ไม่ได้?** — เพราะ gate ได้ค่า `000000` และตัดสินว่าเข้าได้
2. **ทำไมได้ `000000`?** — เพราะ curl พิมพ์ `000` ผ่าน `-w` แม้จะ timeout แล้วจบด้วยรหัสไม่ใช่ 0 ทำให้ `|| echo 000` ต่ออีก `000`
3. **ทำไม `000000` ผ่าน?** — เพราะเทียบสตริงกับ `"000"` แบบเท่ากันทุกตัว ค่าที่ยาวกว่าจึงถือว่า "ไม่ใช่ 000"
4. **ทำไมไม่มีใครเห็น?** — เพราะ log พิมพ์คำว่า "reachable" ไว้หน้าค่า ผู้อ่านเห็นคำว่าผ่านก่อนเห็นค่า และไม่มีเทสของ gate นี้เลย
5. **ทำไมไม่มีเทส?** — เพราะ gate นี้เขียนด้วยรูปแบบที่ตัดสินจากสตริงแทนรหัสจบ และไม่เคยถูกทดสอบกับเคสที่ต้องเข้าไม่ได้ (known-negative) — นี่คือ root cause ของคลาสนี้

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** การเช็คกลางรอบ (`run.sh` ส่วน VPN watchdog) ใช้รหัสจบถูกต้องอยู่แล้ว แต่สองจุดนี้ไม่ได้ใช้ฟังก์ชันเดียวกัน (ละเมิดข้อ "ตัดสินที่โมดูลเดียว" #0003)

## 5. แนวทางการแก้ไข (Fix)

- `ndlp_reachable()` ตัดสินจากรหัสจบของ `curl` โดยตรง
- บรรทัดเช็คขั้น 2: `code="$(curl ... -w "%{http_code}" ...)" || code=000` — ได้ 3 หลักเสมอ
- URL ใช้ `${NDLP_PROBE_URL:-<DEV_HOST>}` เพื่อให้เทสชี้ host ที่รู้คำตอบได้
- หลักฐาน: `test_runsh_probe: 7 passed, 0 failed` บน run.sh ใหม่ · บน run.sh เดิมได้ `2 passed, 5 failed` (เทสจับของเก่าได้จริง)

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** เธรดหลักเห็น session รายงาน unreachable ขัดกับ log ที่บอก reachable จึงส่ง agent (systematic-debugging) ไปสืบ แล้วทำซ้ำเองก่อนรายงาน
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** ตรวจไม่ได้ว่าเริ่มเสียเมื่อไหร่ · วันนี้เกิด 4 ครั้งก่อนถูกจับ
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** เทสข้อ 1–2 เฟลทันทีถ้ารูปแบบเดิมกลับมา

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ทำซ้ำอาการได้ด้วย host ที่ route ไม่ได้ก่อนแก้ และพิสูจน์ว่าเทสเฟลกับโค้ดเก่า

### สิ่งที่ต้องปรับปรุง
- gate ทุกตัวต้องมีเคส known-negative ตั้งแต่วันแรก · คำว่า "ผ่าน" ใน log ต้องมาจากค่าที่วัดได้ ไม่ใช่จาก "ไม่ใช่ค่าที่บอกว่าไม่ผ่าน"
