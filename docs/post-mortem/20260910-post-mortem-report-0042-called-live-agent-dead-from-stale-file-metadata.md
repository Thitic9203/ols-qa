## สรุปสั้น (Executive Summary)

เจ้าของงานสั่งว่าอย่าปล่อยให้ background agent เฟลเงียบ ผมจึงไปวัดว่ามันยังทำงานอยู่ไหม โดยอ่าน
ขนาดไฟล์ด้วย `stat -f %z` และเวลาแก้ไขล่าสุด ทั้งคู่ค้างนิ่ง จึงรายงานว่า **"agent ไม่ได้ทำงานครับ
มันตายตั้งแต่ต้น"** ของจริงคือ agent ทำงานอยู่ตลอดและจบงานสำเร็จในเวลาต่อมา (ใช้เวลารวม 21 นาที
26 tool call) — metadata ของไฟล์นั้นไม่อัปเดตตามเนื้อ ส่วน `wc -c` ที่อ่านไบต์จริงเห็น 1.67 MB
และโตต่อเนื่อง

ซ้ำร้าย ผมเชื่อเลข 143 ไบต์แล้วสั่ง `cat` ทั้งไฟล์ ทั้งที่ผลของเครื่องมือเขียนห้ามไว้ตรงตัวว่า
ห้ามอ่านไฟล์นี้เพราะจะท่วม context — ได้ output 1.6 MB ซึ่งรอดเพราะ harness เซฟลงไฟล์ให้แทนที่จะ
ยัดเข้าบทสนทนา

แก้แล้วด้วยการวัดใหม่ 3 วิธีเทียบกัน แล้วแจ้งเจ้าของงานทันทีว่ารายงานก่อนหน้าผิด ตอนนี้ agent จบงาน
เรียบร้อยและผลของมันถูกนำไปใช้ต่อแล้ว

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

ไฟล์ผลของ background task ถูกเขียนแบบต่อท้ายโดยโปรเซสที่ถือ handle ค้างไว้ ผลคือ **เนื้อไฟล์โตขึ้น
แต่ metadata ของ inode (ขนาดและเวลาแก้ไข) ไม่ถูกรีเฟรชให้ผู้อ่านภายนอกเห็น** ผมใช้ metadata นั้น
เป็นสัญญาณว่ามีชีวิตอยู่ ซึ่งเป็นการวัดคนละอย่างกับคำถามที่ถาม

จุดตัดสินใจที่ผิดคือตอนที่เห็น `stat` กับ mtime ตรงกันแล้วรู้สึกว่า "ยืนยันกันเอง" — ตอนนั้นมันดูถูก
เพราะสำหรับไฟล์ log ทั่วไป ขนาดกับเวลาแก้ไขเดินตามเนื้อจริงเสมอ

### 5 Whys

1. **ทำไมถึงบอกว่า agent ตาย?** — เพราะขนาดไฟล์และเวลาแก้ไขไม่ขยับเลยตลอด 16 นาที
2. **ทำไมถึงเชื่อขนาดกับเวลาแก้ไข?** — เพราะกับไฟล์ที่ถูกเขียนต่อท้าย ปกติทั้งสองค่าจะเดินตามเนื้อไฟล์
3. **ทำไมถึงไม่ตรวจด้วยวิธีที่สองก่อนพูด?** — เพราะคิดว่าตรวจไปแล้วสองอย่าง คือขนาดกับเวลา และทั้งคู่
   ให้คำตอบเดียวกัน
4. **ทำไมสองอย่างนั้นถึงถูกนับเป็นสองการตรวจ?** — เพราะผมนับจาก "จำนวนคำสั่งที่รัน" ไม่ได้นับจาก
   "จำนวนแหล่งข้อมูลที่แตกต่างกัน" ทั้ง `stat -f %z` และ `stat -f %m` อ่าน inode ตัวเดียวกัน
5. **root cause:** ผมถือว่า **สองมุมมองของแหล่งข้อมูลเดียวกัน = การยืนยันข้ามแหล่ง** ทั้งที่มันคือ
   การอ่านแหล่งเดิมสองครั้ง การยืนยันจริงต้องมาจากกลไกที่ต่างกัน ซึ่งในกรณีนี้คือการ **อ่านไบต์จริง**
   (`wc -c`) ไม่ใช่การถาม metadata

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**

| ชั้น | ควรจับได้ไหม | ทำไมไม่จับ |
|---|---|---|
| กฎข้อแรกของ repo (ห้ามพูดสิ่งที่ยังไม่ตรวจ) | ควร | ผมเชื่อว่า**ตรวจแล้ว** เพราะมีตัวเลขในมือ กฎนี้กันการพูดโดยไม่ตรวจ แต่ไม่ได้กันการตรวจผิดคำถาม |
| บทเรียนรายงาน #0016 | ควร | เขียนไว้ในบริบท "บรรทัดสุดท้ายที่โปรเซสพิมพ์" ผมไม่ได้เชื่อมโยงว่า metadata ของไฟล์ก็เป็นของประเภทเดียวกัน |
| บทเรียนรายงาน #0002 ("ชั้นที่พึ่งข้อสมมติเดียวกัน นับเป็นชั้นเดียว") | ควร | ตอนนั้นเขียนไว้สำหรับชุดเทสต์กับ CI ไม่ได้เขียนให้ครอบการวัดสถานะทั่วไป |
| คำเตือนของเครื่องมือที่ห้ามอ่านไฟล์นี้ | ควรกันรอบสอง | ผมตีความว่าคำเตือนตั้งอยู่บนสมมติฐานว่าไฟล์ใหญ่ พอตัวเลขบอกว่า 143 ไบต์ จึงคิดว่าเงื่อนไขไม่ตรงแล้ว |

## 5. แนวทางการแก้ไข (Fix)

- วัดใหม่ด้วย 3 วิธีเทียบกัน (`stat -f %z` · `ls -l` · `wc -c`) แล้ววัดการเติบโตซ้ำอีก 15 วินาที
  จึงเห็นว่า metadata ขัดกับเนื้อไฟล์
- แจ้งเจ้าของงานทันทีในข้อความถัดไปว่ารายงานก่อนหน้าผิด พร้อมตารางตัวเลขทั้งหมดและเหตุผล
  ไม่แก้เงียบ
- จดแถว `PM-2026-09-10-01` ใน `docs/post-mortem/PENDING.md` ในเทิร์นเดียวกับที่รู้ตัว

**ยืนยันแล้วด้วย:**

```
stat -f %z : 143
wc -c      : 1677334
ls -l      : 143
จำนวนบรรทัด: 182
mtime      : 23:43:25 = 1064 วินาทีที่แล้ว | ตอนนี้ 00:01:09
ก่อน 1677334 → หลัง 1685493  โตขึ้น = ยังเขียนอยู่
```

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** ผมจับได้เอง แต่ **จับได้โดยบังเอิญ** — เพราะสั่ง `cat` แล้วได้ 1.6 MB
  ซึ่งขัดกับเลข 143 อย่างชัดเจน ถ้าไม่ได้สั่งคำสั่งที่ไม่ควรสั่งตั้งแต่แรก ผมจะไม่รู้เลย
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** ประมาณ 1 นาทีครึ่งนับจากที่รายงานผิด
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** ใช้ `wc -c` ตั้งแต่ครั้งแรก จะไม่มีอะไรให้จับ เพราะจะไม่เกิด ·
  ข้อนี้ไม่ต้องรอให้มีตัวจับ เพราะเป็นการเลือกเครื่องมือวัดให้ตรงคำถามตั้งแต่ต้น

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- แก้ในแชททันทีที่รู้ตัว ไม่แก้เงียบ และแสดงตัวเลขทั้งหมดให้เจ้าของงานตรวจเองได้
- ไม่ไปแตะ agent เลยตลอดกระบวนการ ทำให้มันจบงานได้ตามปกติ และผลของมันใช้แก้ปัญหาจริงได้
- จดหนี้ post-mortem ในเทิร์นเดียวกับที่รู้ตัว ไม่รอจนจบเซสชัน

### สิ่งที่ต้องปรับปรุง
- ถ้าคำถามคือ "มันยังเขียนอยู่ไหม" เครื่องมือที่ตรงคำถามคือการอ่านไบต์ ไม่ใช่การถาม metadata
- ค่าสองค่าที่ตรงกันแต่มาจากแหล่งเดียวกัน ให้ความมั่นใจแบบผิดๆ ที่อันตรายกว่าค่าเดียว เพราะรู้สึกว่า
  ยืนยันแล้ว
- คำสั่งห้ามของเครื่องมือควรถูกอ่านว่าเป็นข้อจำกัด ไม่ใช่ข้อเสนอที่รอเงื่อนไขมาหักล้าง
