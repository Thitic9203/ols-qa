## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

จุดตัดสินใจที่ผิดคือ 15:34:22 — ถือว่า "เจ้าของงานอนุมัติร่างแล้ว" = ส่งร่างนั้นได้ทันที ทั้งที่ร่างเป็นภาพของ ticket ณ 14:33:31 ซึ่งอายุ 61 นาที ตอนนั้นดูถูกเพราะเพิ่งทำ sweep ครบหลายแหล่ง และไม่มีขั้นใดใน workflow ที่ถามว่าแหล่งเปลี่ยนไปหรือยัง

### 5 Whys

1. **ทำไมรีวิวที่ส่งมีข้อเสนอที่อิง BR ที่ถูกขีดฆ่า?** — เพราะสร้างจาก description ที่ดึงตอน 14:33:31 ก่อน PO แก้ 15:29:56
2. **ทำไมไม่เห็นการแก้ก่อนส่ง?** — เพราะไม่ได้ดึง ticket ซ้ำก่อน POST · sweep รอบ 15:11 ดึงแค่ ticket ข้างเคียง ไม่ได้ดึงตัวหลัก
3. **ทำไมไม่ดึงตัวหลักซ้ำ?** — เพราะถือการอนุมัติในแชทเป็นด่านสุดท้าย แล้วส่งร่างที่อนุมัติไปตรงๆ
4. **ทำไม workflow ปล่อยให้ทำแบบนั้น?** — `skills/tc-review-workflow/SKILL.md:212-240` (Step 5) มีแค่ read-back หลังส่ง ไม่มีด่านก่อนส่งที่เทียบ `updated` ของ ticket/แท็บ TC กับเวลาที่โหลด (ค้น `updated|fresh|re-fetch|stale` ในไฟล์ = 0 จุดที่เกี่ยว) · ข้อ mention `SKILL.md:217` บอกแค่ "ask for the exact id" ไม่ได้บอกว่าต้องเป็น QA Owner ของเอกสาร
5. **ทำไมกฎ #0105 ใน CLAUDE.md ไม่ครอบ?** — กฎเขียนไว้สำหรับ "กระทำการย้อนกลับไม่ได้" และไม่มีเครื่องมือหรือด่านใน workflow ที่บังคับ การส่งข้อความที่แก้ได้ภายหลังจึงไม่ถูกมองว่าเข้าข่าย ทั้งที่คนรับเห็นทันทีที่ส่ง — **root cause:** สัญญาการส่งของ workflow ไม่มีเงื่อนไข "แหล่งต้องยังเป็นฉบับเดียวกับที่รีวิว ณ วินาทีที่ส่ง" และไม่มีแหล่งที่กำหนดตัวคนที่ต้องแท็ก

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- CLAUDE.md §0 (#0105) — เป็นข้อความ ไม่มีชั้นเครื่องบังคับ และผูกกับคำว่า "ย้อนกลับไม่ได้"
- read-back ของ Step 5 — ตรวจปลายทาง/mention/ตัวอักษรตรงกับร่าง ไม่ได้ตรวจว่าร่างยังถูกกับแหล่ง
- ask-guard — ตรวจการถามคำถาม ไม่เกี่ยวกับการส่ง
- memory ของเธรดรีวิว — บันทึก id ที่แท็กในรอบหนึ่งเป็นค่าตายตัว จึงชี้ผิดทางแทนที่จะกัน

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ดึง description ของ ticket คู่กันตอนรีวิวใบถัดไป จึงเห็นการแก้ภายใน 6 นาที
