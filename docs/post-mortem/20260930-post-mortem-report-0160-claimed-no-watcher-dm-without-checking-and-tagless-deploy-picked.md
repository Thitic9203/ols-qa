## สรุปสั้น (Executive Summary)

เมื่อ 30/Sep watcher อัตโนมัติรัน smoke รอบ dev ตั้งแต่ 13:54 ถึง 14:21 น. แต่ไม่ได้สร้างร่างโนติ
ผมจึงเขียนลงคำสั่ง subagent และลงแถว PENDING ว่า watcher "ออกไปเงียบๆ ไม่มี DM และไม่บันทึก deploy" ทั้งที่ยังไม่ได้เปิด DM ดูเลย
ความจริงคือ DM เตือนถูกส่งตอน 14:21:46 น. และ watcher บันทึกประกาศ deploy ที่ไม่มี tag ไว้แล้ว ส่วนที่ผมเช็คคือ id ของประกาศที่มี tag ซึ่งเป็นคนละข้อความกัน
สาเหตุฝั่งเครื่องมือมีดังนี้
- `smoke_watch.py` เลือกประกาศ "ใหม่สุดที่ยังไม่จัดการ" โดยไม่ดูว่ามี tag หรือไม่ ข้อความ 13:53 น. ที่ไม่มี tag จึงชนะประกาศที่มี tag
- watcher ตรวจ tag หลังรันจบ 27 นาทีแล้ว ไม่ได้ตรวจก่อนรัน
- ทุกทางออกหลังได้ lock แจ้งผ่าน `dm()` อย่างเดียวและไม่ print สักบรรทัด log จึงว่างเสมอ

ผมแก้แถว PENDING ภายใน 5 นาทีหลังอ่าน DM กลับมา ร่างโนติสร้างด้วยมือจากรอบเดิม แล้วส่งหลังเจ้าของงานอนุมัติเมื่อ 14:58 น.
โค้ด watcher ยังไม่ได้แก้ เพราะรอคำตอบจากเจ้าของงาน

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys — ส่วนที่ 1 (ข้ออ้าง "ไม่มี DM")

1. **ทำไมผมเขียนว่าไม่มี DM?**
   - เพราะใน log ไม่มีบรรทัดจาก tick 13:54 และในโฟลเดอร์รอบก็ไม่มีไฟล์ร่าง
   - ผมอ่านความว่างนี้ว่าหมายถึง "ไม่ได้ทำอะไรเลย"
2. **ทำไมความว่างของ log ถึงถูกใช้เป็นหลักฐานเรื่อง DM?**
   - เพราะผมไม่ได้ถามก่อนว่า log นี้บันทึก DM ได้หรือเปล่า
   - ความจริงคือ `smoke_watch.py` ไม่ print อะไรเลยหลังได้ lock
   - log จึงว่างทั้งในกรณีที่ส่ง DM และกรณีที่ไม่ได้ส่ง
3. **ทำไมไม่อ่าน DM โดยตรง?**
   - เพราะตอนนั้นผมรีบกันรอบซ้ำ (แก้ state) และรีบส่ง subagent ไปสืบ
   - ผมเขียนสมมติฐานลงคำสั่งในรูป "verbatim facts measured" ทั้งที่ข้อ "no DM" ไม่ได้วัด
4. **ทำไมเรื่อง "ไม่บันทึก deploy" ถึงผิดด้วย?**
   - เพราะผมเช็คเฉพาะ id ที่ผม "คิดว่า" watcher หยิบไป คือประกาศที่มี tag
   - ผมไม่ได้เปิดดูว่ารายการที่ถูกเพิ่มเข้า handled ล่าสุดคือ id ไหน
5. **ทำไมชั้นเดิมจาก #0076 และ #0025 ไม่กัน?** (root cause)
   - มาตรการของ #0076 เป็นกฎให้แนบคำสั่งค้น ขอบเขต และจำนวนก่อน "ส่งต่อเจ้าของงาน"
   - แต่ไม่มีอะไรบังคับตอนที่ข้ออ้างเชิงลบถูกเขียนลง "คำสั่ง subagent" หรือ "แถว PENDING"
   - และกฎไม่มีขั้นให้ถามว่า "แหล่งนี้บันทึกเหตุการณ์ชนิดนี้ได้ไหม"
   - ตัวอย่างที่รู้คำตอบสำหรับแหล่งนี้คือ DM เก่าที่ส่งแน่ๆ แต่ไม่มีใน log

### 5 Whys — ส่วนที่ 2 (watcher)

1. **ทำไมไม่มีร่างโนติ?**
   - เพราะ `version` เป็น None ที่ `:468` จึงเข้าทาง DM เตือนที่ `:469-473`
2. **ทำไม tag เป็น None?**
   - เพราะรอบนี้เริ่มจากประกาศ 13:53 น. ที่ไม่มีลิงก์ (`:416`)
3. **ทำไมเลือกประกาศที่ไม่มีลิงก์?**
   - เพราะ `:391-395` เลือก "ใหม่สุดที่ยังไม่จัดการ"
   - ทีม deploy มักโพสต์ 2 ข้อความต่อ deploy เดียว คือข้อความที่มี tag ก่อน แล้วตามด้วย "Deploy dev done" ที่ไม่มี tag
   - state backup มีรายการ tag = `(no tag link …)` 9 รายการ ตั้งแต่ 10/Sep ถึง 30/Sep
4. **ทำไมไม่หยุดก่อนรัน 27 นาที?**
   - เพราะการตรวจ tag อยู่หลังรัน (`:466`) ทั้งที่รู้ค่า tag ตั้งแต่ `:416`
   - ระหว่างนั้นยัง claim ข้อความที่ไม่มี tag ไปแล้วด้วย ทำให้ประกาศที่มี tag ยังค้างอยู่
5. **ทำไมแบบนี้ยังอยู่ทั้งที่เคยเกิด?** (root cause)
   - 24/Sep เคยเจอคลาสเดียวกัน และแก้ด้วยการเติม state ด้วยมือ
   - note ใน state: "the later "Deploy dev done" (…636868) had none — added by hand 24/Sep"
   - ครั้งนั้นไม่มีการแก้โค้ดและไม่มีเทสต์
   - `smoke/` ไม่มีไฟล์เทสต์ของ `smoke_watch.py` เลย (ls ได้ 0 ไฟล์ `test_smoke_watch*`)
   - `test_notify_guard.py:691` ยังทดสอบว่า start line ที่ไม่มี tag ต้อง "ผ่าน"

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- **SFD (`run_workflow.sh`)**
  - เตือนเฉพาะกรณี rc ≠ 0 หรือถูก kill
  - รอบนี้ rc = 0 จึงไม่เตือน
  - log ว่างก็ไม่ถูกนับเป็นความผิดปกติ
- **notify_guard L5**
  - ทำงานเฉพาะตอนส่งลงช่อง
  - รอบนี้ไม่ได้ไปถึงขั้นนั้น
- **investigation-guard / ask-guard**
  - ไม่ครอบคลุมข้ออ้างเชิงลบที่เขียนลงไฟล์หรือลงคำสั่ง agent
- **กฎ §0**
  - เป็นข้อความที่ต้องอาศัยการจำของผม และไม่มีตัวบังคับ
