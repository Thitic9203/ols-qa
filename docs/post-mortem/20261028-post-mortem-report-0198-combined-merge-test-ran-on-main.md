## สรุปสั้น (Executive Summary)

ก่อน merge PR รอบ 5 (#72–#76, #78, #79) เธรดหลักพิมพ์คำสั่ง shell ยาวเพื่อสร้าง worktree ชั่วคราว merge ทั้ง 7 branch แล้วรันชุดเทสต์ `git worktree add` ล้มเพราะโฟลเดอร์ชื่อเดียวกันค้างอยู่จากคำสั่งครั้งก่อน แต่ขั้นรันเทสต์ต่อด้วย `;` ไม่ใช่ `&&` เทสต์จึงรันในโฟลเดอร์ที่ shell อยู่ (origin/main `c8afad4`) ผล `✅ เขียวครบ 65 ชุด` ถูกรายงานกับเจ้าของงานว่าเป็นผลของ merge รวม เจ้าของงานอนุมัติ merge จากรายงานนั้น ก่อนกด merge เธรดหลักตรวจว่า branch ทั้ง 7 อยู่ใน tree ที่ทดสอบหรือไม่ พบว่ามี 2 จาก 7 จึงหยุด แจ้งเจ้าของงาน รันใหม่ด้วยสคริปต์ที่พิสูจน์ครบ 7 (`a9995b7` เขียว 65 ชุด) แล้วจึง merge

## 1. ปัญหา (Problem Statement)

**สิ่งที่เกิดขึ้น:** ข้อความถึงเจ้าของงาน "เทสต์รวม 7 PR ผ่านครบ 65 ชุดครับ (rc=0, ไม่มี ❌)" ถูกส่งก่อนตรวจว่า tree ที่ทดสอบคืออะไร บรรทัดแรกของ log คือ `merged HEAD c8afad4` ซึ่งเป็น origin/main ไม่ใช่ merge commit
**สิ่งที่ควรจะเป็น:** gate ก่อน merge ต้องวัดผลรวมของทุก branch ที่จะ merge และรายงานต้องแสดงหลักฐานว่า tree นั้นมีครบทุก branch (CLAUDE.md §0 "ตรวจแล้ว ต้องบอกว่าวัดอะไร")

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys
1. ทำไมรายงานว่าเขียวทั้งที่ไม่ได้ทดสอบ merge รวม — เพราะเทสต์รันใน origin/main แล้วเขียว และอ่านแค่บรรทัดท้ายของ log
2. ทำไมเทสต์รันใน origin/main — เพราะ `git worktree add` ล้ม แต่ขั้นรันเทสต์ไม่ได้ผูกกับความสำเร็จของขั้นเตรียม (ต่อด้วย `;`) shell จึงรันต่อในโฟลเดอร์ปัจจุบัน
3. ทำไม `git worktree add` ล้ม — โฟลเดอร์ `.worktrees/tmp-r5-merge-check` ค้างจากคำสั่งครั้งก่อน (merge 3 branch ไว้แล้ว) ที่ไม่มีขั้นลบตัวเอง
4. ทำไมไม่มีอะไรจับก่อนรายงาน — คำสั่งพิมพ์สดทุกครั้ง ไม่มีขั้นพิสูจน์ว่า tree มี branch ครบ และ log เขียนบรรทัด "merged HEAD" แม้ merge ไม่ได้เกิด
5. ทำไมพิมพ์สด — repo ไม่มีเครื่องมือกลางสำหรับ "ทดสอบหลาย branch รวมกัน" จึงเขียนใหม่ทุกรอบ ความถูกต้องขึ้นกับการพิมพ์ครั้งนั้น

ทดสอบสมมติฐานอื่นแล้วตกไป: rtk ไม่ได้กลืนรหัสจบ — `rtk proxy git worktree add <existing>` ได้ `raw_rc=128` และ chain แบบ `&&` หยุดถูกต้อง

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** pre-push และ CI วัดทีละ branch ไม่ได้วัดผลรวม · กฎ §0 เป็นข้อความ ไม่มีเครื่องบังคับ · ชั้นที่จับได้จริงคือการตรวจ ancestor ด้วยมือก่อน merge ซึ่งเป็นนิสัย ไม่ใช่เครื่องมือ

## 4. ผลกระทบ (Impact)

- ไม่มีโค้ดผิดขึ้น main — merge เกิดหลังรันใหม่ที่พิสูจน์ครบ 7 branch แล้ว
- เจ้าของงานได้รับรายงานผิด 1 ครั้งและอนุมัติจากรายงานนั้น (ต้องแจ้งแก้)
- เวลาเพิ่ม 1 รอบของชุดเทสต์

## 5. แนวทางการแก้ไข (Fix)

- ลบ worktree ค้างที่เป็นของเธรดหลักเอง รันใหม่ด้วยสคริปต์ที่หยุดทุกจุดและพิสูจน์ ancestor ก่อนเทสต์
- เพิ่มเครื่องมือกลาง `scripts/test-combined-merge.sh` (spec `docs/sdd/combined-merge-test`) — ปฏิเสธเมื่อโฟลเดอร์มีอยู่แล้ว · หยุดเมื่อ merge ไม่ได้ · พิมพ์ `in-test` ทุก branch และ `combined HEAD … in <worktree>` ก่อนรันเทสต์ · รันเทสต์ในโฟลเดอร์ของตัวเอง · ลบโฟลเดอร์ตัวเองเมื่อจบ

**ยืนยันแล้วด้วย:** `node tools/combined-merge-test/combined_merge.test.js` → `ผ่านครบ 7 ข้อ` (ก่อนมีเครื่องมือ: `❌ 6 failed`) · รอบ 5 จริง: log มี `in-test` 7 บรรทัด + `combined HEAD a9995b7` + `rc=0`

## 7. การตรวจจับปัญหา (Detection)

จับได้โดยเธรดหลักเองก่อนกด merge ด้วย `git merge-base --is-ancestor origin/<branch> HEAD` ของทั้ง 7 branch ใน worktree ที่ทดสอบ (ได้ 2 จาก 7) — ตอนนี้ขั้นนี้อยู่ในเครื่องมือแล้ว ไม่ต้องพึ่งการนึกได้

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ตรวจหลักฐานซ้ำก่อนการกระทำที่ย้อนไม่ได้ (merge) ตาม §0 #0105 และหยุดทันทีที่ไม่ตรง
- แจ้งเจ้าของงานก่อนทำต่อ และไม่ merge จากผลเดิม

### สิ่งที่ต้องปรับปรุง
- อ่านแค่บรรทัดท้ายของ log แล้วรายงาน — บรรทัดสรุปของเครื่องมือไม่ใช่คำตอบจนพิสูจน์ว่าวัดสิ่งเดียวกัน (§0)
- คำสั่งชั่วคราวที่สร้างโฟลเดอร์ต้องลบตัวเองเสมอ
