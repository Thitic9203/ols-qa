## สรุปสั้น (Executive Summary)

งานตามตาราง `ols-session-keepalive` เรียก `session_refresh.js --all` ซึ่งแปลว่า "ยิง refresh ให้ไฟล์ session ทุกใบในเครื่อง" แต่ตัวสคริปต์ส่งโฮสต์ของสภาพแวดล้อมเดียวลงไปเป็นค่าคงที่ (`capture/session_keepalive.sh:31-33`) session ที่ออกโดยสภาพแวดล้อมอื่นจึงถูกส่งไปถาม/ยิง refresh กับเซิร์ฟเวอร์ที่ไม่เคยออก session ใบนั้นให้ ปลายทางตอบปฏิเสธและคุกกี้ของ session นั้นถูกล้างทิ้ง

รากของปัญหาอยู่ในโค้ด ไม่ใช่ในตาราง: ฟังก์ชัน refresh เดิมมีคำตอบของ `/api/auth/get-session` อยู่ในมือแล้ว แต่ไม่เคยอ่านมันก่อนตัดสินใจ จึงยิง `POST /auth/refresh-token` ต่อไม่ว่าปลายทางจะรู้จัก session ใบนั้นหรือไม่

ปัจจุบันแก้แล้วในโค้ด: `recognisedHere()` เป็นประตูที่ยอมให้หมุนเฉพาะ session ที่สภาพแวดล้อมปลายทางรับรองว่าเป็นของตัวเอง และ `stateEnvHost()` / `selectTagsForEnv()` อ่านจากตัว session เองว่าเป็นของสภาพแวดล้อมไหน ทั้งสามฟังก์ชันถูกตรึงด้วย `capture/session_refresh.test.js` ซึ่งรันแล้วเขียวทั้งชุด (`exit=0`) ณ 2026-09-10

## 1. ปัญหา (Problem Statement)

- `capture/session_keepalive.sh:31-33` ตั้งค่าคงที่ `PROD=1`, `OLS=<OLS_HOST>`, `AUTH_API=<AUTH_HOST>` แล้วเรียก `node capture/session_refresh.js --all` — โฮสต์ชุดเดียวถูกใช้กับไฟล์ session ทุกใบในเครื่อง
- รอบที่เริ่ม `2026-09-09 21:06:48` และจบ `2026-09-09 22:32:17` จบด้วย `refresh rc=1` = ไม่มี session ใดถูกต่ออายุเลย (`logs/session-keepalive.log:985` และ `:1085` ของ repo capture bot)
- ในผลสถานะของรอบเดียวกันนั้น มี **13 tag** ที่รายงาน `session rejected by server — needs human login` (นับจาก log บรรทัด 985–1085)
- โค้ดเดิม (`capture/session_refresh.js.bak-preenvguard`) เรียก `/api/auth/get-session` แล้วไม่นำคำตอบมาเป็นเงื่อนไขก่อนยิง `POST /auth/refresh-token`

**สิ่งที่ควรจะเป็น:** งานที่ทำงานกับ session "ทุกใบ" ต้องอ่านก่อนว่าแต่ละใบเป็นของสภาพแวดล้อมไหน แล้วยิงเฉพาะใบที่ปลายทางรับรอง — กฎเดียวกับที่รายงาน #0027 สรุปไว้ว่าค่าที่ผูกกับสภาพแวดล้อมห้ามถูกใช้โดยไม่ตรวจว่าเป็นของ env ไหน คำอธิบายกฎนี้ถูกเขียนกำกับไว้แล้วที่ `capture/session_refresh.js:91-103`

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

`--all` เป็นคำสั่งระดับ "ทุกใบในเครื่อง" แต่โฮสต์ที่ใช้ทำงานเป็นค่าระดับ "สภาพแวดล้อมเดียว" สองระดับนี้ถูกวางไว้ในบรรทัดติดกันโดยไม่มีอะไรเชื่อมว่าใบไหนคู่กับโฮสต์ไหน ตอนเขียนมันดูถูกเพราะรอบก่อนหน้ามีแต่ session ของสภาพแวดล้อมเดียวในเครื่อง ค่าคงที่จึง "ถูก" มาตลอดจนวันที่มี session ของสภาพแวดล้อมอื่นปนเข้ามา

จุดตัดสินใจที่ผิดคือในฟังก์ชัน refresh เอง: คำตอบของ `/api/auth/get-session` ซึ่งบอกได้ทันทีว่าปลายทางรู้จัก session ใบนี้หรือไม่ ถูกดึงมาแล้วไม่ถูกอ่าน โค้ดจึงเดินหน้ายิง refresh ทุกกรณี

### 5 Whys

1. **ทำไม session ตาย?** — เพราะถูกยิง `POST /auth/refresh-token` ไปยังเซิร์ฟเวอร์ที่ไม่ได้ออก session ใบนั้น ปลายทางปฏิเสธและคุกกี้ถูกล้าง
2. **ทำไมถึงยิงไปผิดเซิร์ฟเวอร์?** — เพราะโฮสต์ถูกกำหนดเป็นค่าคงที่ตัวเดียวใน `session_keepalive.sh:31-33` แล้วใช้กับ `--all`
3. **ทำไมค่าคงที่ตัวเดียวถึงใช้กับทุกใบได้?** — เพราะไม่มีขั้นตอนไหนอ่านว่าไฟล์ session แต่ละใบเป็นของสภาพแวดล้อมไหน
4. **ทำไมถึงไม่อ่าน ทั้งที่มีข้อมูลอยู่ในมือ?** — เพราะผลของ `/api/auth/get-session` ถูกใช้เป็นข้อมูลรายงาน ไม่ได้ถูกใช้เป็นเงื่อนไขก่อนลงมือ
5. **ทำไมถึงออกแบบให้เป็นแบบนั้น?** — **root cause:** งานที่ทำงานเป็นชุดถูกเขียนโดยสมมติว่าสมาชิกทุกตัวในชุดเป็นชนิดเดียวกัน แทนที่จะให้แต่ละตัวประกาศตัวเองก่อนถูกกระทำ แก้ที่จุดนี้ปิดทั้งคลาส ไม่ใช่เฉพาะกรณี refresh

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**

- exit code ของงานตามตาราง — จับไม่ได้โดยออกแบบ: `rc=1` แปลว่า "ไม่มีอะไรถูกต่ออายุ" ซึ่งเป็นค่าปกติของคืนที่ session หมดอายุอยู่แล้ว ไม่ได้แยกจาก "ต่ออายุไม่ได้เพราะเรายิงผิดที่"
- log — บันทึกครบ แต่ไม่มีใครอ่านระหว่างรอบ และไม่มีการแจ้งเตือนเมื่อจำนวน `rejected by server` พุ่งขึ้น
- เทสต์ — ก่อนเหตุการณ์ `session_refresh.test.js` ตรึงเรื่อง `resolveAuthApi` (หนี้ #3) ไว้เท่านั้น ไม่มีเทสต์ใดพูดถึงการจับคู่ session กับสภาพแวดล้อม

## 5. แนวทางการแก้ไข (Fix)

- `capture/session_refresh.js:87` — เพิ่ม `recognisedHere(who)` ยอมรับเฉพาะคำตอบที่มี `body.user` เท่านั้น สถานะ 200 ที่ body ว่าง (คำตอบของสภาพแวดล้อมที่ไม่รู้จัก session ใบนี้) ถือว่าไม่ใช่ของเรา
- `capture/session_refresh.js:104`, `:121` — เพิ่ม `stateEnvHost()` และ `selectTagsForEnv()` อ่านจากคุกกี้ที่ผูกกับโฮสต์และรายการ `origins` ในตัวไฟล์ session เอง จึงไม่มีแหล่งความจริงที่สองให้เพี้ยน
- `capture/session_refresh.js:214-221` — ทางเดินสามสถานะ: รับรอง → หมุน · ไม่รับรอง → ไม่ยิงเลย · ตัดสินไม่ได้ → ไม่ยิงเลย และการปฏิเสธไม่ถูกนับเป็นความล้มเหลวของการหมุน เพราะไม่มีอะไรถูกทดสอบ
- ไฟล์เดิมถูกเก็บไว้เป็น `capture/session_refresh.js.bak-preenvguard` เพื่อเทียบย้อนหลัง

**ยืนยันแล้วด้วย:** `node capture/session_refresh.test.js` → ผ่านทั้งชุด `exit=0` เมื่อ 2026-09-10 โดยเคสสุดท้ายอ่านไฟล์ state จริงบนดิสก์ ไม่ใช่ fixture ล้วน และมีเคสชื่อ *"mixed set: only the target environment is selected (the 2026-09-09 failure, inverted)"* ตรึงเหตุการณ์นี้ไว้โดยตรง

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- log บันทึกครบพอที่จะสร้างไทม์ไลน์ย้อนหลังได้ ทั้งเวลาเริ่ม-จบและสถานะรายบัญชี
- ไฟล์เดิมถูกเก็บเป็น `.bak-preenvguard` ทำให้เทียบได้ว่าโค้ดเดิมตัดสินใจผิดตรงไหน
- การแก้เลือกทางที่ปิดทั้งคลาส (ให้ session ประกาศตัวเอง) แทนการเพิ่มเงื่อนไขเฉพาะกรณี

### สิ่งที่ต้องปรับปรุง
- คำสั่งที่ทำงานกับ "ทุกใบ" ต้องถูกมองว่าอันตรายตั้งแต่ตอนเขียน จนกว่าจะพิสูจน์ได้ว่าสมาชิกทุกตัวเข้ากันได้กับพารามิเตอร์ที่ใช้
- ค่าที่บอกว่า "ไม่มีอะไรเกิดขึ้น" (`rc=1`) ไม่ควรกลืนกรณี "ทำไม่ได้เพราะทำผิดที่" ไว้ด้วยกัน — คนละความหมาย ควรแยกรหัส
