## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

กลไกที่ทำให้พลาดไม่ใช่ความประมาทตอนแก้ แต่เป็น **การที่ข้ออ้างที่ยังไม่ตรวจถูกคอมมิตลงไฟล์ไปแล้ว** พอมันอยู่ในไฟล์ที่เราเขียนเอง มันเลิกหน้าตาเหมือนการเดา และกลายเป็นสิ่งที่รอบถัดมาหยิบมาใช้เป็นหลักฐาน

หัวไฟล์ของเทสตัวเก่าเขียนไว้ตรงๆ ว่า *"Everything under skills/ and commands/ is copied into the generic helix plugin"* ซึ่งขัดกับสิ่งที่ `CLAUDE.md` ของ repo นี้ระบุไว้เองว่า ไฟล์ generic ตัวใหม่ที่ยังไม่มีใน `helix` **จะไม่ถูกสร้างอัตโนมัติ** เว้นแต่ตั้ง `HELIX_SYNC_NEW=1` ไฟล์ทั้ง 3 ไม่เคยถูกนำเข้า `helix` จึงไม่มีอยู่ที่นั่น และลิงก์ในไฟล์เหล่านั้นก็ไม่มีวันพังใน plugin

### 5 Whys

1. **ทำไมลิงก์ที่ใช้งานได้ 3 จุดถึงถูกลบ?** — เพราะเชื่อว่ามันเป็น 404 ใน plugin ที่ deploy แล้ว
2. **ทำไมถึงเชื่อแบบนั้น?** — เพราะ `synced_links.test.js` ระบุไฟล์ทั้ง 3 ไว้ในชุด `PRE_EXISTING` พร้อมคอมเมนต์ว่า "are real dangling links in the deployed plugin"
3. **ทำไมคอมเมนต์นั้นถึงเขียนแบบนั้น?** — เพราะหัวไฟล์ตั้งสมมติฐานเหมารวมว่าทุกอย่างใต้ `skills/` และ `commands/` ถูกคัดลอกเข้า `helix`
4. **ทำไมสมมติฐานนั้นถึงผิด?** — เพราะการซิงก์อัปเดตเฉพาะไฟล์ที่ **มีอยู่แล้ว** ใน `helix` ไฟล์ใหม่ถูกข้ามโดยตั้งใจ ซึ่งเขียนไว้ใน `CLAUDE.md` อยู่แล้ว และไม่เคยมีใครเปิด `helix` ไปนับว่าไฟล์ 3 ตัวนี้อยู่ในนั้นจริงไหม
5. **ทำไมถึงไม่มีใครเปิดดู?** — **root cause:** ข้ออ้างเกี่ยวกับระบบปลายทางถูกเขียนลงในคอมเมนต์ของเครื่องมือที่ไม่ได้มองระบบนั้น เมื่อคอมมิตแล้ว มันถูกอ่านเป็นข้อเท็จจริงในรอบถัดไป — คนอ่านแยกไม่ออกว่าบรรทัดนั้นเคยถูกตรวจหรือไม่ เพราะไม่มีอะไรในไฟล์บอกไว้

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** ไม่มีชั้นไหนครอบเลย — `check-no-secrets.sh` ดูเรื่องความลับ · เทสใน `tools/` ตรวจโครงสร้างและกฎ ไม่ได้ตรวจว่าข้ออ้างในคอมเมนต์เป็นจริง · ไม่มีเทสใดเปรียบเทียบรายชื่อไฟล์ระหว่าง `ols-qa` กับ `helix` สิ่งที่จับได้จริงคือผลลัพธ์ของสคริปต์ซิงก์ที่พิมพ์ออกมาหลังคอมมิตไปแล้ว ซึ่งคือการจับ **หลัง** ของเสียหลุดออกไป ไม่ใช่ก่อน

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ผลลัพธ์ที่ขัดกับข้ออ้างถูกอ่านและยอมรับทันที ไม่ใช่หาทางอธิบายให้เข้ากับข้ออ้างเดิม
- การย้อนคืนทำภายในนาทีครึ่ง และคอมมิตย้อนอธิบายไว้ตรงๆ ว่าข้ออ้างเดิมผิดเพราะอะไร ไม่ใช่ย้อนเงียบๆ
- ความผิดพลาดซ้อนเรื่องมาร์กเกอร์ทับ frontmatter ถูกจับได้ในรอบเดียวกัน และปิดด้วยเทส ไม่ใช่ด้วยการจำ

### สิ่งที่ต้องปรับปรุง
- คอมเมนต์ในโค้ดของเราเองไม่ใช่หลักฐาน มันคือ "ของที่จริง ณ ตอนเขียน" เหมือน memory และ WIP note ทุกประการ ต้อง re-verify ก่อนใช้
- ชุดรายชื่อยกเว้นตายตัวที่มีคำอธิบายเชิงข้อเท็จจริงกำกับ เป็นที่ซ่อนชั้นดีของสมมติฐานที่ไม่มีใครตรวจ — ให้เครื่องมืออ่านจากตัวไฟล์เอง (มาร์กเกอร์) ดีกว่าให้คนพิมพ์รายชื่อพร้อมเหตุผล
- คำว่า "dangling link" เป็นข้อความเกี่ยวกับ **ปลายทาง** ไม่ใช่เกี่ยวกับไฟล์ต้นทาง เครื่องมือที่มองเห็นแค่ฝั่งต้นทางจึงยืนยันมันไม่ได้เลย
