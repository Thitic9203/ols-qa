## สรุปสั้น (Executive Summary)

ผมรายงานเจ้าของงานว่า **"ยืนยันบัญชี pre-prod ได้ 0 จาก 15 บัญชี หมดอายุทั้งหมด"** ทั้งที่ไม่เคยเปิดไฟล์ state ของบัญชีไหนมาไล่ดูอายุคุกกี้เลยสักไฟล์ ตัวเลข 0 มาจากบรรทัดสรุปของ `session_verify.js` เพียงบรรทัดเดียว

ของจริงเมื่อไล่ครบทั้ง 15 แถวคือ มี **1 บัญชีที่คุกกี้ auth ยังไม่หมดอายุ (เหลือ 9.3 ชั่วโมง)** และอีก 14 บัญชีหมดอายุมาแล้วราว 69 ถึง 73 ชั่วโมง ตัวเลข 0 จึงผิดตั้งแต่หน้าตัวเลข

สาเหตุจริงมี 2 ชั้น ชั้นเครื่องมือคือ `session_verify.js` ยุบผลลัพธ์ 3 แบบที่ต่างกันโดยสิ้นเชิง — **session ตาย · ไฟล์ผิดบัญชี · เครื่องมือของตัวเองพัง** — ให้เหลือถังเดียวคือ "ยังไม่ verified" แล้วพิมพ์เป็นบรรทัด `N/M verified` ชั้นคนคือผมอ่านบรรทัดสรุปนั้นแล้วรายงานต่อเป็นข้อเท็จจริงเกี่ยวกับ **อายุ session** ซึ่งเป็นคนละเรื่องกับสิ่งที่บรรทัดนั้นวัด ทั้งที่เครื่องมือพิมพ์ชั่วโมงที่เหลือของทุกแถวไว้ให้อยู่แล้ว

ตอนนี้ใส่ตัวกันไว้ในเครื่องมือแล้ว (relaunch เบราว์เซอร์เมื่อหลุด) แต่ยัง **ไม่ได้คอมมิต** และกฎฝั่งการรายงานอยู่ในหัวข้อ 6

## 1. ปัญหา (Problem Statement)

- ผมรายงานเจ้าของงานว่ายืนยัน session ได้ **0 จาก 15 บัญชี** และสรุปต่อเองว่า **"หมดอายุทั้งหมด"**
- ที่มาของเลข 0 คือผลรัน `session_verify.js` ที่คืน error **ข้อความเดียวกันเป๊ะทั้ง 13 บัญชี** ซึ่งอ่านตรงๆ ได้ว่าเป็นเบราว์เซอร์ล่ม 1 ครั้ง ไม่ใช่ session ตาย 13 ใบ
- เครื่องมือตัวเดียวกันนี้ **พิมพ์ชั่วโมงที่เหลือของทุกแถวอยู่แล้ว** — `capture/session_verify.js:74` เรียก `authHoursLeft(t.file)` และบรรทัดที่ 99 พิมพ์ค่านั้นออกมาต่อแถว ผมจึงมีตัวเลขจริงอยู่ตรงหน้าตั้งแต่แรก แต่ไปหยิบบรรทัดสรุปมาแทน
- เมื่อไล่เปิดไฟล์ state ทั้ง 15 บัญชีจริง พบว่า **1 บัญชียังไม่หมดอายุ เหลือ 9.3 ชั่วโมง** และ 14 บัญชีหมดอายุมาแล้วราว 69 ถึง 73 ชั่วโมง
- เจ้าของงานเป็นคนทักเองว่าเพิ่งล็อกอินให้เมื่อคืน ซึ่งขัดกับคำว่า "หมดอายุทั้งหมด" ที่ผมรายงาน

**สิ่งที่ควรจะเป็น:** ก่อนพูดตัวเลขใดๆ ต้องวัดจากสิ่งที่เป็นตัวเลขนั้นจริง — อายุ session อ่านจากวันหมดอายุของคุกกี้ในไฟล์ state ไม่ใช่จากจำนวนแถวที่เครื่องมือ verify ผ่าน · กฎข้อแรกสุดของ repo (`CLAUDE.md` — มีได้ 3 สถานะ ตรวจแล้ว · ยังไม่ตรวจ · ตรวจไม่ได้) และกฎ always-on ข้อ 17 (เคลมอะไรต้องมีหลักฐาน)

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

กลไกอยู่ที่ท้ายไฟล์ `capture/session_verify.js`

```js
} catch (e) { err = e.message.slice(0, 60); }          // บรรทัด 93

const match = actual && actual.toLowerCase() === t.email.toLowerCase();
...
const bad = rows.filter((r) => !r.match);              // บรรทัด 104
console.log(`${rows.length - bad.length}/${rows.length} verified`);
```

`match` เป็นจริงได้ทางเดียวคือ **ถามระบบแล้วได้อีเมลกลับมาตรงกับที่ไฟล์อ้าง** ดังนั้นทุกความล้มเหลวไม่ว่าสาเหตุใด — session ตายจริง · ไฟล์ถือบัญชีผิด · เบราว์เซอร์ของเครื่องมือเองล่ม — ตกลงถัง `bad` เหมือนกันหมด แล้วถูกพิมพ์ออกมาเป็นตัวเลขเดียว `N/M verified`

ตัวเลขนั้นตอบคำถามว่า **"ยืนยันตัวตนสำเร็จกี่ใบ"** ซึ่งไม่ใช่คำถามที่ผมกำลังถาม คำถามจริงคือ **"session ไหนยังไม่หมดอายุ"** และคำตอบของคำถามนั้นอยู่คนละที่ คืออยู่ในคุกกี้ของไฟล์ state ที่ `authHoursLeft()` อ่านให้แล้วและพิมพ์ไว้ทุกแถว

### 5 Whys

1. **ทำไมถึงรายงานว่า 0 จาก 15 บัญชีหมดอายุ?** — เพราะหยิบบรรทัด `N/M verified` จากผลรันมาใช้เป็นคำตอบ
2. **ทำไมบรรทัดนั้นถึงเป็น 0?** — เพราะเบราว์เซอร์ของเครื่องมือล่ม 1 ครั้ง แล้วทุกแถวที่เหลือล้มด้วย error ข้อความเดียวกัน และ error ทุกชนิดถูกนับเป็น "ไม่ผ่าน" ที่ `session_verify.js:104`
3. **ทำไมถึงเอาเลข "ยืนยันไม่ผ่าน" ไปพูดแทน "หมดอายุ"?** — เพราะไม่ได้แยกว่าเครื่องมือวัดอะไร เห็นตัวเลขที่เข้ากับเรื่องที่กำลังจะพูดพอดี จึงใช้เลย
4. **ทำไมถึงไม่แยก?** — เพราะไม่ได้เปิดไฟล์ state ดูเลยแม้แต่ไฟล์เดียว ถ้าเปิดดู 1 ไฟล์จะเห็นทันทีว่าอายุคุกกี้เป็นคนละค่ากับผลการยืนยันตัวตน
5. **ทำไมถึงไม่เปิด?** — **เพราะยอมรับตัวเลขจากเครื่องมือที่ยังไม่เคยพิสูจน์ว่ามันวัดสิ่งที่เราถาม แล้วรายงานต่อทันทีโดยไม่มีการวัดฝั่งข้อมูลดิบมาคาน** — นี่คือ root cause: เครื่องมือที่รวมความล้มเหลวหลายชนิดไว้ในตัวเลขเดียว บวกกับนิสัยหยิบบรรทัดสรุปไปพูดโดยไม่ตรวจว่าบรรทัดนั้นตอบคำถามอะไร

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**

| ชั้นที่ควรจับ | ทำไมไม่จับ |
|---|---|
| ตัวเครื่องมือเอง | ไม่มีตัวแยกระหว่าง "ตรวจไม่ได้" กับ "ตรวจแล้วไม่ผ่าน" — ทั้งคู่ตกถัง `bad` เดียวกัน (คลาสเดียวกับบทเรียนรายงาน #0005 ที่ว่าการ์ดต้องมีสถานะที่ 3 คือตรวจไม่ได้) |
| เอาต์พุตต่อแถว | จับได้ครับ — มันพิมพ์ชั่วโมงที่เหลือไว้ทุกแถวอยู่แล้ว แต่ผมไม่ได้อ่าน ชั้นนี้ล้มเพราะคน ไม่ใช่เพราะเครื่องมือ |
| กฎ `CLAUDE.md` ข้อแรกสุด + always-on ข้อ 17 | เป็นตัวหนังสือ ไม่มีกลไกบังคับตอนพิมพ์ตัวเลขลงแชท |
| รายงาน #0019 และ #0016 ที่เขียนบทเรียนคลาสนี้ไว้แล้ว | เป็นเอกสาร ไม่ได้แปลงเป็นเครื่องมือ จึงกันการเกิดซ้ำไม่ได้ |

## 5. แนวทางการแก้ไข (Fix)

- **แก้ที่เครื่องมือ** — `capture/session_verify.js:77-80` เพิ่ม relaunch เมื่อเบราว์เซอร์หลุด พร้อมคอมเมนต์อธิบายว่าเบราว์เซอร์ล่ม 1 ครั้งทำให้ทุกแถวที่เหลือล้มด้วยข้อความเดียวกัน ซึ่งอ่านผิดเป็น session ตายหลายใบ

```js
// A dead/crashed browser fails newContext() with the same message for every
// remaining account — that reads as N real dead sessions when it is really one
// tooling crash. Relaunch before trusting it, so one crash cannot poison the rest.
if (!browser.isConnected()) browser = await chromium.launch({ headless: true, args: resolverArgs() });
```

- **แก้ที่ตัวเลขที่รายงานไป** — ไล่เปิดไฟล์ state ครบทั้ง 15 บัญชีแล้วรายงานค่าจริงให้เจ้าของงานทราบในเซสชันนั้น

**ยืนยันแล้วด้วย:** `grep -n "isConnected" ~/ols-qa-testing-bot/capture/session_verify.js` → พบที่บรรทัด 80 · `ls ~/ols-qa-testing-bot/capture/state_*.json | wc -l` → 35 ไฟล์ · `git show HEAD:capture/session_verify.js | grep -c isConnected` → **0** แปลว่าตัวกันนี้ยังอยู่แค่ในไฟล์บนดิสก์ **ยังไม่ถูกคอมมิต** (`git status --short` แสดง ` M capture/session_verify.js`)

> **บรรทัดสรุปของเครื่องมือ ไม่ใช่คำตอบของคำถามที่เรากำลังถาม จนกว่าจะพิสูจน์ว่ามันวัดสิ่งเดียวกัน**
> ก่อนหยิบตัวเลขจากเอาต์พุตของเครื่องมือไปพูด ต้องตอบ 2 ข้อ — (1) ตัวเลขนี้นับอะไรเป็น "ผ่าน" (2) ของที่ถูกนับเป็น "ไม่ผ่าน" มีกี่สาเหตุที่ต่างกัน ถ้ามากกว่า 1 สาเหตุ **ห้ามใช้ตัวเลขนั้นตอบคำถามที่เจาะจงสาเหตุเดียว** ให้ไปวัดจากข้อมูลดิบแทน
> และ **"ตรวจไม่ได้" ต้องไม่ถูกนับรวมกับ "ตรวจแล้วไม่ผ่าน" ในตัวเลขเดียวกัน** ไม่ว่าจะในเครื่องมือหรือในประโยคที่พูดกับเจ้าของงาน (ต่อยอดจากบทเรียนรายงาน #0005)

เขียนไว้ที่รายงานฉบับนี้ และสรุปย่อในหัวข้อ `## Post-mortems` ของ `CLAUDE.md`

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** เจ้าของงานจับได้เอง จากการที่คำว่า "หมดอายุทั้งหมด" ขัดกับสิ่งที่ตัวเองทำเมื่อคืน (เพิ่งล็อกอินให้) ไม่มีกลไกใดในระบบจับได้
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** ไม่กี่นาทีหลังรายงาน เพราะเจ้าของงานมีข้อมูลที่ค้านอยู่ในมือพอดี ถ้าเป็นตัวเลขที่เจ้าของงานไม่มีทางค้านได้ ความผิดพลาดนี้จะไม่มีใครจับได้เลย
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** P3 และ P4 — เมื่อบรรทัดสรุปแยก "ตรวจไม่ได้" ออกมาเอง และพิมพ์จำนวนบัญชีที่คุกกี้ยังไม่หมดอายุแยกต่างหาก ตัวเลขที่ผิดจะไม่มีทางถูกสร้างขึ้นมาตั้งแต่แรก ไม่ต้องรอให้คนสังเกต

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- จดแถว `OPEN` ลง `PENDING.md` ทันทีในเทิร์นที่รู้ตัว ความผิดพลาดจึงไม่หายไปพร้อมเซสชัน และรายงานฉบับนี้เขียนได้จากบันทึกนั้น
- ตอนไปวัดใหม่ ไล่ครบทั้ง 15 แถว ไม่ได้สุ่มดูบางไฟล์แล้วเหมา

### สิ่งที่ต้องปรับปรุง
- ตัวเลขที่ "เข้ากับเรื่องที่กำลังจะพูดพอดี" คือจุดที่ต้องระวังที่สุด ไม่ใช่จุดที่ควรรีบใช้ — ตรงกับบทเรียนรายงาน #0019 ที่เขียนไว้เองว่า *ผลลัพธ์ที่เข้ากับเรื่องที่เชื่ออยู่แล้วพอดี คือเหตุให้ตรวจซ้ำ ไม่ใช่เหตุให้ผ่าน*
- error ข้อความเดียวกันเป๊ะหลายบรรทัดติดกัน คือลายเซ็นของความล้มเหลว **1 ครั้ง** ไม่ใช่ N ครั้ง ควรอ่านออกตั้งแต่เห็น
- การแก้ที่เครื่องมือแล้วไม่คอมมิต เท่ากับยังไม่ได้แก้สำหรับรอบถัดไปที่ใช้เครื่องอื่น
