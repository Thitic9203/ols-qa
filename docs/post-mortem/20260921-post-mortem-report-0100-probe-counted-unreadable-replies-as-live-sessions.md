## สรุปสั้น (Executive Summary)

ระหว่างรอบ smoke test บน training69 ผมเขียนสคริปต์เฉพาะกิจไว้ตรวจว่า session ที่บันทึกไว้ 8 ไฟล์ยังล็อกอินอยู่ไหม สคริปต์พิมพ์ `ALIVE=8/8` และผมรายงานตัวเลขนั้นให้เจ้าของงานทันที

ของจริงคือ 6/8 — สองไฟล์ (`rg9021_training`, `school_admin_1200000001_01`) ได้ HTTP 200 กลับมาพร้อม **body ว่างเปล่า** ซึ่งแปลว่าไม่ได้ล็อกอิน สาเหตุคือสคริปต์ตั้งค่า `role = 'unparsable'` เมื่อ parse JSON ไม่ผ่าน แล้วเงื่อนไขนับเป็น `role !== 'no-user' && role !== 'null'` ซึ่งค่า `'unparsable'` รอดทั้งสองข้อ คำตอบที่อ่านไม่ออกจึงถูกนับเป็นสำเร็จ

แก้โดยเขียนตัวตรวจใหม่ที่พิมพ์ความยาว body จริงและแยกสถานะ "อ่านไม่ได้" ออกจาก "ผ่าน" แล้วเชื่อมเฉพาะ 6 session ที่ยืนยันแล้วเข้ารอบเทสต์ ไม่มีความเสียหายปลายทาง เพราะผมตรวจซ้ำก่อนเอาไปใช้จริง

## 1. ปัญหา (Problem Statement)

- สคริปต์เฉพาะกิจพิมพ์บรรทัดสุดท้ายว่า `ALIVE=8/8` และผมยกบรรทัดนั้นมาพูดกับเจ้าของงานว่า "8/8 session ยังมีชีวิต"
- ตัวตรวจรอบสองที่พิมพ์เนื้อคำตอบจริง ได้ผลว่า
  ```
  rg9021_training               200  NON-JSON len=0
  school_admin_1200000001_01    200  NON-JSON len=0
  ```
  สองรายการนี้คือคำตอบ 200 ที่ไม่มีเนื้อหา = ไม่มี session ผู้ใช้
- ตัวตรวจรอบสามที่แยกสถานะชัดเจน สรุปเป็น `LOGGED-IN=6/8`

**สิ่งที่ควรจะเป็น:** ตัวนับต้องนับเฉพาะรายการที่ *พิสูจน์แล้ว* ว่าผ่านนิยาม และรายการที่อ่านคำตอบไม่ได้ต้องถูกนับเป็น "ตรวจไม่ได้" ซึ่งห้ามรวมเข้ากับ "ผ่าน" ตาม `CLAUDE.md` §0 ("ตรวจไม่ได้ ห้ามนับรวม ไม่ผ่าน" และในทางกลับกันก็ห้ามนับรวมผ่าน) และ §1 ("นับสิ่งที่วัดจริง ศูนย์ = ปฏิเสธ")

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

เงื่อนไขนับของสคริปต์เขียนเป็น "ไม่ใช่ค่าที่รู้จักว่าแย่" แทนที่จะเป็น "ใช่ค่าที่รู้จักว่าดี" — โครงสร้างแบบ denylist ทำให้ค่าใหม่ที่ไม่เคยคิดถึง (`'unparsable'`) ตกไปอยู่ฝั่งสำเร็จโดยอัตโนมัติ ตอนเขียนมันดูถูกเพราะผมคิดถึงแค่สองกรณีที่ตั้งใจดัก (ไม่มี user กับ role ว่าง) และไม่ได้คิดว่า "อ่านคำตอบไม่ออก" เป็นสถานะที่สาม

### 5 Whys

1. **ทำไมผมถึงรายงาน 8/8?** — เพราะสคริปต์พิมพ์ `ALIVE=8/8` และผมยกบรรทัดสรุปของเครื่องมือมาเป็นคำตอบ
2. **ทำไมสคริปต์ถึงพิมพ์ 8/8?** — เพราะ 2 รายการที่ parse JSON ไม่ผ่านถูกตั้งค่าเป็น `role='unparsable'` แล้วผ่านเงื่อนไขนับ
3. **ทำไมเงื่อนไขนับถึงปล่อยผ่าน?** — เพราะเขียนเป็น denylist (`!== 'no-user' && !== 'null'`) ไม่ใช่ allowlist ของค่า role ที่ถือว่าล็อกอินจริง
4. **ทำไมถึงเขียนเป็น denylist?** — เพราะตอนออกแบบผมนึกถึงเฉพาะรูปแบบความล้มเหลวที่คาดไว้ล่วงหน้า และไม่ได้แยกสถานะ "ตรวจไม่ได้" ออกมาเป็นสถานะของตัวเอง
5. **ทำไมถึงไม่แยกสถานะ "ตรวจไม่ได้" ออกมา?** — **เพราะผมไม่ได้เอาเครื่องมือที่เขียนเองไปทดสอบกับตัวอย่างที่รู้คำตอบก่อนเชื่อผลของมัน ทั้งที่ `CLAUDE.md` §0 กำหนดไว้ชัดว่าต้องผ่าน "ต้องพบ 1 · ต้องไม่พบ 1" ก่อน** — นี่คือ root cause จริง เพราะถ้าทำขั้นนี้ ตัวอย่าง "ต้องไม่พบ" จะเปิดโปงช่องนี้ทันทีไม่ว่าช่องจะอยู่ตรงไหนของเงื่อนไข

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- `CLAUDE.md` §0 มีกฎเรื่องเครื่องมือที่เขียนเองต้องผ่านตัวอย่างที่รู้คำตอบอยู่แล้ว แต่เป็น **กฎที่บังคับด้วยความจำ ไม่มีเครื่องบังคับ** สคริปต์เฉพาะกิจที่เขียนสดในเซสชันจึงไม่ผ่านด่านไหนเลย
- ไม่มีชั้นไหนตรวจว่า "บรรทัดสรุปของเครื่องมือ" ตรงกับรายละเอียดรายบรรทัดที่เครื่องมือเดียวกันพิมพ์ออกมา ทั้งที่ในผลลัพธ์รอบแรกมีคำว่า `unparsable` โผล่อยู่ 2 บรรทัดต่อหน้าต่อตาแล้ว
- ที่จับได้ไม่ใช่เพราะชั้นป้องกัน แต่เพราะผมบังเอิญไปเห็นว่าค่า role ขัดกับบัญชีรายชื่อ ซึ่งเป็นความบังเอิญ ไม่ใช่กลไก

## 5. แนวทางการแก้ไข (Fix)

- เขียนตัวตรวจใหม่ที่ **พิมพ์ความยาวและหัวของ body จริง** แทนที่จะสรุปให้ก่อน ทำให้เห็นด้วยตาว่า 2 รายการตอบ 200 พร้อม body ว่าง
- เขียนตัวตรวจรอบสามที่แยกสถานะชัด: body ว่าง → พิมพ์ `EMPTY-BODY = NOT LOGGED IN` และ **ไม่นับ** เข้าตัวนับ ผลลัพธ์ `LOGGED-IN=6/8`
- แจ้งเจ้าของงานแก้ไขทันทีในเทิร์นถัดจากที่รู้ตัว และบันทึกแถว `OPEN` ใน `PENDING.md` ในเทิร์นเดียวกัน
- เชื่อมเฉพาะ session ที่ยืนยันแล้ว 6 ตัวเข้าเลนเทสต์ โดยจับคู่ตาม `activeRole` ที่วัดได้จริง ไม่ใช่ตามชื่อไฟล์

**ยืนยันแล้วด้วย:** ผลรันของตัวตรวจรอบสาม แสดงทีละรายการพร้อมสถานะ และปิดท้ายด้วย `LOGGED-IN=6/8` ซึ่งตรงกับจำนวนบรรทัดที่มี `activeRole` จริง 6 บรรทัด

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** ผมจับได้เอง จากการเห็นว่าค่า role ที่สคริปต์พิมพ์ขัดกับบทบาทที่บัญชีรายชื่อระบุ ไม่ใช่จากชั้นป้องกันใดๆ
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** ประมาณ 2 นาทีหลังรายงานตัวเลขผิดออกไป
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** ตัวนับที่พิมพ์สถานะที่สาม (`ตรวจไม่ได้`) ออกมาเป็นตัวเลขของตัวเองเสมอ จะทำให้บรรทัดสรุปอ่านเป็น `6 ผ่าน · 2 ตรวจไม่ได้` ตั้งแต่รอบแรก ซึ่งเห็นความผิดปกติได้ทันทีโดยไม่ต้องอาศัยว่าใครจะบังเอิญสังเกต

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ไม่ได้เอาตัวเลข 8/8 ไปใช้ตัดสินอะไรต่อ — ก่อนจับบัญชีเข้าเลนจริงผมตรวจซ้ำอีกรอบ ทำให้ความผิดพลาดไม่ลามเข้าไปในผลเทสต์
- แจ้งเจ้าของงานทันทีที่รู้ตัว ไม่รอสรุปตอนท้าย

### สิ่งที่ต้องปรับปรุง
- เครื่องมือวัดที่เขียนเองต้องถูกปฏิบัติเหมือนของที่ยังพิสูจน์ไม่ได้ จนกว่าจะรันกับตัวอย่างที่รู้คำตอบ — ไม่ใช่เชื่อเพราะเป็นของที่เพิ่งเขียนเองกับมือ
- ในผลรอบแรกมีคำว่า `unparsable` พิมพ์อยู่ต่อหน้าแล้ว แต่ผมอ่านผ่านเพราะสายตาไปหยุดที่บรรทัดสรุป — บรรทัดสรุปต้องเป็นสิ่งที่อ่านทีหลัง ไม่ใช่สิ่งแรก
