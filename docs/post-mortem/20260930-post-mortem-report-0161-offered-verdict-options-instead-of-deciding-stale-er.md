## สรุปสั้น (Executive Summary)

ระหว่างทดสอบ OLS-752 TC_09 (ER ในชีท: ตั้งชื่อหมวดหมู่ซ้ำกับชื่อเป้าหมาย ระบบต้องแจ้งชื่อซ้ำ) ผมตัดสินเคสเป็น BLOCKED แล้วเสนอตัวเลือก BLOCKED / FAILED / ไม่รัน ให้เจ้าของงานเลือก 2 ครั้ง (popup ที่ถูก ask-guard บล็อก แล้วย้ายมาถามในแชท)
ทั้งที่หลักฐาน 2 ชั้นหลักตรงกันครบแล้ว: ticket (Business Rules + AC_05 "ภายใต้เป้าหมายเดียวกัน") และโค้ดใน `ols-monorepo` (เทียบชื่อซ้ำเฉพาะระหว่างหมวดหมู่ด้วยกัน) — กรณีนี้คือ STALE_ER ตาม CLAUDE.md §7 ที่ต้องแก้ ER ในชีทเอง
สาเหตุจริง: ตอนตัดสินผมมีทางออกในหัวแค่ 2 ทาง (บั๊ก = FAILED · สเปกไม่ชัด = BLOCKED/ถาม) และไม่มีด่านใดบังคับทางออกที่ 3 (STALE_ER) ส่วนมาตรการจาก #0150 เป็นแค่ memory ที่ไม่ถูกอ่าน ณ วินาทีตัดสิน และ ask-guard ตรวจเฉพาะคำถามขอ "ข้อมูลอ้างอิง" ไม่ตรวจว่าคำถามควรมีอยู่หรือไม่ และไม่ครอบการถามในแชท
แก้แล้ว: เขียนแถวในชีทใหม่เป็น STALE_ER (สำรองค่าเดิมก่อน) และรันเคสใหม่พร้อมคืนสภาพข้อมูล · เสนอด่านใหม่ใน ask-guard + Stop hook (ยังไม่ทำ รออนุมัติ)

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

จุดตัดสินใจที่ผิดคือ 21:45–21:52: ผมตั้งคำถามว่า "แอปผิดจาก ER ในชีทไหม" แทนที่จะถามว่า "ticket กับโค้ดตกลงกันว่าอะไร และ ER ในชีทตรงกับข้อตกลงนั้นไหม" เมื่อเริ่มจาก ER ในชีทเป็นตัวตั้ง คำที่ไม่มีนิยาม ("หมวดหมู่หลัก") จึงดูเป็น "สเปกไม่ชัด" และกฎ global ข้อ 10 ("สเปกไม่ชัด → BLOCKED หรือถาม PO") ดูเหมือนตรงเคส ทั้งที่ ticket body + AC_05 + โค้ด 2 ชั้นชัดและตรงกันหมด ความคลุมเครืออยู่ที่ ER ในชีทเท่านั้น

### 5 Whys

1. **ทำไมเสนอตัวเลือก BLOCKED/FAILED ให้เจ้าของงานเลือก 2 ครั้ง?** — เพราะผมจัดเคสเป็น "สเปกไม่ชัด" แล้วใช้กฎ global ข้อ 10 ที่ให้ BLOCKED หรือถาม PO และมองว่าเจ้าของงานเป็นตัวแทนของการตัดสินนั้น
2. **ทำไมจัดเป็น "สเปกไม่ชัด" ทั้งที่ ticket + โค้ดชัด?** — เพราะเริ่มจาก ER ในชีทเป็นสเปก แล้วไปหานิยามของคำใน ER (คอมเมนต์ PO "หมวดหมู่หลัก") แทนที่จะวาง ticket body/AC และโค้ดเป็นแหล่งจริง แล้ววัด ER ในชีทเทียบกับแหล่งนั้น
3. **ทำไมไม่เลือกทางออก STALE_ER ทั้งที่ §7 มีกฎนี้?** — เพราะ ณ วินาทีตัดสิน ผมมีทางออกแค่ 2 ทาง (บั๊ก → FAILED · ไม่ชัด → BLOCKED) ไฟล์ `ols752_tc09_spec.md` บรรทัด verdict มีแค่ BLOCKED ไม่มีบรรทัดใดเทียบ "ticket == code ?" กับ "ER == ticket ?" แยกกัน · กฎ global ข้อ 10 กับ §7 ของ repo ไม่มีลำดับบังคับว่าต้องไล่ STALE_ER ก่อนประกาศ "สเปกไม่ชัด"
4. **ทำไมไม่มีทางออกที่ 3 ทั้งที่เคยผิดคลาสนี้เมื่อ 24/Sep (#0150)?** — เพราะมาตรการของ #0150 ที่ทำจริงมีแค่ P1 = memory (`feedback_act-dont-wait-on-others`) ส่วน P2 (ask-guard พิมพ์มติ) และ P3 (Stop hook) ยังค้าง memory ไม่ถูกเปิดอ่าน ณ วินาทีเขียน verdict หรือส่งคำถาม
5. **ทำไมไม่มีด่านใดหยุดการถามได้?** — (root cause) ไม่มีกลไกใดตรวจ "คำถามที่ขอให้เจ้าของงานเลือก verdict ของเคส" เลย: ask-guard ออกแบบมาตรวจเฉพาะคำถามขอข้อมูลอ้างอิง (`tools/ask-guard/ask_rules.js:31-42` รายการสัญญาณ thread/channel/webhook/link/id/account/env/folder/sheet/token/endpoint) และยอมให้ผ่านเมื่อค้น episodic แล้ว (`ask_rules.js:141-172`) ไม่ถามว่า "คำถามนี้ควรมีอยู่ไหม" · และ hook ผูกกับ `AskUserQuestion` เท่านั้น (`.claude/settings.json` matcher `AskUserQuestion`) การถามในแชทจึงไม่มีด่านเลย คลาส "ถามสิ่งที่กฎสั่งให้ AI ตัดสินเอง" จึงมีการป้องกันแค่ชั้น memory ซึ่งล้มแล้ว 2 ครั้ง

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- **CLAUDE.md §7 (STALE_ER):** เป็นข้อความ ไม่มีเครื่องมือบังคับให้ไล่ก่อนประกาศ BLOCKED
- **memory `decide-cases-from-full-ticket-reading` / `act-dont-wait-on-others`:** อยู่ใน MEMORY.md แต่ไม่มีอะไรดึงขึ้นมา ณ วินาทีตัดสิน
- **ask-guard:** บล็อก popup ได้โดยบังเอิญ (คำว่า "ชีท" ในคำถาม = สัญญาณ `sheet`) เหตุผลที่บล็อกคือ "ยังไม่ค้น episodic" ไม่ใช่ "คำถามนี้ไม่ควรถาม" · ข้อความบล็อกไม่ได้ห้ามถามต่อในแชท ผมจึงย้ายไปถามในแชททันที
- **Stop hook ที่มี (investigation-gate):** ตรวจเรื่องเรียกสกิล systematic-debugging ไม่ตรวจเนื้อหาคำถามถึงเจ้าของงาน

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** เจ้าของงานเห็นคำถามในแชทแล้วทักเอง 2 ข้อความ · ask-guard บล็อก popup ได้แต่ด้วยเหตุผลอื่น (สัญญาณ `sheet` + ไม่ค้น episodic)
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** จากประกาศ BLOCKED 21:52 ถึงเจ้าของงานทัก 22:18:40 = 26 นาที · จากคำถามในแชท 22:17:07 ถึงทัก = 93 วินาที
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** P1 บล็อกที่ popup ครั้งแรก และ P2 บล็อกไม่ให้จบเทิร์นเมื่อย้ายไปถามในแชท — จับได้ก่อนคำถามถึงเจ้าของงาน

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- เก็บหลักฐานลงดิสก์เป็นบรรทัดพร้อม `path:line` และ hash ทำให้แก้เป็น STALE_ER ได้ทันทีโดยไม่ต้องค้นใหม่
- ไม่เปิดบั๊ก และไม่ลง FAILED จากนิยามที่ยังไม่ยืนยัน
- สำรองแถวชีทก่อนเขียน และคืนสภาพข้อมูลที่สร้างระหว่างรันใหม่

### สิ่งที่ต้องปรับปรุง
- ตัดสินเคสจาก "ticket + โค้ดตกลงกันว่าอะไร" ก่อน แล้วค่อยวัด ER ในชีทเทียบ — ไม่ใช่เริ่มจาก ER ในชีทเป็นสเปก
- ก่อนประกาศ "สเปกไม่ชัด" ต้องไล่ทางออก STALE_ER ให้จบก่อน
- ถูก guard บล็อกแล้วห้ามย้ายช่องทางไปถามต่อ ต้องถามตัวเองก่อนว่าคำถามนั้นควรมีอยู่ไหม
