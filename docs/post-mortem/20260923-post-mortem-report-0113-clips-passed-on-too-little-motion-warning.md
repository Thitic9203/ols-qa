## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

กลไกตรวจการกระตุก (`verify_video.py:186-202`): เฟรมหนึ่งนับว่า "อยู่ช่วงเคลื่อนไหว" ถ้าค่ามัธยฐานของความต่างในย่าน ±6 เฟรม > 0.35 และนับว่า "ค้างซ้ำ" ถ้าความต่างของตัวเอง < 0.02 · ตรวจเฉพาะเมื่อเฟรมเคลื่อนไหว ≥ 25 ถ้าน้อยกว่านั้นผ่านพร้อมคำเตือน (ยกเว้นใส่ `--strict-motion`)

กลไกที่ทำให้เฟรมเคลื่อนไหวน้อยและค้างซ้ำสูง (subagent A/B, ตัวอัดจริง fps 3, 1920x1080, dpr 2): CDP screencast ส่งเฟรมเฉพาะตอนหน้าวาดใหม่ · headless Chromium ไม่วาดเคอร์เซอร์ → `page.mouse.move` บนพื้นที่ไม่มี hover ได้ 0 เฟรมใน 3.08 วินาที · หน้านิ่ง 3 วินาทีได้ 1 เฟรม · CSS animation ได้ 180 เฟรม · ที่ fps 3 ย่าน ±6 เฟรมกว้าง ±2 วินาที (6 เฟรม ÷ 3 fps) และการวาดใหม่ของแอปตอนเปิด dialog / reload มาเป็นก้อน ห่างกัน ≥333 ms → ถูกนับเป็นเฟรมค้างซ้ำ · เมื่อใส่เคอร์เซอร์ที่วาดลงหน้าตาม mousemove ได้ค้างซ้ำ 0.0% และ PASS

### 5 Whys

1. **ทำไมคลิป 4 ไฟล์ถูกพลิกเป็นผ่านทั้งที่ค้างซ้ำ 35–60%?** — เพราะตัดสินจาก `verified.passed=true` ใน capture.json ซึ่งเป็นจริงแม้การตรวจการกระตุกไม่ได้รัน
2. **ทำไม `verified.passed` เป็นจริงทั้งที่ไม่ได้วัด?** — เพราะ `qa_recorder.js:474` เรียก `verify_video.py` โดยไม่ใส่ `--strict-motion` · ค่าเริ่มต้นของตัวตรวจคือ "เคลื่อนไหวน้อยกว่า 25 เฟรม = ผ่านพร้อมคำเตือน" และตัวอัดบันทึกแค่ผ่าน/ไม่ผ่าน ไม่ได้บันทึกว่าวัดไปกี่เฟรม
3. **ทำไมคลิปเหล่านี้เคลื่อนไหวน้อยกว่า 25 เฟรม?** — เพราะที่ fps 3 screencast ส่งเฟรมเฉพาะตอนหน้าวาดใหม่ และ headless ไม่วาดเคอร์เซอร์ การขยับเมาส์จึงไม่สร้างเฟรม คลิปส่วนใหญ่จึงถูกนับว่านิ่ง
4. **ทำไมทั้งเซสชัน 22/Sep และเธรดหลัก 23/Sep ไม่เห็นคำเตือน?** — เพราะอ่านแค่ธงบูลีนใน capture.json ไม่ได้อ่านข้อความเตือนหรือจำนวนเฟรมที่วัด และเขียนลงแผนงานว่า "verify+gate ผ่าน" โดยไม่ได้ระบุว่าผ่านด้วยการวัดอะไร กี่เฟรม
5. **ทำไมด่านถึงยอมให้ "วัดไม่ได้" ออกมาเป็น "ผ่าน"?** — root cause: ด่านตรวจคลิปมีสามสถานะ (ผ่าน / ตก / วัดไม่ได้) แต่ส่งออกเป็นบูลีนสองสถานะ และค่าเริ่มต้นยุบ "วัดไม่ได้" รวมเข้ากับ "ผ่าน" — เป็นคลาสเดียวกับ #0006/#0010/#0012 (ตัวรันเทสต์ที่รัน 0 ข้อแล้วเขียว) ที่รอบก่อนปิดเฉพาะตัวรันเทสต์ ไม่ได้ไล่ด่านชนิดอื่นที่มีรูปแบบเดียวกัน

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- `verify_video.py` มี `--strict-motion` อยู่แล้ว แต่ไม่มีผู้เรียกคนไหนใส่ธงนี้ — ชั้นมีอยู่แต่ไม่ได้ต่อสาย
- postmortem-guard / pre-push ตรวจเฉพาะ repo นี้ ไม่ครอบตัวอัดในบอท
- บทเรียน #0006/#0010/#0012 เขียนไว้เป็นกฎแต่ไม่มีเครื่องมือที่ไล่หาด่านที่ "ผ่านเมื่อวัด 0"
- ปัจจัยร่วม: รายงาน #0105 เคยพบค้างซ้ำ 38.2% แล้วยอมรับคำอธิบายว่ามาจาก CPU โดยไม่ได้วัดระดับเฟรม — สาเหตุที่ไม่ได้วัดถูกรับไป กลไก fps 3 + ไม่มีเคอร์เซอร์จึงยังไม่ถูกพบในรอบนั้น (#0105 และ #0106 ไม่ใช่รายงานเรื่องการกระตุกโดยตรง รายงานนี้ไม่ได้แก้ไขรายงานทั้งสอง)

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

| # | มาตรการ | ชนิด | สถานะ |
|---|---------|------|-------|
| P1 | `qa_recorder.js` เรียก `verify_video.py` ด้วย `--strict-motion` เป็นค่าเริ่มต้น — เคลื่อนไหว < 25 เฟรม = ตก ไม่ใช่ผ่าน · เทสต์คู่ที่ป้อนคลิปนิ่งแล้วต้องได้ตก 1 ข้อ และคลิปเคลื่อนไหวพอต้องผ่าน 1 ข้อ | เครื่องมือ + เทส | กำลังทำ (เธรดหลัก) |
| P2 | สคริปต์อัดใส่จุดเคอร์เซอร์ที่วาดลงหน้าตาม mousemove เพื่อให้ screencast มีเฟรมตอนเมาส์ขยับ (A/B: 0.0% ค้างซ้ำ PASS) | เครื่องมือ | กำลังทำ (เธรดหลัก) — อนุมัติเฉพาะ Profile_TC_004 + Content_TC_005 |
| P3 | ข้อความผ่านของตัวตรวจที่บันทึกลง capture.json / แผนงาน ต้องมีจำนวนเฟรมเคลื่อนไหวและ % ค้างซ้ำที่วัดได้ — "ผ่าน" ที่ไม่มีตัวเลขไม่นับ | กฎ + เครื่องมือ | ค้าง |
| P4 | ไล่ด่านอื่นในตัวอัด/ตัวตรวจที่ "ผ่านเมื่อวัด 0" รอบเดียวกัน (ปิดคลาส ไม่ใช่ปิดเคส) | ตรวจทาน | ค้าง |
