ระหว่าง 23:31–23:36 น. วันที่ 21/Sep session ของบัญชี `ct9020` `rg9020` `st9020` `st9021` บน training69 ตายพร้อมกันทั้งที่คุกกี้ยังเหลืออายุ 23 ชั่วโมง ไทม์ไลน์ที่วัดได้ตรงกับเวลาที่กู้ session ของ `tc9020`/`tc9021` (2 บัญชีอื่น) พอดี ทำให้ตอนแรกดูเหมือนบั๊ก "ล็อกอินบัญชีหนึ่งฆ่า session บัญชีอื่น" — ตรวจโค้ดแล้วปฏิเสธสมมติฐานนั้น: `session_capture.js` เปิด browser context ใหม่แยกทุกบัญชี (`session_capture.js:148-151`) และฝั่ง ols-monorepo (`session.service.ts`) ทุกเมธอดที่จบ/หมุน session ผูกกับ `session.userId` ของบัญชีนั้นเองเท่านั้น ไม่มีเส้นทางโค้ดที่บัญชีหนึ่งจบ session ของอีกบัญชี

สาเหตุจริงคือ session ฝั่งเซิร์ฟเวอร์มี **idle timeout 30 นาที** แยกต่างหากจากอายุคุกกี้ 24 ชม. (`api-env.ts:52-56` `AUTH_SESSION_IDLE_TTL_MS` default `30*60*1000`) และ `SessionContextGuard` เว้น `GET /auth/get-session` ไว้ **ไม่นับเป็นกิจกรรมที่ต่ออายุ** โดยตั้งใจ (`session-context.guard.ts:27-29`) — ขณะที่ `session_verify.js` ที่ใช้ตรวจ "session ยังไหม" เรียก **เฉพาะ** `GET /auth/get-session` ผ่าน API context ล้วนๆ ไม่มีการโหลดหน้า (`session_verify.js:109-118`, ตั้งใจแบบนี้เพื่อเลี่ยงบั๊กคลาส #0092) ผลคือการรัน `session_verify.js` ซ้ำกี่ครั้งก็ไม่เคยต่ออายุ session จริง 4 บัญชีนี้ไม่มีกิจกรรมจริง (หน้าเว็บ/เรียก API อื่น) มานานเกิน 30 นาทีก่อน 23:36 จึงถูกเซิร์ฟเวอร์ตัดทิ้งเอง ไม่เกี่ยวกับการกู้ session ของ `tc9020`/`tc9021` เลย เป็นเรื่องบังเอิญที่เวลาใกล้กัน ซ้ำเติมด้วยว่าไม่มี keepalive ตัวไหนดูแล training69 ในช่วงนั้น (`session-keepalive.log` ตัวเดียวที่มีอยู่ชี้ production เท่านั้น และรันครั้งสุดท้ายก่อนเหตุการณ์กว่า 90 นาที) แก้แล้วด้วยการกู้ session ทั้ง 4 บัญชีสำเร็จ (`verify_t69_all_234112.log` = 10/10) ยังไม่มีการแก้เครื่องมือ/เอกสาร — รอเจ้าของงานอนุมัติมาตรการป้องกันด้านล่าง

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

**กลไกที่ตรวจแล้วและปฏิเสธ (ไม่ใช่สาเหตุ):**
- `session_capture.js:148-151` — ทุกบัญชีเปิด `chromium.launch()` + `browser.newContext()` ใหม่แยกกันในแต่ละรอบ `captureOne()` ไม่มี `userDataDir`/persistent profile ที่จะพาคุกกี้บัญชีอื่นติดมาได้
- `session_verify.js:109-118` — ใช้ `request.newContext({storageState})` แยกต่อบัญชี เป็น pure API request ไม่มีการแชร์ browser/cookie jar ข้ามบัญชีเช่นกัน
- `ols-monorepo/.../session.service.ts` — `rotate()` (บรรทัด 55-64) จบเฉพาะ token เดิมของ**ผู้ใช้เดียวกัน**ที่กำลัง re-authenticate ในทรานแซกชันเดียว, `endAllSessionsOwnedBy()` (บรรทัด 98-107) จบ session ของ `session.userId` เดียวเท่านั้น — grep `concurrent.?session|single.?session|device.?bound|device.?fingerprint|session.?limit|revoke.*other` ทั่ว `apps/api/src/modules/auth` (ไม่รวม node_modules/.spec.ts) ได้ 0 ผลลัพธ์ — ไม่มีโค้ดที่บัญชีหนึ่งจบ session อีกบัญชีในระบบที่ทีมนี้ดูแล (NDLP SSO ชั้นบนเป็นระบบภายนอกที่ตรวจไม่ได้จาก repo นี้ แต่ไม่จำเป็นต้องอ้างถึงเพราะพบกลไกที่อธิบายได้ครบแล้วในชั้นที่ตรวจได้)

**กลไกจริง:**
- `session-liveness.policy.ts:3-8` — `isSessionLive()` ต้องการ `lastActivityAt + idleTtlMs > now` แยกจาก `expiresAt` (อายุคุกกี้) โดยสิ้นเชิง
- `session-context.guard.ts:27-29` — `refreshActivity = !(GET && path.endsWith('/auth/get-session'))` เขียนตั้งใจให้ `GET /auth/get-session` **ไม่ต่ออายุ** `lastActivityAt`
- `session_verify.js:100-105` (คอมเมนต์ในไฟล์เอง) เลือกยิง `GET /auth/get-session` ด้วยคุกกี้ที่บันทึกไว้ **โดยไม่โหลดหน้า** ตั้งใจเพื่อเลี่ยงบั๊กคลาส #0092 (page-load ทำให้ NDLP-link proxy สร้าง session ใหม่ให้แบบเงียบๆ จนตรวจแล้ว "ok" ทั้งที่ session เดิมตายแล้ว) — การแก้ #0092 ถูกต้องสำหรับปัญหาของมันเอง แต่มีผลข้างเคียงที่ไม่เคยถูกบันทึกไว้ที่ไหน: **`session_verify.js` เองก็ไม่เคยต่ออายุ session ที่มันตรวจ**
- 4 บัญชีนี้ไม่มีกิจกรรมจริง (page load / เรียก API อื่นนอกจาก get-session) มานานพอที่จะเกิน 30 นาที ก่อน 23:36 — ไม่มี keepalive ใดดูแล training69 อยู่เลย (สคริปต์กลางที่มีชี้ production ตายตัว) การรัน `session_verify.js` ซ้ำๆ ที่ 23:14 → 23:22 → 23:31 ให้ผล "ok" ทุกครั้งกลบความจริงว่านาฬิกา idle เดินไม่หยุด จนตัดที่ 23:36

### 5 Whys

1. **ทำไม session ของ 4 บัญชีตายพร้อมกันในหน้าต่าง 5 นาที?** — เพราะไม่มีกิจกรรมจริง (นอกจาก get-session) เกิน 30 นาที นาฬิกา idle ฝั่งเซิร์ฟเวอร์ตัดพร้อมกันโดยบังเอิญตรงกับช่วงเวลาที่เข้าไปตรวจ
2. **ทำไมรัน `session_verify.js` ที่ 23:31 บอก "ok" ทั้งที่นาฬิกาใกล้หมด?** — เพราะ `session_verify.js` เรียกเฉพาะ `GET /auth/get-session` ซึ่งฝั่งเซิร์ฟเวอร์ตั้งใจไม่นับเป็นกิจกรรมที่ต่ออายุ (`session-context.guard.ts:27-29`)
3. **ทำไมออกแบบให้ verify ไม่ต่ออายุ?** — เพราะการแก้บั๊กคลาส #0092 (page-load ทำให้ session ที่ตายจริงดูเหมือนฟื้นเอง) ต้องเลี่ยงการโหลดหน้า ซึ่งเป็นการแก้ที่ถูกต้อง แต่ทำให้ verify กลายเป็นเครื่องมือ "อ่านอย่างเดียว" ที่ไม่มีผลต่อสถานะจริงของบัญชี
4. **ทำไมไม่มีอะไรมาต่ออายุแทน?** — เพราะไม่มี keepalive job ตัวไหนตั้ง target เป็น training69 เลย (`session_keepalive.sh:30-33` ล็อก `OLS=<PROD_HOST> (production)` ไว้ตายตัวสำหรับ production เท่านั้น) และไม่มีการสร้าง keepalive เฉพาะสำหรับรอบ training69 นี้
5. **ทำไมไม่มีใครสร้าง keepalive สำหรับ training69 ตั้งแต่ย้ายรอบมา?** — เพราะ `README-training-run.md` §4 เขียนกฎเรื่อง "ห้ามเปิดตัวอุ่นพร้อมชุดเทสต์" (กันการชนกันของบัญชีเดียวกัน) แต่ไม่เคยเขียนกฎอีกด้านคือ "ถ้าไม่ได้รันชุดเทสต์ต่อเนื่อง ต้องมี keepalive อยู่เสมอ มิฉะนั้นบัญชีที่ไม่ได้ใช้งานจะตายใน 30 นาที" — เอกสารสอนแค่ครึ่งเดียวของกฎ (ห้ามชนกัน) แต่ไม่ได้สอนอีกครึ่ง (ต้องมีตัวต่ออายุเสมอเมื่อไม่ได้ใช้งานต่อเนื่อง) — **root cause จริง**

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- `README-training-run.md` §4 ครอบคลุมเฉพาะ "คุกกี้หมุนชนกันเมื่อถือสำเนาบัญชีเดียวกัน 2 ที่พร้อมกัน" ไม่ครอบคลุม "บัญชีที่ไม่มีใครใช้งานต่อเนื่องจะโดน idle timeout ตัดเงียบ"
- `session_verify.js` เองพิมพ์ "ok" + ชั่วโมงคุกกี้ที่เหลือ ซึ่งดูน่าเชื่อถือ (23.1h) แต่ไม่มีบรรทัดไหนเตือนว่าตัวเลขนี้ไม่เกี่ยวกับนาฬิกา idle 30 นาทีที่แยกกันอยู่ — ผู้ใช้เครื่องมือ (รวมถึง AI) จึงอ่านว่า "ปลอดภัยไปอีก 23 ชม." ทั้งที่ผิด
- keepalive กลางที่มีอยู่จริงชี้ production ตายตัว ไม่มีการ์ดใดเตือนว่า "กำลังทำงานบน training69 แต่ไม่มี keepalive คลุมสภาพแวดล้อมนี้อยู่เลย"
- ไม่มี lint/CI ตรวจว่าทุก environment ที่ปรากฏใน `capture/accounts_*.json` ต้องมี keepalive job ที่ target ตรงกันอยู่จริงระหว่างรอบทำงาน

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ก่อนสรุปว่าเป็นบั๊ก "ล็อกอินบัญชีหนึ่งฆ่าบัญชีอื่น" ได้อ่านโค้ดจริงของทั้ง `session_capture.js`/`session_verify.js` และ `ols-monorepo` auth module ก่อน แทนที่จะเชื่อสมมติฐานเดิมใน `PENDING.md` — ป้องกันการเปิดบั๊กผิดตัวและเสียเวลาสืบผิดทาง
- log ทุกไฟล์ที่ใช้เป็นหลักฐาน (`verify_t69_all_*.log`, `capture_*.log`, `session-keepalive.log`) มีอยู่แล้วบนดิสก์ ไม่ต้องยิง training69 ซ้ำเพื่อสืบสาเหตุ

### สิ่งที่ต้องปรับปรุง
- `PENDING.md` แถวเดิมเปิดด้วยสมมติฐานเชิงกลไก ("ล็อกอินบัญชีหนึ่งฆ่า session บัญชีอื่น") ทั้งที่ยังไม่ได้ตรวจโค้ด — ถ้าไม่มีการสืบสวนรอบนี้ อาจถูกอ้างต่อเป็นข้อเท็จจริงในรอบหน้า
- ไม่มีเอกสารไหนอธิบาย idle TTL 30 นาทีแยกจากอายุคุกกี้ 24 ชม. มาก่อน ทั้งที่กลไกนี้อยู่ในโค้ดมานานและเคยเป็นสาเหตุของ #0072/#0026 มาแล้ว
