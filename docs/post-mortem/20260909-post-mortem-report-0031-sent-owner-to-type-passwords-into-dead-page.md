## สรุปสั้น (Executive Summary)

เจ้าของงานสั่งให้เก็บ session ล็อกอินของ training69 จำนวน 10 บัญชี เมื่อเปิดเบราว์เซอร์ครั้งแรก ทุกบัญชีล้มด้วย
`ERR_CERT_AUTHORITY_INVALID` ผมเดาว่าเป็นโปรแกรมความปลอดภัยในเครื่องที่ re-sign ใบรับรอง (เคยมีบันทึกเรื่องนี้ในหน่วยความจำ)
จึงเสนอให้ข้ามการตรวจใบด้วย `INSECURE_TLS=1` เจ้าของงานอนุมัติ รอบที่สองผ่านเรื่องใบรับรองไปได้ แต่เครื่องมือหาช่องอีเมลไม่เจอ
แล้ว **พิมพ์ว่า `could not find #email — type both fields yourself` พร้อมเปิดหน้าต่างค้างไว้ให้กรอก** ผมส่งรายชื่ออีเมลให้เจ้าของงาน
ไปนั่งพิมพ์ตาม

ของจริงคือ **โฮสต์ SSO ของ training69 ตอบ HTTP 404 ทุก path** ด้วย body 19 ไบต์ `404 page not found` รวมทั้งหน้าแรก
หน้าต่างที่เจ้าของงานถูกสั่งให้กรอกรหัสผ่านลงไปจึงเป็นหน้า 404 ไม่ใช่หน้าล็อกอิน ต่อให้พิมพ์ถูกก็เข้าไม่ได้

สาเหตุมี 2 ชั้นซ้อนกัน: **ผมข้ามสัญญาณเตือนโดยไม่ตรวจสิ่งที่มันเตือน** (ใบรับรองที่ผิดปกติกับ 404 เป็นอาการของเหตุเดียวกัน คือ
reverse proxy ไม่มี route ของโฮสต์นี้) และ **เครื่องมือกลืนความล้มเหลว 3 ชนิดให้เหลือข้อความเดียว** เพราะทิ้งผลลัพธ์ของ
`page.goto` และดักหา selector ด้วย `.catch(() => {})`

แก้แล้วที่ชั้นเครื่องมือ: อ่านรหัสตอบกลับและปฏิเสธเมื่อ ≥ 400 · หา `#email` ไม่เจอแล้วปฏิเสธพร้อมพิมพ์ input ที่เห็นจริง ·
เจอหน้าเว็บตายแล้วหยุดทั้งรอบ ยืนยันด้วยเทสต์ใหม่ 8 เคสที่รันกับเซิร์ฟเวอร์จำลอง 3 แบบ เขียวครบ
ส่วนตัว portal ที่ล่มเป็นเรื่องของทีมที่ดูแล ingress แก้จากฝั่งเราไม่ได้

## 1. ปัญหา (Problem Statement)

- รอบแรกทุกบัญชีล้มทันทีด้วย `page.goto: net::ERR_CERT_AUTHORITY_INVALID at https://<T69_SSO_HOST>/sign-in/embed`
- ใบรับรองของโฮสต์นั้นคือ `issuer=CN=TRAEFIK DEFAULT CERT` `subject=CN=TRAEFIK DEFAULT CERT` `notBefore=Sep  9 03:07:20 2026 GMT`
  — ใบที่ Traefik สร้างเองเมื่อหาใบจริงของโฮสต์ไม่เจอ และเพิ่งถูกสร้างเช้าวันเดียวกัน
- รอบที่สองด้วย `INSECURE_TLS=1` เครื่องมือพิมพ์ `[t69_ct9020_training] could not find #email — type both fields yourself.`
  แล้วเปิดหน้าต่างค้างรอ ผมส่งรายชื่ออีเมลทั้ง 10 ให้เจ้าของงานพิมพ์
- บัญชีแรกจบด้วย `FAILED: timed out waiting for an auth cookie — nothing saved` หลังรอครบ 8 นาที
- ยิงตรวจเองด้วย `curl` ได้ผลว่าโฮสต์นั้นตอบ **404 ทุก path รวมหน้าแรก** ด้วย body 19 ไบต์เท่ากันทุกครั้ง
  ขณะที่โฮสต์ของตัวแอป OLS ตอบ 200 ตามปกติ
- เก็บ session ได้ **0 จาก 10 บัญชี** ไม่มีไฟล์ `state_t69_*.json` ถูกสร้างเลย

**สิ่งที่ควรจะเป็น:** เครื่องมือต้องปฏิเสธตั้งแต่รู้ว่าหน้าปลายทางตอบ 404 และห้ามเชิญให้คนกรอกรหัสผ่านลงหน้าที่ยังไม่ได้ยืนยันว่าเป็นหน้าล็อกอิน
ตามกฎข้อแรกสุดของ repo (ห้ามพูดสิ่งที่ยังไม่ได้ตรวจเหมือนเป็นข้อเท็จจริง) และตามบทเรียนของรายงาน #0005 ที่ระบุว่าการ์ดต้องมีสถานะที่ 3
คือ "ตรวจไม่ได้" และสถานะนั้นต้องนำไปสู่การปฏิเสธ

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

ความผิดพลาดไม่ได้อยู่ที่ "เดาผิดว่าเป็น Bitdefender" อย่างเดียว — การเดานั้นถูกจับได้และแก้คำพูดไปแล้วภายในไม่กี่นาที
สิ่งที่แพงกว่าคือ **ลำดับการกระทำ**: ผมเจอสัญญาณเตือน แล้วเลือก "ทำให้สัญญาณเงียบ" ก่อนที่จะ "ตรวจสิ่งที่สัญญาณกำลังเตือน"

ใบรับรองที่ผิดปกติกับ 404 ไม่ใช่ปัญหา 2 เรื่อง แต่เป็นอาการ 2 อย่างของเหตุเดียวกัน คือ reverse proxy ไม่มี route ของโฮสต์นี้
จึงตกไปใช้ทั้งใบสำรองและ backend 404 ของตัวเอง ถ้ายิง `curl` 1 ครั้งก่อนเสนอให้ข้ามการตรวจใบ — ใช้เวลาราว 2 วินาที —
จะเห็น 404 ทันที และคำถามที่ถามเจ้าของงานจะเปลี่ยนจาก "จะข้ามการตรวจใบไหม" (คำถามที่ตั้งอยู่บนสมมติฐานผิด)
เป็น "portal ล่ม จะรอหรือจะแจ้งทีม" ซึ่งเป็นคำถามที่ถูก

ชั้นที่สองคือตัวเครื่องมือเอง มันมีจุดกลืนความล้มเหลว 3 จุดต่อกันเป็นทอด:

- ทิ้งค่าที่ `page.goto` คืนมา จึงไม่มีทางรู้ว่าเซิร์ฟเวอร์ตอบ 404
- `waitForSelector('#email').catch(() => {})` กลืนทั้ง "ช่องย้ายที่" "หน้าไม่ใช่หน้าล็อกอิน" และ "เบราว์เซอร์ตาย"
- ตอนกรอกไม่สำเร็จ พิมพ์ประโยคเดียวว่า `type both fields yourself` แล้ว **เดินต่อ** ไปรอคุกกี้ 8 นาที

ผลรวมคือความล้มเหลวเชิงสภาพแวดล้อมถูกนำเสนอต่อมนุษย์ในรูปของ "คุณช่วยพิมพ์เองหน่อย" ซึ่งอ่านแล้วเหมือนงานเดินปกติ

### 5 Whys

1. **ทำไมเจ้าของงานถูกสั่งให้พิมพ์รหัสผ่านลงหน้า 404?** — เพราะเครื่องมือรายงานว่าหาช่องอีเมลไม่เจอ แล้วเปิดหน้าต่างค้างไว้ให้กรอกเอง
2. **ทำไมเครื่องมือถึงรายงานแบบนั้นแทนที่จะปฏิเสธ?** — เพราะมันไม่เคยตรวจว่าหน้าที่โหลดมาเป็นหน้าอะไร มันทิ้งรหัสตอบกลับของ `page.goto` และดัก selector ด้วย `.catch(() => {})`
3. **ทำไมถึงไปถึงขั้นโหลดหน้านั้นได้ ทั้งที่รอบแรกถูกใบรับรองสกัดไว้แล้ว?** — เพราะผมเสนอให้ข้ามการตรวจใบด้วย `INSECURE_TLS=1` และเจ้าของงานอนุมัติ
4. **ทำไมผมถึงเสนอให้ข้าม ทั้งที่ยังไม่รู้ว่าหน้านั้นคืออะไร?** — เพราะผมจับคู่อาการกับความจำเรื่อง AV ที่ re-sign ใบรับรอง แล้วถือว่าอธิบายได้แล้ว จึงข้ามไปหาวิธีทำให้ผ่าน โดยไม่ยิงดูสถานะของหน้าเลยสักครั้ง
5. **ทำไมการจับคู่กับความจำถึงถูกนับว่าเพียงพอ?** — **เพราะคำอธิบายที่ "เข้ากันได้" ถูกใช้แทนคำอธิบายที่ "ตรวจแล้ว" เมื่อมันชี้ไปทางที่ทำให้งานเดินต่อได้** สัญญาณเตือนที่ขวางอยู่จึงถูกมองเป็นอุปสรรคที่ต้องข้าม ไม่ใช่ข้อมูลที่ต้องอ่าน — และนี่คือ root cause ที่ปิดได้ทั้งคลาส ไม่ใช่แค่เคสใบรับรอง

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**

- **การตรวจใบรับรองของเบราว์เซอร์** — จับได้ และจับถูกด้วย มันคือชั้นเดียวที่ทำงาน แต่ถูกปิดด้วยมือ
- **`require_target.js`** — ตรวจแค่ว่าปลายทางเป็น env ที่ห้ามแตะไหม ไม่ได้ตรวจว่าปลายทางยังมีชีวิตอยู่ไหม อยู่นอกขอบเขต
- **`session_capture.js`** — ควรเป็นชั้นที่จับ แต่กลืนความล้มเหลวไว้ทั้ง 3 จุดตามข้างบน
- **เทสต์ของ `session_capture.js`** — **ไม่มีอยู่เลยก่อนวันนี้** จึงไม่มีอะไรตรึงพฤติกรรมตอนหน้าปลายทางพัง
- **ตัวผมเอง** — มีข้อมูลครบตั้งแต่นาทีที่ 1 (ใบรับรองผิดปกติ + ทุกบัญชีล้มเหมือนกันเป๊ะ) แต่ตีความว่าเป็นปัญหาเฉพาะที่ของเครื่อง แทนที่จะเป็นสัญญาณว่าปลายทางผิดปกติ

## 5. แนวทางการแก้ไข (Fix)

- `capture/session_capture.js` — อ่านค่าที่ `page.goto` คืนมา และโยน error พร้อมธง `fatalEnv` เมื่อสถานะเป็น `null` หรือ ≥ 400

- `capture/session_capture.js` — กรณีเจอช่องแต่กรอกไม่สำเร็จ ก็ปฏิเสธ ไม่พิมพ์ประโยคชวนให้กรอกเองอีกต่อไป

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** subagent ที่ถูกส่งไปสืบด้วย `superpowers:systematic-debugging` เป็นคนยิงดูรหัสตอบกลับของหน้านั้นเป็นคนแรก
  แล้วผมยืนยันซ้ำเองด้วย `curl` · เจ้าของงานเป็นคนเปิดประเด็นก่อนหน้านั้นด้วยคำว่า "แว้ปๆ ไรละ" ซึ่งชี้ว่ามีอะไรผิดปกติบนจอ
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** ราว 12 นาทีนับจากรอบเก็บครั้งแรกล้ม และราว 8 นาทีนับจากที่ผมส่งเจ้าของงานไปพิมพ์
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** P1 ทำให้เครื่องมือปฏิเสธทันทีที่โหลดหน้าเจอ 404 โดยไม่ต้องรอมนุษย์ ไม่ต้องรอ 8 นาที
  และไม่ต้องมีใครสังเกตว่าหน้าต่างเด้งแปลกๆ — เวลาที่ใช้รู้ลดจาก 12 นาทีเหลือทันทีที่ request แรกจบ

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ถามเจ้าของงานก่อนข้ามการตรวจใบรับรอง แทนที่จะกดเอง — ทำให้การตัดสินใจเรื่องความปลอดภัยอยู่กับคนที่ควรตัดสิน
- แยก subagent ไปสืบตามกฎ ทำให้ได้คำตอบภายในไม่กี่นาทีแทนที่จะงมเอง
- ไม่เชื่อผล subagent ทันที ยิง `curl` ยืนยันเองก่อนรายงาน
- ไม่มีรหัสผ่านถูกพิมพ์โดย agent ไม่มีข้อมูลถูกเขียนบน training69 และตัวยกเว้นถูกออกแบบให้ไม่รั่วไปหางานตามตาราง

### สิ่งที่ต้องปรับปรุง
- **คำอธิบายที่ "เข้ากันได้กับอาการ" ไม่ใช่คำอธิบายที่ "ตรวจแล้ว"** โดยเฉพาะเมื่อมันชี้ไปทางที่ทำให้งานเดินต่อได้ — ตรงนี้คือจุดที่ผมพลาด
- ต้นทุนของการตรวจ (1 คำสั่ง ~2 วินาที) เทียบกับต้นทุนของการเดา (เจ้าของงานนั่งพิมพ์ในหน้าที่ตายแล้ว) ต่างกันหลายร้อยเท่า
  และผมประเมินต้นทุนฝั่งหลังต่ำเกินไปเพราะไม่ได้คิดว่ามันจะไปจบที่มนุษย์
- เครื่องมือที่ส่งหน้าต่างให้มนุษย์กรอกรหัสผ่าน ต้องถือมาตรฐานสูงกว่าเครื่องมือทั่วไป เพราะข้อความของมันคือคำสั่งที่คนทำตาม
