## สรุปสั้น (Executive Summary)

เลนซ้อม R3 เปิดไลฟ์บน dev 2 ครั้ง แล้วรายงานว่าเหลือวิดีโอย้อนหลัง 2 รายการ "status DRAFT" ผมพิมพ์ต่อให้เจ้าของงานว่าเป็นแบบร่างทั้งคู่และผู้เรียนมองไม่เห็น
แล้วถามว่าจะลบไหม โดยไม่เคยเปิดสถานะจริง · เลนลบ (C1) อ่านสถานะก่อนลบแล้วพบว่า 1 รายการเป็น PUBLISHED จึงไม่แตะ ·
ผมแจ้งแก้ในแชทแล้วขออนุมัติใหม่ แต่ตัวเลือก "ลบรายการนี้ (แนะนำ)" ก็ยังไม่ได้ตรวจว่าระบบยอมให้ลบสื่อที่เผยแพร่อยู่ไหม
ผลคือเซิร์ฟเวอร์ตอบ 409 `media.not_deletable` เพราะลบได้เฉพาะ DRAFT และ PENDING_EDIT · ตอนนี้วิดีโอยังเป็นเผยแพร่ รอเจ้าของงานเลือกทางใหม่

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

คำว่า "DRAFT" มาจากบรรทัด ledger ของเลน R3 ซึ่งเขียนตามที่เลนคิดว่าเป็น ไม่ใช่ค่าที่อ่านจาก API ทีละรายการ ผมเอาไปพูดต่อตรงๆ
และเติมข้อสรุปของตัวเองว่า "ผู้เรียนมองไม่เห็น" ต่อจากคำนั้นอีกชั้น · รอบแก้ ผมตรวจโค้ดเรื่อง soft delete แต่ไม่ได้ตรวจเงื่อนไขว่าสถานะไหนลบได้
ทั้งที่เปิดไฟล์ `media.entity.ts` ส่วนที่มี `isDeletable()` ซึ่งเรียก `status.isDeletable()` ไปแล้ว

### 5 Whys

1. ทำไมเจ้าของงานตัดสินใจบนข้อมูลผิด — เพราะคำถามบอกว่าทั้ง 2 รายการเป็นแบบร่าง
2. ทำไมคำถามบอกแบบนั้น — เพราะผมคัดคำของเลน R3 มาโดยไม่ได้ `GET` สถานะเอง
3. ทำไมไม่ได้ `GET` — เพราะข้อมูลอยู่ใน ledger ที่ดูเป็นระเบียบ มี id ครบ จึงถูกอ่านเป็นผลวัด ทั้งที่เป็นคำบรรยายของเลน
4. ทำไมรอบแก้ยังแนะนำทางที่ทำไม่ได้ — เพราะตรวจแค่คำถามที่นึกถึง (ลบแล้วกู้ได้ไหม) ไม่ได้ตรวจคำถามก่อนหน้า (ลบได้ไหม)
5. ทำไมไม่มีชั้นไหนจับ — ด่านที่มีอยู่ (#0076, #0080) ผูกกับข้ออ้างเชิงลบและคำว่า "ตรวจแล้ว" แต่ไม่ครอบ "สถานะของข้อมูลที่จะให้เจ้าของงานตัดสินใจ" ในตัวเลือกของป๊อปอัป

## 4. ผลกระทบ (Impact)

- เจ้าของงานต้องตอบคำถามเดิม 2 รอบ และตัวเลือกที่ผมแนะนำทั้ง 2 รอบใช้ไม่ได้
- วิดีโอย้อนหลังจากการซ้อม 1 รายการยังเป็นเผยแพร่บน dev ผู้เรียนเปิดดูได้ ตั้งแต่ราว 21:36 จนกว่าจะแก้
- ไม่มีข้อมูลของใครถูกลบหรือแก้ผิด เพราะเลน C1 และ C2 ตรวจสถานะก่อนลงมือและหยุดเมื่อไม่ตรง

## 5. แนวทางการแก้ไข (Fix)

- แจ้งแก้ในแชทแล้วว่ารายการ `01a0b4f1` เป็นเผยแพร่
- ถามเจ้าของงานใหม่ด้วยทางที่ตารางสถานะใน `media-status.vo.ts` อนุญาตจริง: สถานะ Published ไป PendingEdit ได้ด้วย RequestEdit แล้ว PendingEdit อยู่ในรายการที่ลบได้ (`MEDIA_DELETABLE_STATUSES = [Draft, PendingEdit]`) · ทาง "ยกเลิกการเผยแพร่ แล้วค่อยลบ" **ใช้ไม่ได้** เพราะ Unpublished ไปได้แค่ RequestEdit → PendingEdit หรือ Republish → Published และ Unpublished ไม่อยู่ในรายการที่ลบได้
- ข้อจำกัดที่ยังไม่ได้ตรวจ: สื่อชนิด LIVESTREAM ที่ยังรอเก็บไฟล์ไลฟ์ถูกปฏิเสธการลบเพิ่มอีกชั้นโดย `media.entity.ts` `isAwaitingLivestreamArchive()` และ **ยังไม่ได้ตรวจ** ว่า request-edit อนุญาตกับสื่อ LIVESTREAM หรือไม่
- *แก้ไข 2026-09-18:* ฉบับแรกของข้อนี้เสนอ "ยกเลิกการเผยแพร่ แล้วค่อยลบ" ว่าตรวจแล้ว ซึ่งผิด · ดูรายงาน #0083

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

1. **ก่อนถามเจ้าของงานให้อนุมัติการเขียน/ลบข้อมูล ต้อง `GET` สถานะของทุกรายการในคำถามในเทิร์นนั้นเอง** และใส่สถานะที่อ่านได้ลงในข้อความคำถาม
2. **ตัวเลือกที่ติดป้าย "(แนะนำ)" ต้องตรวจแล้วว่าทำได้จริง** — ชี้ path:line ของเงื่อนไขที่อนุญาตการกระทำนั้น ไม่ใช่แค่เงื่อนไขของผลลัพธ์
3. บรรทัด ledger ที่เลนเขียนเป็นคำบรรยาย ไม่ใช่ผลวัด — ถ้าจะอ้างสถานะ ต้องอ่านจาก API

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- คำสั่งงานของเลนลบบังคับตรวจก่อนลบและจำกัดขอบเขตเฉพาะสถานะที่อนุมัติ จึงไม่มีการลบผิด

### สิ่งที่ต้องปรับปรุง
- ข้อมูลที่ใช้ตัดสินใจลบ ต้องอ่านสดทุกครั้ง ไม่รับต่อจากเลนอื่น
- เมื่อแนะนำทางใด ต้องตรวจว่าระบบอนุญาตการกระทำนั้นก่อน
