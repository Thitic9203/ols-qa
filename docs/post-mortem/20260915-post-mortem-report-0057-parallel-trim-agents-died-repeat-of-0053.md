## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไม 5 ใน 6 เลนตัดฉากตายก่อนทำงาน?** — เพราะ stream ของ agent เงียบเกิน 600 วินาทีหลัง (หรือระหว่าง) tool call แรกๆ (4 เลน) และเพราะ API ตอบ rate-limit 429 (1 เลน) — infrastructure-level, ไม่ใช่บั๊กใน task/prompt
2. **ทำไม stream stall / rate limit เกิดตอนนี้?** — เพราะมี agent ทำงานพร้อมกัน **11 ตัว** ในเซสชันเดียว (5 อัดใหม่ + 6 ตัดฉาก) ซึ่งแต่ละตัวยิง API request จำนวนมาก (context-mode tools, cliptool, gate_postclip) พร้อมกันหมด — ใช้แบนด์วิดท์/โควตาของ API ร่วมกันจนล้น
3. **ทำไม dispatch พร้อมกัน 11 ตัว?** — เพราะเจ้าของงานสั่งชัดว่า "แยก agent ทำให้มากที่สุด" (ตอนอัดใหม่) แล้วต่อมาสั่ง "จัดการมาเลย" (ตัดฉาก) โดยไม่มีใครหยุดคิดว่า 2 ชุดคำสั่งนี้จะถูกนับรวมกันเป็นภาระ API เดียวกัน — ตัดสินใจ dispatch ชุดใหม่ 6 ตัวโดยไม่เช็คว่ามีกี่ตัวกำลังรันอยู่แล้ว (`ListAgents` ไม่ได้ถูกเรียกก่อน dispatch รอบนั้น)
4. **ทำไมมาตรการ "persist ก่อน print" จาก #0053 ไม่ช่วย?** — เพราะมาตรการนั้นบอกว่า "เขียนทันทีที่มีผลลัพธ์แรก" แต่ agent ที่ตายด้วย stream stall ตายตั้งแต่**ช่วงสำรวจ/โหลด context-mode tools** ซึ่งเป็นขั้นตอนก่อนที่จะมีผลลัพธ์อะไรให้ persist เลย — คำสั่งเดิมไม่ได้บังคับว่า "เขียนบรรทัดแรกก่อนเรียก tool ตัวแรกด้วยซ้ำ" ยังมีช่องว่างตรงจุดเริ่มต้น
5. **Root cause จริง (จุดที่ยังไม่ปิด):** จำนวน agent พร้อมกันในเซสชันเดียวเกินขีดที่ infrastructure รองรับได้อย่างเสถียร — ยังไม่มีใครวัดได้ว่าเพดานที่แท้จริงคือกี่ตัว (11 ตัวพัง, ยังไม่เคยวัดว่า 5-6-7-8 ตัวจะพังไหม) และไม่มีกลไกใดในเซสชันที่เช็คจำนวน agent ที่กำลังรันอยู่ก่อน dispatch ชุดใหม่

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** #0053 ปิดได้แค่ "ราคา" ของปัญหา (เปลี่ยนจาก print-heartbeat เป็น persist-first) ไม่ได้ปิดตัวปัญหาเอง (สาเหตุที่ stream เงียบยังตรวจไม่ได้จริงเพราะไม่มี log ฝั่ง harness/transport ให้ดู — ระบุไว้ตรงๆ ใน #0053 เองแล้ว) รอบนี้พิสูจน์ว่ามาตรการที่มีไม่พอ เพราะไม่มีชั้นไหนเลยที่เช็ค "กำลังมี agent รันอยู่กี่ตัว" ก่อนจะ dispatch เพิ่ม — ไม่มีเพดานจำนวน agent พร้อมกันที่บังคับไว้ที่ไหนเลย

## 5. แนวทางการแก้ไข (Fix)

- Dispatch ใหม่ 5 เลนที่ตาย (agent id `a77c2cb956fd3396f`, `a546996774eedb88e`, `a56ced3f511511aad`, `a298827b0d228aa36`, `a46d2c480b689fa5e`) ด้วย case list เดิมทุกตัวอักษร (ยืนยันแล้วว่าไม่มีเคสไหนถูกแก้ไปก่อนหน้า เพราะ log ว่าง = ไม่มีการเขียนจริง)
- เพิ่มคำสั่งในทุก prompt: "Your very first action must be to append one line to your log file … before doing anything else" — ปิดช่องว่างที่ #0053's persist-first ยังไม่ครอบ (ช่วงก่อนมี tool result แรก)
- ลดจำนวน agent พร้อมกัน — ไม่ dispatch ซ้อนกับ agent อัดใหม่ชุดเดิมอีก (เช็คด้วย `ListAgents` ก่อน dispatch: พบว่าเหลือ subagent ทำงานจริงแค่ 1 ตัว ณ ตอนนั้น ก่อนจะ dispatch retry 5 ตัว)

**ยืนยันแล้วด้วย:** เลน System B จบงานจริงระหว่างที่เขียนรายงานนี้ — 24/24 เคส (11 ผ่าน + 13 ต้องอัดใหม่ถูกต้อง) verdict readback ยืนยันครบทุกเคสที่ผ่าน — *ผล retry ของอีก 5 เลนยังไม่ทราบ ณ เวลาที่เขียนรายงานฉบับนี้ ดู Action Items*

- ตรวจ log ไฟล์จริงก่อนรายงานเจ้าของงาน (ไม่เชื่อแค่ข้อความ failure summary) ทำให้รู้ชัดว่า 5 เลนไม่มีอะไรถูกเขียนเลย ไม่ใช่แค่ "เขียนไม่ครบ"

### สิ่งที่ต้องปรับปรุง
- ควรเรียก `ListAgents` เช็คภาระที่มีอยู่ก่อน dispatch ชุดใหม่เสมอ โดยเฉพาะเมื่อเพิ่งมี agent ชุดก่อนยังไม่รายงานผลครบ
- คำสั่ง "persist ก่อน print" ที่เขียนจาก #0053 ยังกว้างเกินไป ("ตามที่ทำงานไป") ต้องเจาะจงกว่านั้นว่า "ก่อนเรียก tool ตัวแรกด้วยซ้ำ"
