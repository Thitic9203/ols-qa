## สรุปสั้น (Executive Summary)

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

hook ของ `rtk` เขียนคำสั่ง `grep` ใหม่ให้เป็นคำสั่งของ rtk เพื่อลดขนาดเอาต์พุตที่เข้า context · สำหรับการอ่าน นี่คือการย่อผล แต่เมื่อผลถูก redirect ลงไฟล์ ผลที่ย่อ/จัดรูปก็กลายเป็นเนื้อไฟล์
และ `rtk grep` ไม่ได้รักษาความหมายของ `-v` (พิมพ์บรรทัดที่ตรงแทนบรรทัดที่ไม่ตรง) ในขณะที่รหัสจบยังเป็น 0 จึงไม่มีสัญญาณอะไรบอกว่าผลผิด

### 5 Whys

1. **ทำไมไฟล์ที่ stage ลบไป 126 บรรทัด?** — เพราะเนื้อไฟล์เป็นเอาต์พุตของ `rtk grep` ไม่ใช่ผลของ `grep -v`
2. **ทำไมเนื้อไฟล์เป็นเอาต์พุตของ rtk?** — เพราะ hook เขียนคำสั่ง `grep` ใหม่ทั้งคำสั่ง รวมถึงกรณีที่ผลถูก redirect ลงไฟล์ และ `rtk grep` ไม่รักษาความหมายของ `-v`
3. **ทำไม subagent ใช้ shell pipe/redirect เขียนไฟล์ใน repo?** — เพราะต้องแยกแถวของคนอื่นออกจากไฟล์ที่ถูกแก้ร่วมกัน และ `grep -v > file` เป็นวิธีปกติของ shell · ไม่มีบันทึกว่า brief ของ subagent ห้ามการเขียนไฟล์ผ่าน shell pipe (โฟลเดอร์งานเก็บไว้แค่ `PM0091.jsonl` กับ `PM0091_RESULT.md` ไม่มีตัว brief)
4. **ทำไมบทเรียนจาก #0051 และ #0090 ไม่กันเหตุนี้?** — #0051 จดว่าเอาต์พุตของ rtk ไม่ใช่ผลจริง แต่ในบริบท "อ่านแล้วรายงาน" · #0090 จดเรื่อง `grep|sed` บนไฟล์ secrets ในบริบท "พิมพ์ค่าลับ" · ทั้งสองไม่ได้ขยายเป็นกฎว่า **คำสั่ง shell ที่ผลถูกเขียนลงไฟล์ อาจถูก hook เปลี่ยนความหมาย** และไม่มีชั้นเครื่องมือใดตรวจ
5. **ทำไมไม่มีชั้นใดปฏิเสธก่อน stage?** — เพราะ hook ของ rtk เขียนคำสั่งใหม่แบบไม่แยกว่าผลไปที่ context หรือไปที่ไฟล์ และ postmortem-guard ไม่เทียบจำนวนแถวของบัญชีหนี้ที่ stage กับ HEAD (ค้น `HEAD|decreas|fewer|removed|shrink|git show` ใน `tools/postmortem-guard/*.js` ที่ไม่ใช่เทสต์ ไม่พบการเทียบแบบนี้) — root cause ของคลาสนี้คือ ตัวเขียนคำสั่งใหม่ถูกออกแบบให้ย่อสิ่งที่คนอ่าน แต่ถูกใช้กับคำสั่งที่ผลเป็นข้อมูลที่ต้องถูกต้องทุกไบต์

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- rtk hook — ไม่แยกกรณี redirect/pipe ลงไฟล์ และรหัสจบเป็น 0
- postmortem-guard — ถูกรันก่อนที่ไฟล์จะถูกสร้างผิด (step 15) และไม่มีกฎว่าแถวในบัญชีหนี้ต้องไม่ลดลงเมื่อเทียบกับ HEAD · pre-commit ไม่ได้ถูกทดสอบกับ blob นี้เพราะไม่ได้คอมมิต จึง **ไม่ทราบ** ว่าจะปฏิเสธหรือไม่
- brief ของ subagent — ไม่มีบันทึกว่าห้ามเขียนไฟล์ผ่าน shell pipe
- ชั้นที่จับได้จริง: การตรวจ `git diff --cached --stat` ของ subagent ก่อนคอมมิต (คนทำ ไม่ใช่เครื่องมือ)

## 8. บทเรียนที่ได้ (Lessons Learned)
