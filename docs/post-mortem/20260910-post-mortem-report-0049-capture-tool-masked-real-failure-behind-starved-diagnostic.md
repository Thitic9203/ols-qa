## สรุปสั้น (Executive Summary)

ตัวอัดคลิป `g2dbg_record_wheelfix.js` เขียนเช็คท้ายการรันไว้เป็นรายการ guard clause ตามลำดับที่เขียนในไฟล์ ไม่ใช่ตามลำดับเหตุ-ผล:
ตัวแปร `failed` (เก็บ exception ของขั้นตอนที่ล้มกลางทาง) ถูกตั้งค่าไว้ตั้งแต่บรรทัด 690 แต่เช็คของมัน
(`if (failed) die('run aborted mid-flow…')`) อยู่ท้ายสุดที่บรรทัด 769 ขณะที่เช็คอาการปลายทางสองข้อ
(`die('capture hit the … scratch budget…')` บรรทัด 732 และ `die('capture starved…')` บรรทัด 738) เรียก
`process.exit` ไปก่อนเสมอ ผลคือเมื่อขั้นตอนล้มจริงจนคลิปสั้นผิดปกติ เครื่องมือจะรายงานว่า "เฟรมไม่พอ ปิดโปรแกรมหนักแล้วรันใหม่"
แทนที่จะบอกว่าขั้นตอนไหนล้มด้วยอะไร คืนนี้บั๊กนี้ยิงจริงกับการรันเคส `Badge_TC_004` (คลิปยาวเพียง 1.761 วินาที
25 เฟรม `uniqueFps` ตกเหลือ 14.19 จากพื้น 20) ถูกจับได้จากการเปิดดูค่ากระจายจริง (`medianGapMs: 19` ≈ 52 fps —
เครื่องไม่ได้ช้า) แล้วเทียบกับบทเรียนของรายงาน #0028 ที่เคยเจอรูปแบบเดียวกันมาก่อน แก้แล้วโดยแยกตรรกะตัดสินผล
ออกเป็นโมดูลบริสุทธิ์ `recorder_verdict.js` ที่เช็ค `failed` ก่อนเสมอ พร้อมเทสต์ 9 เคสที่รันผ่านจริง (exit code 0)
ยืนยันทั้งพฤติกรรมใหม่และการเดินสายของไฟล์จริง

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

จุดตัดสินใจที่ผิดไม่ได้เกิดตอนเขียนข้อความ `die()` แต่ละข้อ (แต่ละข้อความบรรยายอาการของมันถูกต้อง) —
จุดที่ผิดคือ**ลำดับที่วางเช็คทั้งสามไว้ในไฟล์** เขียนตามลำดับที่ "คิดขึ้นได้" (สแครตช์บัดเจ็ตก่อน เพราะเป็น
ข้อจำกัดทางดิสก์ที่ชัดที่สุด → เฟรมเรตก่อน เพราะเป็นตัวชี้วัดคุณภาพคลิปที่ชัดรองลงมา → ขั้นตอนที่ล้มเป็น
ข้อสุดท้าย เพราะดูเหมือนเป็น "เคสพิเศษ" มากกว่า "เช็คคุณภาพมาตรฐาน") ไม่ใช่ตามลำดับ**เหตุ-ผล** เมื่อ
ขั้นตอนหนึ่งล้ม มันคือสาเหตุต้นทางของทุกอย่างที่ตามมา (คลิปสั้น → เฟรมเรตต่ำ) แต่โค้ดกลับให้ผลลัพธ์ปลายทาง
(เฟรมเรตต่ำ) ได้พูดก่อนสาเหตุต้นทาง เพราะ `die()` เรียก `process.exit` ทันทีที่เจอเงื่อนไขแรกที่เป็นจริง
ไม่มีกลไกใดใน guard-clause แบบเรียงลำดับธรรมดาที่จะ "มองย้อนกลับ" ไปถามว่ามีสาเหตุอื่นที่รู้อยู่แล้วหรือไม่
ก่อนจะพิมพ์ข้อความอาการปลายทางออกไป

ที่ทำให้ลำดับผิดนี้ไม่มีใครจับได้จนกว่าจะยิงจริงมีสามอย่างประกอบกัน หนึ่ง `stats` (ก้อนตัวเลขที่มาจาก
การนับเฟรม) กับ `failed` (exception ของขั้นตอน) เป็นข้อมูลคนละก้อนที่คำนวณจากคนละกลไก ไม่มีฟิลด์ไหนใน
`stats` บอกว่า "ค่านี้ต่ำเพราะคลิปสั้นจากความล้มเหลว" — โค้ดต้องเทียบทั้งสองก้อนเองถึงจะรู้ สอง ทั้ง
สแครตช์บัดเจ็ตและเฟรมเรตต่ำเป็นเงื่อนไขที่**เกิดขึ้นจริงและอันตรายจริง**เมื่อไม่มีขั้นตอนล้ม (เช่นเครื่อง
โหลดหนักจริงๆ) จึงดูสมเหตุสมผลที่จะเขียนเป็นเช็คแยกอิสระจากกัน สาม บั๊กคลาสนี้เคยถูกวินิจฉัยถูกต้อง
มาแล้วในรายงาน #0028 — วินิจฉัยถูกทั้งอาการและกลไก แต่ทางแก้ที่แท้จริง (ทำให้เครื่องมือแยกสาเหตุให้เอง)
ถูกวางไว้เป็นรายการ "ค้าง" ในตาราง Action Items แล้วไม่เคยถูกหยิบมาทำต่อ

### 5 Whys

1. **ทำไมผู้ปฏิบัติงานถึงเกือบได้รับคำแนะนำว่า "ปิดโปรแกรมหนักแล้วรันใหม่" สำหรับเคส `Badge_TC_004`?**
   — เพราะ `die()` พิมพ์ข้อความ `capture starved: 14.19 unique fps against a 20 floor … Close other
   heavy work and re-run…` ออกมาจริง ในขณะที่สาเหตุจริงคือขั้นตอนหนึ่งล้มกลางทาง
2. **ทำไมข้อความถึงพูดเรื่องเฟรมเรตแทนที่จะพูดเรื่องขั้นตอนที่ล้ม?** — เพราะเช็ค
   `if (stats.uniqueFps < MIN_UNIQUE_FPS) die(...)` ที่บรรทัด 736–738 เจอเงื่อนไขเป็นจริงและเรียก
   `process.exit` ไปก่อน โดยที่โค้ดไม่เคยวิ่งไปถึงเช็ค `if (failed) die(...)` ที่บรรทัด 769 เลย
3. **ทำไมเช็ค `failed` ถึงอยู่หลังเช็คอาการ ทั้งที่ `failed` ถูกตั้งค่าไว้ตั้งแต่บรรทัด 690 ซึ่งอยู่ก่อนหน้ามาก?**
   — เพราะทั้งสามเช็คถูกเขียนเรียงกันเป็นรายการ guard clause ตามลำดับที่นึกออก (สแครตช์บัดเจ็ต →
   เฟรมเรต → ขั้นตอนล้ม) ไม่ใช่ตามลำดับว่าอันไหนคือสาเหตุต้นทางของอันไหน
4. **ทำไมไม่มีใครจัดลำดับตามเหตุ-ผลตั้งแต่แรก?** — เพราะ `stats` ก้อนตัวเลขจากการนับเฟรม ไม่มีข้อมูล
   เชื่อมโยงกับ `failed` เลย ทั้งสองเช็คแยกกันดูสมเหตุสมผลเมื่อพิจารณาทีละเงื่อนไข (เครื่องโหลดหนักจริง /
   ดิสก์เต็มจริง ก็เป็นสาเหตุที่ถูกต้องได้เหมือนกัน) — ต้องมีคนตั้งคำถามชัดๆ ว่า "ถ้าเงื่อนไขทั้งสองเป็นจริง
   พร้อมกัน อันไหนควรถูกพูดก่อน" ถึงจะเห็นปัญหา และไม่มีใครถามคำถามนั้นตอนเขียนโค้ดครั้งแรก
5. **ทำไมคำถามนั้นไม่เคยถูกถาม ทั้งที่รายงาน #0028 เคยเจอบั๊กคลาสเดียวกันมาก่อนแล้วและวินิจฉัยกลไกนี้
   ไว้ถูกต้องครบถ้วน?** — **เพราะทางแก้ที่แท้จริง (P4 ของรายงาน #0028: "ให้ด่านตรวจแยกสาเหตุให้เองระหว่าง
   'ช้าทั้งคลิป' กับ 'นิ่งเป็นช่วง'") ถูกบันทึกไว้ถูกต้องในตาราง Prevention แต่มีสถานะ "ค้าง — นอกขอบเขต
   ของรอบนั้น" โดยไม่มีกลไกใดบังคับให้กลับมาทำต่อ มันจึงเป็นแค่บรรทัดเดียวในตารางที่ไม่มีอะไรเตือนซ้ำ ไม่ใช่
   หนี้ที่มีวันครบกำหนดเหมือนแถวใน `docs/post-mortem/PENDING.md`** — นี่คือ root cause จริง: ปัญหาไม่ใช่
   "ไม่รู้ว่าต้องแก้อะไร" (รู้แล้วตั้งแต่ #0028) แต่คือ "รู้แล้วแต่ไม่มีกลไกบังคับให้ทำ" จนกว่าโค้ดเดิมจะยิงพัง
   ซ้ำอีกรอบจริงๆ

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- **รายงาน #0028 เอง** — วินิจฉัยกลไกนี้ถูกต้องทุกประการและเสนอทางแก้ที่ถูกต้อง (P4) แต่ขอบเขตของรอบนั้น
  จำกัดไว้แค่แก้ checkpoint เฉพาะไฟล์ `*.play.json` ที่เป็นต้นเหตุของครั้งนั้น ไม่ได้แตะตัวเครื่องมือ
  `g2dbg_record_wheelfix.js` เอง ซึ่งเป็นไลบรารีกลางที่ทุกสคริปต์อัดใช้ร่วมกัน — แก้จุดเดียวไม่ใช่การปิดคลาส
  (บทเรียนเดียวกับรายงาน #0012 เรื่อง "ปิดบั๊กคลาสไหน ต้องไล่หาไฟล์อื่นที่เป็นคลาสเดียวกันในรอบเดียวกัน")
- **ตาราง Action Items ของรายงาน #0028** — บันทึกไว้ถูกต้องว่า P4 ยัง "Open" แต่ไม่มีกลไกใดในเครื่องมือ
  หรือ hook ของ repo ที่จะเตือนซ้ำเมื่อ Action Item สถานะ Open ของรายงานเก่ายังไม่ถูกปิด (ต่างจาก
  `docs/post-mortem/PENDING.md` ที่มี hook 10 ชั้นบังคับให้ต้องจัดการก่อนจะทำงานอื่นต่อได้)
- **ไม่มีเทสต์ใดๆ คลุม `g2dbg_record_wheelfix.js` เลยก่อนคืนนี้** — ไฟล์นี้เป็นจุดตัดสินใจที่มีผลว่าคลิปไหน
  "ห้ามส่ง" แต่ไม่เคยมี regression gate ใดจับการจัดลำดับผิดของ `die()` calls ได้เลยจนกว่าจะมีคนอ่านผลจริง
  อย่างละเอียดด้วยตัวเอง

## 5. แนวทางการแก้ไข (Fix)

- **แยกตรรกะตัดสินผลท้ายการรันออกเป็นโมดูลบริสุทธิ์** — เพิ่มไฟล์ `out/review-vdo-integration/recorder_verdict.js`
  (off-repo) ที่รับ `{failed, stats, minUniqueFps, maxScratchMb, mp4}` แล้วตัดสินตามลำดับเหตุ-ผลที่ถูกต้อง:
  1. `failed` (สาเหตุ) → `reason: 'step-failed'`, ข้อความระบุชัดว่า "This is the cause… those numbers
     are a consequence of the run ending early, not a machine-load problem"
  2. `stats.overBudget` (ไม่มีขั้นตอนล้ม แต่ดิสก์เต็มจริง) → `reason: 'scratch-budget'`
  3. `stats.uniqueFps < minUniqueFps` (ไม่มีขั้นตอนล้ม แต่เฟรมเรตจริงๆ ต่ำ) → `reason: 'starved'`
  4. `stats` อ่านไม่ได้ → `reason: 'no-stats'`, ปฏิเสธเสมอ ไม่ใช่ผ่านเงียบๆ (โมดูลอ้างถึงบทเรียนรายงาน
     #0005/#0006 ตรงๆ ในคอมเมนต์)
- **แก้ `g2dbg_record_wheelfix.js`** — เพิ่ม `require('./recorder_verdict.js')` ที่บรรทัด 35 · แทนที่เช็ค
  `stats.overBudget` / `stats.uniqueFps` ที่เคยอยู่ตรงๆ ในไฟล์ (เดิมบรรทัด 730–741) ด้วยการเรียก
  `verdict({...})` ที่บรรทัด 733 แล้วเช็ค `if (V.fatal) { capture.cleanup(); die(V.message); }` ที่บรรทัด
  740–743 · จุดเช็ค `if (failed) die(...)` เดิมที่บรรทัด 769 ถูกลบออก เหลือเพียงคอมเมนต์อธิบายว่า `failed`
  ถูกจัดการโดย `verdict()` ไปแล้ว — ยืนยันด้วย `grep` ว่า literal `die(\`capture starved` เดิมหายไปจากไฟล์
  จริงหมดแล้ว (grep คืนค่าว่าง, exit code 1)

**ยืนยันแล้วด้วย:** รันคำสั่ง `node test_recorder_verdict.js` จริง ได้ผลลัพธ์:

```
ok   a clean run is not fatal
ok   a step failure with GOOD capture numbers reports the step
ok   a step failure with STARVED numbers still reports the step, never starvation
ok   a step failure with starved numbers still SHOWS the capture numbers
ok   a step failure outranks the scratch budget too
ok   starvation with NO step failure is still reported as starvation
ok   scratch budget with no step failure is reported as the budget
ok   missing stats is a refusal, not a pass
ok   the live recorder consumes this module and checks the step failure first

all green — 9 checks ran
```

รหัสจบของคำสั่ง (`echo $?`) = **0** — รวมเคสที่จำลองรูปทรงของ `Badge_TC_004` โดยตรง
(`uniqueFps: 14.19`) และเคสสุดท้ายที่**อ่านซอร์สไฟล์จริง**ของ `g2dbg_record_wheelfix.js` มายืนยันว่า
require โมดูลจริง เรียก `verdict()` จริง และไม่มี literal เดิมหลงเหลือ — ไม่ใช่แค่คำกล่าวอ้างในคอมเมนต์
ว่า "แก้แล้ว" (ตามบทเรียนรายงาน #0001: คำประกาศคุณสมบัติของโค้ดตัวเองต้องมีเทสต์ยืนยัน)

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** ไม่ใช่ automation — ก่อนคืนนี้ไม่มีเทสต์ใดคลุมไฟล์นี้เลย จับได้จากการอ่าน
  `capture.json` ของเคส `Badge_TC_004` และข้อความ `die()` อย่างละเอียด แล้วเทียบกับบทเรียนของรายงาน
  #0028 ที่มีอยู่แล้ว (ค่ากลางปกติแต่สแปน/ค่าสูงสุดผิดปกติ = เหตุการณ์เดียว ไม่ใช่ภาวะทั้งคลิป)
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** ไม่สามารถระบุนาทีที่แม่นยำได้จากหลักฐานที่มี — ระบุได้แค่ว่าเกิดขึ้นในคืน
  เดียวกัน จาก `capture.json` เขียน 22:54 → ไฟล์สำรองของการแก้ ~23:05 → มติเจ้าของงานบันทึก ~23:10
  คือภายในเวลาประมาณ 15–20 นาที
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** `test_recorder_verdict.js` ที่เพิ่มเข้ามาตอนนี้จะจับ regression ได้
  ทันทีถ้าใครแก้โค้ดกลับไปเป็นลำดับเดิมโดยไม่ตั้งใจ (เคสสุดท้ายอ่านซอร์สไฟล์จริงเทียบ ไม่ใช่แค่เทสต์โมดูล
  แยกส่วน) — แต่ยังไม่มีกลไกอัตโนมัติใดที่จะจับ "ข้อความ `die()` ชี้ผิดสาเหตุ" ได้ตั้งแต่ครั้งแรกที่บั๊ก
  รูปแบบเดียวกันเกิดใหม่ในไฟล์อื่นที่ยังไม่ได้ตรวจ (P4 ด้านบน) — ยังต้องพึ่งคนอ่านอย่างละเอียดเหมือนคืนนี้

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ไม่เชื่อข้อความ `die()` ตรงๆ แต่เปิดตัวเลขกระจายจริง (`medianGapMs`, `spanSeconds`, `p95GapMs`)
  เทียบกับบทเรียนที่มีอยู่แล้วจากรายงาน #0028 — คือการทำตามกฎ P3 ของรายงานนั้นเป๊ะ พิสูจน์ว่ากฎนั้นใช้ได้จริง
  เมื่อมีคนนำไปปฏิบัติ ไม่ใช่แค่ข้อความในเอกสาร
- แก้ที่ต้นเหตุจริงในโค้ดทันทีพร้อมเทสต์ยืนยันในรอบเดียวกัน แทนที่จะบันทึกเป็นกฎแล้วเลื่อนการแก้จริงออกไป
  เหมือนที่ #0028's P4 เคยเป็น
- เทสต์ใหม่ (`test_recorder_verdict.js`) เขียนเคสที่ตรวจ "ข้อความ" ไม่ใช่แค่ "รหัสจบ" (`v.reason`,
  `v.message` ต้องมี substring ที่ถูกต้อง) ตรงตามบทเรียนรายงาน #0002/#0006 ที่ผูกไว้ในคอมเมนต์ของไฟล์เทสต์เอง

### สิ่งที่ต้องปรับปรุง
- รายงาน #0028 วินิจฉัยกลไกนี้ถูกต้องทุกประการและเสนอทางแก้ที่ถูกต้อง (P4) แต่ปล่อยไว้เป็นบรรทัด "ค้าง"
  ในตาราง Action Items โดยไม่มีกลไกบังคับให้ทำต่อ — จนเกิดซ้ำจริงอีกครั้งภายใน 2 วัน ก่อนจะถูกแก้จริงคืนนี้
- ก่อนคืนนี้ `g2dbg_record_wheelfix.js` ซึ่งเป็นตัวอัดคลิปหลักของงานทั้งชุด และเป็นจุดตัดสินใจว่าคลิปไหน
  "ห้ามส่ง" ไม่มีเทสต์คลุมเลยสักบรรทัด — จุดตัดสินใจที่มีผลกระทบสูงขนาดนี้ควรมีเทสต์ตั้งแต่วันแรกที่เขียน
  ไม่ใช่รอให้พังจริงก่อนถึงจะมี
- เทสต์ใหม่ที่เขียนขึ้นมีจุดคลาดเคลื่อนเล็กน้อยที่ควรบันทึกไว้ตรงๆ: ค่าคงที่ `STARVED` ในไฟล์เทสต์ใช้
  `p95GapMs: 19, maxGapMs: 5251.9` (ตัวเลข `maxGapMs` ตรงกับตัวอย่างในรายงาน #0028 พอดี) ขณะที่ตัวเลขจริง
  ของเคส `Badge_TC_004` คือ `p95GapMs: 322, maxGapMs: 522.9` — มีเพียง `uniqueFps: 14.19` เท่านั้นที่ตรงกัน
  ระหว่างค่าคงที่ในเทสต์กับข้อมูลจริง แม้คอมเมนต์ในไฟล์เทสต์จะเขียนว่า "the exact shape of the 10/Sep
  Badge_TC_004 run" ก็ตาม — ความคลาดเคลื่อนนี้**ไม่กระทบความถูกต้องของตรรกะที่แก้** (`verdict()` ตัดสินจาก
  `failed` / `overBudget` / `uniqueFps < floor` เท่านั้น ไม่ได้ใช้ค่า `p95GapMs`/`maxGapMs` ในการตัดสิน)
  แต่คอมเมนต์ที่อ้างว่า "exact shape" ควรใช้ตัวเลขจริงจาก `capture.json` แทนตัวเลขที่หยิบยืมมาจากรายงานอื่น
