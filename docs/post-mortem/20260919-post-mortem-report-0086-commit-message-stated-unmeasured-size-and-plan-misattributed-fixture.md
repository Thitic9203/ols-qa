## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

ตัวเลข "~20 KB" เป็นค่าที่คาดไว้ตอนวางแผนย่อ ไม่ใช่ค่าที่วัดได้ และถูกพิมพ์ลงข้อความคอมมิตในคำสั่งเดียวกับ `git push` จึงไม่มีจังหวะวัดระหว่างสองขั้นนี้
ส่วน `Content_TC_005` ถูกเลือกเพราะเป็นเคสที่เลน RC3 *กำลังอัด* ตอนเกิดเหตุ ซึ่งจำได้ง่ายกว่าเคสที่ *เสียข้อมูล* จึงเขียนตามความจำแทนการเปิดรายงานต้นทาง

### 5 Whys

1. **ทำไมข้อความคอมมิตมีตัวเลขผิด?** — เพราะเขียนขนาดที่คาดไว้แทนขนาดที่วัดได้
2. **ทำไมไม่วัดก่อน?** — เพราะรวม add + commit + push ไว้ในคำสั่งเดียว และไม่มีขั้นใดระหว่างนั้นที่บังคับให้เอาค่าจริงมาใส่
3. **ทำไมใส่ `~` ได้ทั้งที่ #0083 ห้ามแล้ว?** — เพราะมาตรการของ #0083 เป็นกฎที่เขียนไว้สำหรับรายงาน post-mortem และมี `check.js` ตรวจเฉพาะไฟล์รายงาน ไม่ครอบคลุมข้อความคอมมิต และไม่ครอบคลุม repo อื่น
4. **ทำไมแผนผูก fixture ผิดเคส?** — เพราะสรุปจากความจำเรื่องเลนที่กำลังอัดอยู่ ไม่ได้ยกบรรทัดจากรายงาน #0085 ที่มีอยู่แล้วในเซสชันเดียวกัน
5. **ทำไมทั้งสองเรื่องหลุดออกไป?** — root cause: **ข้อความถาวร (ข้อความคอมมิต / เอกสารแผน) ถูกเขียนจากความจำ และไม่มีชั้นเครื่องใดตรวจก่อนที่ข้อความจะถาวร** กฎห้าม `~` มีอยู่แค่ในเอกสาร จึงพึ่งความจำของผู้เขียนเพียงชั้นเดียว

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- `tools/postmortem-guard/check.js` ตรวจเฉพาะไฟล์รายงาน post-mortem
- `git-staging-guard` ตรวจแค่การ stage แบบเหมา ยังไม่ได้อ่านข้อความคอมมิต
- pre-push ของ ols-qa-evidence รันเทสต์ ไม่ได้ตรวจข้อความ
- ไม่มีชั้นใดเทียบเนื้อหาแผนกับรายงาน post-mortem ที่อ้างถึง
