## สรุปสั้น (Executive Summary)

- เธรดหลักคอมมิตแผน `5c12a69` บน `main` ในเครื่อง แล้วรัน `git push -q` และรายงานเจ้าของงานว่าแผน "ขึ้น main แล้ว"
- push จริงถูกปฏิเสธ เพราะคอมมิต release bump อัตโนมัติ (`a282256` v1.55.2, 15:26:40 +0700) เข้า origin ก่อนคอมมิตแผน (15:28:50 +0700) แต่ `-q` ซ่อนข้อความปฏิเสธ

- พบเองตอนเริ่มรอบถัดไป แก้ด้วย rebase บน origin/main → `5755557` แล้ว push สำเร็จ ยืนยันด้วย `git log origin/main`
- ชั้นป้องกันใหม่: ตัวยืนยันหลัง push ที่วัดจาก origin จริง (ดูหัวข้อ 6) แทนการพึ่งการอ่าน output ของ push

## 1. ปัญหา (Problem Statement)

- `git reflog` ในเครื่อง: `5c12a69 HEAD@{2026-10-14 15:28:50 +0700}: commit: docs(plan): apply adversarial review — …`
- `git log origin/main` มีคอมมิต release `a282256 2026-10-14 08:26:40 +0000 chore(release): bump version to v1.55.2` อยู่ก่อน — origin เดินหน้าไปแล้วตอนที่ push ออกไป จึงเป็น non-fast-forward และถูกปฏิเสธ
- `5c12a69` ไม่เคยอยู่บน origin (`git log origin/main` ไม่มีคอมมิตนี้) ตัวที่ขึ้นจริงคือ `5755557` จากการ rebase: `5755557 HEAD@{2026-10-14 15:47:51 +0700}: rebase (finish): returning to refs/heads/main`

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

จุดตัดสินใจที่ผิดคือการเลือก "หลักฐาน" ของสถานะ remote: คำสั่ง `git log` ไม่มีอาร์กิวเมนต์อ่านแค่ branch ในเครื่อง ซึ่งมีคอมมิตใหม่ตั้งแต่ตอน commit แล้ว จึงให้ผลเหมือนกันทั้งกรณี push สำเร็จและล้มเหลว — เป็นการวัดที่ไม่มีทางตก ตอนนั้นมันดูถูกเพราะเคย push ผ่านติดกันหลายครั้ง และไม่เห็นข้อความ error ใดๆ บนจอ (ซึ่งเป็นผลของ `-q`)

### 5 Whys

1. **ทำไมเจ้าของงานได้รับสถานะ "ขึ้น main แล้ว" ที่ไม่จริง?** — เพราะเธรดหลักสรุปจาก `git log` ฝั่ง local ว่าคอมมิตอยู่บน main
2. **ทำไม `git log` ฝั่ง local ถึงถูกใช้เป็นหลักฐาน?** — เพราะไม่มีขั้นตอนบังคับที่ต้องวัดจาก origin หลัง push และไม่เห็น error บนจอจึงถือว่าสำเร็จ
3. **ทำไมไม่เห็น error?** — เพราะใช้ `git push -q` ซึ่งซ่อนข้อความ `! [rejected] … (fetch first / non-fast-forward)` และผลลัพธ์ของคำสั่งที่ส่งกลับมาก็ไม่ได้ถูกอ่านเป็นรหัสจบแยก
4. **ทำไม push ถึงถูกปฏิเสธตั้งแต่แรก?** — เพราะ repo มี workflow release ที่คอมมิต version bump ขึ้น main อัตโนมัติหลังทุก push ที่แตะของ release ทำให้ origin เดินหน้าภายในไม่กี่นาทีหลัง push ก่อนหน้า — local main ที่ไม่ได้ fetch ก่อน commit จึงล้าหลังบ่อยมาก (วันนี้มี bump 6 ครั้ง: v1.55.1–v1.55.6)
5. **ทำไมสภาพที่ push ล้มบ่อยขนาดนี้ยังไม่มีตัววัดผลหลัง push?** — root cause: เคลม "อยู่บน remote แล้ว" ไม่มีชั้นเครื่องมือใดบังคับ มีแต่กฎตัวหนังสือ (global ข้อ 17) ที่พึ่งให้ผู้เคลมเลือกคำสั่งตรวจถูกเอง และ repo นี้ทำให้ push ล้มเป็นเรื่องปกติ (release bump อัตโนมัติ) โดยไม่มีอะไรตรวจปลายทางให้

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- กฎ global ข้อ 17 ห้ามเคลม push โดยไม่เช็ค `git log` — ถูกทำตามตามตัวอักษร (เช็ค `git log` แล้ว) แต่ไม่ได้ระบุว่าต้องเป็น `origin/main` จึงเปิดช่องให้ log ฝั่ง local ผ่าน
- `scripts/hooks/pre-push` รันเทสต์ก่อน push — ทำงานก่อนส่ง ไม่รู้ผลของการส่ง และกรณี non-fast-forward ถูก server ปฏิเสธหลังจากนั้น
- ไม่มี hook หรือเครื่องมือใดตรวจหลัง push ว่า sha อยู่บน origin จริง
- รายงานที่ใกล้เคียง: #0064 (พูดกลไกของ push เป็นข้อเท็จจริงก่อนทดลอง) และ #0092 (รายงาน session ยังดีจากการโหลดหน้า ซึ่งเป็นการวัดตัวแทน) — คลาสเดียวกันคือ "วัดผิดวัตถุแล้วเคลม" แต่คนละพื้นผิว ไม่มีรายงานก่อนหน้าเรื่องเคลมสถานะ push โดยตรง (ค้นด้วย `grep -l -i "origin/main\|rejected\|push -q" docs/post-mortem/2*.md` ได้ 20 ไฟล์ อ่านสรุปแล้วไม่มีเคสนี้)

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- พบเองก่อนเจ้าของงานพึ่งสถานะนั้นไปทำงานต่อ และแก้ด้วย rebase ไม่ใช้ force-push
- เปิดแถว PENDING พร้อม sha ทั้งสองตัว ทำให้รายงานนี้ตรวจย้อนได้จาก reflog

### สิ่งที่ต้องปรับปรุง
- การวัดที่ให้ผลเหมือนกันทั้งกรณีสำเร็จและล้มเหลวไม่ใช่การวัด — ต้องเลือกคำสั่งที่ตกได้จริง
- `-q` บน push ทำให้ช่องทางเดียวที่จะเห็นการปฏิเสธหายไป ต้องมีตัวยืนยันที่ไม่พึ่ง output ของ push
