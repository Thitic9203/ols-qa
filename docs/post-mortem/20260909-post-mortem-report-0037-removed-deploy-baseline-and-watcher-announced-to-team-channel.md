## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### กลไกที่ทำให้คีย์เดียวเปลี่ยนผลลัพธ์ทั้งหมด

`main()` เลือกใบที่จะยิงด้วยลูปสั้นๆ ที่ `smoke_watch.py:291-295`

```
for m in msgs:            # newest first — take the newest unhandled one
    ok, _ = is_dev_deploy_done(m)
    if ok and m["id"] not in state["handled"]:
        hit = m
        break
```

มีเงื่อนไข 2 ข้อ คือ **ผ่านด่านความสมบูรณ์** และ **ยังไม่เคยถูกจัดการ** ประเด็นอยู่ที่ลูปนี้ **ไม่ได้หยุดที่ใบล่าสุด
แต่ไล่ลงไปเรื่อยๆ จนกว่าจะเจอใบที่ครบทั้งสองข้อ** ผลคือ

- ใบ deploy ที่ยังหมุนอยู่ ณ ตอนนั้น **ตกด่านที่ `deploy_trigger.py:101-102`** — ด่านทำงานถูกต้อง
- ลูปจึงเดินต่อลงไปข้างล่าง แล้วไปเจอใบเช้าที่ ✅ อยู่แล้ว และเพิ่งถูกผมปลดออกจากเส้นฐาน
- ใบเช้าครบทั้งสองเงื่อนไข ลูปจึงหยุดที่ใบนั้น

**นี่คือจุดที่ต้องเข้าใจให้ตรง** การปลดเส้นฐานไม่ได้แค่ "เล่นเหตุการณ์เก่าซ้ำ" อย่างที่ผมคิดตอนนั้น แต่มัน
**ทำให้ตัวเฝ้าไปลงมือกับใบที่ตกยุค ในจังหวะที่มันกำลังปฏิเสธใบปัจจุบันอยู่พอดี** ด่านกันของที่ทำงานถูกต้อง
กลับกลายเป็นตัวที่ผลักลูปให้เลื่อนลงไปหาใบเก่า

และไม่มีอะไรในไฟล์นี้ที่ดูอายุของใบที่เลือกได้เลย — คำว่า `age` ปรากฏที่เดียวคือ `smoke_watch.py:188-191`
ซึ่งเป็นอายุของ **ไฟล์ล็อก** ไม่ใช่ของข้อความ ส่วนช่อง `timestamp` ของข้อความไม่เคยถูกอ่านสักครั้ง

### ทำไมผมถึงไปแก้ไฟล์สถานะตั้งแต่แรก

สองอย่างประกอบกัน และทั้งคู่เป็นคุณสมบัติของเครื่องมือ ไม่ใช่ความบังเอิญ

1. **ไม่มีโหมดที่ไม่ส่งจริง** — ค้นทั้งไฟล์ด้วย `argparse` · `sys.argv` · `--dry` · `dry_run` · `no_send`
   ได้ **0 รายการ** ท้ายไฟล์เป็น `sys.exit(main())` และ `main()` ไม่รับพารามิเตอร์ใดเลย แปลว่าการรันตัวนี้
   มีความหมายเดียวคือ "ทำของจริง" ไม่มีท่ารันเพื่อดูว่ามันจะทำอะไร
2. **เส้นฐานตอนติดตั้งเป็นของที่พิมพ์เอง** — ข้อความ `baseline at install — pre-existing, never run` ที่อยู่ใน
   ไฟล์สถานะ **ไม่ปรากฏในซอร์สไฟล์ใดเลย** (ค้น `smoke/` · `sfd/` · สคริปต์ระดับบนสุดแล้วไม่พบ) เพราะ
   `load_state()` ที่ `:178` คืน `{"handled": {}}` เมื่อไม่มีไฟล์ ซึ่งแปลว่ารอบแรกจะยิงกับ deploy ที่ค้างอยู่ในช่องทันที
   คนติดตั้งจึงต้องเขียนเส้นฐานกันเอาไว้เอง — **ไฟล์สถานะถูกทำให้เป็นช่องที่คนกรอกตั้งแต่นาทีแรก**

พอไฟล์นั้นเป็นของที่ผมเพิ่งพิมพ์ลงไปเมื่อ 4 นาทีก่อน การลบออก 1 บรรทัดจึงไม่รู้สึกเหมือน "แก้สถานะของระบบที่กำลังเดินอยู่"
มันรู้สึกเหมือนแก้ไฟล์ตั้งค่าของตัวเอง ทั้งที่เป็นการกระทำเดียวกันเป๊ะ

### 5 Whys

1. **ทำไมช่องของทีมถึงได้รับข้อความ `Starting smoke test on dev` ทั้งที่ไม่มี deploy ใหม่?** — เพราะตัวเฝ้าไปยิงกับ
   ประกาศ deploy ของเมื่อเช้า ซึ่งผมทำให้มันกลับมามีสิทธิ์อีกครั้งด้วยการลบคีย์ออกจาก `handled`
2. **ทำไมการลบคีย์เดียวถึงทำให้มันยิง?** — เพราะการเป็นสมาชิกของ `handled` คือสิ่งเดียวที่กั้นระหว่างข้อความหนึ่งใบ
   กับการโพสต์จริง (`:293`) และลูปเลือกใบที่ **ผ่านด่านและยังไม่เคยจัดการ** ตัวที่ใหม่ที่สุด ใบเก่าที่ถูกปลดเส้นฐาน
   จึงชนะทันทีที่ใบปัจจุบันยังไม่ผ่านด่าน
3. **ทำไมผมถึงไปแก้ไฟล์สถานะ?** — เพราะผมต้องการพิสูจน์ว่า flow เดินครบเส้น และเครื่องมือนี้ **ไม่มีทางพิสูจน์ตัวเอง
   โดยไม่โพสต์ของจริง** ไม่มีโหมดซ้อม ไม่มีสวิตช์ไม่ส่ง
4. **ทำไมการพิมพ์ลงไฟล์สถานะถึงดูเป็นท่าปกติ?** — เพราะขั้นตอนติดตั้งของเครื่องมือนี้บังคับให้ต้องพิมพ์เส้นฐานลงไปเอง
   อยู่แล้ว ไฟล์สถานะจึงถูกสถาปนาเป็น "ของที่คนแก้ได้" ก่อนที่มันจะทำหน้าที่เป็นด่านกันของเสียอีก
5. **สาเหตุที่แท้จริง:** เครื่องมือที่ผลลัพธ์เดียวที่สังเกตได้คือ **ผลข้างเคียงที่ส่งออกไปข้างนอกและย้อนกลับไม่ได้**
   แต่ไม่มีโหมดซ้อม จะบังคับให้คนที่ดูแลมันต้องซ้อมกับของจริง และเมื่อขั้นตอนติดตั้งของมันยังต้องให้คนพิมพ์ค่าลง
   ไฟล์สถานะด้วยมือ ด่านเดียวที่ปกป้องช่องของทีมก็ถูกลดชั้นลงเป็นช่องกรอกของผู้ดูแลไปพร้อมกัน

### ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ

| ชั้น | ทำไมไม่จับ |

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

รายงาน #0034 ปิดด้วยคำเตือนว่า "ให้ใช้โหมดที่ไม่ส่งจริง" ซึ่งใช้กับเครื่องมือตัวนี้ไม่ได้เพราะมันไม่มีโหมดนั้น

*เครื่องมือที่ผลลัพธ์เดียวที่สังเกตได้คือการส่งออกไปข้างนอก ต้องมีโหมดซ้อมตั้งแต่วันแรกที่เขียน*

**ข้อที่ต้องขยายจาก #0034 ให้ชัด** — #0034 เขียนว่าห้ามแก้ไฟล์สถานะของ job ที่ยังติดตั้งอยู่ รอบนี้ผมทำผิดข้อนั้นเป๊ะ
แต่ไม่รู้สึกว่ากำลังทำ เพราะในหัวคิดว่า "กำลังตั้งค่าตัวที่เพิ่งติดตั้ง" ไม่ใช่ "กำลังแก้สถานะของ job ที่เดินอยู่"
กฎจึงต้องระบุตรงๆ ว่า **job ที่เพิ่งติดตั้งเมื่อไม่กี่นาทีก่อน ก็คือ job ที่เดินอยู่** และนาทีแรกหลังติดตั้งคือช่วงที่
อันตรายที่สุด เพราะยังไม่มีใครรู้ว่ามันจะทำอะไร

- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** ไม่ใช่การจับให้เร็วขึ้น แต่เป็นการทำให้เกิดไม่ได้ — P1 ทำให้การพิสูจน์

  **การตรวจจับหลังส่งไม่มีประโยชน์กับความผิดพลาดชนิดนี้ เพราะความเสียหายเกิดครบตั้งแต่วินาทีที่ข้อความออกไป**

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี

- เครื่องมือถูกออกแบบมาดีจริง ด่านทุกด่านทำงานถูกต้องในรอบที่เกิดเหตุ รวมถึงด่านที่ปฏิเสธ deploy ที่ยังหมุนอยู่
  ซึ่งเป็นด่านที่เพิ่งเขียนในวันเดียวกัน · ความเสียหายจึงจำกัดอยู่ที่ข้อความ 1 ใบและรอบทดสอบ 1 รอบ
- ไฟล์สถานะบันทึกทั้งเวลาและ tag ของทุกใบที่จัดการ ทำให้ไล่ย้อนได้ครบโดยไม่ต้องเปิดช่องดู
- แยกการตัดสินใจออกมาไว้ที่ `deploy_trigger.py` เป็นฟังก์ชันบริสุทธิ์ ทำให้ตรวจสอบได้ว่าด่านไม่ได้พัง

### สิ่งที่ต้องปรับปรุง

- **เครื่องมือที่ยิงออกไปข้างนอก ต้องเขียนโหมดซ้อมมาพร้อมกันตั้งแต่วันแรก** ไม่ใช่ค่อยเติมทีหลัง เพราะวันแรก
  คือวันที่คนเขียนอยากลองมันมากที่สุด และเป็นวันที่ยังไม่มีใครรู้ว่ามันจะทำอะไร
- **ขั้นตอนติดตั้งที่บังคับให้คนพิมพ์ค่าลงไฟล์สถานะ คือการสอนคนให้แก้ไฟล์นั้น** ถ้าไฟล์นั้นเป็นด่านกันของด้วย
  ก็เท่ากับสอนให้คนแก้ด่าน · สิ่งที่โปรแกรมต้องการเพื่อเริ่มทำงาน โปรแกรมต้องสร้างเอง
- **"ผมแค่อยากดูว่ามันทำงานไหม" ไม่ได้ทำให้ผลลัพธ์เบาลงเลย** ข้อความที่ออกไปถึงทีมมีน้ำหนักเท่ากันทุกใบ
  ไม่ว่าคนส่งจะตั้งใจให้เป็นการทดลองหรือไม่ · เจตนาอยู่ในหัวผม ผลอยู่บนหน้าจอคนอื่น
- **ผิดซ้ำภายใน 34 นาทีหลังเขียนกฎเอง** เป็นหลักฐานตรงๆ ว่ากฎที่เป็นตัวหนังสือกันเรื่องแบบนี้ไม่ได้
  ต่อให้เพิ่งเขียนเสร็จหมาดๆ ก็ตาม
