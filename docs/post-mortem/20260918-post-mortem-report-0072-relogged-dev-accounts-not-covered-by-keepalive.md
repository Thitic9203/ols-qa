## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

คำถามที่ผมถามตอน 08.15 คือ "session ใช้ได้ไหม" ซึ่งตอบได้แค่ ณ นาทีนั้น · คำถามที่ต้องถามคือ "session จะยังใช้ได้ตอนที่เลนเริ่มอัดไหม"
ซึ่งตอบได้จากรายชื่อของตัวรักษา session เท่านั้น และไม่เคยถูกเปิดดู · ในรอบเดียวกันผมรู้อยู่แล้วว่ามีตัวรักษา session (อ้าง pid 8307
ในเธรดนี้ตั้งแต่ต้น) แต่ไม่ได้ถามว่ามันดูแลบัญชีไหน

### 5 Whys

1. **ทำไม 3 บัญชีตาย?** — ไม่มีการใช้งานเกิน 30 นาที เซิร์ฟเวอร์ตัด session ทิ้ง
2. **ทำไมไม่มีการใช้งาน?** — ตัวรักษา session ไม่ได้ดูแลบัญชีเหล่านี้
3. **ทำไมไม่ได้ดูแล?** — รายชื่อตายตัวตั้งแต่ตอนเริ่มโปรเซส (17/Sep) ไม่ตามบัญชีที่ล็อกอินเพิ่มทีหลัง
4. **ทำไมไม่มีใครเห็นก่อนส่งเลน?** — การตรวจก่อนส่งเลนของผมคือ `session_verify.js` ซึ่งวัดสถานะ ณ จุดเวลา ไม่ได้วัดว่ามีอะไรรักษาสถานะนั้น
5. **ทำไมตัวตรวจก่อนอัดไม่จับตั้งแต่ก่อนส่ง?** — `recording_preflight.js` ถูกเรียกโดยเลน *หลัง* ส่งไปแล้ว ไม่ได้ถูกเรียกโดยเธรดหลัก *ก่อน* ส่ง
  **root cause:** ด่านตรวจ session ของ #0062 ยังไม่ถูกผูกเข้ากับจุดที่เธรดหลักส่งงาน (รายงาน #0062 เขียนไว้เองว่า "ยังไม่ได้ผูกเป็นด่านบังคับ")
  และไม่มีข้อตรวจว่า "ทุกบัญชีที่จะใช้ อยู่ในรายชื่อของตัวรักษา session ที่ยังมีชีวิต"

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** `recording_preflight.js` จับได้จริง (เลน RA หยุดถูกต้อง ไม่อัดทับด้วย session ตาย) แต่จับได้ช้า
เพราะอยู่ในมือเลน ไม่ใช่ในมือคนส่งเลน

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

| # | มาตรการ | ชนิด | สถานะ |
|---|---------|------|-------|
| P1 | ก่อนส่งงานที่ใช้ session เธรดหลักต้องรัน `recording_preflight.js` เอง สำหรับทุก tag ที่จะส่งให้เลน · ไม่ใช่ให้เลนรันหลังรับงาน | กฎ | ทำแล้ว (รายงานนี้ + สรุปใน `CLAUDE.md`) |

**กฎที่เพิ่มจากเหตุนี้:** *"session ใช้ได้ตอนนี้" ไม่ใช่คำตอบของ "session จะใช้ได้ตอนที่งานเริ่ม"* — ก่อนรายงานว่าบัญชีพร้อม
หรือก่อนส่งเลน ต้องชี้ได้ว่าตัวรักษา session ที่ยังมีชีวิตตัวไหนดูแล tag นั้น · ชี้ไม่ได้ = ยังไม่พร้อม
