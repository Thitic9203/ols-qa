## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไม session dev ตายทั้งหมด?** — คุกกี้ NDLP หมดอายุ 24 ชม. หลัง relink ครั้งสุดท้าย และ refresh หลังหมดอายุได้ 401
2. **ทำไมไม่มีการ relink ก่อนหมด?** — `decide()` สั่ง relink เฉพาะเมื่อเหลือไม่ถึง `WINDOW_MS = 2h` (`capture/session_relink_dev.js:33`, `:49`) และ `session_keepalive_dev.sh:66` ข้าม relink เมื่อ rc=3 (VPN หลุด, `:42-43`)
3. **ทำไม 2 เงื่อนไขนั้นทำให้พลาด?** — ช่วงต่ออายุมีแค่ 2 ชม. ต่อวัน ถ้า VPN หลุดช่วงนั้นช่วงเดียวก็ไม่มีโอกาสอีก และ 22 ชม. ก่อนหน้าที่ VPN ต่ออยู่ไม่ได้ถูกใช้เลย
4. **ทำไมรอบ 16:36 ที่ VPN ต่ออยู่ไม่ฟื้น session ที่ OLS ตาย?** — `decide()` ดูแค่อายุคุกกี้ NDLP · OLS ตายแต่ NDLP ยังดี = `ok` → ข้าม · มีแต่ `--force` ที่ฟื้นได้ และต้องสั่งด้วยมือ
5. **ทำไมออกแบบไว้แบบนั้น?** — ตัวต่ออายุออกแบบจากกรณีปกติ (เครื่องเปิด VPN ต่อ) ไม่มีเทสต์ของกรณี "VPN หลุดตลอดช่วงต่ออายุ" และ "OLS ตายแต่ NDLP ยังดี" root cause = ช่วงต่ออายุแคบและเงื่อนไขฟื้นดูแค่คุกกี้ ไม่ทนต่อการหยุดชะงักที่เกิดได้จริง

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** กฎ "VPN หลุดให้ข้ามแบบเงียบ" ทำให้ไม่มีการแจ้ง · `session_status.js` อ่านแค่ไฟล์ ไม่มีใครรันจนเริ่มงาน · เทสต์ของ relink ครอบแค่ขอบ 2 ชม. ไม่ครอบกรณีหยุดชะงัก

## 5. แนวทางการแก้ไข (Fix)

- `<bot>/capture/session_relink_dev.js` — ต่ออายุเมื่อเหลือน้อยกว่า 18 ชม. (เดิม 2 ชม.) และฟื้น session ที่ OLS ตายแต่ NDLP ยังดีอัตโนมัติด้วยเส้นทางเดียวกับ `--force` (§10)
- ไม่ relink บัญชีที่โปรเซสอื่นใช้อยู่ (กฎเดิมของเจ้าของงาน 5/Oct: refresh ทำให้ชุดเดิมใช้ไม่ได้) — ตรวจไม่ได้ = เลื่อน · ข้อจำกัด: จับได้เฉพาะโปรเซสที่มีชื่อ tag ใน command line หรือเปิดไฟล์ state ค้างอยู่
- เทสต์ใหม่ 2 เคส: VPN หลุดตลอดช่วง 2 ชม. เดิม แล้วกลับมา → relink · OLS ตาย + NDLP ยังดี → relink อัตโนมัติ

**ยืนยันแล้วด้วย:** รันเทสต์ `capture/*.test.js` ครบ 30 ไฟล์บน checkout หลักของบอทหลัง merge → 30 ผ่าน 0 ไม่ผ่าน · ตัวตรวจ OLS-dead ทดสอบกับเคสที่รู้คำตอบ: session ที่ยังดี → `true` · session ที่ตาย → `false` · `origin/main` = `03826dd` (job รันจาก checkout นี้)
