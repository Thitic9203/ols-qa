## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

มี 2 ชั้นที่พลาดต่อกัน: (ก) ตัวสแกนตัดสินผิด (ข) main verify ไม่ลึกพอจึงไม่จับ.

### 5 Whys

1. **ทำไม `LP_023/024` ขึ้นบอร์ดเป็นผ่าน?** — เพราะ `system_falsepos_final.json` ตัดสิน PASS และ main เอาเลขนั้นขึ้นบอร์ดโดยเชื่อว่า verify แล้ว.
2. **ทำไมตัวสแกนตัดสิน PASS ทั้งที่มีแถบคำตัดสิน?** — เพราะ `scan36.py:87-88` `GATE_CAPTION_TITLE = "รหัสเทสเคส"` จัดบรรทัด CAPTION ที่ถูก gate ติดธง `รหัสเทสเคสฝังในคลิป` ให้เป็น ALLOWED (ชื่อ fixture) แล้วย้ายออกจากกอง BLOCKING ก่อน ตาข่ายจับแถบคำตัดสินจึงไม่เห็น.
3. **ทำไมถึงจัด `รหัสเทสเคสฝังในคลิป` เป็นชื่อ fixture?** — เพราะรวมสองสิ่งที่ต่างกันเป็นอันเดียว: "ชื่อ test-data/fixture ที่มี TC token" (ผ่านได้) กับ "แถบ TC-code/ER/verdict ที่ฝังในคลิป" (ตก) — token `TC_\d` โผล่ทั้งคู่ แต่ความหมายตรงข้าม.
4. **ทำไม main ไม่จับตอน verify รอบแรก?** — เพราะ verify รอบแรกอ่าน field `deciding_text` ที่ subagent สรุปมาเอง (ซึ่งบอกว่า url-bar/title) ไม่ได้รีเดอไรฟ์จาก OCR ดิบหรือดูเฟรมจริง.
5. **ทำไมถึงเชื่อ field สรุปของ subagent?** — root cause: ปฏิบัติกับ "ผลสรุปของ subagent" เป็นหลักฐาน ทั้งที่มันคือ "ของที่จริง ณ ตอน subagent เขียน" ต้องรีเดอไรฟ์จากของดิบเองเสมอ (เดียวกับ #0025/#0016). การนับ verdict ตรง 370/225 ให้ความมั่นใจปลอมว่า "ตรวจแล้ว" ทั้งที่ตรวจแค่ว่า field ตรงกับ field.

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- ตัวสแกน re-scan เองมีตาข่ายจับแถบคำตัดสิน (จับ Feed_052/Feed_011/Search_121 ได้) แต่ชั้น ALLOWED-title มาก่อน จึงกินเคสนี้ไปก่อนตาข่ายเห็น.
- main verify รอบแรกไม่มีขั้น "รีเดอไรฟ์จาก OCR ดิบ" — มีแค่ "นับ + สุ่มดู field" ซึ่งไม่ใช่การวัดของจริง.
- ไม่มีเทสที่ pin ว่า "แถบ TC ER PASS = ตก · ชื่อ fixture = ผ่าน" ในตัวสแกน.

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- พอเจ้าของงานสั่งเช็คละเอียด ทำการรีเดอไรฟ์จากของดิบจริง (ไม่ใช่ดู field ซ้ำ) + ยืนยันด้วยเฟรมจริง จึงจับได้แน่นอน ไม่ใช่เดา.
- ทิศแก้เป็นทิศเข้มขึ้น (พลิก false-PASS → fail) และแก้เลขที่เผยแพร่ผิดทันที.

### สิ่งที่ต้องปรับปรุง
- verify ครั้งแรกต้องรีเดอไรฟ์จากหลักฐานดิบตั้งแต่ต้น ไม่ควรพูดคำว่า "VERIFIED" จากการนับ + ดู field สรุปของ subagent — ต้องถือว่าผลสรุปของ subagent = ของที่จริงตอนมันเขียน ต้องตรวจซ้ำจากดิบ.
- ตัวจำแนกของเครื่องมือตรวจต้องแยก "ชื่อที่มี TC token" กับ "แถบคำตัดสินที่มี TC token" ให้ขาด ห้ามรวมด้วย substring เดียว.
