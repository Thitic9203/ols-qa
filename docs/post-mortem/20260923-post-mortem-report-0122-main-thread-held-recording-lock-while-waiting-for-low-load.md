## สรุปสั้น (Executive Summary)

รอบอัดคลิป training69 ใช้ตัวล็อกกลาง `lanes_0923/REC.lock` (สร้างด้วย `mkdir`) เพื่อให้ทั้งเครื่องอัดได้ทีละคลิป
loop background ของเธรดหลักสำหรับอัดช่วงต่อท้าย `Content_TC_005` สั่ง `mkdir REC.lock` ก่อน แล้วค่อยวนรอ load < 6 จึงถือล็อกไว้เปล่าๆ ตั้งแต่ 15:12:02 ถึงราว 15:16 (เวลาเครื่อง) โดยไม่มี node ลูกรันอยู่เลย

**สิ่งที่ควรจะเป็น:** ถือล็อกเฉพาะช่วงที่อัดจริง — รอ load ลดโดยไม่ถือล็อก → ลอง `mkdir` ครั้งเดียว → ถ้าจองได้ตรวจ load ซ้ำ ถ้าขึ้นเกินให้ปล่อยทันที → อัด → ปล่อยทุกกรณี (ตามเจตนาของล็อกใน `LANE_BRIEF.md:11` "One recording at a time machine-wide" ซึ่งมีไว้เพื่อให้เลนผลัดกันอัด ไม่ใช่ให้ใครจองรอ) · เจ้าของงานยืนยันหลักนี้ภายหลังใน UPDATE #6 ของกติกา ("one set at a time, check right away, don't wait")

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

loop เดิมเขียนแบบ "จองก่อนเพื่อกันคนอื่นแซง แล้วค่อยรอให้เครื่องว่าง" ซึ่งดูสมเหตุสมผลจากมุมของ loop เดียว (ได้คิวแน่นอน) แต่ตัวล็อกมีไว้แบ่งเครื่องให้หลายเลน การจองระหว่างรอจึงเท่ากับยึดเครื่องทั้งเครื่องไว้ในช่วงที่ตัวเองก็ยังอัดไม่ได้ และบังคับให้เลนอื่นรอทั้งที่เลนนั้นอาจอัดได้ (เกณฑ์ load ของเลน U คือ 8 สูงกว่า 6 ของเธรดหลัก)

### 5 Whys

1. **ทำไมเลน U รอล็อกครบ 180 วินาทีแล้ว take เริ่มไม่ได้?** — เพราะ `REC.lock` ถูก pid 29690 ของเธรดหลักถือไว้ตั้งแต่ 15:12:02 ทั้งที่ไม่มีการอัดเกิดขึ้น
2. **ทำไมเธรดหลักถือล็อกทั้งที่ไม่ได้อัด?** — เพราะ loop สั่ง `mkdir REC.lock` ก่อน แล้วค่อยวนรอ load < 6 ภายในช่วงที่ถือล็อก
3. **ทำไม loop เขียนลำดับนั้น?** — เพราะลำดับ รอ → จอง → ตรวจซ้ำ → อัด → ปล่อย ไม่ได้ถูกเขียนไว้ที่ไหนเลย ทั้งในกติกาที่เธรดหลักเขียนให้เลน (`LANE_BRIEF.md:11` แยกเรื่อง load กับเรื่องล็อกเป็นสองประโยคที่ไม่ผูกลำดับ) และในโค้ด — ทุก loop ประกอบลำดับใหม่ด้วยมือ
4. **ทำไมกติกาที่เธรดหลักเขียนเองจึงไม่มีลำดับ ทั้งที่เป็นคนออกแบบล็อก?** — เพราะเธรดหลักเขียนกติกาเป็นข้อความแล้วส่งให้เลนทันที โดยไม่ได้ลองรันกติกานั้นตามตัวอักษรกับกรณีที่มีคนถือล็อก/load สูงสักครั้ง ถ้าลองรันจะเห็นว่าข้อความอนุญาตให้จองแล้วรอได้
5. **ทำไมบทเรียน #0121 (ห้ามเขียนสภาพการรันด้วยมือ ให้ใช้คำสั่งเดียวที่มีเทสต์) ไม่ครอบเรื่องนี้?** — เพราะมาตรการ #0121 ปิดเฉพาะ "ตัวแปรสภาพแวดล้อม" (`t69_env.sh`) ไม่ได้ขยายไปทั้งคลาส "โปรโตคอลที่เลนต้องทำตาม" · root cause ของคลาส: โปรโตคอลที่ใช้ทรัพยากรร่วมอยู่ในรูปข้อความที่แต่ละคนตีความเอง ไม่ได้อยู่ในคำสั่งเดียวที่บังคับลำดับและมีเทสต์ผ่านแล้ว

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- `capture/load_gate.js` (#0120) ตรวจ load ภายในสคริปต์อัดก่อน `startRecording` เท่านั้น ไม่รู้จักล็อก และ loop รอที่ถือล็อกอยู่ข้างนอกสคริปต์
- `tools/agent-dispatch-guard/` (#0121) ตรวจข้อความ prompt ตอนส่ง agent — loop นี้เป็น background task ของเธรดหลักเอง ไม่ผ่านการส่ง agent และ guard ไม่มีเช็คเรื่องลำดับล็อก
- ตัวล็อก `mkdir` ไม่มีเวลาหมดอายุหรือการแจ้งเตือนว่าถือนานโดยไม่มีลูก — มีเพียงเลนที่รอเป็นคนเห็น ซึ่งคือสิ่งที่เกิดขึ้น

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** เลน U บันทึกบรรทัด `failed` พร้อมชื่อ owner ของล็อก ตัวเฝ้า heartbeat พาบรรทัดนั้นมาถึงเธรดหลัก

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ไฟล์ owner มี label + pid + เวลา ทำให้ชี้ผู้ถือได้ทันที และเธรดหลักลบล็อกเฉพาะหลังเทียบ owner ว่าเป็นของตัวเอง
- เลน U ไม่ลบล็อกของคนอื่น ทำตามกติกา แล้วรายงานพร้อมชื่อผู้ถือ

### สิ่งที่ต้องปรับปรุง
- โปรโตคอลที่มีลำดับ (รอ/จอง/ตรวจซ้ำ/ปล่อย) ต้องเป็นโค้ดที่มีเทสต์ตั้งแต่ก่อนส่งให้เลนแรก — ไม่ใช่สองประโยคแยกกันในกติกา
- มาตรการของรายงานก่อน (#0121) ต้องขยายไปทั้งคลาส ("สิ่งที่เลนต้องทำตาม") ไม่ใช่แค่ตัวอย่างที่เพิ่งพลาด
