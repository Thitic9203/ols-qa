## สรุปสั้น (Executive Summary)

ระหว่างรอบ smoke test บน dev มีการรายงานเจ้าของงานว่า "การตรวจขอบเขตล่วงหน้าได้ผลลัพธ์ว่างเปล่า 0 บรรทัด" ทั้งที่ **ไม่เคยเปิดไฟล์ขอบเขตนั้นอ่าน** เลย เลข 0 มาจากเอาต์พุตที่ `rtk` ย่อ/กลั้นไว้แล้วแสดงให้ดู ซึ่งถูกอ่านเหมือนเป็นเนื้อไฟล์จริง ของจริงไฟล์มี **114 บรรทัด / 14,090 ไบต์ / parse ได้ครบ 111 รายการ** สาเหตุจริงคือการอ่านสถานะจาก **การแสดงผลของเครื่องมือ (rtk) ที่ย่อเอาต์พุต** แทนที่จะอ่านจากไฟล์จริง แล้วพูดผลนั้นกับเจ้าของงานเหมือนเป็นข้อเท็จจริงที่ตรวจแล้ว ปิดอาการด้วยการเปิดไฟล์อ่านจริง (ยืนยัน 111 รายการ) สถานะ: อาการปิดแล้ว รายงานฉบับนี้ปิดหนี้ค้าง

## 1. ปัญหา (Problem Statement)

- รายงานเจ้าของงานว่าการตรวจขอบเขต (scope pre-check) ได้ผล **"ว่างเปล่า 0 บรรทัด"** — เป็นการพูดสถานะเหมือนเป็นข้อเท็จจริงที่ตรวจแล้ว
- **ไม่เคยเปิดไฟล์ขอบเขตนั้นอ่านด้วย Read หรือ `wc -l`** — เลข 0 มาจากเอาต์พุตที่ `rtk` ย่อ/แสดงให้ดูเท่านั้น
- ของจริง: ไฟล์ขอบเขตมี **114 บรรทัด · 14,090 ไบต์ · parse เป็นรายการได้ครบ 111 รายการ** (ตัวเลขจากแถว ledger ที่บันทึกวันเกิดเหตุ)

**สิ่งที่ควรจะเป็น:** ก่อนพูดจำนวนใดๆ กับเจ้าของงาน ต้องอ่านจากแหล่งที่เป็นสถานะจริง (เปิดไฟล์ / `wc -l` / `wc -c`) ไม่ใช่จากการแสดงผลของเครื่องมือที่อาจย่อเอาต์พุต — ตามกฎข้อแรกสุดของ repo ("ทุกประโยคที่พูดเหมือนข้อเท็จจริง ต้องมาจากการเปิดดูของจริงรอบนี้") และกฎ global ข้อ 17 (เคลมอะไรต้องมีหลักฐาน)

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

`rtk` เป็น proxy ที่ hook เขียนนำหน้าคำสั่งอัตโนมัติ และมัน**กลั้น/ย่อเอาต์พุตของลูก** (วัดไว้แล้วใน memory `reference_rtk-buffers-long-running-runs`: log ค้าง 0 ไบต์ 15 นาทีแล้วค่อยกระโดดเป็น 274 KB ตอนโปรเซสจบ) สิ่งที่มันแสดงบนจอในจังหวะหนึ่งจึงไม่ใช่เนื้อไฟล์ทั้งหมด การเอาเลขจากการแสดงผลนั้นมาพูดว่า "ไฟล์ว่าง 0 บรรทัด" คือการเอา **การแสดงผลของเครื่องมือ** มาแทน **สถานะจริงของไฟล์** จุดตัดสินใจที่ผิดคือ ณ จังหวะที่จะพูดจำนวนกับเจ้าของงาน ไม่ได้ถามว่า "เลขนี้มาจากการเปิดไฟล์จริงหรือมาจากสิ่งที่เครื่องมือแสดง" — ตอนนั้นมันดูถูกเพราะเอาต์พุตบนจอ "ดูเหมือน" เป็นผลของคำสั่งครบถ้วนแล้ว

### 5 Whys

1. **ทำไมรายงานว่า "0 บรรทัด ว่างเปล่า"?** — เพราะเอาต์พุตที่เห็นบนจอตอนนั้นไม่มีบรรทัดข้อมูลแสดง
2. **ทำไมเชื่อว่าเอาต์พุตบนจอ = เนื้อไฟล์?** — เพราะถือว่าการแสดงผลของคำสั่ง (ผ่าน rtk) เป็นเนื้อหาไฟล์ที่ครบถ้วนแล้ว
3. **ทำไมไม่เปิดไฟล์อ่านยืนยันก่อนพูด?** — เพราะคิดว่าเลขที่เห็นเพียงพอที่จะรายงาน ไม่ได้แยกระหว่าง "ผลที่เครื่องมือแสดง" กับ "สถานะจริงของไฟล์"
4. **ทำไมถึงไม่แยกสองอย่างนี้?** — เพราะไม่มีนิสัย/ด่านบังคับว่า "ตัวเลขที่จะพูดกับเจ้าของงานต้องมาจากการเปิดของจริง ไม่ใช่จากการแสดงผลของ tool ที่อาจย่อ"
5. **ทำไมไม่มีด่านนั้น?** — **root cause:** กฎ "อ่านสถานะจากสิ่งที่เป็นสถานะจริง" (#0016) มีอยู่ในเชิงหลักการแล้ว แต่ยังไม่มีตารางจับคู่ชัดเจนว่า **แหล่งไหนคือสถานะจริง vs แหล่งไหนคือของที่บังเอิญอยู่ใกล้** สำหรับกรณี "เนื้อไฟล์" โดยเฉพาะเมื่อเอาต์พุตวิ่งผ่าน `rtk` ที่ย่อ/กลั้น — จึงพลาดซ้ำในรูปแบบใหม่ (rtk-truncation) ที่ #0016 ยังไม่ได้ครอบ

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** ไม่มีชั้นเครื่องจับคำรายงานสถานะในแชทได้เลย (คำพูดกับเจ้าของงานไม่ผ่าน gate/test ใด) · กฎ prose (#0016, กฎข้อแรกสุด) เป็นชั้นที่พึ่งความจำ ซึ่งถูกข้ามในจังหวะที่เอาต์พุตบนจอ "ดูเหมือน" น่าเชื่อ · memory `reference_rtk-buffers-long-running-runs` อธิบายพฤติกรรม rtk ไว้แล้ว แต่ผูกกับบริบท "log 0 ไบต์ตอนรันยาว" ไม่ได้ผูกกับบริบท "อ่านจำนวนบรรทัดของไฟล์"

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** จับได้เองเมื่อเปิดไฟล์จริงอ่านต่อ พบว่ามี 111 รายการ ขัดกับคำที่รายงานไป
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** ภายในรอบเดียวกันวันเกิดเหตุ (ระดับความละเอียดของ ledger คือรายวัน)
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** ทำ P1 เป็นนิสัยบังคับ — ตัวเลขที่จะพูดกับเจ้าของงานต้องมาพร้อมคำสั่งที่รันจริง (`wc -l <file>` + output) ในเทิร์นเดียวกัน ทำให้ "ยังไม่ได้เปิดไฟล์" โผล่ให้เห็นก่อนพิมพ์

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- จดหนี้ `OPEN` ทันทีในวันเกิดเหตุ — ชั้นที่ 2 ทำงาน ทำให้ความผิดพลาดไม่หายไปกับเซสชัน และถูกหยิบมาปิดได้ในภายหลัง

### สิ่งที่ต้องปรับปรุง
- แยกให้ขาดระหว่าง "ผลที่เครื่องมือแสดง" กับ "สถานะจริงของของที่ถาม" — โดยเฉพาะเมื่อเอาต์พุตวิ่งผ่าน `rtk` ที่ย่อ/กลั้น การเห็นว่าง ≠ ของว่าง (คลาสเดียวกับ empty-grep #0030)
