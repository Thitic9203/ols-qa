## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

คำถามที่ต้องตอบไม่ใช่ "ทำไมลืม `-e`" แต่คือ **ทำไมถึงลงมือติดตั้งงานตามตารางโดยไม่ตรวจก่อนว่ามันล้มเหลวเป็นไหม**
คำตอบอยู่ในหัวไฟล์ของสคริปต์เอง บรรทัด 9-10 เขียนไว้ว่า *"A failure is harmless by design: session_refresh.js
persists a state file only on a 2xx, so a run with the VPN down leaves every saved session untouched."*
ประโยคนั้นถูกต้องทุกคำ — ความล้มเหลวไม่ทำให้ข้อมูลเสียหายจริง แต่มันถูกใช้ต่อไปอีกขั้นหนึ่งโดยไม่มีใครทัก คือ
**"ไม่เป็นอันตราย" ถูกอ่านเป็น "ไม่ต้องรายงาน"**

สองคำนี้ไม่เหมือนกันเลย ผลของการล้มเหลวแบบเงียบในงานนี้ไม่ใช่ข้อมูลพัง แต่คือ **ไม่มีใครรู้ว่าต้องไปล็อกอิน**
แล้ว pool ของบัญชีตายทั้งชุด ซึ่งเป็นสิ่งเดียวที่งานนี้ถูกสร้างขึ้นมาเพื่อป้องกัน · เมื่อความล้มเหลวถูกจัดว่าไม่สำคัญ
การใส่ `-e` หรือเก็บรหัสจบก็ดูเป็นงานที่ไม่จำเป็น และคำสั่งดูแลบ้าน (ตัดล็อก) ก็ถูกวางไว้ท้ายไฟล์อย่างเป็นธรรมชาติ
โดยไม่มีใครนึกว่ามันจะกลายเป็นผู้กำหนดรหัสจบของทั้งงาน

ชั้นถัดมาที่ควรจะกันไว้กลับถูกทำให้เป็นชั้นเดียวกัน `sfd/workflow_heartbeat.py:353` เขียนว่า
`ok_now = (stamp_rc == 0) if stamp_rc is not None else (exit_code == 0)` — งานที่ผ่าน harness จะมี status
stamp เป็นแหล่งความจริง ส่วนงานที่ไม่ผ่าน harness ตกกลับไปใช้รหัสจบของ launchd งานนี้ plist เรียกสคริปต์ตรงๆ
ไม่ผ่าน `sfd/run_workflow.sh` จึงไม่มี stamp และเมื่อรหัสจบเป็นค่าที่ตัวงานเลือกเองว่า 0 เสมอ **ชั้นวัดผลลัพธ์
ที่ออกแบบมาให้ไม่ขึ้นกับสาเหตุ (SFD 2b) กับชั้นวัดรหัสจบ (SFD 4) ก็อ่านตัวเลขเดียวกัน** — ตรงกับบทเรียนที่ repo นี้
เขียนไว้แล้วว่า *ชั้นป้องกันที่พึ่งข้อสมมติเดียวกัน นับเป็นชั้นเดียว*

ส่วนช่อง `log_file` เป็นความผิดพลาดคนละใบที่ประกอบกันพอดี ผู้ลงทะเบียนกรอกเส้นทางสตรีมของ launchd ซึ่งเป็น
คำตอบที่ถูกต้องตามแบบแผนของทุกงานอื่น แต่ไม่ได้เปิดดูว่าไฟล์นั้นมีไบต์ไหม และมันไม่มีวันมี เพราะสคริปต์
redirect เอาต์พุตของตัวเองไปที่อื่นตั้งแต่บรรทัด 27 · ถ้าเปิด `ls -l` ครั้งเดียวจะเห็นทันที

และมาตรการ P4 ของรายงาน #0009 คือชั้นสุดท้ายที่ควรจับข้อ ค. ได้ มันถูกบันทึกว่า Done พร้อมข้อความ
"ไม่พบที่อื่น" ทั้งที่คำสั่งเดียวกันวันนี้คืน 3 hit — **การสแกนที่รายงานว่าเรียบร้อยโดยไม่บอกจำนวนที่นับได้
คือคลาสของรายงาน #0002 มาปรากฏอยู่ในตัวมาตรการป้องกันเสียเอง**

### 5 Whys

1. **ทำไมงานต่ออายุ session รายงานว่าสำเร็จทุกครั้งทั้งที่ต่ออายุไม่ได้เลย?** — เพราะรหัสจบของสคริปต์คือรหัสจบ
   ของคำสั่งตัดล็อกที่บรรทัด 30 ไม่ใช่ของคำสั่งที่ทำงานจริง
2. **ทำไมรหัสจบของคำสั่งที่ทำงานจริงถึงไม่ถูกใช้?** — เพราะบรรทัด 11 เป็น `set -uo pipefail` ไม่มี `-e`
   สคริปต์จึงเดินต่อผ่านความล้มเหลว และรหัสจบของทั้งไฟล์กลายเป็นของคำสั่งสุดท้ายที่รัน ซึ่งเป็นงานดูแลบ้าน
3. **ทำไมถึงไม่ใส่ `-e` และไม่เก็บรหัสจบไว้เอง?** — เพราะหัวไฟล์บรรทัด 9-10 ประกาศไว้เองว่าความล้มเหลว
   ไม่เป็นอันตรายโดยการออกแบบ ผู้เขียนจึงสรุปว่าไม่ต้องจัดการกับกรณีล้มเหลว
4. **ทำไม "ไม่เป็นอันตราย" ถึงกลายเป็น "ไม่ต้องรายงาน"?** — เพราะสองคำนี้ถูกใช้แทนกันโดยไม่มีใครแยก
   ทั้งที่ราคาของการเงียบในงานนี้ไม่ใช่ข้อมูลเสียหาย แต่คือไม่มีใครไปล็อกอิน แล้ว pool ตายทั้งชุด
   ซึ่งเป็นสิ่งเดียวที่งานนี้มีไว้ป้องกัน
5. **ทำไมไม่มีชั้นไหนจับได้เลยตลอด 7 รอบ?** — **root cause: สำหรับงานที่ไม่ผ่าน harness ระบบ SFD
   นิยามคำว่า "สำเร็จ" ด้วยรหัสจบเพียงค่าเดียว (`workflow_heartbeat.py:353`) และรหัสจบเป็นค่าที่ตัวงาน
   เลือกเองได้** เมื่องานเลือกเป็น 0 เสมอ ทุกชั้นที่อ่านค่านั้นจึงกลายเป็นชั้นเดียวกัน รวมถึงชั้นวัดผลลัพธ์
   ที่ตั้งใจสร้างให้ไม่ขึ้นกับสาเหตุ · ปิดด้วยการเตือนหรือด้วยการจำไม่ได้ ต้องปิดด้วยการมีแหล่งความจริงที่ตัวงาน
   เขียนเองไม่ได้ (status stamp ของ harness) และด้วยการพิสูจน์อย่างน้อย 1 ครั้งว่างานนั้นล้มเหลวแล้วดังจริง

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**

| ชั้นที่มีอยู่ | ทำไมไม่จับ |
|---|---|
| SFD Level 1 — fail-loud contract | ต้องมีใครสักคนเก็บรหัสจบจริง · สคริปต์นี้ไม่เก็บ และไม่มี trap |
| SFD Level 2/3 — harness + notify แบบดัง | งานไม่ได้ห่อด้วย `sfd/run_workflow.sh` เลย (plist เรียกสคริปต์ตรงๆ) จึงไม่มีอะไรดักรหัสจบ และ `fail_notify.py` ไม่เคยถูกเรียกสักครั้ง |

| SFD Level 2b — outcome staleness | `workflow_heartbeat.py:353` ให้งานที่ไม่มี stamp ใช้ `exit_code` เป็นนิยามของสำเร็จ · `last_ok_epoch` จึงถูกรีเซ็ตทุกรอบ งานไม่มีวันเข้าเกณฑ์ `max_stale_s` 64800 วินาที |

| ธง `"trap_wired"` | ไม่มีในแถวนี้ ซึ่งถูกต้องตามกฎเพราะงานไม่ได้ห่อ wrapper — ผลคือไม่เหลือชั้นไหนเลยนอกจากรหัสจบ และไม่มีอะไรทักว่าสภาพนี้แปลว่าไม่มีตาข่าย |
| มาตรการ P4 ของรายงาน #0009 (สำหรับข้อ ค.) | บันทึกว่า Done ด้วยข้อความ "ไม่พบที่อื่น" โดยไม่มีตัวเลขกำกับ · คำสั่งเดียวกันวันนี้คืน 3 hit |
| กฎ SFD ใน `CLAUDE.md` | เป็นตัวหนังสือ · และงานนี้ **ถูกลงทะเบียนครบ** จึงดูเหมือนอยู่ในระบบเรียบร้อยแล้ว ทั้งที่ทุกชั้นที่มันต่ออยู่อ่านค่าเดียวกัน |

## 5. แนวทางการแก้ไข (Fix)

**สถานะ: ยืนยันข้อบกพร่องครบทั้ง 3 ข้อด้วยการวัด · การแก้โค้ดยังไม่ถูกลงมือ** เขียนตามจริง ไม่ใช่เขียนให้ดูจบ

สิ่งที่ทำไปแล้วในรอบนี้ ทั้งหมดเป็นการอ่านและการวัด ไม่มีการเขียนใดๆ ที่ปลายทาง:

- เปิดซอร์ส `capture/session_keepalive.sh` ทั้งไฟล์ ยืนยันบรรทัด 11 และบรรทัด 30 · ยืนยันว่างานจริงอยู่ในบล็อก
  ที่ถูก redirect ทั้งก้อนที่บรรทัด 27
- อ่านแถวของ label นี้จาก `sfd/workflows.json` และวัดขนาดไฟล์ล็อกทั้ง 2 ไฟล์
- อ่าน plist ยืนยันว่า `ProgramArguments` เรียกสคริปต์ตรงๆ ไม่ผ่าน `sfd/run_workflow.sh`
- วัด `launchctl list` ได้ `LastExitStatus=0`
- อ่าน `sfd/workflow_heartbeat.py` บรรทัด 353 และ 311 เพื่อยืนยันว่าตาข่ายทั้ง 2 ชั้นอ่านค่าเดียวกัน
  และหลักฐานที่แนบ DM มาจากช่องที่ชี้ไฟล์เปล่า
- สรุปเนื้อล็อกจริงแบบไม่เปิดเผยชื่อบัญชี ได้ 7 รอบ ทุกรอบเป็น `needs human login`
- รัน grep เดิมของ #0009 ซ้ำ ได้ 3 hit ใน 3 ไฟล์
- จดแถวหนี้ `PM-2026-09-06-10` แล้วปิดเป็น `DONE` พร้อมชื่อไฟล์รายงานนี้

**ข้อจำกัดที่ต้องบอกตรงๆ:** หลักฐานจากล็อกเป็น **การยืนยันประกอบ ไม่ใช่ตัวพิสูจน์** ว่าการต่ออายุล้มเหลว —
บัญชีในล็อกหมดอายุไปแล้วตั้งแต่ก่อนรอบเหล่านั้น สคริปต์ที่ทำงานถูกต้องก็จะรายงาน `needs human login` เหมือนกัน
และประชากรบัญชีฝั่ง dev กับฝั่ง prod ถูกใช้งานคนละวันกัน · **ตัวพิสูจน์อยู่ที่ซอร์ส** คือรหัสจบของงานเป็นของ
คำสั่งตัดล็อก จึงเป็น 0 โดยไม่ขึ้นกับว่าการต่ออายุเกิดขึ้นหรือไม่ ข้อนี้เป็นจริงเสมอ ไม่ต้องรอให้มีรอบที่ล้มเหลว
มาพิสูจน์

**สเปกของการแก้ ระบุให้ลงมือได้ทันทีโดยไม่ต้องสืบใหม่** (Action Items ข้อ 1-4):

1. ให้ plist เรียกผ่าน `sfd/run_workflow.sh` เพื่อให้งานได้ status stamp และ trap ของ harness แล้วเติม
   `"trap_wired": true` ในทะเบียน — ย้ายงานจาก "รหัสจบอย่างเดียว" ไปเป็น "มีแหล่งความจริงที่ตัวงานเขียนเองไม่ได้"
2. เก็บรหัสจบของ `session_refresh.js` และ `session_status.js` ไว้ แล้วให้สคริปต์จบด้วยค่านั้น ·
   คำสั่งตัดล็อกต้องไม่ใช่ตัวกำหนดรหัสจบไม่ว่ากรณีใด
3. ให้ช่อง `log_file` ชี้ `logs/session-keepalive.log` ซึ่งเป็นไฟล์ที่มีเนื้อจริง
4. ถอดค่าเริ่มต้นออกจาก `capture/session_refresh.js:47` และ `capture/session_capture.js:57-58`
   แล้วเพิ่มการปฏิเสธ training ในตัวสคริปต์เอง ตามรูปแบบเดียวกับที่ #0009 ทำกับ `session_verify.js`

**ยืนยันแล้วด้วย:** output จริงของทุกคำสั่งที่ใช้วัด บันทึกไว้ในหัวข้อ 10 · และ
`node tools/postmortem-guard/check.js` สำหรับตัวเอกสารฉบับนี้

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** เธรดหลักจับได้เอง จากการเปิดซอร์สของงานที่รอบนี้ต้องพึ่ง แล้วตั้งคำถามว่า
  "ถ้างานนี้ล้มเหลว ใครจะรู้" · ไม่มีชั้นอัตโนมัติใดจับได้ และไม่มีทางจับได้ เพราะทุกชั้นอ่านค่าเดียวกัน
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** 2 วัน 7 รอบ (ติดตั้ง 2026-09-04 14:47 · พบ 2026-09-06 เย็น)
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** มาตรการ P1 จับได้ **ในนาทีที่ติดตั้ง** เพราะการฉีดความล้มเหลว 1 ครั้ง

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- เปิดซอร์สอ่านทั้งไฟล์ก่อนสรุป จึงเจอว่ารหัสจบมาจากคำสั่งตัดล็อก ซึ่งเป็นสิ่งที่มองจากพฤติกรรมภายนอกไม่มีวันเห็น
  เพราะภายนอกมันดูสำเร็จเสมอ
- แยกได้ว่าอะไรคือ **ตัวพิสูจน์** (ซอร์ส) กับอะไรคือ **การยืนยันประกอบ** (ล็อก) แล้วเขียนข้อจำกัดนั้นลงในรายงาน
  แทนที่จะใช้ล็อกเป็นหลักฐานเกินกว่าที่มันพิสูจน์ได้
- ไม่หยุดที่ข้อบกพร่องใบแรก แต่ไล่ต่อไปถึงตาข่ายที่ควรจับ แล้วพบว่าตาข่าย 2 ชั้นเป็นชั้นเดียวกัน
