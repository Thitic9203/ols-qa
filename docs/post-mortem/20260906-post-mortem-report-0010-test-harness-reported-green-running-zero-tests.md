## สรุปสั้น (Executive Summary)

`main()` ของชุดเทสต์ทั้ง 2 ไฟล์ กวาดตัวแปรระดับโมดูลที่ชื่อขึ้นต้นด้วย `t_` มาเรียกทีละตัว แล้วตัดสินผลจาก
`if FAILS:` อย่างเดียว ไม่มีที่ไหนนับว่ารันไปกี่ข้อ ผลคือ ถ้าไม่มีชื่อขึ้นต้น `t_` เหลืออยู่เลย ลูปไม่ทำงาน
สักรอบ `FAILS` ว่าง แล้วโปรแกรมพิมพ์ **`all green`** และจบด้วยรหัส 0

ทำซ้ำยืนยันแล้วในรอบนี้: คัดลอกชุดเทสต์ก่อนอัดออกมา 1 ชุด เปลี่ยน `def t_` เป็น `def x_` ทั้ง 42 ข้อ
แล้วรัน ได้ `all green` กับรหัสจบ 0 โดยไม่มีบรรทัด `ok` ออกมาแม้แต่บรรทัดเดียว

ข้อบกพร่องนี้ยังไม่เคยทำให้ผลรอบไหนผิด เพราะชุดจริงมีข้อครบ (ก่อนอัด 42 ข้อ · หลังอัด 53 ข้อ) และรันแล้วเขียวจริง
แต่ที่ต้องอธิบายให้ได้คือ **ไฟล์ทั้ง 2 มีข้อชื่อ `t_zero_checks_is_a_refusal_even_with_no_reason_recorded`
อยู่แล้ว** (บรรทัด 282 และ 520) ซึ่งบังคับกฎ "วัด 0 ข้อ = ปฏิเสธ" ให้กับ **ตัวด่านที่ถูกทดสอบ** และหัวไฟล์
ก็อ้างรายงาน #0006 ไว้ตรงๆ กฎเดินทางไปถึงของที่ถูกวัด แล้วหยุดอยู่ตรงขอบของเครื่องมือที่ใช้วัด

การแก้ที่ต้นเหตุ (ใส่ตัวนับ · ศูนย์ = ปฏิเสธ · บรรทัดผ่านต้องมีตัวเลข) **ยังไม่ถูกลงมือในรอบนี้** เพราะไฟล์ทั้ง 2
เป็นงานที่อีกเลนถืออยู่ระหว่างรอบ จึงบันทึกเป็น Action Item พร้อมสเปกของการแก้ไว้ในหัวข้อ 9

## 1. ปัญหา (Problem Statement)

- `gate_prerecord_test.py:387-397` — `main()` วนเรียกทุก global ที่ขึ้นต้น `t_` แล้วตัดสินด้วย `if FAILS:`
  เท่านั้น ถ้า `FAILS` ว่างจะพิมพ์ `all green` และ `return 0` **ไม่มีตัวแปรใดในฟังก์ชันนี้ที่นับจำนวนข้อที่รันจริง**
- `gate_postclip_test.py:585-601` — โครงเดียวกันทุกบรรทัด ต่างกันแค่มี `setup()` และ `shutil.rmtree` คร่อมลูป
- ทำซ้ำได้: คัดลอกชุดก่อนอัดแล้วเปลี่ยน `def t_` → `def x_` ทั้ง 42 ข้อ แล้วรัน ได้ `all green` รหัสจบ 0
  และ **ไม่มีบรรทัด `ok` ออกมาเลย** ซึ่งเป็นสัญญาณเดียวที่คนจะสังเกตได้ และมันหายไปพร้อมกัน
- หัวไฟล์ของ `gate_prerecord_test.py` บรรทัด 11-12 เขียนไว้เองว่า
  *"รายงาน #0006 — ด่านที่ไม่ได้วัดอะไรเลยพิมพ์เครื่องหมายถูก ที่นี่จึงมีข้อที่ยืนยันว่า ศูนย์การตรวจ = ปฏิเสธ
  และบรรทัดตอนผ่านต้องมีตัวเลขกำกับ"* — พฤติกรรมของ `main()` ในไฟล์เดียวกันขัดกับประโยคนั้นตรงๆ
- ยังไม่ใช่ความเสียหายที่เกิดขึ้นจริง: ชุดจริงรัน 42 และ 53 ข้อ และเขียวทั้งคู่ ข้อบกพร่องนี้จึงเป็นช่องที่เปิดค้างอยู่
  ไม่ใช่ผลที่ผิดไปแล้ว

**สิ่งที่ควรจะเป็น:** จำนวนข้อที่รันจริงต้องถูกนับ · ศูนย์ = ปฏิเสธพร้อมบอกเหตุผล · และบรรทัดตอนผ่านต้องมีตัวเลข
กำกับ ไม่ใช่คำว่า `all green` เปล่าๆ — เป็นกฎเดียวกับที่รายงาน #0006 เขียนไว้และที่ตัวไฟล์นี้บังคับใช้กับด่านอยู่แล้ว

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

`FAILS` เป็นรายการที่ตั้งต้นว่าง ความหมายของมันคือ *"ยังไม่พบข้อที่พัง"* แต่ตอนถึงบรรทัดตัดสิน มันถูกอ่านว่า
*"ทุกข้อผ่าน"* สองความหมายนี้ต่างกันตรงที่ความหมายหลังต้องการข้อมูลเพิ่มอีกหนึ่งอย่าง คือ **จำนวนข้อที่รันไปจริง**
ซึ่งไม่มีใครนับ นี่คือรูปเดียวกับ `rc=0` ในรายงาน #0006 เป๊ะ ต่างกันแค่ภาษาและชื่อตัวแปร

จุดที่ต้องอธิบายให้ได้จริงๆ ไม่ใช่ "ทำไมลืมนับ" แต่คือ **ทำไมถึงลงมือเขียนโดยไม่ตรวจก่อน ทั้งที่กฎอยู่ในไฟล์นั้นเอง**
คำตอบคือ ตอนเขียน ผู้เขียนถือกฎของ #0006 ไว้ในมือจริง และ **เอาไปใช้กับสิ่งที่กำลังทดสอบ** — `gate_prerecord.py`
ได้ `checks_run` และได้เงื่อนไขปฏิเสธเมื่อเป็นศูนย์ครบถ้วน ส่วน `main()` ของชุดเทสต์ไม่ถูกมองว่าเป็น "ด่าน"
มันถูกมองว่าเป็น *สายพานที่พาข้อเทสต์เดินผ่าน* ซึ่งเป็นโครงที่ลอกมาจากตัวรันเทสต์แบบเดิมและ "รู้อยู่แล้วว่าใช้ได้"
กฎจึงถูกทาลงบน subject under test แล้วหยุดที่ขอบของ instrument โดยไม่มีใครถามคำถามเดิมซ้ำอีกฝั่งหนึ่งของขอบ

ผลที่ตามมาคือรูปที่แย่กว่าการไม่มีกฎเลย: ไฟล์นี้ **ประกาศตัวเป็นเจ้าของกฎนั้น** ทั้งในหัวไฟล์และในข้อเทสต์ชื่อ
`t_zero_checks_is_a_refusal_even_with_no_reason_recorded` คนที่เปิดไฟล์อ่านจึงได้หลักฐานว่ากฎนี้ถูกใช้แล้ว
และไม่มีเหตุให้ไปตรวจ `main()` ซ้ำ — คำประกาศกลายเป็นสิ่งที่ปิดบังจุดที่มันไม่ครอบถึง (บทเรียนเดียวกับ #0001)

### 5 Whys

1. **ทำไมชุดเทสต์พิมพ์ `all green` ทั้งที่รันไป 0 ข้อ?** — เพราะ `main()` ตัดสินจากเงื่อนไข `if FAILS:` อย่างเดียว
   และรายการนั้นว่าง
2. **ทำไม `FAILS` ถึงว่าง?** — เพราะลูปไม่ทำงานสักรอบ ไม่มี global ตัวไหนชื่อขึ้นต้นด้วย `t_` ให้เรียก จึงไม่มีรอบไหน
   ที่จะเติมอะไรลงไปได้
3. **ทำไม "ไม่มีอะไรให้รัน" ถึงไม่ถูกมองว่าผิดปกติ?** — เพราะไม่มีตัวนับ ตัวแปรเดียวที่มีตอบได้แค่คำถามว่า
   "มีข้อไหนพังไหม" ซึ่งตอบว่า "ไม่มี" ได้เหมือนกันทั้งตอนที่ทุกข้อผ่าน และตอนที่ไม่ได้รันอะไรเลย
4. **ทำไมถึงไม่ใส่ตัวนับ ทั้งที่วันเดียวกันนั้นเพิ่งเขียนกฎนี้ลงในหัวไฟล์เดียวกัน?** — เพราะกฎถูกอ่านว่าเป็นข้อกำหนด
   ของ **สิ่งที่ถูกทดสอบ** ไม่ใช่ของ **เครื่องมือที่ใช้ทดสอบ** ตัวด่านจึงได้ `checks_run` ครบ ส่วน `main()`
   ถูกลอกรูปจากตัวรันเทสต์เดิมมาโดยไม่ผ่านคำถามเดียวกันแม้แต่ครั้งเดียว
5. **ทำไมขอบเส้นนั้นถึงข้ามไม่ได้เอง?** — **root cause: ชั้นที่ทำหน้าที่ "วัด" ถูกยกเว้นจากกฎการวัดของตัวเองโดยปริยาย**
   ทุกครั้งที่เขียนเครื่องมือวัด ความสนใจทั้งหมดอยู่ที่ว่าสิ่งที่ถูกวัดถูกต้องไหม ไม่มีขั้นตอนไหนถามว่าเครื่องมือวัด
   วัดไปกี่ครั้ง กฎ "ศูนย์ = ปฏิเสธ" จึงหยุดที่ขอบของ subject under test เสมอ และเป็นขอบที่ไม่มีเครื่องมือใด
   ในระบบนี้ข้ามให้ ต้องปิดด้วยการทำให้ตัวรันเทสต์ต้องรายงานจำนวนที่รัน ไม่ใช่ด้วยการจำให้ดีขึ้น

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**

| ชั้นที่มีอยู่ | ทำไมไม่จับ |
|---|---|
| `scripts/list-test-suites.sh` → `run-test-suites.sh` · `scripts/hooks/pre-push` · `.github/workflows/tests.yml` | ทั้งสามตัวรู้จักเฉพาะ `tools/*/*.test.js` ใน repo `ols-qa` · ชุดเทสต์นี้เป็น Python และอยู่นอก repo จึงอยู่นอกทุกด่านตั้งแต่ต้น |
| มาตรการ P5 ของรายงาน #0006 ("ด่านที่ประกาศตัวว่า fail closed ต้องมีเทสต์พิสูจน์") | ครอบ **ด่าน** ไม่ได้ครอบ **ตัวรันเทสต์ของด่าน** ซึ่งเป็นคนละชิ้นและไม่มีใครประกาศคุณสมบัติแทนมัน |
| ตัวชุดเทสต์เอง | มีข้อที่บังคับกฎนี้ให้ด่าน (บรรทัด 282 และ 520) แต่ไม่มีข้อไหนบังคับกฎเดียวกันกับ `main()` ของตัวเอง — เทสต์ทดสอบทุกอย่างยกเว้นตัวมันเอง |
| การใช้งานประจำวัน | ไฟล์มี `t_` ครบเสมอ สภาพที่ทำให้บั๊กแสดงตัว (เปลี่ยนชื่อ ย้ายข้อออก ตัดไฟล์แยก) ไม่เคยเกิดเองในรอบปกติ |

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ทำซ้ำจนได้อาการจริงก่อนเขียนรายงาน แทนที่จะอ่านโค้ดแล้วสรุป — ทำให้ข้อความ `all green` กับรหัสจบ 0
  เป็นของที่วัดได้ ไม่ใช่ข้อสันนิษฐาน
- รันชุดจริงเทียบทันที จึงแยกได้ชัดว่านี่เป็นข้อบกพร่องแฝง ไม่ใช่ผลที่ผิดไปแล้ว — และไม่ต้องไปสั่นคลอน
  ความเชื่อถือของผลรอบนี้โดยไม่จำเป็น
- นับบรรทัด `ok` จาก output แทนที่จะเชื่อบรรทัดสรุป ซึ่งเป็นวิธีเดียวที่ตอบได้ว่าชุดจริงวัดไปกี่ข้อ

### สิ่งที่ต้องปรับปรุง
- **กฎที่เพิ่งเขียนวันเดียวกันถูกใช้กับของที่ถูกทดสอบ แล้วหยุดที่เครื่องมือทดสอบ** — เวลาได้กฎใหม่มาหนึ่งข้อ
  ต้องไล่ถามซ้ำกับทุกชิ้นที่อยู่ในเส้นทางเดียวกัน ไม่ใช่แค่ชิ้นที่กฎนั้นเกิดมาจาก
- **ลอกโครงจากตัวรันเทสต์เดิมโดยไม่ตรวจ** เพราะเชื่อว่า "โครงนี้ใช้มานานแล้ว" — ของที่ใช้มานานเป็นสิ่งที่
  ไม่มีใครเคยตั้งคำถาม ไม่ใช่สิ่งที่เคยผ่านการตรวจ
- **ข้อบกพร่องถูกคัดลอกไปไฟล์ที่ 2 ห่างกัน 30 นาที** — การลอกโครงทำให้ข้อผิดพลาดหนึ่งใบกลายเป็นสองใบ
  ก่อนที่ใครจะได้อ่านใบแรกซ้ำเลยแม้แต่ครั้งเดียว
