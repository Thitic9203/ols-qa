## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

สมมติว่าบัญชีที่มีบทบาท "ครู" (`tc9021`) จะต้องมีสื่อที่สร้างไว้ในระบบ เพราะบัญชีอื่นในกลุ่มเดียวกัน (`tc9020`) มีสื่ออยู่ แต่ไม่เคยตรวจกับ API จริงก่อนพูด ทำให้เจ้าของงานตัดสินใจบนข้อมูลที่ไม่จริง

### 5 Whys

1. **ทำไมแผนปลดล็อกไม่สำเร็จ?** — เพราะ `tc9021` ไม่มีสื่อเลย (`/api/media/me` = 0 ชิ้น) จึงเป็น fixtureOwnerF1 ไม่ได้
2. **ทำไมเสนอแผนที่อ้างว่า tc9021 มีสื่อ?** — เพราะสมมติจากบทบาท "ครู" ว่าน่าจะมีสื่อ ไม่ได้เรียก API ตรวจ
3. **ทำไมไม่เรียก API ตรวจก่อน?** — เพราะมองว่าเป็นข้อมูลที่ "น่าจะจริง" จากรูปแบบของบัญชีอื่น จึงข้ามขั้นตอนการตรวจ
4. **ทำไมถึงไม่ถูกจับก่อนบอกเจ้าของงาน?** — ไม่มีชั้นป้องกันที่บังคับให้ตรวจ API ก่อนเสนอแผนที่อ้างว่าบัญชีมีข้อมูลบางอย่าง
5. **ทำไมยังเดาทั้งที่กฎ §0 ห้ามชัดเจน?** — กฎ §0 ถูกจัดหมวดในหัวว่าเป็นเรื่อง "ข้อเท็จจริง" แต่ตอนเสนอแผนมองว่าเป็น "การประเมิน" จึงไม่ถูกกระตุ้นให้ตรวจ ทั้งที่เป็นเรื่องเดียวกัน

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** กฎ §0 "ห้ามเดา" ครอบคลุมอยู่แล้ว แต่ไม่มีชั้นอัตโนมัติที่บังคับให้ตรวจ API ก่อนเสนอแผนที่พึ่งพาข้อมูลของบัญชี — เป็นการพึ่งพาวินัยล้วน ซึ่งล้มเหลวซ้ำแล้วซ้ำเล่า (ดู #0019 · #0025)

| # | มาตรการ | ชนิด | สถานะ |

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** จับได้เองเมื่อเรียก `/api/media/me` หลังล็อกอินสำเร็จ
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** จับได้หลังจากเจ้าของงานล็อกอินให้ครบ 3 บัญชีแล้ว — ความเสียหาย (เวลาล็อกอินเปล่า) เกิดครบก่อนจะรู้
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** ถ้าเรียก API ตรวจก่อนเสนอแผน จะรู้ทันทีว่าแผนเป็นไปไม่ได้ โดยไม่ต้องรบกวนเจ้าของงานเลย

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ไม่ถึงขั้นเขียนข้อมูล — ขั้นตอนล็อกอินและตรวจ API แยกจากขั้นเขียน จึงจำกัดความเสียหายไว้ที่เวลาที่สูญไป

### สิ่งที่ต้องปรับปรุง
- ข้ออ้างเชิงบวก ("บัญชีนี้มีสื่อ") ต้องถูกจัดเป็น "ข้อเท็จจริงที่ต้องตรวจ" เหมือนกับข้ออ้างเชิงลบ ("ไม่มี X") ทุกประการ
- การ "น่าจะจริง" จากรูปแบบของบัญชีอื่น ไม่ใช่หลักฐาน — แต่ละบัญชีอาจมีข้อมูลต่างกัน
