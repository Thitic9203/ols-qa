## สรุปสั้น (Executive Summary)

ตอนเขียน #0135 เธรดหลักค้นไฟล์มติของรอบ (`ROUND_DECISIONS.md`) ด้วยคำ `LOADMAX` และ `Feed_TC_001` เท่านั้น เจอบรรทัด 61 (17.4x: เคสย้อนไม่ได้คง LOADMAX 8) แล้วเขียนว่า take Feed_TC_001 ที่รัน `LOADMAX 999` "ขัดมติ 17.4x · ไม่พบมติยกเว้น" และเปิดแถว PENDING -04 ตามนั้น

มติเดียวกันยังสั่งให้ "อัดทันทีทีละเคสจากเธรดหลัก ไม่อัดขนานหลายเลน" แต่วันที่ 24/Sep เธรดหลักปล่อยเลน Badge_TC_001 และ Feed_TC_001 ทำงานพร้อมกัน (ดูลำดับเวลาใน #0134) นี่คือการเบี่ยงจากมติจริง และไม่มีรายงานใดชี้ไว้

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

คำถามตอนเขียน #0135 คือ "ค่า `LOADMAX 999` ถูกต้องไหม" จึงค้นด้วยชื่อตัวแปรนั้น ได้มติเก่าที่มีคำนี้ แล้วใช้ "grep ไม่เจอบรรทัดอื่น" เป็นหลักฐานว่าไม่มีมติยกเว้น ทั้งที่มติในไฟล์เป็นข้อความอิสระที่จดด้วยคำของเจ้าของงาน (ไทย) บ้าง ชื่อตัวแปร (ละติน) บ้าง
การเริ่มจากชื่อตัวแปรยังทำให้ไม่ได้อ่านมติ 21.3x ทั้งบรรทัด จึงไม่เห็นว่าครึ่งหลังของมติเดียวกันสั่ง "ไม่อัดขนานหลายเลน" ซึ่งเป็นสิ่งที่ถูกละเมิดจริงในเหตุ #0134

### 5 Whys

1. **ทำไม #0135 เขียนว่า take "ขัดมติ 17.4x · ไม่พบมติยกเว้น"?** — เพราะเธรดหลักค้น `ROUND_DECISIONS.md` ด้วย `LOADMAX` และ `Feed_TC_001` เท่านั้น (#0135 บรรทัด 95) ได้บรรทัด 61 และไม่ได้บรรทัดที่ยกเลิกเกณฑ์ จึงสรุปว่าไม่มีมติยกเว้น
2. **ทำไมการค้นนั้นไม่เจอมติ 21.3x?** — เพราะบรรทัด 81 จดด้วยคำไทย "เกณฑ์โหลด 8/16" ไม่มีคำ `LOADMAX` (0 ครั้ง) · grep `LOADMAX` ได้ 8 บรรทัดที่ไม่มีบรรทัด 81 ส่วน grep `โหลด` ได้ 7 บรรทัดที่มีบรรทัด 81 — เรื่องเดียวกันถูกจดด้วยคำคนละภาษา
3. **ทำไมใช้ผลว่างของการค้นคำเดียวเป็นหลักฐานว่า "ไม่มี"?** — เพราะไม่ได้อ่านมติที่ใหม่กว่า 17.4x ทุกบรรทัด ทั้งที่ไฟล์มีแค่ 92 บรรทัดและมติหลังบรรทัด 61 มี 31 บรรทัด · CLAUDE.md §0 ให้ข้ออ้างเชิงลบแนบขอบเขตและจำนวน แต่ #0135 แนบแค่คำที่ค้น และไม่มีอะไรตรวจว่าขาดขอบเขต
4. **ทำไมไม่มีใครเห็นว่าการเบี่ยงจริงคือการรัน 2 เลนขนานกัน?** — เพราะตอนจ่ายบรีฟ 06.3x ให้เลน Badge ขณะเลน Feed ยังทำงาน เธรดหลักไม่ได้เทียบแผนการจ่ายงานกับมติ 21.3x และตอนเขียน #0134 ก็วิเคราะห์ที่ระดับบัญชีซ้ำ ไม่ได้เปิดมติ 21.3x (#0134 นับ `21.3x` = 0) · ตอนเขียน #0135 การค้นเริ่มจากชื่อตัวแปร ไม่ได้เริ่มจาก "มติล่าสุดสั่งอะไรเรื่องวิธีอัด"
5. **ทำไมทั้งการเขียนข้ออ้างและการจ่ายงานถึงไม่ถูกเทียบกับมติ?** — root cause: มติของเจ้าของงานเก็บเป็นข้อความอิสระที่ไม่มีโครงสร้าง (ไม่มีส่วน "ข้อบังคับที่มีผลอยู่" ที่อ่านด้วยเครื่องได้ เช่น เกณฑ์โหลด หรือจำนวนเลนที่รันพร้อมกันได้) และไม่มีด่านในโค้ดที่ (ก) ปฏิเสธข้ออ้างเชิงลบเรื่องมติที่ไม่ได้มาจากการอ่านทุกบรรทัดที่ใหม่กว่ามติที่อ้าง และ (ข) ตรวจการจ่ายงานเลนเทียบข้อบังคับของรอบ — การค้นคำเดียวและการจ่ายเลนขนานจึงผ่านได้เสมอไม่ว่ามติจะจดด้วยภาษาใด

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- CLAUDE.md §0 (ข้ออ้างเชิงลบต้องแนบคำสั่งค้น + ขอบเขต + จำนวน): เป็นข้อความ ไม่มีตัวตรวจ · #0135 แนบคำสั่งค้นแต่ไม่แนบขอบเขตหรือจำนวนบรรทัด
- กฎจาก #0101 (ต้องเปิดไฟล์มติของรอบก่อนสรุป): #0135 เปิดไฟล์มติจริง (ด้วย grep) จึงไม่ขัดกฎตามตัวอักษร · ข้อเสนอ P2–P4 ของ #0101 ยังค้าง และถึงทำแล้วก็ตรวจแค่ว่า "เคยอ่านไฟล์" ไม่ตรวจว่าอ่านครอบบรรทัดใดบ้าง
- `ask-guard`: เป็น hook ของ AskUserQuestion เท่านั้น (`tools/ask-guard/check.js:4`) ข้อความที่เขียนลงรายงานไม่ผ่านการ์ดนี้
- `postmortem-guard`: ตรวจโครงสร้าง ดัชนี และเลขลำดับ · ไฟล์ .js ที่ไม่ใช่เทสต์ไม่มีรูปแบบตรวจข้ออ้างเชิงลบ (grep `ไม่พบ|ไม่มีมติ` = 0 ไฟล์)
- `agent-dispatch-guard`: `check.js` และ `dispatch_rules.js` ไม่อ้างถึงไฟล์มติเลย (grep `ROUND_DECISIONS|มติ` = 0 บรรทัด) จึงปล่อยบรีฟ 06.3x ออกไปขณะอีกเลนยังรัน
- `REC.lock`: กันการอัดซ้อนในวินาทีเดียวกัน ไม่กันการรัน 2 เลนพร้อมกัน — เผยให้เห็นการซ้อนเมื่อ 23:54:39Z ซึ่งหลังการเผยแพร่ของเลน Feed แล้ว
