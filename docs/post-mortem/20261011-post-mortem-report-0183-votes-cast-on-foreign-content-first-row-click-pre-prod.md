## สรุปสั้น (Executive Summary)

ระหว่างรอบ RTT บน pre-prod บัญชีผู้ดูแลทดสอบมีโหวตลงบนสื่อที่ไม่อยู่ใน ledger ของเลนใดรวม 4 รายการ
2 รายการมาจากสคริปต์อัดคลิปของเลนที่กดแถวแรกของคิวอนุมัติก่อนผลค้นหาจะกรองเสร็จ (หลักฐานในไฟล์ประวัติโหวตของเลน B2)
อีก 2 รายการ (บัญชีผู้ดูแลเนื้อหา 2 บัญชี ไม่อนุมัติบัญชีละ 1) ยังไม่ทราบที่มา — ไม่พบ id ใน ledger หรือ progress log ของเลนใด กำลังสืบแบบอ่านอย่างเดียว
โหวตย้อนไม่ได้ · ตั้งแต่รอบ 3 (11/10 22:2x) ทุกเลนต้องเลือกแถวด้วย id ของ fixture จาก ledger และเทียบ id บนจอก่อนทุกการกระทำที่ย้อนไม่ได้

## 1. ปัญหา (Problem Statement)

- **สิ่งที่ควรเกิด:** การโหวตในคิวอนุมัติทำเฉพาะบนสื่อที่รอบนี้สร้างเอง (fixture ที่อยู่ใน `ledger.jsonl` ของเลน) — บรีฟเลนรอบ 2 เขียนไว้ว่า "Never touch content you did not create"
- **สิ่งที่เกิดจริง:** ตรวจประวัติโหวตของบัญชี pre-prod ครบ 12 บัญชี (GET อย่างเดียว) พบโหวตบนสื่อที่ไม่อยู่ใน ledger ใดเลย 4 รายการ: อนุมัติ 1 · ไม่อนุมัติ 3
- **ขอบเขต:** pre-prod เท่านั้น · บัญชีผู้สร้าง 4 บัญชีเรียก endpoint ประวัติได้ 403 (โหวตไม่ได้) · endpoint ให้จำนวนรวมมากกว่าแถวที่ส่งกลับ 6 แถวใน 3 บัญชี จึงยังมีส่วนที่มองไม่เห็น · การรายงานสื่อ (report) ไม่อยู่ใน endpoint นี้ ยังไม่ได้ตรวจ

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไมโหวตลงสื่อของผู้อื่น?** — สคริปต์กดปุ่มโหวตบนแถวแรกของตารางคิว ไม่ใช่แถวที่มี id ของ fixture
2. **ทำไมแถวแรกไม่ใช่ fixture?** — สคริปต์พิมพ์คำค้นแล้วกดทันที ตารางยังแสดงคิวเต็ม (ยังไม่กรอง) แถวแรกจึงเป็นสื่อของผู้อื่น
3. **ทำไมสคริปต์ไม่รู้ว่ากดผิดแถว?** — ไม่มีการอ่าน id ของแถวหรือของหน้ารายละเอียดก่อนกด ใช้ตำแหน่งแถว (`first` / ลำดับ) เป็นตัวระบุเป้าหมาย
4. **ทำไมไม่มีด่านเทียบ id?** — บรีฟเลนห้าม "แตะของที่ไม่ได้สร้าง" เป็นข้อความ แต่ไม่ได้กำหนดวิธีพิสูจน์ก่อนกด (ไม่มี pre-ledger ที่ต้องมีทั้ง id เป้าหมายและ id ที่เห็นบนจอ)
5. **ทำไมบรีฟไม่มีวิธีพิสูจน์?** — บทเรียน #0144 (ตัวเลือกกว้างกดผิดปุ่ม) ถูกนำไปใช้เป็นคำเตือนในบรีฟ ไม่ได้กลายเป็นด่านในโค้ดหรือรูปแบบ pre-ledger ที่ตรวจได้ด้วยเครื่อง

**สาเหตุราก:** การกระทำย้อนไม่ได้ระบุเป้าหมายด้วยตำแหน่งบนจอแทน id และไม่มีด่านเชิงเครื่องที่เทียบ id บนจอกับ ledger ก่อนกด
**ส่วนที่ยังไม่ทราบ:** ที่มาของโหวต 2 รายการ (02:33 และ 09:14) — ยังไม่ได้พิสูจน์ว่ามาจากสคริปต์ของรอบหรือจากที่อื่น

## 4. ผลกระทบ (Impact)

- สื่อของผู้อื่นบน pre-prod 4 รายการได้คะแนนโหวตที่ไม่ได้ตั้งใจ (ย้อนไม่ได้) — ถ้าคะแนนครบเกณฑ์ สถานะของสื่อนั้นอาจเปลี่ยนเป็นอนุมัติ/ไม่อนุมัติ
- ผลทดสอบ OLS-890 แถวที่ใช้คลิปชุดนั้น (TC_34 / TC_06) ใช้เป็นหลักฐานไม่ได้ ต้องสร้าง fixture ใหม่และอัดใหม่ด้วยการเลือกจาก id
- เลน B2 ต้องหยุดงาน one-way จนตรวจครบทุกบัญชี

## 5. แนวทางการแก้ไข (Fix)

- หยุดการกระทำ one-way บน pre-prod ของเลน B2 จนเขียนรายการครบ (`LB2/incident_foreign_votes.md` — 4 รายการ ตรวจครบ 12 บัญชี)
- บรีฟรอบ 3 (`LANE_BRIEF_ROUND3.md` หัวข้อ "New rule after incident H2"): เลือกแถวด้วย id ของ fixture จาก ledger เท่านั้น ห้ามกดแถวแรก · ก่อนการกระทำย้อนไม่ได้ทุกครั้ง อ่าน id ใน URL/แผงรายละเอียดบนจอ เทียบกับ id ใน ledger และเขียนทั้งสองค่าใน pre-ledger · ไม่ตรง = หยุด
- แยก agent สืบที่มาของโหวต 2 รายการที่ยังไม่ทราบ (อ่านอย่างเดียว ผลเขียนที่ `LB2/incident_attribution.md`)

**ยืนยันแล้วด้วย:** เธรดหลักตรวจไฟล์รายการซ้ำ — พบ 4 id และ grep 2 id ที่ยังไม่ทราบที่มาใน `L*/ledger.jsonl` + `L*/progress.log` ได้ 0 ไฟล์

## 7. การตรวจจับปัญหา (Detection)

- จับได้จากการตรวจประวัติโหวตย้อนหลัง (เลน B2 พบ 2 รายการแรกระหว่างตรวจ TC_34) ไม่ใช่จากด่านก่อนกด
- ควรจับได้ตั้งแต่ก่อนกด: ถ้ามี P2/P3 สคริปต์จะหยุดที่บรรทัด id ไม่ตรงก่อนโหวต

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- Handoff บันทึกเหตุการณ์ทันทีพร้อมไฟล์หลักฐาน และระบุตรงๆ ว่ายังไม่ได้ตรวจบัญชีอื่น
- รอบ 3 สั่งให้ตรวจครบทุกบัญชีแบบอ่านอย่างเดียวก่อนเปิดการกระทำ one-way ใหม่

### สิ่งที่ต้องปรับปรุง
- คำห้ามในบรีฟไม่พอสำหรับการกระทำย้อนไม่ได้ — ต้องมีวิธีพิสูจน์ที่เขียนเป็นข้อมูลและตรวจได้ด้วยเครื่อง
- การตรวจประวัติโหวตควรทำหลังทุกชุดคลิปที่มีการโหวต ไม่ใช่ตอนท้ายรอบ
