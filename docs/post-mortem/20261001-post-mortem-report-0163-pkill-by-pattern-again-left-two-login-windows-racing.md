## สรุปสั้น (Executive Summary)

เจ้าของงานสั่งให้ข้ามการล็อกอินบัญชี Dev หนึ่งบัญชี เธรดหลักหยุดโปรเซสหน้าต่างล็อกอินของบัญชีนั้นด้วย `pkill -f '<สคริปต์ล็อกอิน> <ชื่อบัญชี>'`
ทั้งที่ CLAUDE.md §9 ห้าม `pkill -f`/`killall` และให้หยุดด้วย pid ที่รู้ที่มาเท่านั้น โปรเซสไม่จบด้วย SIGTERM จึงยังรันคู่กับหน้าต่างล็อกอินของบัญชีถัดไปที่เพิ่งเปิด
— สองโปรเซสรอการล็อกอินบัญชีเดียวกันพร้อมกัน เธรดหลักตามปิดด้วย `kill <pid>` (ไม่ผล) และ `kill -9 <pid>` (จบ) แล้วยืนยันด้วย `pgrep` ว่าเหลือตัวใหม่ตัวเดียว
ต้นเหตุคือกฎของ #0039 เป็นข้อความล้วน และ Action Item 4 ของ #0039 (การ์ด PreToolUse ที่ตีกลับ `pkill`/`killall`) ค้างสถานะ Open มาตั้งแต่ 2026-09-09
รอบนี้สร้างการ์ดนั้นแล้วที่ `tools/process-kill-guard/kill_rules.js` พร้อมเทสต์ 9 ข้อ (เขียวครบ) — **การผูกเข้า `.claude/settings.json` ยังรอเจ้าของงานอนุมัติ** ตาม CLAUDE.md §10

## 1. ปัญหา (Problem Statement)

- เธรดหลักรัน `pkill -f '<สคริปต์ล็อกอิน> <ชื่อบัญชี>'` เพื่อหยุดหน้าต่างล็อกอินของบัญชีที่เจ้าของงานสั่งข้าม (ข้อเท็จจริงจากเธรดหลัก 2026-10-01 07.1x +07)
- โปรเซสนั้น (pid ได้จาก `pgrep -fl session_capture.js`) ไม่จบหลังรับ SIGTERM และยังรันอยู่พร้อมกับหน้าต่างล็อกอินตัวใหม่ของบัญชีถัดไป → มีสองโปรเซสรอการล็อกอินบัญชีเดียวกัน
- `kill <pid>` ไม่มีผล · `kill -9 <pid>` ทำให้จบ · `pgrep` หลังจากนั้นเหลือเฉพาะตัวใหม่
- shell เบื้องหลังที่รันโปรเซสเดิมรายงานรหัสจบ 144 (จบด้วยสัญญาณ)
- ในเซสชันเดียวกันก่อนหน้านั้น เธรดหลักใช้ `kill <pid>` กับหน้าต่างล็อกอินอีกตัวได้ถูกต้องแล้ว — คือรู้กฎ แต่ไม่มีอะไรหยุดตอนพิมพ์ผิด

**สิ่งที่ควรจะเป็น:** CLAUDE.md §9 — "หยุดโปรเซสด้วย pid ที่รู้ที่มาเท่านั้น ห้าม `pkill -f`/`killall` เมื่อมีตัวจริงรัน" (`CLAUDE.md:92`) ·
ขั้นตอนที่ถูก: `pgrep -fl` อ่านอย่างเดียว → เลือก pid ที่ตัวเองเปิด → `kill <pid>` → `pgrep -fl` ยืนยัน → ยังอยู่ = `kill -9 <pid>` → ยืนยันอีกครั้ง **ก่อน** เปิดหน้าต่างของบัญชีถัดไป

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

จุดตัดสินใจที่ผิดมีสองจุด: (1) เลือกจับด้วยรูปแบบแทน pid ทั้งที่ pid หาได้ในคำสั่งเดียว และ (2) เปิดหน้าต่างของบัญชีถัดไปโดยไม่ยืนยันว่าตัวเดิมจบแล้ว
ตอนนั้น `pkill -f '<สคริปต์> <ชื่อบัญชี>'` ดูปลอดภัยเพราะรูปแบบมีชื่อบัญชีอยู่ด้วย จึง "ดูเหมือน" เจาะจงพอ — แต่ความเจาะจงของรูปแบบไม่ได้ให้ pid กลับมา
พอ SIGTERM ไม่ได้ทำให้โปรเซสจบ คำสั่งก็จบเงียบ (`pkill` คืน 0 เมื่อส่งสัญญาณได้ ไม่ใช่เมื่อโปรเซสตาย) และไม่มี pid อยู่ในมือให้ตามดูต่อ

### 5 Whys

1. **ทำไมมีหน้าต่างล็อกอินสองตัวรอบัญชีเดียวกัน?** — เพราะโปรเซสเดิมไม่จบหลัง SIGTERM และหน้าต่างของบัญชีถัดไปถูกเปิดโดยไม่ได้ยืนยันว่าตัวเดิมจบแล้ว
2. **ทำไมไม่ได้ยืนยันว่าตัวเดิมจบ?** — เพราะหยุดด้วย `pkill -f` ซึ่งคืนผลสำเร็จเมื่อ "ส่งสัญญาณได้" และไม่คืน pid มาให้ตามดู จึงดูเหมือนงานจบแล้วทั้งที่ยังไม่จบ
3. **ทำไมใช้ `pkill -f` ทั้งที่ §9 ห้ามและเพิ่งใช้ `kill <pid>` ถูกไปก่อนหน้า?** — เพราะกฎอยู่ในรูปข้อความใน CLAUDE.md เท่านั้น การปฏิบัติตามขึ้นกับการนึกออกในจังหวะพิมพ์ ซึ่งพลาดได้ทุกครั้งที่มีแรงกดดัน (เจ้าของงานรออยู่ + ต้องเปิดบัญชีถัดไปทันที)
4. **ทำไมกฎยังเป็นข้อความล้วนหลังผ่าน #0039 มาแล้ว 22 วัน?** — เพราะ #0039 ปิดรายงานด้วยมาตรการชนิด "กฎ" (P1–P3) และระบุเองว่ายังไม่นับว่าปิดคลาส แต่ Action Item 4 (การ์ด PreToolUse) ถูกตั้งเป็น "พิจารณา ต้องให้เจ้าของงานเคาะก่อน" แล้วไม่มีใครยกขึ้นถามเจ้าของงาน
5. **ทำไม Action Item ที่เป็นกลไกถึงค้างได้โดยไม่มีอะไรเตือน?** — เพราะระบบ post-mortem ติดตามหนี้ระดับ "แถว PENDING ที่ยังไม่มีรายงาน" แต่ไม่ติดตาม Action Item ที่ Open อยู่ในรายงานที่ปิดแล้ว รายงานจึงนับเป็น DONE ได้ทั้งที่ชั้นกลไกของมันไม่เคยถูกสร้าง **(root cause: มาตรการที่เป็นกลไกถูกเลื่อนเป็น "พิจารณา" โดยไม่มีเจ้าของและไม่มีจุดบังคับ กฎจึงเหลือแต่ความจำ)**

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- PreToolUse Bash ที่ผูกอยู่ (`customer-content-guard.sh` · `git-staging-guard.sh` · `issue-creation-guard.sh` · `discord-notify-guard.sh --gate`) ไม่มีตัวใดตรวจคำสั่งหยุดโปรเซส — ค้น `grep -rln pkill .claude/hooks tools scripts .claude/settings.json` ได้ 0 ไฟล์ (2026-10-01 ก่อนสร้างการ์ดนี้)
- CLAUDE.md §9 เป็นข้อความ ไม่มีตัวบังคับ
- ตัวเปิดหน้าต่างล็อกอินเองไม่มี pidfile/การปฏิเสธการเริ่มซ้อน (คือ P4 ของ #0039 ที่ค้างอยู่เช่นกัน) จึงไม่มีอะไรห้ามสองหน้าต่างรอบัญชีเดียวกัน

## 5. แนวทางการแก้ไข (Fix)

- ปิดโปรเซสที่ค้างด้วย `kill -9 <pid>` และยืนยันด้วย `pgrep -fl session_capture.js` ว่าเหลือเฉพาะตัวใหม่ (เธรดหลัก 2026-10-01)
- สร้างการ์ด `tools/process-kill-guard/kill_rules.js` — `node kill_rules.js --hook` อ่าน payload PreToolUse แล้วตีกลับ (exit 2) คำสั่ง `pkill`/`killall` · `kill $(pgrep|pidof|lsof|ps …)` · `pgrep … | xargs kill` รวมกรณีที่ซ่อนหลังคำนำหน้า (rtk/sudo/env/timeout/VAR=) หรืออยู่ใน `bash -c` / `$( … )` · ปล่อยผ่าน `kill <pid>` / `kill "$PID"` / `kill $!` / `kill $(cat x.pid)` / `pgrep -fl` และคำว่า pkill ที่เป็นข้อมูล (grep · ข้อความคอมมิต · heredoc)
- เทสต์ `tools/process-kill-guard/kill_rules.test.js` 9 ข้อ: ต้องบล็อก (รูปของเหตุ 1/Oct และ #0039 + 20 รูปแบบ + 8 แบบมีคำนำหน้า) · ต้องปล่อย (10 แบบ pid + 8 แบบข้อมูล) · 3 ข้อรันไฟล์จริงบนดิสก์ผ่าน `--hook` (บล็อก exit 2 · ปล่อย exit 0 · input เสียต้องเตือนไม่เงียบ)

**ยืนยันแล้วด้วย:**
```
$ node tools/process-kill-guard/kill_rules.test.js
9 passed, 0 failed
```
และ `bash scripts/run-test-suites.sh` เขียวทั้งชุด (ผลอยู่ใน §10)

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- เธรดหลักตรวจด้วย `pgrep` เอง เห็นตัวที่ค้าง แล้วปิดด้วย pid และยืนยันอีกครั้ง ไม่ปล่อยให้สองหน้าต่างค้างไว้
- เปิดแถว PENDING ทันทีในเทิร์นนั้น

### สิ่งที่ต้องปรับปรุง
- `pkill` คืนผลสำเร็จเมื่อส่งสัญญาณได้ ไม่ใช่เมื่อโปรเซสตาย — การหยุดโปรเซสต้องยืนยันด้วยการอ่านสถานะซ้ำเสมอ ก่อนเริ่มงานถัดไปที่ใช้ทรัพยากรเดียวกัน
- มาตรการชนิดกลไกที่ถูกตั้งเป็น "พิจารณา" ต้องถูกยกไปถามเจ้าของงานในรอบนั้นเลย ไม่ใช่ปล่อยค้างใน Action Items ของรายงานที่ปิดแล้ว
