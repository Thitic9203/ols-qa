ทั้งสามกองเป็นงานที่ทำเองได้ทั้งหมด และ repo มีทั้งกฎและเครื่องมือรองรับอยู่แล้ว
เจ้าของงานต้องสั่งกลับว่า *"หาทางจัดการมาเพื่อทดสอบให้ได้ … ถ้าเจอสถานการณ์นี้ต้องจัดการมาเองให้ได้นะ

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไมจึงส่งรายงานที่ยังมีงานค้าง** — เพราะเข้าใจว่าหน้าที่ของรอบนี้คือ *รายงานสถานะ* ไม่ใช่ *ทำให้สถานะดีขึ้น*
2. **ทำไมจึงเข้าใจอย่างนั้น** — เพราะคำสั่งเดิมคือ "รัน smoke test แล้วส่งรายงาน" จึงตีความขอบเขตเป็นการวัดผลอย่างเดียว
3. **ทำไมการตีความแคบนั้นจึงผ่านตัวเอง** — เพราะการประกาศข้อจำกัดอย่างซื่อสัตย์ให้ความรู้สึกว่าได้ทำหน้าที่ครบแล้ว ความซื่อสัตย์ถูกใช้แทนความครบถ้วน
4. **ทำไมกฎที่มีอยู่จึงไม่หยุดไว้** — กฎ `feedback_always-find-testing-path` และ `no-blocked-create-the-data` เขียนถึงคำว่า **BLOCKED** ส่วนตัวรันเทสต์พิมพ์คำว่า **skipped** สมองจึงไม่จับว่าเป็นของสิ่งเดียวกัน
5. **ทำไมจึงไม่มีชั้นไหนจับตอนส่งมอบ** — เพราะไม่มีขั้นตอนใดบังคับให้อ่านหัวข้อ caveat ของตัวเองแล้วถามว่าแต่ละบรรทัดทำเองได้ไหม

**สาเหตุที่แท้จริง:** กฎที่มีอยู่ผูกกับ *คำ* (BLOCKED) ไม่ได้ผูกกับ *สภาพ* (เคสที่ไม่ได้ผลลัพธ์เพราะข้อมูลไม่พร้อม)
พอเครื่องมือใช้คำอื่น กฎจึงไม่ทำงาน

## 4. ผลกระทบ (Impact)

- เจ้าของงานต้องสั่งซ้ำ 1 รอบ และเสียเวลาอ่านรายงานที่ยังไม่ใช่ของจริง
- รายงานฉบับแรกให้ภาพครอบคลุมต่ำกว่าความจริง — ตัวเลขที่ทำได้จริงคือผ่าน 119 จาก 121 เคสที่รันได้ ไม่ใช่ 138 จาก 148 ที่มีของค้าง 3 กอง
- ไม่มีข้อมูลเสียหาย ไม่มีอะไรถูกส่งออกนอกทีมในสถานะที่ผิด

## 5. แนวทางการแก้ไข (Fix)

ทำครบในวันเดียวกันหลังได้รับคำสั่ง:

- แก้ชุดทดสอบตกยุค 11 เคส โดยอ้าง ticket ที่ปิดแล้วทุกเคส (OLS-510 · OLS-404 · OLS-657 · OLS-79)
- ปิดบั๊ก "อ่านรายการแค่หน้าแรก" ทั้งคลาส ทำให้ MLV-016 · MLV-019 · MLV-020 · MLV-021 กลับมารันได้
- FEED-131 กลับมาผ่านหลังแก้เกณฑ์ให้ตรงกับข้อกำหนด

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

1. **`skipped` ที่ตัวรันเทสต์พิมพ์เอง = BLOCKED ทุกประการ** — เขียนเพิ่มใน memory
   `feedback_always-find-testing-path` แล้ว ห้ามนับเป็นผลลัพธ์ที่ยอมรับได้ ห้ามใส่รายงานเป็นข้อจำกัด
2. **ด่านอ่าน caveat ของตัวเองก่อนส่งมอบ** — เขียนเพิ่มใน `feedback_not-done-while-anything-remains`:
   ไล่ทุกบรรทัดในหัวข้อข้อจำกัด/หมายเหตุ แล้วถามว่า *"บรรทัดนี้ฉันทำเองได้ไหม"* ทำได้ = ยังส่งไม่ได้
   ข้อจำกัดที่เขียนได้จริงมีแค่สิ่งที่อยู่นอกมือ เช่นต้องรอบัญชีจากทีมอื่น หรือระบบภายนอกไม่ตอบ
3. **`/smoke-test` เขียนเกณฑ์จบรอบไว้ในตัวสกิล** — ทุกเคสที่ไม่ผ่านต้องจบที่สาเหตุที่ยืนยันแล้ว
   พร้อม `path:line` หรือ ticket ที่เปิดอ่านรอบนั้น

## 7. การตรวจจับปัญหา (Detection)

จับได้โดยเจ้าของงานอ่านรายงาน ไม่ใช่โดยชั้นใดในระบบ ซึ่งเป็นจุดอ่อนที่มาตรการข้อ 2 ตั้งใจปิด

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ตัวเลขในรายงานถูกต้องทุกตัว และแยกเคสไม่เสถียรออกจากเคสตกจริงด้วยรอบยืนยัน
- เมื่อถูกสั่งแล้วปิดงานได้ครบภายในวันเดียว โดยทุกการแก้อ้างอิง ticket ที่ปิดแล้ว

### สิ่งที่ต้องปรับปรุง
- **ความซื่อสัตย์ไม่ใช่ตัวแทนของความครบถ้วน** การประกาศว่ามีของค้างไม่ได้ทำให้ของค้างนั้นเสร็จ
- กฎที่ผูกกับคำใดคำหนึ่งจะพังทันทีที่เครื่องมือเปลี่ยนคำ ต้องผูกกับสภาพเสมอ
