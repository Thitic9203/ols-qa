## สรุปสั้น (Executive Summary)

รายงาน #0010 เขียนเมื่อ 2026-09-06 ว่าตัวรันชุดเทสต์พิมพ์ `all green` และจบด้วยรหัส 0 ได้ทั้งที่รันเทสต์ไป 0 ข้อ
และเขียนบทเรียนไว้เองว่า *"เครื่องมือที่ทำหน้าที่วัด ต้องรายงานจำนวนสิ่งที่มันวัดไปเสมอ และศูนย์ต้องเป็นการปฏิเสธ —
ใช้กับตัวรันชุดเทสต์เท่ากับที่ใช้กับด่านที่มันทดสอบ"* แต่การแก้ในรอบนั้นลงมือกับ **2 ไฟล์ที่เกิดเหตุเท่านั้น**
ไม่มีใครไล่หาไฟล์อื่นที่เป็นคลาสเดียวกัน วันถัดมาสแกนพบอีก **2 ไฟล์** ที่มีบั๊กเดิมทุกประการ และทำซ้ำยืนยันได้

## 1. ปัญหา (Problem Statement)

`tests/test_shape_watch.py` และ `tests/test_log_rotate.py` มี `main()` ที่ตัดสินผลจาก `if FAILS:` อย่างเดียว
ไม่มีที่ใดนับว่ารันไปกี่ข้อ เมื่อไม่มีฟังก์ชันขึ้นต้นด้วย `t_` ให้เก็บ ลูปไม่ทำงาน `FAILS` ว่าง โปรแกรมพิมพ์
`all green` แล้วคืน 0

ทำซ้ำยืนยันแล้วด้วยการเปลี่ยน `def t_` เป็น `def zz_` ในสำเนา:

```
test_shape_watch.py          rc=0  output= all green
test_log_rotate.py           rc=0  output= all green
```

**สิ่งที่ควรจะเป็น:** รันไป 0 ข้อ = ปฏิเสธ ไม่ใช่ผ่าน — กฎที่รายงาน #0006 ตั้งไว้ และ #0010 ยืนยันซ้ำ

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไมตัวรันพิมพ์เขียวทั้งที่ไม่ได้วัด** — เพราะมันอ่านแค่ `FAILS` ว่างหรือไม่ ซึ่ง "ยังไม่พบความล้มเหลว" กับ "ตรวจแล้วผ่าน" ใช้ตัวแปรเดียวกัน
2. **ทำไมถึงยังมีไฟล์แบบนี้เหลือ ทั้งที่เพิ่งแก้เมื่อวาน** — เพราะการแก้รอบ #0010 ลงมือกับไฟล์ที่เกิดเหตุ ไม่ได้ลงมือกับคลาส
3. **ทำไมไม่ได้ลงมือกับคลาส ทั้งที่รายงานเขียนบทเรียนระดับคลาสไว้เอง** — เพราะไม่มีขั้นตอนใดในการปิดรายงานที่บังคับให้ **รันคำสั่งค้นหาไฟล์อื่นที่เข้าข่าย แล้วรายงานตัวเลขที่นับได้**
4. **ทำไมถึงไม่มีขั้นตอนนั้น** — เพราะ `TEMPLATE.md` มีหัวข้อ "แนวทางการป้องกัน" ที่รับข้อความอิสระ ผู้เขียนจึงเขียนบทเรียนได้ครบถ้วนโดยไม่เคยต้องพิสูจน์ว่าไล่ปิดครบ
5. **ทำไมถึงยอมรับได้ว่ายังไม่พิสูจน์** — เพราะประโยค "ปิดคลาสแล้ว" ฟังดูเป็นข้อเท็จจริงพอๆ กับ "ปิดไฟล์นี้แล้ว" ทั้งที่อันหลังวัดได้ อันแรกวัดไม่ได้ถ้าไม่นับ

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ**

- **ชุดเทสต์ของตัวเอง** — ทั้ง 2 ไฟล์ไม่มีข้อไหนยืนยันคุณสมบัติของ `main()` ตัวเอง (บทเรียนเดียวกับ #0001 · #0005 · #0006)
- **CI** — `.github/workflows/tests.yml` รันเฉพาะ `tools/*/*.test.js` ใน repo `ols-qa` ไฟล์เหล่านี้อยู่ในชุดเครื่องมือ off-repo จึงอยู่นอกสายตา CI ทั้งหมด
- **`scripts/run-test-suites.sh`** — นับจำนวนชุดที่รันและปฏิเสธเมื่อเป็นศูนย์ **แต่วัดที่ระดับ "ชุด" ไม่ใช่ระดับ "ข้อในชุด"** ชุดที่รัน 0 ข้อแล้วคืน 0 จึงถูกนับเป็นชุดที่ผ่าน
- **รายงาน #0010 เอง** — บทเรียนถูกต้อง แต่การลงมือแคบกว่าบทเรียน และไม่มีอะไรตรวจช่องว่างนั้น

## 4. ผลกระทบ (Impact)

- **ไม่มีผลต่อผลการทดสอบรอบใด** — ชุดจริงรัน 17 และ 4 ข้อจริง (วัดหลังแก้) ไม่เคยมีรอบที่รัน 0 ข้อเกิดขึ้นจริง
- **ความเสี่ยงที่ปิดไป** — ถ้าวันหนึ่งมีคน rename ฟังก์ชัน ย้ายไฟล์ หรือ import พัง ชุดเทสต์ที่ตรึงตัวเฝ้าชีท (ซึ่งเป็นชั้นที่จับเหตุชีทค้าง 6 วันตามรายงาน PM-010) จะเงียบและเขียว
- **ต้นทุนที่เกิดจริง** — 1 รอบตรวจ และความน่าเชื่อถือของประโยค "ปิดคลาสแล้ว" ในรายงานฉบับก่อน

## 5. แนวทางการแก้ไข (Fix)

ใช้รูปเดียวกับที่ #0010 ใช้ เพื่อให้โค้ดฐานพูดภาษาเดียวกัน — นับสิ่งที่รันจริง และศูนย์คือการปฏิเสธด้วยรหัสจบ 2

```python
    ran = 0
    for name, fn in sorted(globals().items()):
        if name.startswith("t_") and callable(fn):
            check(name[2:], fn)
            ran += 1
    print()
    # รายงาน 0 ข้อ = ปฏิเสธ ไม่ใช่ผ่าน (post-mortem #0006 · #0010)
    if ran == 0:
        print("ปฏิเสธ — ชุดเทสต์นี้รันไป 0 ข้อ จึงไม่ได้วัดอะไรเลย ผลนี้ไม่ใช่ผ่าน")
        return 2
    if FAILS:
        print(f"{len(FAILS)} FAILED: {', '.join(FAILS)}")
        return 1
    print(f"all green — {ran} checks run")
    return 0
```

**ยืนยันแล้วด้วย:** รันจริงทั้ง 2 ขา และอ่านรหัสจบโดยไม่ผ่าน pipe (ครั้งแรกอ่านผ่าน pipe ได้รหัสของ `tail` ซึ่งผิด จึงวัดใหม่)

```
  zero-test  test_shape_watch.py       exit=2
  normal     test_shape_watch.py       exit=0
  zero-test  test_log_rotate.py        exit=2
  normal     test_log_rotate.py        exit=0
```

บรรทัดตอนผ่านมีตัวเลขกำกับแล้ว: `all green — 17 checks run` และ `all green — 4 checks run`

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

**กฎที่เพิ่มจากเหตุนี้:** เขียนไว้ใน `CLAUDE.md` หัวข้อ Post-mortems รายการนี้

1. **การปิดคลาสต้องมีตัวเลขที่นับได้ ห้ามเป็นประโยคบรรยาย** — รายงานที่อ้างว่าปิดคลาส ต้องแนบ **คำสั่งค้นหาที่รันจริง ขอบเขตที่ค้น และจำนวนที่นับได้** (เช่น "สแกน 37 ไฟล์ พบเข้าข่าย 3 ทำซ้ำยืนยัน 2") ประโยคว่า "ไม่พบที่อื่น" ลอยๆ ใช้ไม่ได้ — กฎนี้ #0011 ตั้งไว้แล้วสำหรับการสแกน และรอบนี้ยืนยันว่าต้องใช้กับ **ทุกรายงานที่อ้างว่าปิดคลาส** ไม่ใช่เฉพาะรายงานที่เกิดจากการสแกน
2. **บทเรียนที่เขียนกว้างกว่าการลงมือ ต้องถูกประกาศว่ายังไม่ปิด** — ถ้ารายงานเขียนบทเรียนระดับคลาสแต่แก้เฉพาะจุด ต้องเปิดแถว `OPEN` ค้างไว้สำหรับส่วนที่ยังไม่ไล่ ไม่ใช่ปิดรายงานแล้วถือว่าจบ

**ชั้นที่แข็งขึ้น ไม่ใช่คำเตือนซ้ำ:** ชั้นที่หายไปคือ *ไม่มีใครวัดที่ระดับ "ข้อในชุด"* — `scripts/run-test-suites.sh` ปฏิเสธเมื่อไม่มีชุดให้รัน แต่ไม่รู้ว่าแต่ละชุดรันไปกี่ข้อ ข้อเสนอที่ยังไม่ได้ลงมือ (รอเจ้าของงานตัดสิน) คือให้ตัวรันรวมอ่านตัวเลข `N checks run` จากผลของแต่ละชุด แล้วปฏิเสธชุดที่ไม่รายงานตัวเลขมาเลย

## 7. การตรวจจับปัญหา (Detection)

- **ที่จับได้รอบนี้** คือการสังเกตว่า **บรรทัดสรุปไม่มีตัวเลข** ไม่ใช่การที่อะไรพัง — ตรงกับบทเรียนของ #0006 ว่าเครื่องหมายถูกเปล่าๆ ปิดบังด่านที่ค่อยๆ วัดน้อยลง การบังคับให้พิมพ์ตัวเลขจึงเป็นทั้งการแก้และการตรวจจับ
- **ที่ยังตรวจไม่ได้** คือชุดเครื่องมือ off-repo ทั้งก้อนไม่มี CI รันให้ ใครไม่รันมือก็ไม่มีใครรู้

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ไม่เชื่อรูปแบบที่เห็น แต่ทำซ้ำยืนยันจริงก่อนเรียกว่าบั๊ก — ทำให้แยกได้ว่าไฟล์ที่ 3 **ไม่ใช่** คลาสเดียวกัน ถ้าเหมาไปก็จะแก้ของที่ไม่ได้พัง
- จับได้เองว่าอ่านรหัสจบผ่าน pipe แล้วได้ค่าของคำสั่งอื่น จึงวัดใหม่แทนที่จะรายงานเลขที่ผิด

### สิ่งที่ต้องปรับปรุง
- เขียนบทเรียนระดับคลาสแล้วลงมือระดับไฟล์ คือการประกาศคุณสมบัติที่ยังไม่มีใครตรวจ — บทเรียนเดียวกับ #0001 ที่ว่าคอมเมนต์ประกาศคุณสมบัติของโค้ดตัวเองไม่ใช่หลักฐาน
- จดแถวใน `PENDING.md` ช้ากว่าที่กฎกำหนด (กฎบอกให้จดในเทิร์นที่รู้ตัว) เพราะตอนนั้นมีอีกเลนกำลัง push อยู่ และแถว `OPEN` จะบล็อกคอมมิตของเลนนั้น จึงจดบันทึกถาวรไว้ในโฟลเดอร์งานของรอบก่อน แล้วเติมแถวจริงเมื่อ push จบ — บอกเจ้าของงานตรงๆ ในแชทว่าเลื่อนเพราะอะไร ไม่ได้เลื่อนเงียบ
