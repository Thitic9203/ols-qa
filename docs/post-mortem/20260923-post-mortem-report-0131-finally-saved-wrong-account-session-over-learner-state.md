## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

finally ถูกเขียนให้ "บันทึก session ที่หมุนแล้วทุกครั้ง" เพื่อไม่ให้ token ที่หมุนหาย (CLAUDE.md §9: refresh แล้วต้องเซฟทันที) แต่ไม่ได้คิดกรณีที่หน้าไม่ได้เป็นบัญชีตาม tag

### 5 Whys

1. **ทำไมไฟล์ผู้เรียนถือ session ของบัญชีครีเอเตอร์?** — เพราะ finally เขียน storageState ของหน้าที่ยังเป็นบัญชีครีเอเตอร์ลงไฟล์ของผู้เรียน
2. **ทำไมหน้ายังเป็นบัญชีครีเอเตอร์?** — เพราะการสลับบัญชีในหน้าเดียวด้วย cookie + localStorage ไม่สำเร็จ (ด่านจับได้ถูกต้อง)
3. **ทำไม finally ยังเขียน ทั้งที่ด่าน throw?** — เพราะ finally บันทึกทุก tag โดยไม่อ่านก่อนว่าหน้าเป็นใคร
4. **ทำไมไม่มีการตรวจเจ้าของก่อนเขียน?** — เพราะฟังก์ชันบันทึก state ใน lib เดิมรับ tag เป็นพารามิเตอร์แล้วเชื่อ tag นั้น
5. **ทำไมออกแบบให้เชื่อ tag?** — เพราะ tag ถูกมองเป็นความจริง ทั้งที่ความจริงคือผลของ `get-session` ณ วินาทีที่เขียน (root cause: เขียนไฟล์ตัวตนโดยไม่พิสูจน์ตัวตนร่วมเวลา — หลักเดียวกับ CLAUDE.md §0 ข้อ contemporaneous)

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** ด่าน GUARD ในสคริปต์จับการสลับผิดได้ แต่ป้องกันแค่การกระทำในหน้า ไม่ป้องกัน finally · `session_verify.js` จับได้หลังเขียนแล้วเท่านั้น
