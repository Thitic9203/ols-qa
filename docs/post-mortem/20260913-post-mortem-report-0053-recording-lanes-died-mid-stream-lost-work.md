## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

**กลไกที่ยืนยันแล้ว:** ทั้ง 3 เลนที่ตายมี `tool_use` เท่ากับ `tool_result` พอดี (Lane 1: 5/5, Lane 3: 8/8, Lane 4: 3/3) — ไม่มี tool call ค้างแม้ตัวเดียว หลังจาก tool result สุดท้ายกลับมาสำเร็จ (`is_error:false`) และ harness แปะ `total_tokens_reminder` เตรียมส่ง request รอบถัดไป **ไม่มี token คำตอบออกมาอีกเลย 602–609 วินาที** จนกระทั่ง watchdog ของ harness ("stream watchdog") ตัดที่ 600 วินาทีพอดี เขียน `[Request interrupted by user]` ปิดท้าย transcript คำว่า "did not recover" ในข้อความ error บอกว่า harness เคยพยายามกู้สตรีมนั้นแล้วไม่สำเร็จ

**ตัวควบคุมที่ปิดสมมติฐานอื่นทั้งหมด:** Lane 2 (System) ถูกจ่ายงานห่างจาก Lane 1 เพียง 14 วินาที ใช้โมเดล/กลไกเดียวกัน แต่วิ่งผ่านหน้าต่าง 600 วินาทีเดียวกันได้สบาย (517 tool call ต่อเนื่อง) — และ Lane 2 คือเลนที่ใช้ VPN+Playwright+login ครบ ขณะที่ Lane 4 ไม่แตะ browser/network/session file เลย (filesystem+JSON ล้วน) แต่ตายเหมือน Lane 1/3 เป๊ะ ตัดสมมติฐาน VPN, Playwright, login, API ล่มทั้งระบบ, token หมด (เหลือ ~14.6–14.7M จาก ~15M), คนกด Stop (เวลาฆ่าห่างกันคนละเวลาแต่ห่างจาก token สุดท้ายของตัวเอง 602–609s พอดี = timer รายตัว), และ sleep-loop (Lane 4 ไม่มี sleep เลยสักครั้ง ยังไม่เคยเข้าลูป polling ที่สั่งไว้ด้วยซ้ำ) ออกทั้งหมด

**heartbeat ที่มีอยู่แล้วไม่ช่วย:** ทุก lane prompt มีข้อกำหนด "print status line, no command >3 min" อยู่แล้วตั้งแต่ต้น และทุกเลนทำตามครบ (คำสั่งยาวสุดในทั้ง 3 เลนคือ 3.0 วินาที) — พิสูจน์ว่า print-based heartbeat แก้ปัญหานี้ไม่ได้ เพราะสิ่งที่ตายคือชั้นสตรีมของโมเดล ไม่ใช่ชั้นคำสั่ง และ `print`/`echo` ไปอยู่ใน transcript ซึ่งหายไปพร้อม agent ถ้า agent ถูกตัด

### 5 Whys

1. **ทำไมงานที่ทำเสร็จแล้วถึงหายไปหมด?** — เพราะไม่มีเลนไหนเขียนไฟล์ลงดิสก์ก่อนตาย มีแต่ผลลัพธ์ที่ค้างอยู่ใน conversation context ของ transcript ที่ถูกตัด
2. **ทำไมไม่มีการเขียนไฟล์ก่อนตาย?** — เพราะ lane prompt สั่งให้ "print heartbeat หลังทำแต่ละเคส" ไม่ได้สั่งให้ "เขียนผลลัพธ์ย่อยลงดิสก์ทันที" — งานจริงยังไม่ถึงขั้นตอนแรกที่ prompt กำหนดให้บันทึกผล (ทุกเลนยังอยู่ในขั้นสำรวจ/อ่านไฟล์ ยังไม่ถึงขั้น "จบ 1 เคส" ที่จะ log)
3. **ทำไมเลนตายเร็วขนาดนี้ (53–64 วินาที) ทั้งที่ไม่มีคำสั่งค้าง?** — สตรีมคำตอบของโมเดลเงียบหลัง tool result สุดท้ายกลับมา
4. **ทำไมสตรีมถึงเงียบ?** — **ตรวจไม่ได้จากหลักฐานที่มี** ไม่มี HTTP status / error object / retry counter บันทึกไว้ที่ไหนเลยทั้งใน transcript ของเลนและของเซสชันแม่ ต้องมี log ฝั่ง harness/transport ถึงจะตอบได้
5. **ทำไมชั้นป้องกันที่มี (heartbeat instruction) ไม่จับ?** — เพราะกฎเดิมออกแบบมาให้ "สื่อสารว่ายังไม่ตาย" ผ่านการ print ซึ่งเป็นข้อมูลที่อยู่ใน context เดียวกับสิ่งที่กำลังจะถูกทำลาย ไม่ใช่ข้อมูลที่อยู่นอก blast radius ของความล้มเหลว — กฎที่ป้องกันความล้มเหลวต้องอยู่คนละที่กับจุดที่ล้มเหลว

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** ชั้นเดียวที่มีคือ heartbeat-by-print ในตัว lane prompt เอง ซึ่งพิสูจน์แล้วว่าไม่ใช่ชั้นป้องกันจริง (ข้อ 5 ข้างบน) — ไม่มีชั้นอื่นเลยที่ทำหน้าที่ตรวจจับ "เลนตายเงียบ" จากภายนอก (main thread ไม่ได้ poll active ระหว่าง 04:23 ถึง 04:34) และไม่มีชั้นไหนแยก "ยังไม่เริ่มเขียน log" ออกจาก "ตายไปแล้ว"

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** session แม่ (ตัวเอง) จับได้จาก task-notification ที่ harness ส่งมาอัตโนมัติตอน agent ถูกฆ่า (`status: failed`) — ไม่ใช่การพบเงียบๆ แล้วปกปิด
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** รู้ทันทีที่ notification มาถึง (600s หลังตาย ตามดีไซน์ของ watchdog) แต่กว่าจะรู้ว่า**งานหายไปด้วย**ต้องรอจนสืบด้วย systematic-debugging เสร็จ (ราว 1 ชั่วโมงหลังเหตุ)
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** main thread poll heartbeat ทุก 60–90 วินาที (P3) จะจับได้ภายใน ~2 นาทีแทนที่จะรอ 600s ของ watchdog

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- ใช้ `superpowers:systematic-debugging` จริงจัง อ่าน transcript ดิบทั้ง 5 ไฟล์แทนการเดา และเจอ "ตัวควบคุมที่รอด" (Lane 2) ซึ่งเป็นหลักฐานเดียวที่พลิกคดีจาก "น่าจะเป็น VPN/sleep" เป็น "ไม่ใช่ทั้งคู่"
- บอกตรงๆ ว่าสาเหตุต้นทาง (ทำไมสตรีมเงียบ) ตรวจไม่ได้จากหลักฐานที่มี แทนที่จะเดาสาเหตุให้ดูครบ
- แจ้ง peer session ทั้ง 2 ตัวให้แก้คำแนะนำที่ผิดก่อนที่งานของพวกเขาจะเสียหายแบบเดียวกัน

### สิ่งที่ต้องปรับปรุง
- ไม่ได้ poll ไฟล์ log ระหว่างที่เลนกำลังทำงาน (เช็กครั้งแรกที่ 04:34:14 คือ 10+ นาทีหลังตาย) — ทำให้รู้ช้ากว่าที่ควร
- lane prompt รอบแรกยังใช้ pattern "print heartbeat" ที่ไม่เคยพิสูจน์ว่าใช้ได้ผลกับความล้มเหลวชนิดนี้ (เพิ่งรู้ว่าไม่ช่วยหลังเกิดเหตุแล้ว)
