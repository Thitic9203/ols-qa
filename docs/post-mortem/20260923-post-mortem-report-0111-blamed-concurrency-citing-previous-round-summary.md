## สรุปสั้น (Executive Summary)

รอบ smoke test บน training69 มี 12 เคสตกด้วย error เดียวกันคือ `[mint] refusing a password login on 'training'`
ผมสรุปกับเจ้าของงานว่าสาเหตุคือการรัน 6 workers พร้อมกันทำให้ SSO หมุนโทเคนแล้วสำเนาหนึ่งฆ่าอีกสำเนา
และเสนอให้รันซ้ำที่ 1 worker เจ้าของงานอนุมัติ รันซ้ำแล้ว **ตกซ้ำครบทั้ง 12 เคสด้วย error เดิม** ข้อสรุปจึงผิด

ที่มาของข้อสรุปผิดคือผมหยิบข้อ 3 ของ `ROUND_SUMMARY.md` รอบ 2026-09-21 ซึ่งอธิบายอาการคนละเรื่อง
มาใช้เป็นคำอธิบายของรอบนี้ โดยไม่มีหลักฐานของรอบนี้รองรับเลย

สาเหตุจริงหาเจอทีหลังในเซสชันเดียวกัน คือ OLS จำกัดอัตราเรียก `/api/auth/get-session` แล้วตอบ 429
ส่วนชุดเทสต์อ่านทุกอย่างที่ไม่ใช่ 200 เป็น "ไม่ได้ล็อกอิน" (รายละเอียดอยู่ในรายงาน #0112)
ตอนนี้แก้ต้นเหตุแล้วและรายงานนี้ปิดเฉพาะส่วนที่เป็นความผิดพลาดของการให้ข้อสรุป

## 1. ปัญหา (Problem Statement)

- รอบรันเวลา 22:19 บน training69 ได้ผล ผ่าน 105 · ตก 17 · ข้าม 4 จาก 126 เคส โดย 12 เคสตกด้วยข้อความเดียวกันจาก `tests/e2e/setup/mint.ts:29`
- ผมรายงานกับเจ้าของงานว่า **"ตัวเร่งคือการรัน 6 workers พร้อมกัน แต่ละ worker เปิด context จากไฟล์ session ใบเดียวกัน พอฝั่งเซิร์ฟเวอร์หมุนโทเคน สำเนาที่เหลือกลายเป็นของเก่าทันที"** และอ้างว่า *"ยืนยันว่าตรงกับที่รอบเมื่อวานเจอและแก้ด้วยการรัน 1 worker แล้วผ่านทันที (`ROUND_SUMMARY.md` ข้อ 3)"*
- หลักฐานเดียวที่ผมมีคือไฟล์สรุปของ **รอบอื่น** ผมไม่ได้วัดอะไรในรอบนี้เลยที่ชี้ว่าการหมุนโทเคนเกิดขึ้นจริง
- รันซ้ำตามที่เสนอด้วย `--workers=1 --retries=0` ผลคือ `run-r2.log` ลงท้ายว่า `12 failed` · `7 passed` (7 ที่ผ่านคือ setup ล้วน) — ตกซ้ำครบทุกเคสด้วย error เดิม

**สิ่งที่ควรจะเป็น:** ตาม `CLAUDE.md` ข้อ 0 — ข้อสรุปจากไฟล์สรุปรอบก่อนห้ามพูดเป็นข้อเท็จจริงของรอบปัจจุบัน ต้องมี VERIFY แยกของรอบนี้ ถ้ายังไม่มีต้องพูดว่า "ยังไม่ได้ตรวจ" แล้วไปตรวจ

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

จุดตัดสินใจที่ผิดคือตอนที่ผมเห็นอาการ "session ตายกลางรอบ" แล้วนึกออกว่าเคยอ่านคำอธิบายอาการคล้ายกันมาก่อน
แทนที่จะถามว่า "รอบนี้มีหลักฐานอะไรบ้าง" ผมถามว่า "เคยมีคำอธิบายแบบไหนที่เข้ากับอาการนี้"
คำอธิบายที่หยิบมาเข้ากันได้ดีพอที่จะฟังดูสมเหตุสมผล จึงไม่ได้รู้สึกว่ากำลังเดา

ที่ทำให้ตอนนั้นดูถูกต้อง คือไฟล์ที่ผมอ้างเป็นเอกสารของ repo เอง เขียนโดยเซสชันก่อนหน้า มีรายละเอียดทางเทคนิคครบ
และอธิบายอาการที่หน้าตาเหมือนกัน — ความน่าเชื่อถือของ**รูปแบบเอกสาร**ถูกใช้แทนความน่าเชื่อถือของ**หลักฐาน**

### 5 Whys

1. **ทำไมเจ้าของงานได้รับสาเหตุที่ผิด?** — เพราะผมบอกว่าเป็น concurrency ทั้งที่ยังไม่ได้ตรวจ
2. **ทำไมถึงบอกว่าเป็น concurrency?** — เพราะ `ROUND_SUMMARY.md` ของรอบ 21/Sep อธิบายอาการคล้ายกันไว้แบบนั้น
3. **ทำไมถึงเอาคำอธิบายของรอบอื่นมาใช้กับรอบนี้?** — เพราะอาการที่เห็น (session ตายกลางรอบ) ตรงกันพอที่จะรู้สึกว่าเป็นเรื่องเดียวกัน
4. **ทำไมความรู้สึกว่า "เรื่องเดียวกัน" ถึงผ่านไปได้โดยไม่ถูกตรวจ?** — เพราะผมไม่ได้แยกให้ชัดว่าอะไรคือ "สิ่งที่วัดในรอบนี้" กับ "สิ่งที่อ่านมาจากที่อื่น" ตอนเรียบเรียงรายงาน ทั้งสองอย่างถูกเขียนต่อกันเป็นย่อหน้าเดียว
5. **ทำไมถึงไม่แยก?** — **เพราะตอนนั้นไม่มีขั้นตอนบังคับให้ทุกประโยคที่เป็นสาเหตุต้องระบุว่าหลักฐานมาจากไฟล์ไหนของรอบไหน — ข้อความที่อ้างรอบอื่นกับข้อความที่วัดเองจึงหน้าตาเหมือนกันทุกประการเมื่อส่งถึงเจ้าของงาน**

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- `CLAUDE.md` ข้อ 0 เขียนกฎนี้ไว้ตรงตัวแล้ว แต่เป็นกฎที่ต้องจำเอง ไม่มีเครื่องมือบังคับ
- investigation-guard บังคับให้เรียกสกิลตรวจสอบก่อนจบเทิร์น แต่ไม่ได้ตรวจ**เนื้อหา**ของข้อสรุปว่าอ้างหลักฐานของรอบไหน
- ไม่มีชั้นไหนเลยที่ดูความต่างระหว่าง "ข้อความที่มี path:line ของรอบนี้" กับ "ข้อความที่อ้างไฟล์สรุปของรอบอื่น"

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** ผมจับได้เอง จากผลการรันซ้ำที่เสนอเอง — แผนแก้ที่ผิดกลายเป็นการทดลองที่ล้มสมมติฐานตัวเอง
