**สภาพแวดล้อมที่ได้รับผลกระทบ:** session ของบัญชี QA บน training69 (st9020 · st9021 · tc9020 · rg9020 · rg9021 · pv9021 ฯลฯ)

## สรุปสั้น (Executive Summary)

รอบนี้ `relogin_t69.js` เปิด keepalive `tc9020_ka.js` ให้ทุกบัญชีหลังล็อกอิน ตัว keepalive ทำงานรอบละ 7 นาที โดยโหลด `/robots.txt` แล้วเรียก `GET /api/auth/get-session` แต่ฝั่ง OLS ตั้งใจไม่นับ get-session เป็นกิจกรรม (`session-context.guard.ts:27-29`) session จึงหมดตาม idle 30 นาที นับจากการเรียก API จริงครั้งสุดท้าย ตรงกับที่วัดได้ทั้ง 3 ครั้งที่หลุดใน 24/Sep ทุกบรรทัดใน log เป็น `cookiesChanged:false` เธรดหลักบอกเจ้าของงานหลายรอบว่า "keepalive ทำงานอยู่" แต่ไม่เคยทดสอบกับ session ที่ว่างเกิน 30 นาที ทั้งที่ #0103 (21/Sep) หาต้นเหตุเดียวกันนี้เจอแล้ว แต่มาตรการของรายงานนั้นยังไม่ได้ลงมือทำ

## 1. ปัญหา (Problem Statement)

- **สิ่งที่ควรเกิด:** session ของบัญชี QA อยู่ได้ตลอดช่วงอัด โดยเจ้าของงานไม่ต้องล็อกอินซ้ำ
- **สิ่งที่เกิดจริง:** session หลุดประมาณ 30 นาทีหลังการเรียก API จริงครั้งสุดท้าย ทุกบัญชี · keepalive จบด้วย `session not valid`
- **ขอบเขต:** ทุกบัญชี training69 ที่ใช้ keepalive นี้ในรอบ

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไม session หลุด?** — idle 30 นาทีครบ เพราะไม่มีคำขอที่นับเป็นกิจกรรม
2. **ทำไม keepalive ไม่นับ?** — เรียกแค่ get-session ซึ่ง guard ยกเว้นไว้ (`refreshActivity = !(GET && path.endsWith('/auth/get-session'))`)
3. **ทำไมเขียน keepalive แบบนั้น?** — ใช้ get-session เป็นทั้งตัวตรวจและตัวต่ออายุ โดยไม่อ่านโค้ด guard ทั้งที่ #0103 บันทึกไว้แล้ว
4. **ทำไมไม่รู้ว่าไม่ได้ผล?** — เกณฑ์ "ทำงาน" คือโปรเซสยังรันและ get-session ตอบ 200 ซึ่งไม่ได้วัดสิ่งที่ต้องการ (อายุ session หลังว่าง) · ไม่เคยทดสอบปล่อยว่างเกิน 30 นาที
5. **ทำไมผิดซ้ำ #0103?** — (root cause) มาตรการของ #0103 ค้างรออนุมัติ และไม่มีชั้นใดบังคับให้เครื่องมือใหม่ในรอบถัดไปรับบทเรียนนั้น keepalive ตัวใหม่จึงเกิดขึ้นพร้อมข้อผิดพลาดเดิม

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- #0103 — มาตรการเป็นข้อเสนอ ยังไม่ได้ลงมือทำ
- `recording_preflight.js` — ตรวจว่า session ใช้ได้ ณ ตอนนั้น ไม่ได้ตรวจว่า keepalive ต่ออายุได้จริง

## 4. ผลกระทบ (Impact)

- เจ้าของงานต้องล็อกอินซ้ำหลายครั้งในรอบ 23–24/Sep (เคยทักด้วยความไม่พอใจว่า "ให้ล็อกอินอยู่ได้")
- งานอัดคลิปค้างรอ login หลายช่วง · take ล้มเมื่อ session หลุดกลางงาน
- เธรดหลักรายงาน "keepalive ทำงานอยู่" ที่ไม่ถูกต้อง

## 5. แนวทางการแก้ไข (Fix)

- `tc9020_ka.js` (bot repo นอก repo นี้, สำรองไฟล์เดิมไว้): ทุกรอบเรียก get-session (อ่านว่าใคร) + `GET /api/users/me/profile` (touch) · ถือว่าตายเมื่อ touch ≠ 200 · log ใส่ `touch` · `KA_MAXN` เริ่มต้น 120 (≈14 ชม. ที่รอบละ 7 นาที)

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

1. **กฎ:** ห้ามบอกเจ้าของงานว่า keepalive ทำงาน จนกว่าจะทดสอบกับ session จริงที่ปล่อยว่างเกิน 35 นาที แล้วยังใช้ได้บน env นั้น
2. **ในตัวเครื่องมือ:** keepalive ตรวจผลการ touch ทุกรอบ ไม่ใช่แค่ get-session
3. **ทดสอบจริง (Action Item 1):** ครั้งถัดที่บัญชีล็อกอิน OLS ให้ปล่อยว่าง 36 นาที (มีแค่ keepalive ทำงาน) แล้วตรวจ `get-session` ว่ายังมี user · บันทึกผลลงรายงานนี้
