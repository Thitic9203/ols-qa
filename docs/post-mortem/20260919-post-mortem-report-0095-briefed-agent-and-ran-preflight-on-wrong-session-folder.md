## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

ตอนเขียน brief ตำแหน่ง `capture/state_<tag>.json` ดูถูกเพราะเป็นตำแหน่งมาตรฐานที่ CLAUDE.md §9 และเครื่องมือ session ทั่วไปใช้ แต่รอบนี้ session ใหม่ถูกเก็บในโฟลเดอร์ของรอบ และ keepalive ถูกตั้งให้ `cd` เข้าโฟลเดอร์นั้น ข้อเท็จจริงนี้อยู่ในบทสนทนาเท่านั้น
preflight ก็ไม่ได้ช่วย เพราะตรวจ "มี keepalive รันอยู่ไหม" กับ "ไฟล์ในโฟลเดอร์ที่ถูกสั่งยังมีชีวิตไหม" แยกกัน ผลที่ได้จึงดูเป็นเหตุเป็นผล (keepalive มีชีวิต แต่ session ตาย) แทนที่จะบอกว่า "ตรวจไม่ได้"

### 5 Whys

1. **ทำไม agent ได้ brief ที่ชี้โฟลเดอร์ session ผิด?** — เพราะเธรดหลักเขียนตำแหน่ง session จากความจำของตำแหน่งมาตรฐาน `capture/` ไม่ได้อ่านจากโปรเซส keepalive ที่รันอยู่
2. **ทำไมตำแหน่งมาตรฐานถึงผิดในรอบนี้?** — เพราะรอบนี้ session pre-prod ที่ล็อกอินใหม่ถูกเก็บในโฟลเดอร์ของรอบ และ keepalive ทำงานในโฟลเดอร์นั้น (`keepalive_preprod.sh:5`) ส่วนไฟล์ใน `capture/` เป็นชุดเก่าที่ไม่มีใครดูแล — ข้อเท็จจริงนี้เป็นความรู้เฉพาะรอบ ไม่มีไฟล์หรือเครื่องมือใดประกาศไว้
3. **ทำไม preflight ที่เธรดหลักรันเองไม่ชี้ว่าโฟลเดอร์ผิด แต่ออกผลว่า "4 dead"?** — เพราะ `recording_preflight.js` รับ `--accounts-dir` อิสระจาก `--pidfile` (`:43-45`) · ชั้น keepalive ตรวจแค่ pid ยังรัน (`:62-68`) จึงผ่าน · ชั้นบัญชีอ่านไฟล์จากโฟลเดอร์ที่ถูกสั่ง (`:124-126`) ได้ผลตายจริงของไฟล์เก่า — ทั้งสองชั้นถูกต้องตามที่ออกแบบ แต่ไม่มีชั้นไหนตรวจว่าสองอย่างนี้เป็นของชุดเดียวกัน
4. **ทำไมผลผิดนั้นเกือบขึ้นบอร์ด?** — เพราะบอร์ดเลือก `preflight_*.log` ล่าสุดตามชื่อ โดยไม่มีข้อมูลว่าผลนั้นตรวจโฟลเดอร์ไหน และ "4/4 dead · REFUSED" ก็เป็นผลที่เป็นไปได้จริงหลัง session หมดอายุ จึงไม่มีอะไรดูผิดปกติจากบรรทัดสรุป
5. **ทำไมคลาสนี้ (ชี้แหล่ง session ผิด) ยังเกิดซ้ำหลัง #0092?** — root cause: **ไม่มีแหล่งความจริงเดียวของ "โฟลเดอร์ที่ keepalive กำลังดูแล"** — ทั้ง brief ของ agent และ preflight รับตำแหน่งจากคนพิมพ์ ขณะที่ความจริงอยู่ใน cwd ของโปรเซส keepalive · มาตรการของ #0092 แก้ว่า "ตรวจอย่างไร" (ถาม get-session ตรงจากไฟล์) แต่ไม่ได้แก้ว่า "ตรวจไฟล์ไหน" จึงยังได้ผลที่วัดถูกวิธีแต่ผิดชุดไฟล์

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- CLAUDE.md §9 "ชี้ keepalive ที่ยังมีชีวิตที่ดูแล tag นั้น + เธรดหลักรัน `recording_preflight.js` เอง" — เธรดหลักรันเองแล้วจริง แต่กฎไม่ได้บังคับว่าโฟลเดอร์ที่ส่งให้ preflight ต้องมาจาก keepalive
- #0092 (preflight ถาม get-session ตรงจากไฟล์ ไม่ผ่านการโหลดหน้า) — ทำงานถูก จึงรายงาน "dead" ของไฟล์เก่าได้แม่นยำ ไม่ใช่ชั้นที่ครอบคำถาม "ไฟล์ถูกชุดไหม"
- ชั้นตรวจ keepalive ใน `recording_preflight.js:62-68` — ยืนยันแค่ว่ามีโปรเซส ไม่ยืนยันว่าโปรเซสนั้นดูแลโฟลเดอร์ที่กำลังตรวจ
- agent-dispatch-guard — ตรวจรูปแบบ brief (เขียนผลลงดิสก์ก่อน tool ถัดไป) ไม่ได้ตรวจความถูกต้องของ path ใน brief
- ไม่มีชั้นใดครอบ path ของ session ใน brief

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

ชั้นที่แข็งขึ้นกว่า #0092 คือให้ **ตำแหน่งที่ตรวจมาจากโปรเซส keepalive เอง** จนโฟลเดอร์ผิดกลายเป็น "ตรวจไม่ได้" แทนผลที่ดูสมเหตุสมผล — ทุกข้อที่แตะเครื่องมือเป็น **ข้อเสนอ รอเจ้าของงานอนุมัติ ยังไม่ได้ทำ**

| # | มาตรการ | ชนิด | สถานะ |
|---|---------|------|-------|
| P1 | `recording_preflight.js` อ่าน cwd จริงของโปรเซส keepalive (pid จาก `--pidfile`) เช่นด้วย `lsof -p <pid> -a -d cwd` แล้วเทียบกับ `--accounts-dir` (หลัง resolve realpath) · ไม่ตรง = `REFUSED` แบบ "ตรวจไม่ได้: โฟลเดอร์ที่สั่งไม่ใช่โฟลเดอร์ที่ keepalive ดูแล" ไม่ออกผล live/dead · อ่าน cwd ไม่ได้ = ตรวจไม่ได้เช่นกัน · ต้องมีเทสต์ที่รู้คำตอบ (โฟลเดอร์ตรง 1 · ไม่ตรง 1) | เครื่องมือ | ค้าง — ข้อเสนอ รออนุมัติ |
| P2 | preflight พิมพ์โฟลเดอร์ที่ตรวจ (หลัง resolve) ในบรรทัดหัวของผล เพื่อให้บอร์ดและคนอ่านเห็นว่าผลนี้เป็นของชุดไหน | เครื่องมือ | ค้าง — ข้อเสนอ รออนุมัติ |
| P3 | brief ของ agent ทุกฉบับที่ใช้ session ระบุโฟลเดอร์ session โดยคัดจาก cwd ของ keepalive ที่รันอยู่ในคำสั่งเดียวกัน ไม่ใช่จากความจำ | กฎ | ค้าง — ข้อเสนอ รออนุมัติ |

**กฎที่เพิ่มจากเหตุนี้:** ตำแหน่ง session ที่ส่งให้ agent หรือ preflight ต้องอ่านจากโปรเซส keepalive ที่รันอยู่ ไม่ใช่จากความจำหรือตำแหน่งมาตรฐาน (บันทึกในสรุปของ `docs/CLAUDE-ARCHIVE.md` § Post-mortems) · ชั้นเครื่องมือ P1–P2 รออนุมัติ
