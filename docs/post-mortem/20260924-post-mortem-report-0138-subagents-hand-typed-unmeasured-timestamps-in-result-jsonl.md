## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

บรรทัดผลถูกเขียนเป็นข้อความ JSON ทั้งบรรทัด ช่อง `ts` จึงเป็นแค่ข้อความอีกช่องที่ agent เติมเอง ค่าที่ได้ละเอียดแค่นาทีและเดินหน้าเกินเวลาจริง ต่างจากไฟล์ probe ที่สคริปต์สร้างเวลาจาก `toISOString()` ในคำสั่งเดียวกับการเขียน
ไม่มีด่านใดเทียบค่าเวลากับนาฬิกาหรือกับเวลาเขียนไฟล์ ค่าที่อยู่ในอนาคตเกือบ 50 นาทีจึงเข้าไปอยู่ในไฟล์ผลได้เหมือนค่าที่วัดจริง

### 5 Whys

1. **ทำไม `ts` ในไฟล์ผลชุด D เป็นค่าที่ไม่ได้วัด?** — เพราะ subagent พิมพ์ค่าเวลาลงในข้อความ JSON เอง (ระดับนาที เช่น `07:26+07:00`) ไม่ได้ให้นาฬิกาเครื่องเติมค่าในคำสั่งเดียวกับที่เขียนบรรทัด
2. **ทำไม subagent ถึงพิมพ์เวลาเอง?** — เพราะไฟล์ผลทุกชุด (A–D) มีช่อง `ts` ทุกบรรทัด แต่ไม่มีเครื่องมือเขียนผลที่ประทับเวลาให้ วิธีที่ agent ใช้คือพิมพ์ทั้งบรรทัดรวมเวลาเอง · สมมติฐาน: รูปแบบผลในบรีฟกำหนดช่อง `ts` ไว้โดยไม่บอกวิธีได้ค่า (จะตรวจด้วยการเปิดบรีฟต้นฉบับ — ค้น `grep -rl tickets_D` ในโฟลเดอร์รอบได้ 2 ไฟล์ ไม่มีบรีฟ)
3. **ทำไมค่าที่เกินเวลาจริงถึงไม่ถูกจับตอนเขียน?** — เพราะไม่มีตัวตรวจไฟล์ผลใดเทียบ `ts` กับนาฬิกา · `agent-dispatch-guard` (`check.js` · `dispatch_rules.js`) ไม่มีการตรวจเรื่องเวลาเลย (grep `timestamp|toISOString|date|เวลา` = 0) · ค่า 08:27 ที่ช้ากว่าเวลาเขียนไฟล์ 49 นาที 56 วินาทีจึงผ่าน
4. **ทำไมยังไม่มีตัวตรวจ ทั้งที่ผิดคลาสนี้มาแล้ว 3 ครั้ง (#0060 · #0083 · #0094)?** — เพราะมาตรการของ #0094 (ให้เครื่องมือประทับเวลาเอง) ครอบเฉพาะ `recording_preflight.js` และ `gen_board_data.py` และสถานะในรายงาน #0094 ยังเป็น "ค้าง — รออนุมัติ" · กฎ CLAUDE.md §0 "เวลาต้องวัด" เป็นข้อความที่ถึง subagent แต่ไม่มีอะไรบังคับ
5. **ทำไมทุกครั้งแก้ได้แค่ที่จุดเดียว?** — root cause: ช่องเวลาในผลของงานทุกชนิด (บอร์ด · ไทม์ไลน์ · ชื่อไฟล์ · ไฟล์ผลของ agent) เปิดให้คนหรือ agent พิมพ์เอง ไม่มีทางเขียนผลที่ประทับเวลาจากนาฬิกาโดยบังคับ และไม่มีตัวตรวจร่วมที่ปฏิเสธเวลาไม่ละเอียดถึงวินาทีหรือเกินเวลาเขียนไฟล์ — หลักฐานว่าเป็นทั้งคลาส: 3 จาก 4 ไฟล์ผลในรอบเดียวกัน (A · B · D) มีรูปแบบเดียวกัน ส่วนไฟล์ C ที่เขียนด้วยเวลาจากนาฬิกาถูกต้อง 66/66

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- CLAUDE.md §0 "เวลาต้องวัด ห้ามประมาณ": เป็นข้อความ ไม่มีตัวตรวจ
- มาตรการ #0094 (P1–P2 เครื่องมือประทับเวลาเอง): ครอบ 2 เครื่องมือเฉพาะ และยังค้างตามรายงาน #0094 · ไม่ครอบไฟล์ผลของ subagent
- `git-staging-guard` (มาตรการ #0086): บล็อกตัวเลขประมาณในข้อความคอมมิตเท่านั้น ไฟล์ผลอยู่นอก repo
- `agent-dispatch-guard`: ตรวจบรีฟเรื่องการเขียนผลลงดิสก์ก่อน tool ถัดไป (`PERSIST-BEFORE-PRINT`) แต่ไม่ตรวจว่าเวลาในผลมาจากไหน (grep เรื่องเวลา = 0)
- การตรวจผลของเธรดหลัก: ไม่มีขั้นตรวจช่องเวลา

- **ใครจับได้ / จับได้ยังไง:** ไฟล์ D ถูกแก้พร้อมบรรทัด correction เมื่อ 07:37:04 +07 — ไฟล์และแถว PENDING ไม่ระบุว่า subagent พบเองหรือเธรดหลักพบ · บรรทัด 25–32 ของไฟล์ D และไฟล์ A · B ผมพบตอนเขียนรายงานนี้ด้วยการวัดทั้ง 4 ไฟล์ ไม่มีเครื่องมือใดจับ

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- การแก้ไฟล์ D เก็บค่าที่พิมพ์เองไว้ในช่องชื่อชัด (`ts_handtyped_unmeasured`) และตั้ง `ts=null` แทนการลบ ทำให้ตรวจย้อนได้
- บรรทัด correction และ `tickets_D_decision.md` บอกเวลาจาก `date` จริง และไฟล์ probe ประทับเวลาจากนาฬิกาเอง
- ไฟล์ C ของอีกเลนเขียนเวลาจากนาฬิกาถูกต้องทั้งหมด ใช้เป็นตัวอย่างที่รู้คำตอบได้

### สิ่งที่ต้องปรับปรุง
- การแก้ต้องครอบทุกบรรทัดในไฟล์ (บรรทัด 25–32 หลุด) และทุกไฟล์ข้างเคียงในรอบเดียวกัน (A · B) ตามกฎปิดคลาสจาก #0003
- ช่องเวลาในผลต้องมาจากเครื่องมือ ไม่ใช่จากข้อความที่ agent พิมพ์
