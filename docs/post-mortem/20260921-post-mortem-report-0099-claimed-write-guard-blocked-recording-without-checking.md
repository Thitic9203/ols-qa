## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

ผมมี memory หลายก้อนที่พูดถึงการ์ดในฐานะ "ชั้นป้องกัน 7–8 ชั้นของกล่องเครื่องมือ"
(`project_ols-write-guard-training-readonly`) ซึ่ง **ถูกต้องสำหรับเครื่องมือแก้ชื่อ** แต่ผมอ่านมันเป็น
"ครอบทุกอย่างในกล่องเครื่องมือ" แล้วใช้ต่อทันทีโดยไม่ตรวจ ตอนนั้นข้อความนี้ "ดูถูก" เพราะมันเข้ากับ
ท่าทีระมัดระวังที่กฎสอนไว้ — การพูดว่ามีการ์ดขวางอยู่ฟังดูปลอดภัยกว่าการพูดว่าไม่มี จึงไม่รู้สึกว่าต้องตรวจ

### 5 Whys

1. **ทำไมเจ้าของงานถึงอนุมัติให้ผ่อนการ์ดที่ไม่ได้ขวางอะไร?** — เพราะตัวเลือกในคำถามที่ผมตั้งบอกว่าการ์ดขวางอยู่
2. **ทำไมคำถามถึงบอกว่าการ์ดขวางอยู่?** — เพราะผมเขียนข้ออ้างนั้นลงไฟล์ขออนุมัติโดยไม่มีหลักฐาน
3. **ทำไมถึงเขียนโดยไม่มีหลักฐาน?** — เพราะผมสรุปขอบเขตของการ์ดจาก memory แทนที่จะไล่เส้นทางเรียกจริงของตัวอัด
4. **ทำไมถึงคิดว่า memory พอ?** — เพราะ memory พูดถึงการ์ดในภาพรวมว่าเป็นชั้นป้องกันของ "กล่องเครื่องมือ" ผมจึงเหมารวมโดยไม่แยกว่าโมดูลไหนเรียกมันจริง และข้ออ้างที่ฟังดู "ปลอดภัยกว่า" ไม่กระตุ้นให้ผมตรวจ
5. **ทำไมข้ออ้างที่ยังไม่ตรวจถึงหลุดไปถึงคำถามขออนุมัติได้?** — **root cause: ไม่มีชั้นไหนบังคับว่าข้อความในตัวเลือกของ `AskUserQuestion` ต้องผ่านเกณฑ์หลักฐานเดียวกับข้อความอื่น** ask-guard ตรวจแค่ว่าเคยค้นบันทึกก่อนถามหรือยัง ไม่ได้ตรวจว่าข้ออ้างเชิงข้อเท็จจริงในคำถามมีหลักฐานไหม คำถามจึงกลายเป็นช่องทางที่ข้อความยังไม่ตรวจเดินทางไปถึงการตัดสินใจของเจ้าของงานได้โดยไม่ผ่านด่านใดเลย

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**

- `investigation-guard` — ไม่ครอบ เพราะงานนี้ไม่ได้ถูกจัดเป็นการตรวจสอบความล้มเหลว
- `ask-guard` — ทำงานและบล็อก 2 ครั้ง แต่บล็อกเรื่อง "ค้นบันทึกก่อนถามหรือยัง" เท่านั้น
  ไม่ได้ตรวจความจริงของข้อความในตัวเลือก
- `write_guard` เอง — ออกแบบให้ fail-closed และถ้าผมแก้จริงก็ต้องแก้ถึง 4 จุด
  ความยากของมันคือสิ่งเดียวที่ทำให้ผมหยุดตรวจก่อน จึงบังเอิญทำหน้าที่เป็นด่านสุดท้าย
- ไม่มีชั้นไหนที่ตรวจว่า "ข้ออ้างเรื่องพฤติกรรมของโค้ดมี `path:line` แนบหรือยัง"

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

| # | มาตรการ | ชนิด | สถานะ |
|---|---------|------|-------|
| P1 | เพิ่มชั้นใหม่ใน `ask-guard`: ถ้าข้อความของคำถามหรือของตัวเลือกมีข้ออ้างเชิงกลไก (รูปประโยคแนว "X บล็อก/ปฏิเสธ/ต้องแก้ Y ก่อน" · ชื่อไฟล์ `*.js` ที่อ้างพฤติกรรม) ต้องมี `path:line` อยู่ในข้อความนั้น มิฉะนั้นบล็อกพร้อมข้อความว่าให้แนบหลักฐานหรือเขียนว่า "ยังไม่ตรวจ" | เครื่องมือ (hook) | ค้าง |

"ใครเรียกมัน" ไม่ใช่สิ่งที่ "เอกสารบอกว่ามันคุ้มครองอะไร" เขียนไว้ที่รายงานฉบับนี้และสรุปใน
`docs/CLAUDE-ARCHIVE.md` § Post-mortems

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** ผมเองจับได้ ตอนกำลังจะลงมือแก้การ์ด — เพราะการ์ดถูกออกแบบให้ต้องแก้
  ถึง 4 จุด ความไม่สมเหตุสมผลของงานจึงทำให้หยุดตรวจเส้นทางเรียกก่อน ไม่ใช่เพราะมีชั้นไหนเตือน
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** ประมาณ 3 นาที นับจากที่เขียนข้ออ้างผิดลงไฟล์
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** P1 จะจับตั้งแต่ก่อนคำถามถูกส่งถึงเจ้าของงาน คือเร็วกว่ารอบนี้
  หนึ่งขั้นเต็ม เพราะรอบนี้ความผิดพลาดหลุดไปถึงการตัดสินใจแล้วจึงค่อยจับได้

  การทำให้ของอันตรายแก้ยากมีประโยชน์จริง

- ข้ออ้างที่ฟังดู "ปลอดภัยกว่า" (มีการ์ดขวางอยู่) ต้องการหลักฐานเท่ากับข้ออ้างที่ฟังดูเสี่ยง — ความรู้สึก
  ปลอดภัยไม่ใช่เหตุผลที่จะข้ามการตรวจ

  ข้อความอื่น ไม่ใช่ของร่างๆ
