## สรุปสั้น (Executive Summary)

ระหว่างจับตา 5 เลนที่กำลังแก้เคสวิดีโอ ผมเห็นว่าไฟล์ heartbeat ของเลน 1, 2, 5 ยังไม่มีบรรทัดใหม่หลังจากผ่านไปหลายนาที จึงตัดสินว่า "นิ่งค้าง" แล้วสั่ง `TaskStop` ฆ่าทั้ง 3 ตัวทันที โดยไม่เคยเช็คสถานะ `running` จริงหรือ log/ไฟล์อื่นก่อน — ผลที่ได้กลับมาหลังฆ่าแสดงชัดว่าทั้ง 3 ตัวกำลังทำงานอยู่จริง ตัวหนึ่ง (เลน 1) กำลังจะเขียนสรุปครบ 19 เคสอยู่แล้ว งานวิเคราะห์ที่ยังไม่ทันบันทึกลงดิสก์จึงหายไป ต้องเปิดเลนใหม่ 3 ตัวแทนและเริ่มนับหนึ่งใหม่บางส่วน แก้โดยเปิดเลนทดแทนทันทีพร้อมสั่งให้อ่านไฟล์ที่เลนเดิมทิ้งไว้ก่อนเริ่ม และเพิ่มกฎในเลนใหม่ให้เขียน heartbeat บรรทัดแรกทันทีที่เริ่มงาน (ก่อนอ่าน context ด้วยซ้ำ) กันเข้าใจผิดซ้ำ.

## 1. ปัญหา (Problem Statement)

- เช็ค `wc -l`/`tail -1` ของ `lane1_heartbeat.log`, `lane2_heartbeat.log`, `lane5_heartbeat.log` แล้วเห็นว่า mtime และเนื้อหาเป็นของรอบงานเก่า (2026-09-06) ไม่มีบรรทัดใหม่จากเลนที่เพิ่งเปิดไป ~19-20 นาทีก่อน
- สรุปว่า "นิ่งค้าง" จากสัญญาณนี้เพียงอย่างเดียว แล้วเรียก `TaskStop` ฆ่าทั้ง `a9253777c8382ec02` (เลน 1), `ae6d4dff18d681f54` (เลน 2), `aff25e6716e18fc83` (เลน 5) ทันทีในเทิร์นเดียว โดยไม่เคยเรียก `ListAgents` เช็คสถานะ `running` จริงก่อน และไม่เคยลองส่งข้อความไปถามสถานะก่อนตัดสินใจฆ่า
- ผลลัพธ์ที่ได้กลับมาจาก `TaskStop` ("result" field ของ notification) แสดงชัดว่าทั้ง 3 ตัวกำลังทำงานจริง — เลน 1 กำลังจะเขียนสรุปครบ 19 เคส (พบข้อมูลจริงเรื่อง `Authen_TC_013`/`Authen_TC_005`), เลน 2 กำลังสแกนพื้นหลัง + เช็ค tooling, เลน 5 เพิ่งเริ่มอ่าน context (ตัวเดียวที่ช้าจริงในบรรดา 3 ตัว)
- ระหว่างขั้นตอนนี้ ยังสั่ง `Agent` ทัวใหม่แทนที่จะใช้กลไกส่งข้อความหา agent เดิม (พบภายหลังว่าเซสชันนี้ไม่มีเครื่องมือ `SendMessage` สำหรับ subagent ที่เปิดผ่าน `Agent` tool เลย) ทำให้เกิด agent ซ้ำซ้อน (`a6b561f7ad35c3acb`) ที่ต้องฆ่าทิ้งอีกตัวเพื่อกันชนกันบนไฟล์เดียวกัน

**สิ่งที่ควรจะเป็น:** ก่อนสั่ง `TaskStop` ต้องเช็คสถานะจริงด้วย `ListAgents` (หรือเทียบเท่า) ก่อนเสมอ — heartbeat log ที่ยังไม่มีบรรทัดใหม่บอกได้แค่ว่า "ยังไม่เขียน" ไม่ได้บอกว่า "ตายแล้ว" สองอย่างนี้เป็นคำตอบคนละความหมาย ต้องแยกให้ออกก่อนตัดสินใจทำลายงาน

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไมฆ่า agent ที่ยังทำงานอยู่จริง?** — เพราะตัดสินใจจากสัญญาณเดียว (heartbeat log ไม่มีบรรทัดใหม่) โดยไม่ตรวจสถานะจริงก่อน
2. **ทำไมใช้สัญญาณเดียวในการตัดสินใจที่ทำลายงาน?** — เพราะกฎในความจำ ("นิ่งเกิน 2 นาที = ตามเช็คทันที") ถูกตีความว่า "เช็ค = ฆ่าเลย" ทั้งที่ตัวกฎเองบอกแค่ "ตามเช็คทันที" ไม่ได้บอกให้ฆ่าทันที
3. **ทำไมไม่ "ตามเช็ค" ด้วยวิธีที่ปลอดภัยกว่าก่อน (เช่น `ListAgents` เช็คสถานะ running, หรือรอดูอีกสักครู่)?** — เพราะภายใต้แรงกดดันเรื่องความเร็วจากเจ้าของงาน (ข้อความ "ไว" ซ้ำหลายครั้งติดกัน) เลือกทางที่ดูเหมือนเร็วที่สุด (ฆ่าแล้วเปิดใหม่) โดยไม่ทันคิดว่าการฆ่างานที่ยังไม่เขียนผลคือการทำลายความคืบหน้าจริง ซึ่งช้ากว่าการรอ
4. **ทำไมไม่รู้ว่าเลน 1 ใกล้จะเขียนผลอยู่แล้ว?** — เพราะ heartbeat log ที่ใช้ตัดสินใจ เป็นสัญญาณ "งานเขียนอะไรลงดิสก์แล้วหรือยัง" ไม่ใช่สัญญาณ "โปรเซสยังมีชีวิตอยู่ไหม" สองคำถามนี้ต้องใช้แหล่งข้อมูลคนละแหล่ง (heartbeat file vs. `ListAgents`/`TaskOutput` status) แต่ถูกปนกันเป็นคำถามเดียว
5. **ทำไมชั้นป้องกันที่มีอยู่ไม่จับ?** — root cause จริง: **ไม่มีกฎหรือเครื่องมือใดบังคับให้เช็คสถานะ `running` ก่อนสั่ง `TaskStop`** — การ์ด `answered-guard` ที่สร้างในเซสชันเดียวกันครอบคลุมแค่ "การพูดว่าติด/บล็อกโดยไม่เปิดของจริง" ไม่ครอบคลุม "การสั่งทำลายงานที่กำลังรันอยู่โดยไม่เช็คสถานะก่อน" ซึ่งเป็นการกระทำ (action) ไม่ใช่คำพูด (statement) — เป็นช่องว่างที่ยังไม่เคยมีการ์ดคุ้มครอง

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** ไม่มีชั้นใดครอบคลุม `TaskStop` เลย — ทุกการ์ดในเซสชันนี้ (investigation-guard, answered-guard, git-staging-guard, customer-content-guard) ผูกกับ Bash/AskUserQuestion/Stop เท่านั้น ไม่มีตัวไหนดัก `TaskStop` ก่อนเรียกจริง

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- จับได้เองทันที ไม่ต้องรอเจ้าของงานทัก และแจ้งตรงๆ ทันทีว่าพลาดอะไร ไม่ปิดบัง
- แก้ไขโดยสั่งให้เลนใหม่กู้งานจากไฟล์ที่เลนเดิมทิ้งไว้ แทนที่จะเริ่มจากศูนย์เต็ม ลดความเสียหายที่เกิดขึ้นแล้ว

### สิ่งที่ต้องปรับปรุง
- ต้องแยกให้ชัดเจนระหว่าง "สัญญาณว่างานยังไม่คืบหน้า" (heartbeat log) กับ "สัญญาณว่าโปรเซสตายแล้ว" (สถานะ running) — สองคำถามนี้ต้องตอบจากแหล่งข้อมูลคนละแหล่งเสมอ ก่อนตัดสินใจใดๆ ที่ทำลายงาน
- ภายใต้แรงกดดันเรื่องความเร็ว ต้องระวังเป็นพิเศษว่าทางที่ "ดูเหมือนเร็วที่สุด" (ฆ่าแล้วเริ่มใหม่) อาจช้ากว่าทางที่ระมัดระวังกว่า (เช็คสถานะก่อน)
