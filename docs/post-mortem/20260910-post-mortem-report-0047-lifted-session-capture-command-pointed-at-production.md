## สรุปสั้น (Executive Summary)

ระหว่างขั้นตอน "เอา session กลับมา" ของรอบตรวจหลักฐานวิดีโอ Integration (env ที่เจ้าของงานยืนยันไว้ตั้งแต่ 7/Sep คือ **pre-prod**) มีการส่งคำสั่งให้เจ้าของงานรัน `./capture/session_capture_prod.sh` เพื่อเก็บ session — สคริปต์ตัวนี้อ่าน host จาก `capture/prod_resolve.json` เสมอไม่ว่าจะส่ง flag อะไรมาก็ตาม และ `prod_resolve.json` ก็ประกาศตัวเองไว้ในคอมเมนต์แรกว่าเป็นค่าคงที่ของ "OLS production smoke test (2026-09)" — สคริปต์นี้จึงไม่มีทางชี้ไปที่ไหนอื่นนอกจาก production ไม่ว่าใครจะตั้งใจใช้กับ env ไหน

เจ้าของงานรันคำสั่งนั้นและกรอกรหัสผ่านให้จริง — ตรวจพบไฟล์ session ของบัญชี admin จากทะเบียน production (`accounts.json`, 15 บัญชี) ถูกเขียนขึ้นอย่างน้อย 14 ไฟล์ในช่วง 18:13:35–18:51:56 น. ของเย็นวันนั้น และอย่างน้อย 1 ไฟล์ในนั้นมีคุกกี้และ origin ที่ชี้ไปที่โฮสต์ OLS ของ production โดยตรง (ตรวจสอบสด ไม่ใช่การอนุมาน) ยืนยันว่าไม่ใช่แค่หน้าจอเปิดค้างไว้เฉยๆ แต่เป็นการล็อกอินที่สำเร็จจริง

สาเหตุจริงไม่ใช่ "ไม่มีคำเตือนอยู่ตรงไหนเลย" — ตารางใน `CLAUDE.md` เองเขียนกำกับไว้แล้วว่าสคริปต์นี้ "**ตัวห่อสำหรับ production**" และตัวอย่างคำสั่งสองบรรทัดที่วางไว้ข้างกันก็มาจากเอกสารเดียวกัน สิ่งที่ขาดไปคือ **ขั้นตอนที่บังคับให้เทียบคำสั่งที่กำลังจะยกไปให้คนอื่นรัน กับ environment ที่รอบงานนั้นประกาศไว้ ก่อนส่งออกไป** — ป้ายกำกับที่ถูกต้องมีอยู่แล้วในเอกสาร แต่ไม่มีขั้นตอนใดบังคับให้อ่านมันในจังหวะที่กำลังจะหยิบคำสั่งไปใช้จริง

แก้ทันทีในรอบเดียวกันด้วยการเปิดของจริงวัดปลายทางที่ถูกต้องของ pre-prod และประกอบคำสั่งที่ถูกต้องขึ้นใหม่ (บันทึกไว้ใน `ROUND_DECISIONS.md` ของรอบงาน) แต่ **ยังไม่มีมาตรการเชิงกลไกใดที่ป้องกันไม่ให้เหตุการณ์แบบนี้เกิดซ้ำ** — งานที่ค้างจริงคือการเพิ่มด่านตรวจในตัวสคริปต์เอง หรือในขั้นตอนที่ต้องยกคำสั่งไปให้มนุษย์รัน

## 1. ปัญหา (Problem Statement)

- `~/ols-qa-testing-bot/capture/session_capture_prod.sh` (บรรทัด 15-32) อ่าน host ทั้งหมดจาก `capture/prod_resolve.json` แล้ว `exec node capture/session_capture.js` พร้อมตั้ง `PROD=1` ตายตัว — **ไม่มี flag หรือ environment variable ใดที่ทำให้สคริปต์นี้ชี้ไปที่ pre-prod ได้เลย** ต่อให้ส่ง `--role` หรือ tag อะไรมาก็ตาม มันยังคงยิง host จาก `prod_resolve.json` เหมือนเดิม
- `capture/prod_resolve.json` ประกาศตัวเองในฟิลด์ `_note` (บรรทัดแรกของไฟล์) ว่าเป็น "Client-side DNS override for the **OLS production smoke test (2026-09)**" และมี `names` เป็นรายการโฮสต์ของ production ทั้งชุด (พอร์ทัล + OLS + backend APIs)
- `CLAUDE.md:351` (ตารางเครื่องมือใต้หัวข้อ "ต้องล็อกอิน = ใช้ saved session เท่านั้น") เขียนกำกับไว้ตรงๆ อยู่แล้วว่า `session_capture_prod.sh` คือ "ตัวห่อสำหรับ **production**" และ `CLAUDE.md:358-359` วางตัวอย่างคำสั่งไว้ 2 บรรทัดติดกัน:
  ```
  ./capture/session_capture_prod.sh --all         # เก็บทุกบัญชีที่ยังไม่มี session
  ./capture/session_capture_prod.sh --role "Admin content"
  ```
- ทะเบียนบัญชี `capture/accounts.json` (สร้างจากชีต Go-Live แท็บ "Account on Prod") มี **15 บัญชี** ตรงกับที่บันทึกไว้ในแถวหนี้ `PM-2026-09-10-06`
- ไฟล์ session ของบัญชีในทะเบียนนั้น ถูกเขียน/อัปเดตในเย็นวันเดียวกัน อย่างน้อย **14 ไฟล์** ระหว่าง 18:13:35–18:51:56 (รายละเอียดในไทม์ไลน์)
- ตรวจสอบเนื้อไฟล์ session อย่างน้อย 1 ไฟล์ (บัญชี `bobbie.gul2448`, mtime 18:51:56) มี **cookie domain และ origin ที่ตรงกับโฮสต์ OLS ของ production เป๊ะ** (ตัวเดียวกับที่ระบุอยู่ใน `prod_resolve.json`'s `names[0]`) — ยืนยันว่าเป็นการล็อกอินที่สำเร็จเข้า production จริง ไม่ใช่แค่หน้าต่างเปิดค้าง
- แผนงานของรอบนี้ (`~/ols-qa-testing-bot/out/review-vdo-integration/LOT1-SHOOTING-SCRIPT.md:7` และ `ROUND_DECISIONS.md:5`) ระบุ environment ของรอบนี้เป็น **pre-prod** เท่านั้น ยืนยันโดยเจ้าของงานตั้งแต่ 7/Sep/2026

**สิ่งที่ควรจะเป็น:** ทุกคำสั่งที่กำลังจะถูกยกไปให้เจ้าของงานรันด้วยมือ (โดยเฉพาะคำสั่งที่เกี่ยวกับการล็อกอิน ซึ่งเป็นขั้นตอนเดียวที่ AI ทำแทนไม่ได้ตามกฎของ repo) ต้องถูกเปิดตรวจก่อนเสมอว่าปลายทางจริงตรงกับ environment ที่รอบงานประกาศไว้หรือไม่ — ตรงกับกฎที่ออกมาจากรายงาน #0027 ("ค่าที่ระบุปลายทางต้องเปิดของจริงยืนยันในรอบนั้นก่อนใช้เสมอ") และ #0009 ("เปิดซอร์สอ่านก่อนรันเครื่องมือที่ยิงออกนอกเครื่อง")

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

ความผิดพลาดนี้ต่างจาก #0027 และ #0009 ตรงจุดหนึ่งที่สำคัญ: ทั้งสองรายงานก่อนหน้าอธิบายกรณีที่ **ค่าที่ใช้ไม่มีชื่อ environment กำกับอยู่ในตัวเองเลย** (ที่อยู่หน้าล็อกอินที่จำไว้ไม่บอกว่าเป็นของ env ไหน, ค่าเริ่มต้นของ `session_verify.js` ไม่มีป้ายเตือนใดๆ) — รอบนี้ **ป้ายกำกับที่ถูกต้องมีอยู่แล้ว** ทั้งในชื่อไฟล์ (`_prod`), ในคอมเมนต์ต้นไฟล์ของ `prod_resolve.json`, และในตาราง `CLAUDE.md` ที่เขียนคำว่า "production" ไว้ตรงๆ แต่ป้ายกำกับที่ถูกต้องก็ยังไม่พอ เพราะ **ไม่มีขั้นตอนใดบังคับให้อ่านป้ายนั้นในจังหวะที่กำลังจะยกคำสั่งไปให้เจ้าของงานรัน** — นี่คือจุดตัดสินใจที่พลาด

### 5 Whys

1. **ทำไมเจ้าของงานถึงล็อกอินเข้า production?** — เพราะคำสั่งที่ถูกส่งให้รันคือ `./capture/session_capture_prod.sh` ซึ่งอ่าน host จาก `prod_resolve.json` เสมอ ไม่มีทางเลือกอื่น
2. **ทำไมถึงส่งคำสั่งนั้นให้รันในรอบที่ต้องใช้ pre-prod?** — เพราะคำสั่งถูกยกมาจากเอกสารอ้างอิงเรื่อง "วิธีเก็บ session" (`CLAUDE.md:345-359`) โดยไม่ได้เปิดไฟล์ `.sh` หรือ `prod_resolve.json` ตรวจก่อนว่ามันจะพาไปที่ไหนสำหรับรอบงานนี้โดยเฉพาะ
3. **ทำไมการยกมาจากเอกสารถึงไม่ทำให้เกิดการเทียบกับ environment ของรอบงาน?** — เพราะป้ายกำกับ "production" ในตารางเอกสาร (`CLAUDE.md:351`) ถูกอ่านผ่านในฐานะ "นี่คือเครื่องมือที่ใช้เก็บ session" ไม่ได้ถูกอ่านในฐานะ "เครื่องมือนี้ใช้ได้กับ environment เดียวเท่านั้น และต้องเทียบกับ environment ของรอบงานปัจจุบันก่อน"
4. **ทำไมป้ายกำกับที่ถูกต้องอยู่แล้วยังไม่ทำให้เกิดการเทียบ?** — เพราะไม่มีขั้นตอนในกระบวนการที่บังคับให้ "หยุดเทียบ environment" ก่อนส่งคำสั่งออกไปให้มนุษย์รันจริง — การตรวจสอบก่อนใช้ (ที่รายงาน #0027/#0009 วางไว้แล้ว) ถูกออกแบบมาสำหรับคำสั่งที่ **AI รันเอง** ไม่ใช่คำสั่งที่ **AI ร่างให้คนอื่นรันด้วยมือ**
5. **ทำไมช่องว่างนี้ถึงไม่เคยถูกปิด ทั้งที่มีรายงาน 2 ฉบับก่อนหน้าพูดเรื่องเดียวกัน?** — **root cause จริง:** มาตรการของ #0027 และ #0009 ทั้งคู่แก้ที่ "เครื่องมือที่ AI เรียกเอง" (แก้ default, แยกไฟล์ roster, เพิ่ม guard ในตัวสคริปต์ที่ AI สั่งรัน) แต่ไม่มีรายงานฉบับใดพูดถึง **จุดที่คำสั่งถูกร่างขึ้นเพื่อส่งให้มนุษย์คนอื่นเป็นผู้กดรันเอง** ซึ่งเป็นเส้นทางที่ไม่มีการ execute โดย AI เลยสักขั้นตอน จึงไม่มี "ผลลัพธ์ที่ AI เห็น" ให้ใช้ตรวจสอบย้อนกลับได้ทันที — ต้องปิดที่ **ขั้นตอนก่อนส่งมอบคำสั่งให้มนุษย์รัน** ไม่ใช่ที่ตัวเครื่องมือเพียงอย่างเดียว

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**

| ชั้นที่มีอยู่ | ทำไมไม่จับ |
|---|---|
| ป้ายกำกับ "ตัวห่อสำหรับ production" ใน `CLAUDE.md:351` | เป็นตัวหนังสือเฉยๆ ไม่มีกลไกบังคับให้อ่านในจังหวะที่กำลังจะส่งคำสั่งออกไป — คู่กับบทเรียนของ #0009 ที่ว่า "กฎที่เป็นตัวหนังสืออย่างเดียวจะถูกทำตามจนถึงนาทีที่มีเครื่องมือเดาปลายทางให้เงียบๆ" |

| ตัวสคริปต์ `session_capture_prod.sh` เอง | ไม่มีการตรวจสอบใดๆ ว่าผู้เรียกตั้งใจใช้กับ environment ไหน — มันถูกออกแบบมาให้ตัดสินใจแทนผู้ใช้ตั้งแต่ต้น (นั่นคือจุดประสงค์ของมัน) จึงไม่มีทาง "ปฏิเสธ" ได้เลยแม้จะผิดบริบท |

## 5. แนวทางการแก้ไข (Fix)

- **ประกอบคำสั่งที่ถูกต้องสำหรับ pre-prod ขึ้นใหม่** โดยยิงอ่านจริงหา portal ที่ถูกต้อง (ผ่าน `probe_portal.js`) แทนการเดาจากชื่อโฮสต์ — บันทึกไว้ใน `ROUND_DECISIONS.md` (หัวข้อ "2026-09-10 18.5x — แก้ของตัวเอง") พร้อมรูปแบบคำสั่งที่ถูกต้อง (ตั้ง `PORTAL` / `OLS` / `ROSTER` เป็นค่าของ pre-prod อย่างชัดเจน ผ่าน `session_capture.js` โดยตรง ไม่ผ่าน wrapper ที่ล็อก production)
- **ยืนยันซ้ำด้วยของจริงว่าบัญชีที่เคยถูกจดว่า "เข้าไม่ได้"** (ระหว่างที่ลองผิด portal) ไม่ได้เสียจริง — วัดสดหลังแก้แล้วได้ `5/5 verified` ทั้ง 5 บัญชีที่ทดสอบ พร้อมบทบาทที่เซิร์ฟเวอร์ตอบจริง

**สิ่งที่ยังไม่ได้ทำ ณ ตอนเขียนรายงานนี้ (ตรงไปตรงมาตามที่ตรวจพบ ไม่ใช่การกลบเพื่อให้ดูจบ):**
- ยังไม่มีการเพิ่ม guard ใดๆ ลงในตัว `session_capture_prod.sh` หรือ `prod_resolve.json` เพื่อป้องกันการใช้ผิดครั้งถัดไป — ไฟล์ทั้งสองที่ตรวจสอบในรอบนี้ยังเป็นเนื้อหาเดิมทุกประการ ไม่มีการแก้โค้ดเลย
- ยังไม่ได้ตรวจสอบ/ยืนยันว่าไฟล์ session ของบัญชี production ที่ถูกเก็บไปโดยไม่ตั้งใจ (อย่างน้อย 14 ไฟล์) ถูกลบทิ้งหรือปล่อยให้หมดอายุแล้วหรือไม่

**ยืนยันแล้วด้วย:** การอ่านซอร์สสด (`session_capture_prod.sh` ทั้งไฟล์, `prod_resolve.json` ทั้งไฟล์) · การเปรียบเทียบ mtime ของ `state_obec_admin01_uat.json` (`2026-09-10 18:13:35`) กับตัวเลขในแถวหนี้ `PENDING.md` ตรงกันถึงวินาที · การตรวจ cookie/origin ของ `state_bobbie.gul2448.json` พบว่าชี้ไปโฮสต์ OLS ของ production เป๊ะ · การอ่าน `ROUND_DECISIONS.md` ทั้งช่วงที่เกี่ยวข้อง (บรรทัด 90-230) ยืนยันว่าเซสชันเดียวกันเป็นผู้พบและแก้ไขปัญหานี้เอง

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

| # | มาตรการ | ชนิด | สถานะ |
|---|---------|------|-------|
| P1 | เพิ่ม guard ในตัว `session_capture_prod.sh` เอง — พิมพ์คำเตือนชัดเจนและถามยืนยัน (หรือต้องการ flag เช่น `I_MEAN_PRODUCTION=1`) ก่อนเปิดเบราว์เซอร์จริง เพราะสคริปต์นี้ไม่มีทางเลือก environment อื่นเลย การรันมันจึงเท่ากับการยืนยันเจตนาไปแล้วครึ่งหนึ่ง | เครื่องมือ | ค้าง |
| P2 | สร้าง `session_capture_preprod.sh` เป็น wrapper คู่ขนานของ pre-prod ให้สมมาตรกับตัวของ production (ปัจจุบันมีแต่สคริปต์เฉพาะกิจ `pp_*`/`preprod_*` จำนวนมาก ไม่มีตัวห่อ turnkey ตัวเดียวที่ต่อ `PORTAL`/`OLS`/`ROSTER` ของ pre-prod ให้ครบเหมือนที่ production มี) — ลดแรงจูงใจที่จะหยิบตัวของ production มาใช้เพราะมันสะดวกกว่า | เครื่องมือ | ค้าง |
| P3 | เพิ่มขั้นตอนบังคับ "เทียบคำสั่งกับ environment ของรอบงานก่อนส่งให้มนุษย์รัน" ให้เป็นด่านแยกจากด่าน "ตรวจก่อนรันเอง" ที่มีอยู่แล้ว — เพราะรายงาน #0027/#0009 ครอบเฉพาะคำสั่งที่ AI รันเอง ไม่ครอบคำสั่งที่ร่างให้คนอื่นรัน | กฎ (เขียนใน `CLAUDE.md` หัวข้อ login/session) | ค้าง |

**กฎที่เพิ่มจากเหตุนี้:** ยังไม่มีการแก้โค้ดหรือเพิ่มกฎใหม่จริงในรอบนี้ (ขอบเขตของงานที่มอบหมายคือการเขียนรายงานเท่านั้น ไม่ใช่การลงมือแก้) — มาตรการ P1-P5 ข้างต้นคือสิ่งที่ต้องทำต่อ ไม่ใช่สิ่งที่ทำเสร็จแล้ว บันทึกไว้ตรงๆ เพื่อไม่ให้เข้าใจผิดว่าปิดคลาสนี้แล้ว จุดที่สำคัญที่สุดในมาตรการทั้งหมดคือ **P3** เพราะมันคือ root cause จริง (ข้อ 5 ใน 5 Whys) — P1/P2/P4/P5 ล้วนเป็นการปิดช่องเฉพาะจุด ไม่ใช่การปิดคลาส "คำสั่งที่ร่างให้มนุษย์รันไม่เคยผ่านด่านเทียบ environment" ซึ่งยังเปิดอยู่สำหรับเครื่องมืออื่นทุกตัวที่ยังไม่ถูกสแกน

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** จับได้เองภายในเซสชันเดียวกัน ระหว่างพยายามหาสาเหตุว่าทำไม session ของ pre-prod ที่เพิ่งเก็บไปยืนยันตัวตนไม่ผ่าน (`GET /api/auth/get-session` ตอบว่างเปล่า) — การไล่สาเหตุนั้นพาไปเจอว่าคำสั่งที่ใช้อยู่จริงคือ `session_capture_prod.sh` ไม่ใช่คำสั่งที่ตั้งใจ ไม่ใช่มีสัญญาณเตือนใดๆ จากระบบที่ชี้ตรงมาที่ความผิดพลาดนี้โดยตรง
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** ไม่สามารถระบุนาทีที่แน่นอนได้จากหลักฐานที่มี (ดูหมายเหตุในไทม์ไลน์) แต่ทั้งหมดเกิดขึ้นและถูกพบภายในค่ำวันเดียวกัน (2026-09-10) ไม่ได้ค้างข้ามวัน
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** มาตรการ P1 (guard ในตัวสคริปต์) จะทำให้ไม่มี "รอบหน้า" ให้ต้องจับเลย เพราะสคริปต์จะปฏิเสธตั้งแต่ก่อนเปิดเบราว์เซอร์ — ดีกว่าการพึ่งการไล่สาเหตุย้อนหลังหลังจากล็อกอินสำเร็จไปแล้ว เพราะ ณ จุดนั้นย้อนคืนไม่ได้อีกต่อไป

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- แม้ป้ายกำกับ "production" จะถูกมองข้ามตอนหยิบคำสั่ง แต่การไล่หาสาเหตุตอนที่ session ยืนยันตัวตนไม่ผ่าน ก็นำไปสู่การเปิดสคริปต์ดูจริงอย่างรวดเร็ว ไม่ใช่การเดาซ้ำ
- `ROUND_DECISIONS.md` บันทึกกระบวนการแก้ไขไว้ละเอียดพอที่รายงานฉบับนี้สามารถสร้างไทม์ไลน์ส่วนใหญ่ย้อนหลังได้โดยไม่ต้องเดา
- คำสั่งที่ถูกต้องสำหรับ pre-prod ถูกพิสูจน์ด้วยการยิงอ่านจริง (อ่าน iframe ของแอปเอง) ไม่ใช่การเดาจากชื่อโฮสต์ครั้งที่สอง — เรียนรู้จากการเดาผิดครั้งแรกทันที

### สิ่งที่ต้องปรับปรุง
- **คำสั่งที่จะยกให้มนุษย์รันด้วยมือ ยังไม่เคยผ่านด่านตรวจเดียวกับคำสั่งที่ AI รันเอง** — ทั้งที่เป็นเส้นทางที่อันตรายกว่า เพราะเมื่อมนุษย์กดรันและกรอกรหัสผ่านไปแล้ว ไม่มีทางย้อนกลับได้เหมือนคำสั่งที่ AI รันเองแล้วเห็นผลก่อนตัดสินใจขั้นต่อไป
- ป้ายกำกับที่ถูกต้องในเอกสาร (`CLAUDE.md:351` เขียนว่า "production" ตรงๆ) ไม่เพียงพอเมื่อไม่มีขั้นตอนบังคับให้เทียบมันกับบริบทงานปัจจุบันในจังหวะที่กำลังจะใช้ — ต้องมีด่านกลไก ไม่ใช่พึ่งว่า "มีเขียนไว้แล้ว"

## 10. Technical Appendix

**ไฟล์ที่เกี่ยวข้อง (อยู่ใน `~/ols-qa-testing-bot/` off-repo ทั้งหมด ไม่มีไฟล์ใดถูกแก้ในรอบนี้):**
- `capture/session_capture_prod.sh` — wrapper ที่ล็อกปลายทางเป็น production เสมอ (บรรทัด 15-32 อ่าน host จาก `prod_resolve.json`)
- `capture/prod_resolve.json` — ค่าคงที่ปลายทาง production พร้อมคอมเมนต์ระบุตัวเองว่าเป็นของ "OLS production smoke test (2026-09)"
- `capture/session_capture.js` — เครื่องมือจริงที่รับ `PORTAL`/`OLS`/`ROSTER` จาก environment variable ได้ (ใช้ตรงเพื่อ pre-prod ได้ถูกต้อง ถ้าไม่ผ่าน wrapper)
- `capture/accounts.json` — ทะเบียนบัญชี production (15 บัญชี, สร้างจากชีต Go-Live tab "Account on Prod")
- `capture/accounts_preprod.json` — ทะเบียนบัญชี pre-prod (13 บัญชี, คนละชุดโดยสิ้นเชิง)
- `out/review-vdo-integration/ROUND_DECISIONS.md` — บันทึกมติของรอบงานนี้ รวมการค้นพบและแก้ไขปัญหานี้ในเซสชันเดียวกัน
- `out/review-vdo-integration/LOT1-SHOOTING-SCRIPT.md:7` — ยืนยัน environment ของรอบนี้คือ pre-prod

**ข้อจำกัดของการตรวจสอบในรอบนี้ (ระบุตรงๆ ตามที่ตรวจไม่ถึง ไม่ใช่การเดาให้ครบ):**
- ตัวเลข "รัน 2 ครั้ง" มาจากแถวหนี้ `PENDING.md` โดยตรง — รายงานฉบับนี้ไม่มีหลักฐานอิสระ (เช่น shell history หรือ log การ invoke) มายืนยันจำนวนครั้งที่แน่นอน มีเพียงรูปแบบที่สอดคล้องกัน (ตัวอย่าง 2 บรรทัดใน `CLAUDE.md:358-359` + บัญชีบทบาท "Admin content" 6 ใบมีอยู่จริงในทะเบียน) ซึ่งเป็นการอนุมาน ไม่ใช่การพิสูจน์
- จำนวนบัญชีที่เจ้าของงาน "กรอกรหัสผ่านจริง" เทียบกับจำนวนไฟล์ session ที่ถูกเขียน/อัปเดต (14 ไฟล์) ไม่เท่ากันเสมอไป — `state_obec_admin01_uat.json` มี cookie เฉพาะโดเมนกลาง (`<NDLP_ROOT_DOMAIN>`) เท่านั้น ไม่มี cookie เฉพาะของโฮสต์ OLS แยกต่างหาก ดังนั้นหลักฐานที่ยืนยันได้แน่ชัดสำหรับไฟล์นี้คือการที่บัญชีนี้อยู่ในทะเบียน production เท่านั้น (ไม่อยู่ใน roster ของ pre-prod เลย) บวกกับ mtime ที่ตรงกับแถวหนี้เป๊ะ ไม่ใช่จากเนื้อ cookie โดยตรง ส่วน `state_bobbie.gul2448.json` มีคุกกี้ของโฮสต์ OLS แยกต่างหากชัดเจน จึงเป็นหลักฐานที่หนักแน่นกว่า — ไม่ได้ไล่ตรวจเนื้อไฟล์ทั้ง 14 ไฟล์ทีละไฟล์ในรอบนี้ เพราะ 2 ไฟล์ที่ตรวจแล้วเพียงพอต่อการยืนยันข้อเท็จจริงหลักของรายงาน
