## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไมเคลมว่า "อัปเดตแล้ว" ก่อนอ่านกลับ?** เพราะเครื่องมือทุกตัวในสายการเขียน (`build_board.js` → `check_theme.js`
   → `Artifact.publish`) ตอบสำเร็จหมด (exit 0 / THEME OK / publish OK) จึงตีความว่า "งานฝั่งเราจบแล้ว = อัปเดตแล้ว"
2. **ทำไมถือว่า exit 0 ของเครื่องมือฝั่งเขียนเท่ากับ "อัปเดตแล้ว"?** เพราะไม่มีขั้นบังคับแยกระหว่าง "เขียนสำเร็จ"
   กับ "ปลายทางแสดงผลถูกต้อง" — ทั้ง 2 อย่างถูกปฏิบัติเป็นเรื่องเดียวกันในขั้นตอนทำงาน ทั้งที่ #0018 เคยเขียนกฎแยกไว้แล้ว
3. **ทำไมกฎที่เขียนไว้แล้ว (#0018) ไม่ถูกใช้ในรอบนี้?** เพราะกฎนั้นอยู่ในรายงาน post-mortem ซึ่งเป็นความจำ ไม่ใช่
   ขั้นบังคับในเครื่องมือ `check_theme.js` เอง — `check_theme.js` วัดได้แค่ธีม (สี/ฟอนต์) ไม่มีขั้นใดในสาย
   เครื่องมือที่บังคับให้ดึงหน้า live กลับมาอ่านก่อนพิมพ์ว่า "สำเร็จ"
4. **ทำไม `check_theme.js` ไม่ครอบคลุมเรื่องนี้?** เพราะถูกออกแบบมาเพื่อป้องกันการเปลี่ยนธีมโดยไม่ได้รับอนุมัติ
   (ตามกฎบอร์ดข้อ 3) ไม่ใช่เพื่อยืนยันว่าเนื้อหาที่ตั้งใจ (เลน/tiles/blocker) ขึ้นจริงบนหน้าที่เผยแพร่
5. **ทำไมไม่มีขั้นอ่านกลับบังคับแยกจาก `check_theme.js`?** เพราะเช้าวันเดียวกัน (#0066/PM-05) เพิ่งบันทึกบทเรียน
   เรื่อง "ต้องอ่านกลับก่อนเคลมว่าอัปเดต" ไว้เป็นความจำ แต่ยังไม่ได้แปลงเป็นขั้นตอนบังคับในเครื่องมือหรือ checklist
   ที่ใช้ทุกครั้งก่อนพูดคำว่า "อัปเดตแล้ว" — รอบบ่ายของวันเดียวกันจึงเกิดซ้ำแบบเดียวกันทันที

**สาเหตุเชิงกลไก:** บทเรียนจาก #0018/#0020/PM-05 ถูกบันทึกเป็นความจำ (ledger + รายงาน) แต่ยังไม่ถูกแปลงเป็น
ขั้นบังคับเชิงกลไกในเครื่องมือ (`check_theme.js` หรือ script ที่ครอบการ publish) — จึงพึ่งการจำกฎในเทิร์นถัดไป
ซึ่งพลาดได้ง่ายเมื่อทำงานเร็วและมีเครื่องมือหลายตัวตอบ "สำเร็จ" พร้อมกัน

## 4. ผลกระทบ (Impact)

- **ไม่มีข้อมูลผิดถึงเจ้าของงานจริง** — อ่านกลับพบว่าเนื้อหาถูกต้องครบทุกจุด (3 tiles · 6 lanes · blocker ใหม่)
- **ความเสี่ยงเชิงกระบวนการ** — ถ้ารอบนั้น `check_theme.js` ผ่านแต่เนื้อหาจริงมีช่องว่าง (เหมือนที่เกิดใน #0066
  เมื่อเช้าของวันเดียวกัน) เจ้าของงานจะได้รับลิงก์ที่ผิดโดยไม่มีใครรู้จนกว่าจะมีคนสังเกตเอง
- **ผิดซ้ำภายในวันเดียวกัน** — เกิดห่างจากรายงาน #0066 (เช้า) เพียงไม่กี่ชั่วโมง แสดงว่าการจดบทเรียนอย่างเดียว
  ไม่เพียงพอที่จะกันไม่ให้เกิดซ้ำในรอบถัดไปของวันเดียวกัน

## 5. แนวทางการแก้ไข (Fix)

**สิ่งที่ทำแล้ว:** อ่านลิงก์ live กลับมาตรวจในเทิร์นถัดไป ยืนยันเนื้อหาถูกต้องครบ — ไม่ต้องแก้ไขข้อมูลใดเพิ่ม

**ยังไม่ทำ (ต้องทำต่อ):** ยังไม่มีขั้นบังคับเชิงกลไกที่ปฏิเสธการพูดคำว่า "อัปเดตแล้ว" ก่อนอ่านหน้า live กลับมา
ตรวจเนื้อหา — ดูหัวข้อ 6

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

1. **แยก "เขียนสำเร็จ" กับ "ปลายทางแสดงผลถูกต้อง" ให้เป็นขั้นตอนคนละขั้นเสมอ** — exit 0 ของ `build_board.js`/
   `check_theme.js`/publish ตอบได้แค่ขั้นแรก คำว่า "อัปเดตแล้ว" ต้องรออ่านขั้นที่สองก่อนเท่านั้น
2. **ทุกครั้งที่ publish บอร์ด ต้องเรียก `Artifact.read` ดึงหน้า live กลับมาตรวจก่อนพูดคำว่า "อัปเดตแล้ว"** —
   ไม่ใช่ทางเลือกที่ทำ "ถ้ามีเวลา" แต่เป็นขั้นบังคับก่อนพิมพ์คำนั้นเสมอ
3. **บทเรียนที่เกิดซ้ำภายในวันเดียวกัน (เช้า #0066 → บ่าย #0068) แสดงว่าความจำอย่างเดียวไม่พอ** — ต้องหาทางทำให้
   ขั้นอ่านกลับเป็นส่วนหนึ่งของ workflow การ publish บอร์ดเอง ไม่ใช่พึ่งการจำกฎจากรายงานเก่า
   *(ยังไม่ได้สร้างเป็นเครื่องมือ — เป็นข้อเสนอ ไม่ใช่ของที่มีอยู่แล้ว)*

**กฎที่เพิ่มจากเหตุนี้:** *ห้ามพูดคำว่า "อัปเดตแล้ว" กับสิ่งที่คนอื่นต้องเห็น ทันทีที่เครื่องมือฝั่งเขียนตอบสำเร็จ
(exit 0 / THEME OK / publish OK) — ต้องอ่านหน้า live กลับมาตรวจเนื้อหาก่อนพูดคำนั้นเสมอ ไม่มีข้อยกเว้นเรื่องความเร่งด่วน*
· และ *บทเรียนที่เพิ่งเกิดในวันเดียวกัน (เช้า) ต้องถูกนำมาเช็คก่อนทำงานประเภทเดียวกันซ้ำ (บ่าย) ไม่ใช่แค่จดไว้เป็นรายงาน*
