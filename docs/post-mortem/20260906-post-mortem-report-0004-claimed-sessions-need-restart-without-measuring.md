## สรุปสั้น (Executive Summary)

ตอนส่งมอบ hook ชุดใหม่ ผมปิดท้ายรายงานด้วยข้อจำกัดหนึ่งข้อว่า hook อ่าน `settings.json`
ตอนเปิดเซสชัน เซสชันที่เปิดค้างอยู่จึงยังไม่เห็นกฎใหม่จนกว่าจะเปิดใหม่ แล้วขอให้เจ้าของงาน
ปิด-เปิดเซสชันอื่นที่ทำงานบน repo นี้อยู่ ข้อความนั้นเขียนเหมือนเป็นข้อเท็จจริงที่ตรวจแล้ว
ความจริงคือผมไม่เคยวัดเลย และมันผิด

เจ้าของงานตอบกลับว่า "เราทำงาน session อื่นอยู่ปิดไม่ได้" — คำแนะนำที่ผิดจึงไปถึงจุดที่
เจ้าของงานต้องตัดสินใจกับมันแล้ว รอบถัดมาผมวัดของจริงและพบว่าเซสชันที่เปิดค้างอยู่ก่อน hook
จะมีตัวตนกว่า 3 ชั่วโมง ทำตาม hook ใหม่โดยไม่ต้องรีสตาร์ต ผมแก้คำพูดในแชททันที
ไม่มีการปิดเซสชันใดเกิดขึ้นจริง

## 1. ปัญหา (Problem Statement)

ข้อความที่ส่งถึงเจ้าของงานเขียนไว้ว่า *"guard ตัวใหม่ยังไม่คุ้ม session ที่เปิดค้างอยู่ก่อนหน้า —
hook อ่าน `settings.json` ตอนเปิด session ตัวที่รันอยู่แล้วจะยังไม่เห็นกฎใหม่จนกว่าจะเริ่ม session ใหม่
ถ้าต้องการให้คุ้มทันที รบกวนปิด-เปิด session อื่นที่ทำงานบน repo นี้อยู่ครับ"

ประโยคนี้ไม่มีการวัดรองรับแม้แต่ครั้งเดียว มันเป็นการอนุมานจากความคุ้นเคยว่าโปรแกรมมักอ่าน
ไฟล์ตั้งค่าตอนเริ่มทำงาน ไม่ใช่สิ่งที่เปิดดูในรอบนั้น

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

สาเหตุไม่ใช่ "ไม่มีข้อมูล" — ข้อมูลที่หักล้างอยู่ในเทิร์นเดียวกันนั้นแล้ว ผมเพิ่งเห็นกับตาว่า hook
ที่ผมต่อสายกลางเซสชันทำงานทันทีกับ prompt ถัดไป แล้วอีกไม่กี่นาทีต่อมาก็เขียนข้อความที่บอกว่า
สิ่งนั้นเกิดขึ้นไม่ได้ สาเหตุคือผมหยิบ "ความรู้ทั่วไปเรื่องโปรแกรมอ่านไฟล์ตั้งค่า" มาตอบ
แทนที่จะหยิบสิ่งที่เพิ่งวัดได้

ตัวเร่งอีกชั้นคือรูปประโยค ผมเขียนมันเป็น "ข้อจำกัดที่ควรทราบ" ต่อท้ายรายงานที่ทุกบรรทัดก่อนหน้า
มีหลักฐานแนบครบ ผู้อ่านจึงไม่มีทางแยกออกว่าบรรทัดสุดท้ายนี้คนละชั้นความน่าเชื่อถือกับที่เหลือ
**การเอาข้อความที่ไม่ได้ตรวจไปวางในย่อหน้าเดียวกับข้อความที่ตรวจแล้ว คือการยืมความน่าเชื่อถือ**

### 5 Whys

1. ทำไมเจ้าของงานได้คำแนะนำที่ผิด — เพราะผมเขียนข้อจำกัดหนึ่งข้อลงไปโดยไม่ได้วัด
2. ทำไมไม่วัด — เพราะคำตอบ "รู้สึกว่ารู้อยู่แล้ว" จากความคุ้นเคยว่าโปรแกรมอ่านไฟล์ตั้งค่าตอนเริ่ม
3. ทำไมความคุ้นเคยถึงชนะหลักฐานที่อยู่ตรงหน้า — เพราะผมไม่ได้ถามตัวเองว่าประโยคนี้ชี้หลักฐานอะไรได้
   ผมถามแค่ว่ามันฟังดูสมเหตุสมผลไหม
4. ทำไมถึงไม่ได้ถาม — เพราะตอนนั้นอยู่ในโหมด "สรุปส่งงาน" ซึ่งเป็นจังหวะที่คนเขียนกำลังเติมข้อควรระวัง
   ให้ครบ ไม่ใช่จังหวะที่กำลังตรวจ ด่านตรวจทั้งหมดของผมรอบนั้นวางไว้ที่ "ตอนอ้างข้อเท็จจริง"
   ไม่ได้วางไว้ที่ "ตอนเขียนข้อควรระวัง"
5. ทำไมด่านถึงไม่ครอบส่วนนั้น — เพราะผมแยกในใจว่าข้อควรระวังไม่ใช่การเคลม ทั้งที่มันเป็นการเคลม
   ที่ผู้อ่านจะเอาไปลงมือทันที และเป็นประเภทที่แพงที่สุดด้วย เพราะมันสั่งให้คนไป**ทำ**อะไรบางอย่าง

## 4. ผลกระทบ (Impact)

- เจ้าของงานได้รับคำแนะนำให้ปิด-เปิดเซสชันที่กำลังทำงานอยู่ โดยไม่มีเหตุผลรองรับ
- เจ้าของงานตอบกลับตามคำแนะนำนั้นแล้ว จึงไม่ใช่ข้อความที่ผ่านตาเฉยๆ แต่เข้าไปอยู่ในการตัดสินใจ
- ถ้าทำตาม คือเสียงานที่ค้างอยู่ในเซสชันเหล่านั้นโดยเปล่าประโยชน์
- ผลรองที่สำคัญกว่า: มันลดความน่าเชื่อถือของรายงานทั้งฉบับ เพราะผู้อ่านที่จับได้หนึ่งบรรทัด
  ย่อมต้องสงสัยทุกบรรทัด
- ไม่มีข้อมูลสูญหาย ไม่มีเซสชันไหนถูกปิดจริง

## 5. แนวทางการแก้ไข (Fix)

- แก้คำพูดในแชทตรงๆ ในเทิร์นถัดไป ระบุว่าที่บอกไปก่อนหน้าไม่จริง พร้อมหลักฐานที่วัดได้
- หลักฐานที่ใช้ยืนยัน: เวลาเริ่มของเซสชันนั้นอ่านจากรายการแรกที่มี timestamp ใน transcript ของมัน
  เทียบกับเวลาที่ hook ถูกต่อสาย และเทียบกับเวลาที่ไฟล์สถานะบันทึกว่ามันถูกติดธงและใช้ทางออก
- ทดสอบซ้ำในเซสชันของผมเองด้วยคำสั่งที่ปลอดภัย เพื่อยืนยันว่า hook ที่เพิ่มกลางเซสชันมีผลทันที

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

**กฎที่เพิ่มจากเหตุนี้:** ข้อความ "ข้อจำกัด" หรือ "ข้อควรระวัง" ที่บอกให้ผู้อ่าน **ไปทำอะไรบางอย่าง**
ถือเป็นการอ้างข้อเท็จจริงเต็มรูปแบบ ต้องผ่านด่านเดียวกับทุกบรรทัดในรายงาน — ชี้ output หรือไฟล์
ที่วัดได้ทันที ถ้าชี้ไม่ได้ให้เขียนว่า "ยังไม่ได้วัด" ไว้ในประโยคนั้นเอง ห้ามวางไว้เฉยๆ ในย่อหน้าเดียว
กับข้อความที่ตรวจแล้ว เพราะมันจะยืมความน่าเชื่อถือของเพื่อนบ้าน

ข้อย่อยที่ตามมา

- ก่อนเขียนข้อจำกัดของ **สภาพแวดล้อมที่รันอยู่** (harness, hook, เซสชัน, เครื่องมือของระบบ)
  ให้ถามว่ารอบนี้เพิ่งเห็นพฤติกรรมนั้นเกิดขึ้นตรงหน้าหรือเปล่า — ในเหตุนี้คำตอบคือ "เห็นแล้ว
  และเห็นตรงข้ามกับที่กำลังจะเขียน"
- ข้ออ้างที่ **วัดได้ด้วยของที่มีอยู่แล้ว** ห้ามเขียนโดยไม่วัด เวลาเริ่มของเซสชันอ่านได้จาก
  transcript เป็นคำสั่งเดียว ต้นทุนของการวัดคือหนึ่งคำสั่ง ต้นทุนของการเดาคือเจ้าของงาน
  ไปปิดงานตัวเองทิ้ง
- เมื่อคำแนะนำผิดถูกส่งไปแล้ว ให้แก้ให้เห็นชัดในที่เดิม พร้อมบอกว่ามันผิดเพราะอะไร ไม่ใช่แก้เงียบๆ

## 7. การตรวจจับปัญหา (Detection)

จับได้เพราะเจ้าของงานย้อนกลับมาที่เรื่องนี้เอง ("แน่ใจว่าใช้ได้แน่ก็พอละ") ซึ่งทำให้ผมกลับไป
วัดของจริง ไม่ใช่ด่านไหนของระบบจับได้

**นี่คือช่องว่างที่ยังเปิดอยู่** ไม่มีเครื่องมือใดใน repo อ่านข้อความที่ผมพิมพ์ในแชทได้
investigation-guard ตรวจได้แค่ว่ามีการเรียกสกิลสืบหรือยัง และรายงานคำที่กลบการเดา
แต่คำในประโยคนี้ไม่มีคำ hedge เลยสักคำ — มันเขียนแบบมั่นใจเต็มที่ จึงไม่มีอะไรจับได้
ด่านที่เหลืออยู่จริงคือวินัยตอนเขียน กับเจ้าของงานที่ถามย้ำ

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี

- พอถูกถามย้ำ ก็กลับไปวัดของจริงทันที ไม่ใช่ยืนยันคำเดิม
- หลักฐานที่ใช้แก้เป็นของที่กดตามได้ ไม่ใช่คำอธิบาย
- แก้ในที่เดิม ระบุตรงๆ ว่าที่พูดไปก่อนหน้าผิด

### สิ่งที่ต้องปรับปรุง

- หลักฐานที่หักล้างอยู่ตรงหน้าตั้งแต่ก่อนเขียนแล้ว แต่ไม่ถูกหยิบมาใช้ — ปัญหาไม่ใช่การเข้าถึงข้อมูล
  แต่เป็นการไม่ตั้งคำถามกับประโยคของตัวเอง
- ด่านตรวจของตัวเองถูกวางไว้เฉพาะจุดที่ "รู้ตัวว่ากำลังเคลม" ซึ่งแปลว่าประโยคที่อันตรายที่สุด
  คือประโยคที่ไม่รู้ตัวว่าเป็นการเคลม
- เป็นเรื่องเดิมกับรายงาน #0001 คือเชื่อสิ่งที่ตัวเองเขียน/เชื่อ แทนที่จะเปิดของจริงดู
  ชั้นที่ควรจับได้คือกฎข้อแรกสุดของ repo ซึ่งเป็นวินัย ไม่ใช่เครื่องมือ จึงพลาดได้อีก

## 10. Technical Appendix

ข้อเท็จจริงที่วัดแล้วในรอบนี้ ห้ามเดาใหม่

- **hook ใน `.claude/settings.json` มีผลกับเซสชันที่เปิดค้างอยู่ทันที ไม่ต้องปิด-เปิดใหม่**
  วัดจากเซสชันที่เริ่ม 14:01 UTC ถูกติดธงโดย hook ที่ต่อสายราว 16:38 UTC เมื่อเวลา 17:17:00 UTC
  และใช้ทางออกที่มากับ hook นั้นเมื่อ 17:17:12 UTC
- ยืนยันซ้ำในเซสชันของผมเอง: `git-staging-guard.sh` ถูกเพิ่มเข้า `settings.json` กลางเซสชัน
  แล้วปฏิเสธคำสั่ง stage แบบเหมาในเทิร์นถัดมาทันที
- **git hook (`pre-commit` / `pre-push`) เป็นคนละกลไก** ผูกที่ `core.hooksPath` ใน `.git/config`
  ทุกโปรเซสที่รัน git ในโฟลเดอร์นี้จึงเจอเหมือนกันหมด ไม่ขึ้นกับเซสชันของ Claude Code เลย
- วิธีอ่านเวลาเริ่มของเซสชัน: รายการแรกใน transcript ที่มีฟิลด์ `timestamp` — บรรทัดแรกสุดของไฟล์
  เป็น metadata ที่ไม่มี timestamp จึงอ่านบรรทัดแรกเฉยๆ ไม่ได้
