## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

`laneV7_scripts.json` เป็นอาเรย์ของ object ที่หน้าตาเหมือนกันทุกฟิลด์ (`case · play · tag · tab · er_covered · selectors_from · fixture_steps · revert_steps · notes`) ไม่มีฟิลด์สรุประดับบนไฟล์ที่บอกตรงๆ ว่า "เสร็จกี่ ติดกี่" ผมอ่านความยาวของอาเรย์ทั้งก้อน (`len(data) == 6`) แล้วตีความว่าเท่ากับจำนวนเคสที่เขียนบทสำเร็จ ทั้งที่คำตอบจริงของคำถาม "เขียนบทเสร็จกี่เคส" อยู่ในฟิลด์ `play` ของแต่ละรายการ — รายการที่ `play` เป็น string คือเขียนเสร็จจริง รายการที่ `play` เป็น `null` คือเขียนไม่ได้ ซึ่งเลน `laneV7` เองก็บันทึกเหตุผลและคำถามไว้ตรงจุดนั้นอยู่แล้ว

รูปเดียวกันกับ #0025 ทุกประการ — ที่นั่น `session_verify.js` พิมพ์บรรทัดสรุป `N/M verified` ที่ตอบคำถาม "ยืนยันตัวตนผ่านกี่ใบ" ไม่ใช่คำถาม "session ไหนยังไม่หมดอายุ" แต่ผมหยิบเลขนั้นไปตอบคำถามที่มันไม่ได้วัด ที่นี่ก็เช่นกัน `len(array)` ตอบคำถาม "มีกี่รายการอยู่ในไฟล์" ไม่ใช่คำถาม "เขียนบทสำเร็จกี่เคส" แต่ถูกนำไปตอบคำถามหลังโดยไม่ตรวจก่อนว่าเป็นคนละคำถามกัน

### 5 Whys

1. **ทำไมประกาศว่าเขียนบทเสร็จ 6 เคส?** — เพราะอ่านความยาวของอาเรย์ใน `laneV7_scripts.json` (`6`) แล้วใช้ตัวเลขนั้นตรงๆ เป็นคำตอบของ "เขียนบทเสร็จกี่เคส"
2. **ทำไมความยาวอาเรย์ถึงถูกอ่านเป็นจำนวนที่เสร็จ?** — เพราะไฟล์ไม่มีฟิลด์สรุประดับบนที่ประกาศไว้ตรงๆ (เช่น `{"done":4,"blocked":2,"items":[...]}`) ทุกรายการหน้าตาเหมือนกันหมดไม่ว่าจะเขียนบทได้หรือไม่ได้ ความแตกต่างจริงซ่อนอยู่ใน "ค่า" ของฟิลด์ `play` ไม่ใช่ใน "รูปร่าง" ของอาเรย์
3. **ทำไมไม่เปิดอ่านแต่ละรายการก่อนพูด?** — เพราะการอ่าน `len()` ครั้งเดียวเร็วกว่าการไล่เปิดทีละรายการเพื่อเช็คว่า `play` เป็น string หรือ `null` และผลลัพธ์ (`6`) ดูสมเหตุสมผลพอที่จะไม่ตั้งคำถามต่อ — เข้าข่ายบทเรียน #0019 ที่ว่าตัวเลขที่ "เข้ากับเรื่องที่กำลังจะพูดพอดี" คือจุดที่ต้องตรวจซ้ำ ไม่ใช่จุดที่ควรใช้ทันที
4. **ทำไมความเข้าใจผิดนี้ถึงพาไปถึงขั้นสั่งเลนบันทึกวิดีโอไปอัด `LiveStream_TC_008`?** — เพราะขั้นต่อไปตามลำดับงานปกติหลังเชื่อว่า "6 เคสเสร็จ" คือส่งต่อให้เลนบันทึกวิดีโอไปอัดตามบทที่เข้าใจว่าพร้อมทุกเคสในชุดนั้น ไม่มีขั้นใดระหว่างทางที่กรองรายการด้วยฟิลด์ `play` ก่อนประกอบ manifest ส่งต่อ
5. **ทำไมไม่มีอะไรดักไว้ก่อนถึงจะจ่ายงาน?** — root cause จริง: ไม่มีกลไกใดในเส้นทางนี้บังคับให้ "จำนวนเคสที่เสร็จ" มาจากการนับฟิลด์ที่นิยาม "เสร็จ" จริง (`play != null`) แทนความยาวของอาเรย์ที่บรรจุมัน ทั้งขั้นอ่านค่าไปพูดบนบอร์ดและขั้นประกอบ manifest ส่งต่อเลนบันทึกวิดีโอ ไม่มีจุดใดเลยที่ทำการกรองนี้

## 6. แนวทางการป้องกันไม่ให้เกิดปัญหาซ้ำ (Prevention)

| # | มาตรการ | ชนิด | สถานะ |
|---|---------|------|-------|
| P1 | ทุกครั้งที่ต้องพูดหรือประกาศ "เสร็จ N เคส" จากไฟล์ manifest รูปแบบอาเรย์-ของ-object ต้องนับจากฟิลด์ที่นิยาม "เสร็จ" จริง (เช่น `play != null`) ไม่ใช่ `len(array)` — ก่อนพิมพ์ตัวเลขต้องรันตัวกรองแล้วพิมพ์คู่กันเสมอว่า "ทั้งหมด N รายการ · เสร็จจริง M รายการ · ติดคำถาม N-M รายการ" ในบรรทัดเดียวกัน เพื่อไม่ให้ 2 ตัวเลขนี้แยกออกจากกันได้อีก | กฎ + วินัยการอ่านไฟล์ | ทำแล้วในรายงานฉบับนี้ |
| P2 | ก่อนประกอบ manifest ส่งต่อให้เลนบันทึกวิดีโอ (หรือเลนถัดไปใดๆ) ต้องกรองรายการด้วยฟิลด์ที่นิยาม "พร้อมทำงานต่อ" จริงก่อนเสมอ ไม่ปล่อยให้รายการที่ `play == null` หลุดเข้า manifest แม้แต่ใบเดียว — ย้ายจุดตรวจจาก "เลนปลายทางจับได้เอง" (ซึ่งเป็นชั้นที่ 2 ที่ทำงานได้จริงในรอบนี้) มาเป็น "จุดจ่ายงานต้องกรองก่อนส่ง" (ชั้นที่ 1 ที่ยังไม่มี) | เครื่องมือ / ขั้นตอนจ่ายงาน | ค้าง |

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- บันทึกความผิดพลาดไว้ในช่อง `"corrections"` ของบอร์ดตามฟอร์แมตที่ CLAUDE.md บังคับไว้ แทนการแก้ตัวเลขเงียบๆ แล้วไม่มีร่องรอย — ทำให้รายงานฉบับนี้เขียนได้จากหลักฐานที่ยังอยู่ครบ
- เลน `laneV7` ทำหน้าที่ถูกต้อง — เขียน `play: null` พร้อมเหตุผลและคำถามที่ระบุทางเลือกให้เจ้าของงานชัดเจน ไม่เดาทางแก้เอง
- เลน `laneW1` มีการ์ดตรวจ `play` ก่อนเริ่มงานจริง ทำให้ไม่มีการเสียเวลาอัดคลิปกับเคสที่ไม่มีบทรองรับ แม้จะได้รับ manifest ที่มีช่องโหว่มา

### สิ่งที่ต้องปรับปรุง
- อ่านความยาวอาเรย์แล้วตีความเป็น "จำนวนที่เสร็จ" ทันที โดยไม่เปิดอ่านฟิลด์ที่นิยามความเสร็จจริงของแต่ละรายการก่อน — เป็นคลาสเดียวกับ #0025 ที่เพิ่งเขียนไว้เมื่อ 2 วันก่อนหน้า แต่บทเรียนนั้นเขียนแคบอยู่ที่เครื่องมือ `session_verify.js` เฉพาะ ไม่ได้เขียนเป็นกฎกว้างที่ครอบไฟล์ manifest รูปแบบอื่นด้วย
- การจ่ายงานให้เลนถัดไปยังพึ่งการ์ดของเลนปลายทางเป็นด่านเดียว ไม่มีการกรองก่อนส่งที่จุดต้นทาง ซึ่งเป็นจุดที่ควรจับได้ก่อนที่การสั่งงานผิดจะออกไปถึงเลนอื่นเลย
