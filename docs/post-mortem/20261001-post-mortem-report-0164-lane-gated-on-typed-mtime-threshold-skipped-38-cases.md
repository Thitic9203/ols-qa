**สิ่งที่ควรจะเป็น:** เงื่อนไขในคำสั่งงานต้องมาจากค่าที่วัดได้จริง (`CLAUDE.md` §0 "เวลาต้องวัด (`date` / timestamp จริง) ห้ามประมาณ") — ค่าที่วัดได้คือ 07:12:39 และเงื่อนไขที่พอเพียงจริงคือ `session_verify` ผ่าน ซึ่งไม่ต้องพึ่งเวลาเลย

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

จุดตัดสินใจที่ผิดคือตอนเขียนเงื่อนไข (a) เธรดหลักตั้งใจกันไม่ให้เลนใช้ไฟล์ session เก่าจากรอบก่อน จึงพิมพ์ "เวลาประมาณตอนนี้" เป็นเส้นแบ่ง ซึ่งตอนนั้นดูปลอดภัย (ยิ่งเข้มยิ่งไม่ใช้ของเก่า) แต่เส้นที่พิมพ์ช้ากว่าเวลาเซฟจริง 2 นาทีกว่า และไฟล์จะไม่ถูกเขียนใหม่อีกจนกว่าจะล็อกอินใหม่ เงื่อนไขจึงเป็นเท็จตลอดไป

### 5 Whys

1. **ทำไม 38 เคสที่ต้องล็อกอินไม่ถูกรัน?** — เพราะเลนไม่เคยโหลดไฟล์ session และหยุดด้วย NO_SESSION หลังรอ 30 นาที
2. **ทำไมเลนไม่โหลด session ที่ใช้ได้อยู่?** — เพราะคำสั่งงานบอกให้ใช้ได้เมื่อ mtime หลัง 07:15 เท่านั้น ส่วนไฟล์จริงคือ 07:12:39 เงื่อนไขจึงไม่มีวันเป็นจริง
3. **ทำไมคำสั่งงานมีเส้น 07:15?** — เพราะเธรดหลักพิมพ์เวลาจากความรู้สึกว่า "ตอนนี้ประมาณกี่โมง" แทนที่จะคัดลอกค่าจากบรรทัด `SAVED` ใน log หรือ `stat` ของไฟล์ ทั้งที่มีค่านั้นอยู่ในมือแล้ว
4. **ทำไมค่าที่ไม่ได้วัดหลุดเข้าไปในคำสั่งงานได้?** — เพราะไม่มีด่านใดอ่านคำสั่งงานแล้วตรวจว่าเงื่อนไขเวลามาจากค่าที่วัดหรือไม่ — agent-dispatch-guard ตรวจ 8 เรื่องแต่ไม่มีเรื่องเวลา
5. **ทำไมยังไม่มีด่านนั้น ทั้งที่เคยพลาดเรื่องเวลาที่ไม่ได้วัดแล้ว (#0094 · #0138)?** — เพราะมาตรการของรอบก่อนจบที่ข้อความในกฎ §0 และข้อเสนอ "ด่าน dispatch + ตัวตรวจ `ts`" ของ #0138 ยังค้าง ไม่เคยถูกสร้างเป็นกลไก กฎจึงพึ่งความจำของเธรดหลักขณะพิมพ์คำสั่งงาน ซึ่งเป็นชั้นเดียวและพลาดซ้ำได้

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:**
- `CLAUDE.md` §0 (เวลาต้องวัด) — เป็นข้อความ ไม่มีอะไรบังคับตอนเขียนคำสั่งงาน
- agent-dispatch-guard (PreToolUse บน `Agent`) — มี 8 เช็ค ไม่มีเช็คใดดูเงื่อนไขเวลา
- เงื่อนไข (b) `session_verify` เพียงพออยู่แล้ว แต่ถูกเชื่อมด้วย AND กับ (a) ที่เป็นเท็จ ชั้นที่ถูกต้องจึงไม่มีโอกาสทำงาน
- เลนทำตามคำสั่งตามตัวอักษร (ถูกตามหน้าที่) และไม่มีข้อความในคำสั่งให้รายงานความขัดระหว่างเงื่อนไขกับค่าที่เห็นทันที — ได้แต่รอจนหมดเวลา

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** เธรดหลักเห็นเลนหยุดด้วย NO_SESSION ทั้งที่ keepalive บอกว่า session ใช้ได้ แล้วเทียบ log `SAVED` กับเงื่อนไขในคำสั่ง
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** 30 นาที (07:14 → 07:44 ตามช่วงที่เลน poll)
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** ด่าน `TIME_GATE_UNSOURCED` บล็อกตั้งแต่ก่อนส่งคำสั่ง — เวลาที่เสียเป็นศูนย์

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- เลนบันทึก mtime ที่เห็นจริง (07:12:39) ไว้ ทำให้ระบุสาเหตุได้ทันทีโดยไม่ต้องเดา
- เลนไม่ฝืนใช้ session นอกเงื่อนไข และรันแถว guest ที่ทำได้ไปก่อน

### สิ่งที่ต้องปรับปรุง
- เงื่อนไขที่ต้องการจริงคือ "session ใช้ได้" ซึ่งมีเครื่องมือวัดตรงอยู่แล้ว (`session_verify`) — ไม่ควรเพิ่มเงื่อนไขทางอ้อมที่ใช้เวลา
- ถ้าจำเป็นต้องใช้เวลา ต้องคัดลอกค่าที่วัดได้ (ระดับวินาที) พร้อมแหล่ง ไม่ใช่พิมพ์ "ประมาณตอนนี้"
