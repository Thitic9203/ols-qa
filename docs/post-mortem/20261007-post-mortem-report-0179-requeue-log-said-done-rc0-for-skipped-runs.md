## สรุปสั้น (Executive Summary)

`run_seq.sh` เขียน `echo "$(date '+%F %T') done $t rc=$?"` หลัง `run.sh` — `$?` ถูกขยายหลัง command substitution `$(date)` จึงได้ `0` เสมอ และสคริปต์ไม่อ่านผลจริงของใบนั้นจาก `logs/results.log` เลย
รอบ 15:15–15:29 ทั้ง OLS-829 และ OLS-778 จบด้วย `SKIPPED — env unreachable` แต่ `seq.log` เขียน `done OLS-829 rc=0` / `done OLS-778 rc=0` และไม่มีการแจ้งเตือนใดๆ เพราะเจ้าของงานพักโนติไว้ (`.notify_hold`)
แก้: เก็บ `rc=$?` ทันทีหลัง `run.sh` · อ่านสถานะของใบนั้นจากบรรทัดใหม่ใน `results.log` · ผลที่ไม่ใช่ PASSED เด้งแจ้ง macOS · ทดสอบกับบอทจำลอง 4 เคสที่รู้คำตอบ ผ่าน 4/4
สถานะ: แก้แล้ว ใช้กับรอบ rerun 3 (16:53) แล้ว

## 1. ปัญหา (Problem Statement)

- `seq.log` บรรทัด `15:19:31 done OLS-829 rc=0` และ `15:29:28 done OLS-778 rc=0`
- `logs/results.log` ของเวลาเดียวกัน: `SKIPPED | OLS-829 — env unreachable (connection timeout)` และ `SKIPPED | OLS-778 — env unreachable (<DEV_HOST> connection timeout)`
- ทดสอบซ้ำ: `/bin/bash -c 'false; echo "$(date +%T) rc=$?"'` → `rc=0`
- แผนงานที่ส่งเจ้าของงานเขียนว่า OLS-829 "รันใหม่" และ OLS-778 "จะรันต่อ" โดยไม่รู้ว่ารอบก่อนหน้า SKIPPED ทั้งคู่ จนเธรดหลักเปิด `results.log` เองตอน 15:58

**สิ่งที่ควรจะเป็น:** ตัวรันคิวต้องรายงานผลจริงของแต่ละใบ (PASSED / SKIPPED / FAIL / ไม่มีผล) และผลที่ไม่ผ่านต้องเห็นได้โดยไม่ต้องมีคนเปิด log — กฎ `docs/POSTMORTEM_RULE.md` "รหัสจบไม่ใช่หลักฐาน" (#0002) และ CLAUDE.md §0 สถานะงานห้ามอ่านจากรหัสจบหรือบรรทัดที่พิมพ์

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไม `seq.log` บอก `rc=0` ทั้งที่รอบไม่ได้ผล?** — เพราะ `$?` อยู่ในประโยค echo เดียวกับ `$(date)` ค่าจึงเป็นรหัสจบของ `date` ไม่ใช่ของ `run.sh`
2. **ทำไมแม้ได้รหัสจบจริงก็ยังไม่พอ?** — เพราะ `run.sh` จบด้วย 0 เมื่อ session จบปกติ แม้ผลคือ SKIPPED · ผลจริงอยู่ใน `results.log` ที่สคริปต์ไม่ได้อ่าน
3. **ทำไมสคริปต์ไม่อ่านผลจริง?** — เพราะเขียนขึ้นเร็วเป็น "ตัวรันครั้งเดียว" เพื่อปิด #0176 โดยโฟกัสแค่ว่าอยู่รอดหลังเซสชันจบ ไม่ได้กำหนดว่ามันต้องรายงานอะไร
4. **ทำไมไม่มีอะไรเตือน?** — เพราะพักโนติ Discord ไว้ทั้งหมด และสคริปต์ไม่มีช่องแจ้งเตือนของตัวเอง
5. **ทำไมเขียนแบบนั้นได้?** — เพราะไม่มีข้อบังคับว่าตัวรันงานที่เขียนเฉพาะกิจต้องตัดสินจากผลที่บันทึกไว้และผ่านเทสที่รู้คำตอบก่อนใช้งาน (CLAUDE.md §0 ข้อเครื่องมือวัดที่เขียนเองต้องผ่านตัวอย่างที่รู้คำตอบ ถูกใช้กับเครื่องมือวัด แต่ไม่ได้ใช้กับตัวรันคิว)

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** ชั้น L1–L10 ของ `run.sh` ทำงานถูก (`results.log` มี SKIPPED ครบ) · L6 audit ตรวจเฉพาะความขัดกันภายในรอบเดียว ไม่ได้ตรวจ log ของตัวรันคิวที่อยู่นอก `run.sh` · โนติถูกพักโดยเจ้าของงาน — ไม่มีชั้นไหนครอบตัวรันคิว

## 5. แนวทางการแก้ไข (Fix)

- `run_seq.sh` เก็บ `rc=$?` ทันทีหลัง `run.sh` · อ่านสถานะของใบนั้นจากบรรทัดที่เพิ่มขึ้นใน `results.log` หลัง baseline · เขียน `done <ticket> rc=<rc> status=<STATUS|NO_RESULT>` · ผลที่ไม่ใช่ PASSED เด้ง `osascript display notification`
- แก้ pattern รอ lock เป็น `run.sh OLS-` (เดิม `<BOT_DIR>/run.sh OLS` ไม่ตรงกับ `./run.sh`)

**ยืนยันแล้วด้วย:** บอทจำลอง (`RUN_CMD` ปลอม + `results.log` ชั่วคราว) 4 เคส — คาด `PASSED rc=0` · `SKIPPED rc=0` · `NO_RESULT rc=0` · `FAIL rc=7` → ได้ตรงทั้ง 4 · บรรทัดเก่าของใบเดียวกันก่อน baseline ไม่ถูกนับ · `bash -n` ผ่าน · ช่องแจ้งเตือน macOS ยังไม่ได้ทดสอบกับเครื่องจริง (ปิดด้วย `NO_OSA=1` ระหว่างเทส)
