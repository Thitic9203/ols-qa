## สรุปสั้น (Executive Summary)

ตอน 15:59 เธรดหลักรายงานหัวข้อ "สาเหตุจริง" ว่า session ค้างเพราะ traffic ไป API วิ่งผ่าน VPN แบบ full tunnel โดยมีหลักฐานแค่ `route -n get` ชี้ ppp0 และบันทึกรอบก่อนที่พูดเรื่องเดียวกัน
ตรวจละเอียดตอน 16:02 พบว่าทุกโปรเซส Claude บนเครื่อง รวมถึงเซสชันที่ทำงานปกติ ออกทาง ppp0 เหมือนกัน · API ตอบเร็ว (`duration_api_ms` 1223–1675 ใน 3/3 รอบ) · เส้นทางเครือข่ายผ่าน (DF ping 1252 ไบต์ 3/3 · อัปโหลด 600 KB 0.59–0.79 วินาที 3/3) — route ผ่าน ppp0 เพียงอย่างเดียวอธิบายการค้างไม่ได้
สิ่งที่วัดได้จริง: บอท (CLI 2.1.159) มี ECONNRESET ใน 13/77 session วันนี้ ขณะที่ session Desktop วันนี้มี 0 · จุดค้างของ 2 session อยู่ที่ request ไป API ที่ไม่มี error บันทึก — ชั้นที่ค้างตรวจไม่ได้เพราะบอทไม่เปิด debug log
แก้: แจ้งเจ้าของงานพร้อมข้อมูลที่แก้แล้ว · ใช้รอบ rerun 3 (route แยกออก Wi-Fi ที่เจ้าของงานตั้งเอง) เป็นการทดลองวัดผล

- `claude -p` แบบ stream-json 3 รอบ: `api_ms=1675 / 1223 / 1255` เวลาที่เหลือเป็น SessionStart hook (12–73 วินาที)

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

### 5 Whys

1. **ทำไมรายงานว่า ppp0 เป็นสาเหตุ?** — เพราะ route ชี้ ppp0 และมีบันทึกรอบก่อนที่สรุปแบบเดียวกัน
2. **ทำไมถือว่าพอ?** — เพราะบันทึกรอบก่อนถูกอ่านเป็นข้อเท็จจริง ไม่ได้ VERIFY แยก (ขัด §0 "ข้อสรุปจากไฟล์สรุปรอบก่อนห้ามพูดเป็นข้อเท็จจริง")
3. **ทำไมไม่เทียบกับตัวที่ทำงานปกติ?** — เพราะรีบตอบคำสั่ง "อย่าเฟลเงียบ" ด้วยการหยุดคิว และนำเสนอสาเหตุควบคู่ทางแก้ในข้อความเดียว
4. **ทำไมหัวข้อ "สาเหตุจริง" ถูกเติมด้วยสิ่งที่ยังเป็นสมมติฐาน?** — เพราะรูปแบบรายงาน 4 หัวข้อบังคับให้มีคำตอบทุกหัวข้อ และไม่มีช่องให้เขียนว่า "ยังเป็นสมมติฐาน"
5. **ทำไมไม่มีอะไรจับ?** — ไม่มีชั้นตรวจว่าข้อความ "สาเหตุจริง" ต้องมีการทดลองหรือการเปรียบเทียบกับตัวที่ปกติ — root cause: การรายงานสาเหตุไม่มีเงื่อนไขขั้นต่ำว่าต้องหักล้างทางเลือกอื่นแล้ว

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** investigation-guard ตรวจแค่ว่าเรียกสกิล systematic-debugging แล้ว (เรียกแล้วจริง) ไม่ได้ตรวจเนื้อหาของหัวข้อสาเหตุ
